## Why this exists

An interrupted turn leaves a tool sequence unclosed. When the next user message
lands on it, the transcript contains `tool_result → user` — and strict providers
reject that pairing. The reference platform recorded the consequence precisely:
the model *"hallucinate[s] a continuation of the user's message"* instead of
answering it (`agent/turn_finalizer.py:278`, incident #48879).

StackOwl is exposed in exactly one place, and it is **not** the obvious one.

| Path | Exposed? | Why |
|---|---|---|
| Persisted history (`messages`) | **No** | `TranscriptStore.record_turn` has no `role` parameter at all — it takes `user_text`/`assistant_text` and hardcodes the roles. One `INSERT`, one caller. |
| Durable resume (`resume_messages`) | **Yes** | Carries provider-shaped transcripts including `tool_result`, and checkpoints are written *after* tool results are appended — so an interrupted checkpoint ends on one by construction. |

## Model

The two wire shapes differ enough that a role check alone misses one of them:

| Protocol | A tool result looks like |
|---|---|
| openai | a dedicated `{"role": "tool", …}` message |
| anthropic | a **`user`** turn whose content blocks are `{"type": "tool_result", …}` |

**That second row is the whole difficulty.** On the Anthropic wire a tool result
*is* a user turn. Anything reasoning about roles alone sees `user → user` and
finds nothing wrong. `_is_tool_result_turn` therefore compares **shapes**, not
roles.

## Lifecycle

`validate_resume_transcript` runs once, before the first API call, from both
providers (`anthropic_provider.py:555`, `openai_provider.py:555`). Five rules:

```
 resume_messages
       │
       ├─ Rule 1  empty transcript                          ──► raise
       ├─ Rule 2  system role in an anthropic transcript    ──► raise
       ├─ Rule 4  a declared call id with no result         ──► raise
       ├─ Rule 3  LAST turn dangles an unanswered call      ──► raise
       └─ Rule 5  a USER turn directly follows a TOOL RESULT ──► raise   [D01.5]
       │
       ▼
 seed the loop from the transcript
```

**Rule 5 is about ADJACENCY, not the tail — and the first version of it was
wrong.** It was originally written as *"the transcript must not end on a tool
result."* That broke three existing tests, and they were right: a transcript
ending on a tool result is the **normal resume seed**, because the model is
called next and answers it. `test_well_formed_openai_transcript_passes` has
pinned that since B1. Shipping the tail rule would have broken *every* legitimate
resume while claiming to fix a rare edge case.

The defect only appears when a **user message** lands after the result. That is
what an interrupt produces, and it is what Rule 5 rejects.

**Rejects rather than repairs.** This validator's contract is to fail loud before
the first API call so the cause is a typed `ResumeTranscriptError` rather than an
opaque 400. A caller that wants to resume such a checkpoint should close the
sequence deliberately; the validator should not invent an assistant turn on its
behalf.

## Invariants

> **I1.** A `user` turn never directly follows a tool result in a transcript that
> passes validation — on either protocol.
>
> **I2.** A transcript *ending* on a tool result is **valid**. This is stated as an
> invariant precisely because the obvious reading of I1 gets it wrong, and getting
> it wrong breaks every resume. Pinned by
> `test_a_transcript_ENDING_on_a_tool_result_is_still_valid`.
>
> **I3.** Persisted history can never contain a role outside `{user, assistant}`.
> Enforced by migration `0106` at the database boundary, not by convention.

**None.** No settings, no flag. The validator already ran on every resume; this

## Observability

Deliberately thin, and worth stating rather than padding: the validator is
*"pure and side-effect-free apart from a debug entry/exit log"* (its own
docstring). A rejection surfaces as a typed `ResumeTranscriptError` raised to the
caller, which is the signal — not a log line.

```bash
# Has a resume ever been rejected? The exception is typed, so it is greppable
# by name rather than by message text.
cat ~/.stackowl/logs/stackowl.jsonl \
  | jq -r 'select((.fields.exc // "") | test("ResumeTranscriptError")) | "\(.ts) \(.msg)"'
# Expect NOTHING most of the time. Rule 5 fires only on an interrupted turn
# resumed with a new user message, so a quiet result is NO OPPORTUNITY, not
# proof of health — check that an interrupt actually occurred before reading
# silence as success.
```

**No `[cache]`-style INFO line was added.** D01.6's lesson was that diagnostics
logged at debug are invisible — but that applies to a *measurement* nobody can
otherwise obtain. Here the outcome is an exception that already reaches the
caller and the turn record; adding a log line would duplicate it.

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| Interrupted checkpoint resumed with a user message appended | Rule 5 | Typed `ResumeTranscriptError` before any API call | The resume is refused loudly rather than the model answering the wrong thing |
| A transcript legitimately ending on a tool result | — | **Accepted** (I2) | Nothing — normal resume |
| A second writer adds a `tool` row to `messages` | migration `0106` CHECK | `IntegrityError` at the write | Nothing — the write is refused at the boundary |
| Anthropic tool result mistaken for an ordinary user turn | `_is_tool_result_turn` compares shapes | Correctly identified | Nothing |

### Prior art, and where we deliberately diverge

Hermes closes an interrupted tool sequence by **appending a synthetic assistant
message** (`close_interrupted_tool_sequence`), so the transcript is repaired and
the resume proceeds.

**Adopted:** the problem statement and the incident evidence. Their comment is
the clearest available description of the failure — that strict providers do not
merely error, they *continue the user's message* — and that is worth more than
the fix itself, because it explains why a silent repair is dangerous.

**Diverged:**

1. **We reject; they repair.** Their agent is long-lived and repairing keeps a
   session alive. Ours already has a typed-failure contract at this exact seam
   (`ResumeTranscriptError`, raised before the first API call so the cause is not
   an opaque 400), and a validator that silently invents an assistant turn would
   be the first thing in that file to do so.
2. **Our persisted history is immune by a different mechanism.** They sanitise on
   the way out; we cannot construct the shape on the way in, because the writer's
   interface has no `role` parameter — now backed by a database constraint rather
   than by there continuing to be one writer.
3. **We compare shapes, not roles.** Necessary because an Anthropic `tool_result`
   rides inside a `user` turn. Their envelope handling makes the same distinction
   for a different reason (OpenRouter's marker placement).

### How the two Laws hold

**Law 1 — per-conversation prompt caching is sacred.** Untouched: this validates a
transcript before a resume begins and mutates nothing.

**Law 2 — the core is a narrow waist.** Nothing added to the model's tool surface.
One rule, one helper, one migration.
