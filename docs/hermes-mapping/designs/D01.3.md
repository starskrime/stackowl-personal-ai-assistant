## Why this exists

`D01.1` froze the system prompt and `D01.2` placed the cache markers. Neither helps
if the **tools array** changes every turn, because on the Anthropic wire `tools`
renders at **position 0** — before `system` — so a tools array that moves
invalidates marker 1 *and every marker downstream of it*, on every turn.

The map recorded that as a `CONFLICT` and the wave-1 plan deliberately put it
last, noting it "is really a wave-2 consequence rather than a wave-1 fix."

**Unlike every other item in this wave, its premise arrived measured.** `D01.2`
shipped the instrument (`pipeline/cache_audit.py`) and it returned a reading
before this item was opened.

## The decision

**The budgeter goes. Toolsets replace it.** That resolves `X2` — *"Per-turn
`context_budget` budgeter vs toolsets + progressive disclosure. Budgeter should
go."*

**But not here.** The replacement is `D05.2` (Toolsets) and `D05.4` (Progressive
disclosure), both `0/7`. Deleting the budgeter now would remove a working
capability with nothing behind it — `context_budget.tool_budget_tokens` sizes the
presented set to the model's real window minus the turn's measured fixed cost, so
a small-window model is not drowned in schemas. That protection is genuine and
must survive the replacement.

So `D01.3` closes as a **decision with no code**, and the implementation is
`D05.2`'s to carry. `implement` through `validate` are `no_change_needed` — a
legitimate outcome under `PROCESS.md`, and the honest one here.

### What D05.2 must honour

Binding constraints this item hands forward:

1. **The array must be stable for the life of a session.** That is the entire
   point — `D01.2`'s position-0 marker is worthless otherwise.
2. **Window-aware sizing must survive.** Whatever replaces the budgeter still has
   to prevent a small-window model being handed 150 schemas. Losing that to gain
   cache stability would be trading one defect for another.
3. **A toolset change must invalidate the frozen prompt.** `D01.4` built exactly
   that seam (`SessionPromptStore.invalidate_all`) and the capabilities block is
   already one of its named triggers — so this is wiring, not new machinery.

### Questions D05.2 owns, deliberately left open

Recorded rather than pre-empted, because they are toolset-design questions and
answering them here would be deciding `D05.2` without its own brainstorm:

- Are toolsets **per-owl** or global? StackOwl has owls; the reference platform
  has one agent, so its answer does not transfer.
- Does the model's context window still get to **shrink** a configured toolset, or
  is the configuration absolute?
- What happens mid-session when a toolset changes — immediate (paying a rebuild
  via `D01.4`) or deferred to the next incarnation?

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| Tools array varies per turn | `cache_audit` warning | None — this is the accepted state until D05.2 | Nothing; the Anthropic cache under-performs |
| D05.2 lands without window-aware sizing | — | **Not detected.** A small-window model would be flooded with schemas | Degraded answers on small models |
| D05.2 lands without invalidation on toolset change | — | **Not detected.** A toolset change would sit unapplied until rollover | A toolset edit appears to do nothing |

The last two rows are the reason this document exists: they are the ways the
*replacement* can go wrong, and there is nothing in the tree that would catch
either today.

### Prior art, and where we deliberately diverge

**Hermes does not select tools per turn at all.** `agent/agent_init.py:1386` builds
`agent.tools` **once**, from `enabled_toolsets` / `disabled_toolsets`, and the
conversation loop never rebuilds it. That is Law 2 stated literally — *"every model
tool ships on every API call"* — and it is precisely what makes their position-0
marker viable.

**Adopted:** the shape. A toolset is a *configuration*, resolved once, not a
per-query computation.

**Diverged, or rather: not yet converged.** We have a per-query budgeter they never
had, because we grew a context-window protection they solve differently (they cap
by configuration, we cap by measurement). The honest statement is that StackOwl is
*behind* here, and this item is the decision to catch up rather than a defence of
the difference.

**One thing that does not transfer:** they have one agent, so a single global
toolset is sufficient. We have owls, and whether toolsets are per-owl is a real
question their design cannot answer for us — hence it is left to `D05.2`.

### How the two Laws hold

**Law 1 — per-conversation prompt caching is sacred.** This item changes nothing,
so nothing is at risk. Its whole purpose is to record that the *current* state
violates the spirit of Law 1 — a per-turn tools array defeats the caching `D01.1`
and `D01.2` built — and to bind the fix to `D05.2`.

**Law 2 — the core is a narrow waist.** Untouched. Note that Hermes' answer here
*is* Law 2 applied to tools, which is why their array is stable and ours is not.
