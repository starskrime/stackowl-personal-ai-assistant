## Why this exists

D01.1 made StackOwl's system prompt byte-identical for the life of a conversation. On an
OpenAI-protocol backend that is sufficient — prefix caching there is automatic, and the
discount arrives with no further work. **On an Anthropic-protocol backend it buys
nothing at all**, because Anthropic caches only what you explicitly mark, and StackOwl
has never placed a marker: `grep -rn "cache_control" src/` returns zero.

That path is not hypothetical. `anthropic_provider.py` is 802 live lines, constructed at
`providers/registry.py:81`, shipped with `setup/providers/anthropic.yaml`, and handled in
`setup/minimal.py:44`. Anyone who picks Anthropic during onboarding gets a fully wired
provider that re-reads the same ~2700-token frozen prompt at full price on every turn.

**This item exists because the map's premise about it was wrong, twice.**

1. The wave-1 handoff predicted D01.2 would be "likely a no-op — NeraAiRaw is
   OpenAI-protocol, where prefix caching is automatic." True for *this* deployment; false
   for the four protocols StackOwl ships.
2. The map states StackOwl has "no occurrence of `cached_tokens` … anywhere in `src/`."
   Stale — `D01.6` added a three-shape *reader* at `openai_provider.py:114`. What is
   genuinely absent is the *writer*.

### The constraint that shapes everything: four breakpoints

Anthropic caches nothing by default. You mark positions; everything from the start of the
request up to a marker becomes cacheable. **You get at most four.** Placement is the
entire design.

Render order is `tools` → `system` → `messages`, so a marker's value is a function of how
much precedes it and how often those bytes repeat.

### Five candidate spans, four breakpoints

```
┌─ tools ─────────────────────── position 0, shared by every request ─┐  ← marker 1
├─ stable tier      3713 ch ≈  928 tok ── identical for EVERY session │     (dropped)
│  charter + call protocol + downloads rule                            │
├─ capabilities      579 ch ── machine-wide (unconditional, DEBT-24)   │
├─ persona           255 ch ─┐                                         │
├─ owls block        995 ch  ├─ per-owl                                │
├─ skills catalogue 4153 ch ─┘                                         │
├─ profile             0 ch ── per-user                                │
└─ stable_context   1142 ch ── per-session ──── total ~10847 ≈ 2712 tok┘  ← marker 2
   … conversation …
   last-but-one message                                                   ← marker 3
   last message                                                           ← marker 4
```

**The stable tier loses its marker, and that is a measured decision, not an oversight.**
It is the span Hermes considers the whole point — the cross-conversation prefix that a
*new* conversation still hits after missing the session-specific one. But at ~928 tokens
it sits below Anthropic's minimum cacheable prefix on every model except Opus 5, so on
most deployments that breakpoint would be silently dead. The budget goes where it can pay.

### The minimum is model-dependent, and not monotonic

| Model | Minimum | stable tier (~928) | full system (~2712) |
|---|---:|---|---|
| Opus 5, Fable 5 | 512 | caches | caches |
| Opus 4.8, Sonnet 5, Sonnet 4.6/4.5 | 1024 | **misses by ~96** | caches |
| Opus 4.7, Haiku 3.5 | 2048 | misses | caches |
| Opus 4.6, Opus 4.5, Haiku 4.5 | 4096 | misses | **misses — nothing caches** |

A below-minimum marker produces **no error** — just `cache_creation_input_tokens: 0`. It
silently consumes one of the four. This is why the guard below exists.

### The guard: measure, then probe, and only ever learn from success

The minimum is **not** published in the Models API capability tree, so there is nothing
live to query for it. Instead of hardcoding a table that will rot, the module learns:

1. **Measure** the candidate span with `count_tokens`, once per session, cached. On a
   gateway that does not implement that endpoint, fall back to `chars / 4` with a safety
   margin so estimation error fails toward *not marking*.
2. **Probe** — place the marker, then read `cache_creation_input_tokens` from the response.
3. **Learn, asymmetrically.** A non-zero reading is durable knowledge and is persisted. A
   **zero is never persisted and never treated as "dead."**

That asymmetry is the load-bearing part. `D01.6`'s invariant I4 already established that a
zero is ambiguous — below-minimum, cold cache, and *a gateway that reports nothing* all
read zero — and that NeraAiRaw reports no cache fields in any accepted shape. A design
that believed zeros would, on a field-stripping gateway, conclude on turn one that every
marker was dead, persist that, and disable itself permanently with no error. Only
positives are written, so the worst case is that we keep trying and waste nothing.

A zero is only interpreted as "below minimum" **after** that endpoint has been seen to
report a non-zero cache field at least once.

## Lifecycle

```
 request assembled (tools, system, messages)
        │
        ▼
 provider.supports_cache_breakpoints ?
        │ no ──► send unchanged  (byte-identical to today — invariant I4)
        │ yes
        ▼
 _measure_spans()  ── live count_tokens, once per (session_id, model), cached
        │              └─ endpoint absent ──► chars/4 × 0.8, logged at error
        ▼
 apply_cache_breakpoints(tools, system, messages, model=, ttl=, measured_tokens=)
        │
        ├─ STRIP every existing cache_control first   (see I1 note below)
        │
        ├─ cumulative prefix ≥ floor ? ──► mark end of tools array   (marker 1)
        ├─ cumulative prefix ≥ floor ? ──► system str → block list   (marker 2)
        └─ remaining budget ──► the newest CARRIABLE messages    (markers 3, 4)
        │
        ▼
 _request_kwargs()  ── the ONE chokepoint: 3 × create() + stream()
        │
        ▼
 response.usage ──► _report_cache_outcome()  ── the ONE outcome site
                     ├─► cached_input_tokens ──► _record_cost (existing)
                     ├─► "[cache] breakpoints: result" at INFO
                     └─► CacheProbeStore.record() — positives only (I5)
```

**The guard is CUMULATIVE, not per-span. [CORRECTED]** A breakpoint caches the whole
prefix *before* it, so what must clear the model's minimum is the running total up to the
marker, never the individual span. Concretely: a ~330-token tools array and a ~301-token
system prompt each miss the 512 floor alone, yet together they clear it — so marker 2 is
placed while marker 1 is not. A per-span guard drops both. The design as written read as a
per-span check.

**The budget IS reallocated. [CORRECTED]** This reverses the original text ("if a span
fails the minimum guard its breakpoint is **not** reallocated — a simpler, assertable
layout was chosen over a self-optimising one"). That reasoning does not survive contact
with the reference implementation, whose `apply_anthropic_cache_control` computes
`remaining = 4 - breakpoints_used` and hands the leftovers to messages. Reallocation is no
less assertable — the property is "spend every breakpoint that has somewhere legal to go" —
and the original rule wasted a breakpoint on precisely the deployments the minimum guard
exists to protect. A tools array below the floor used to cost a marker; now it costs
nothing.

A message is passed over for two reasons, and **neither costs a breakpoint**: its
cumulative prefix is below the floor, or it has no content block able to carry a marker
(an empty tool/assistant turn — the reference platform's `_can_carry_marker` insight).
Candidates are filtered first and the newest `remaining` of them marked, so a skipped
message moves the marker to an earlier one rather than dropping it.

**Existing markers are stripped before placement.** Not in the original design, and the
reason `I1` holds at all: `complete_with_tools` appends to **one** growing `messages` list
and re-marks it every round. Without stripping, round 2's markers land on the new tail
while round 1's still sit on messages that are no longer the tail — six markers on the
wire, `I1` broken on the second tool iteration. Safe because this module owns every marker
in the codebase.

**One chokepoint, deliberately.** Three `messages.create()` sites plus `stream()` all build
their request in `_request_kwargs()`. `stream()` cannot share a `create()` wrapper — it is
a context-manager factory, not a coroutine — so it shares the kwargs *builder*, which is
the thing that actually has to be single.

**Marking is the LAST mutation before the wire**, and that ordering is load-bearing.
Marking turns a string into a block list, so any later pass written as
`isinstance(content, str)` silently skips a marked message — and the same message would go
normalised on the turn it is unmarked and raw on the turn it is marked, breaking the exact
prefix match the breakpoints exist to protect. The reference platform locks this with a
test that inspects source order. Here it holds *structurally*: per iteration the order is
`trim → mark → send`, and `apply_cache_breakpoints` returns copies, so the loop's own list
stays permanently unmarked and the appends between rounds operate on clean messages.

## Invariants

> **I1.** No request ever carries more than four `cache_control` markers. The hard API
> limit, and the reason one module owns all marking rather than three.
>
> **I2.** A marker is never placed where the **cumulative prefix** is below the minimum
> the module knows about. Given a short request, no `cache_control` appears.
> **[CORRECTED — this invariant cannot be satisfied absolutely, and saying so is the
> honest form of it.]** The per-model minimum (512 / 1024 / 2048 / 4096) is not exposed by
> the Models API, and the design deliberately rejected hardcoding a table that would rot
> with every model release. The learned probe state cannot recover it either: Anthropic
> returns **one** `cache_creation_input_tokens` for the whole request, not one per marker,
> so a positive is never attributable to a span. The guard therefore enforces
> `MIN_CACHEABLE_TOKENS = 512` — the floor *under* the floors, below which nothing caches
> on any model — with an explicit `minimum_tokens` override for a caller that knows better.
> **Consequence, stated rather than hidden:** on a 4096-floor model (Opus 4.6/4.5,
> Haiku 4.5) markers will be placed that do not cache. They cost a wasted breakpoint, never
> a wrong request, and that is the price of not shipping a table that goes stale.
>
> **I3.** A marking failure never fails the turn. If `apply_cache_breakpoints` raises, the
> error is logged and the request is sent **unmarked**. Caching is an optimisation, never a
> dependency — the D01.2 mirror of D01.1's I2.
>
> **I4.** A provider without `supports_cache_breakpoints` sends a byte-identical request to
> today's. This is what makes shipping ON safe on a deployment that cannot use the feature.
>
> **I5.** A zero cache reading is never persisted and never disables marking. Only
> confirmed-positive results are durable. The guard is the first statement of
> `CacheProbeStore.record()`, not a condition at the call site, so a future caller cannot
> forget it — the provider's job is to report what the endpoint said, honestly, including
> a zero; the store's job is to refuse to persist it.
>
> **I6.** The invalidator audit is keyed `(session_key, owl_name)`, never the lane alone.
> **[ADDED — found in `validate`, on live traffic.]** An incident lane runs the staged
> RCA's three owls against one `session_key`, and their personas and tool sets differ *by
> design*. Keyed on the lane, the audit reported three correct prompts as three violations
> — DEBT-21's mistake exactly. An audit that cries wolf on every multi-owl lane trains its
> reader to ignore it.

## Configuration

`cache_ttl` on `ProviderConfig`, alongside `context_chars` and `max_output_tokens` — TTL is
a per-backend economic decision, so a user running two Anthropic backends can set it
differently on each. Default `"5m"`; accepts `"1h"`.

| Value | Write cost | Reads to break even |
|---|---|---|
| `5m` (default) | 1.25× | 2 requests |
| `1h` | 2× | 3+ requests |

5m is the default because a conversation is normally a burst of turns minutes apart. 1h
doubles the write cost, so a conversation that stops after two turns becomes *more*
expensive than not caching at all.

**No enable/disable flag.** The capability gate already makes this inert on every
non-Anthropic provider, so the feature ships ON per the standing rule without needing a
setting that would default off and never be turned on.

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| `apply_cache_breakpoints` raises | exception at the wrapper | Logged `error`; request sent unmarked (I3) | Nothing — the turn succeeds at full price |
| Span below minimum | the guard | Marker skipped, reason logged | Nothing — fewer markers, no wasted breakpoint |
| `count_tokens` unavailable on a gateway | request failure | Falls back to `chars/4` with margin, logged `error` | Nothing — caching still works |
| Gateway strips `usage` cache fields | `cache_creation` and `cache_read` both persistently 0 | Nothing persisted; marking continues (I5) | Nothing — no discount, no self-disable |
| Tools array varies per turn | per-`(lane, owl)` tools hash | Logged `warning` naming D01.3; marker still placed | Nothing — position 0 invalidated, cache under-performs |
| Markers accumulate across tool rounds | would break I1 on iteration 2 | Existing markers stripped before placement | Nothing — the budget stays at 4 |
| `count_tokens` measurement is stale mid-session | not detected, by design | Cached per `(session_id, model)`; a stale figure only shifts a threshold decision, never correctness | Nothing |
| Marker on a non-Anthropic provider | capability gate | Never reached (I4) | Nothing |

### Prior art, and where we deliberately diverge

Hermes' `agent/prompt_caching.py` (165 lines) is the reference: four markers, laid out as
static system prefix, end of system, and the last two non-system messages, with a fallback
to system-plus-three when no static prefix exists.

**Adopted:** the four-marker budget, the last-two-messages tail, the insight that nested
prefixes let a *new* session still hit a shared earlier marker, and — added during
implementation, after Bakir's instruction to read Hermes rather than our summary of it —
two things the design had explicitly ruled out:

- **Budget reallocation** (`remaining = 4 - breakpoints_used`). See the Lifecycle section.
- **Carrier pre-filtering** (`_can_carry_marker`): never spend a marker on a message that
  cannot hold one. Ours skipped such a message but did not try an earlier one, so an empty
  tool turn in the tail silently ate a breakpoint.

Their test suite also supplied the **marking-is-last ordering invariant** documented in
Lifecycle. Reading the 165-line source produced all three; reading our summary of it had
produced none.

**Diverged, with reasons:**

1. **One seam owns every marker.** Hermes marks in three places — `prompt_caching.py`
   (system + messages), `anthropic_adapter.py:1719` (tools), and `run_agent.py:6090` (a
   second system injection). That split is why their own documented "4-marker layout"
   never mentions the tools marker, which is the most valuable of the four. With one
   function seeing tools, system and messages together, the four-breakpoint budget is
   provably respected rather than enforced in three places that cannot see each other.
2. **We spend a breakpoint on tools; they spend it on a static system prefix.** Ours is
   below the cacheable minimum on most models, theirs is not — measured, not assumed.
3. **We guard the minimum; they do not.** Hermes places markers unconditionally. On a
   model with a 4096-token floor several of theirs are silently dead.
4. **We do not implement their envelope-layout handling.** `_can_carry_marker` exists
   because they route through OpenRouter, where a top-level marker on an empty-content
   message is ignored (and on `role: "tool"` causes a silent hang). We speak native
   Anthropic — `system` is a top-level parameter — so that entire class of subtlety does
   not apply. This is the rare case where our implementation is *simpler* than theirs, and
   it is worth stating so nobody ports the complexity back in.
5. **The 20-block lookback: we match them knowingly.** Anthropic documents that a
   breakpoint searches back at most 20 content blocks; Hermes has zero references to this
   and is protected only incidentally, by pruning tool results. We measured ours — 666
   tool-using traces, p50 3 calls, p90 10 (~20 blocks), max 42 — and **9.6% exceed it**.
   We match Hermes for now because `D03`'s tool-result pruning removes the cause, rather
   than spending one of four breakpoints on the symptom.

### How the two Laws hold

**Law 1 — per-conversation prompt caching is sacred.** This item does not merely respect
it; it is the mechanism that *enforces* it on the Anthropic path. D01.1 made the prompt
byte-identical; D01.2 is what actually claims the discount for it.

**Law 2 — the core is a narrow waist; capability lives at the edges.** Nothing is added to
the model's tool surface. No new core tool, no plugin, no MCP server. The change is
provider-internal and invisible to every prompt — with one stated exception: the
invalidator audit hooks into `pipeline/steps/assemble.py`, because that is where the frozen
prompt is built and therefore the only place a silent invalidator can be caught at its
source.
