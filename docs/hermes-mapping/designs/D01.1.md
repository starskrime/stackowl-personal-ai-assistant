## Why this exists

`assemble.run()` executes on every turn and rebuilds the entire system prompt from scratch:
persona + DNA injection, the existing-owls block, a capability banner, a relevance-scored skills
block, the recalled memory context, and a re-probed model window. Four of those six are stable for
the life of a conversation and are being rebuilt for nothing.

The consequence is not merely wasted work. StackOwl's only enabled provider is `NeraAiRaw`, an
OpenAI-protocol gateway, where **prefix caching is automatic on a byte-identical prefix**. A prompt
that changes every turn forfeits that discount silently — there is no marker to blame and no error
to notice. StackOwl has zero occurrences of `cache_control`, `cached_tokens`, or any caching
concept anywhere in `src/`.

It is also a latency problem. The rebuild puts a model-window probe, an embedding similarity scoring
pass, and several database reads on the critical path of **every reply**, before the model is
called at all.

This is one of two items in the map marked `CONFLICT`: StackOwl actively does the opposite of the
reference platform's first law.

## Model

Build a `SessionPrompt` **once** when a conversation starts, persist it, and reuse it verbatim for
every turn of that conversation.

| Part | Today | After | Bakir's decision |
|---|---|---|---|
| persona + DNA | rebuilt per turn | resolved at session start | Q14 — "then deferred is fine" |
| existing-owls block | rebuilt per turn | resolved at session start | Q11 — "keep it, load once" |
| capability banner | rebuilt per turn | resolved at session start | already static |
| skills | relevance-scored per turn, bodies injected | **catalogue only** (names + descriptions) at session start | Q9 — "names + descriptions always, body on demand" |
| memory | recalled per turn against the query | **user profile**, loaded once from an editable file | Q5 + Q13 — "stable picture, always loaded" |
| model window | re-probed per turn | resolved at session start | no reason to re-probe |

### Where the lost capability goes

Nothing is deleted — two behaviours move from the prompt to tool calls the model makes when it
actually needs them.

| Was | Becomes | Tool |
|---|---|---|
| Per-turn memory recall injected into the prompt | The model calls for depth when the conversation needs it | `memory` — **already exists** |
| Per-turn skill scoring, bodies injected | The model reads a skill body when it decides to use one | `skill_view` — **already exists** |

This is why the item is cheaper than it looks: the fallback path is wiring, not building.

### Key

```
SessionPrompt keyed by (session_key, owl_name)
```

`session_key` comes from `D01.7`. The owl is part of the key because switching owl means a
different persona and therefore a different prompt — a distinction Hermes does not need to make.

### Where it lives

**Persisted, not memory-cached.** Hermes keeps an in-memory LRU of live agent objects because their
gateway restarts rarely. StackOwl's core `os.execv`s itself on every code change, so an in-memory
cache would be discarded continuously during development — the exact scenario in which we most
need stable measurements. The prompt is stored alongside the session entry and rehydrated on
restart.

## Lifecycle

```
 message arrives
        │
        ▼
 D01.7 resolves (session_key, session_id)
        │
        ▼
 ┌────────────────────────────────┐
 │ SessionPrompt exists for       │── yes ──► load it, hash it, done
 │ (session_key, owl_name)?       │           (this is the hot path — a lookup)
 └────────────┬───────────────────┘
              │ no
              ▼
 build once:  persona+DNA · owls block · banner
              skill catalogue · user profile · model window
              │
              ▼
 persist, stamp prompt_hash (D01.6)
              │
              ▼
 every subsequent turn of this session reuses it BYTE-IDENTICALLY
              │
              ▼
 session rollover (D01.7) ──► discard; next turn rebuilds
```

`assemble.py` shrinks from an orchestrator to a cache lookup with a cold-start branch.

**Priority order on invalidation.** A `SessionPrompt` is discarded only by: (1) session rollover,
(2) an explicit `/new`, (3) an explicit user-initiated owl or persona edit. Background evolution
does **not** invalidate — it lands at the next rollover, which given daily boundaries is at most
hours away.

## What shipped, and why the order mattered

The freeze is this item's headline and it went **last**. Freezing earlier would have
pinned whichever value the first turn happened to carry. Each volatile part had to
leave first:

1. the next-contact banner → its own delivered chunk
2. `SessionPromptStore` + migration `0102`
3. stable user profile in, query-scoped recall out (keeping prefs + lessons)
4. lessons selected by owl identity rather than by the question
5. the focus clock stopped needing `assemble` to seed it
6. skills → a stable catalogue (names + descriptions; bodies via `skill_view`)
7. the STABLE and VOLATILE tiers named
8. the wall-clock left the system prompt and rides the turn
9. **the freeze**

Steps 7–8 are the correction that matters most. The original design said it adopted
Hermes' tier split and then *"froze even the volatile tier"* — **that adoption was
the error.** Volatile means volatile: a clock cannot be frozen, and neither can a
show-once banner or a "no capabilities *this turn*" instruction. Naming the tiers
gave every future per-turn fact a correct home instead of the next one being
smuggled into the system prompt and quietly costing the cached prefix.

## Invariants

> **I1.** Within one `session_id` **and one owl**, every turn sends a byte-identical system prompt.
> Measured directly: `COUNT(DISTINCT prompt_hash) GROUP BY session_id, owl_name == 1`. This is the
> item's pass/fail test, and `D01.6` exists to make it observable.

**The owl in that statement was missing until 2026-07-27, and without it the gate was
unpassable.** As first written, I1 grouped by `session_id` alone. But a lane can run several owls:
the staged RCA drives `rca_gatherer`, `hypothesis` and `verifier` against one incident lane, and
the live prompts showed `persona_len` cycling 291 / 252 / 255 / 303 inside a single incarnation.
Different owls **must** have different prompts — that is invariant I6, and the entire reason the
prompt cache key is `(session_key, owl_name)`. So the original query counted a correct design as
three violations, and this item would have been judged failed for behaving exactly as specified.

Inferring the owl from `session_key` was rejected: the key contains it for anything that came from
ingress (`owl:secretary:telegram:dm:…`), but an RCA lane's key is a bare incident id shared by all
three owls. Inference would have been right for ordinary conversations and silently wrong for
precisely the lanes that exposed the problem. `cost_records.owl_name` was added instead
(migration `0103`, `DEBT-21`); no provider signature grew, because `TraceContext` already carried
the owl and `_record_cost` already read `session_key` and `session_id` off it.
>
> **I2.** A cold build failure never fails the turn. Any part that cannot be resolved degrades to
> its absence and is logged at `error`; the prompt is built from what succeeded. Today's code
> already degrades this way and that behaviour is preserved.
>
> **I3.** No tool the owl owns becomes invisible as a result of this change. (Bakir, Q22 — hard
> invariant.) Tool presentation is `D01.3`'s problem; this item must not touch it.
>
> **I4.** The owl still sounds like itself. Persona and DNA reach the model with the same fidelity
> as today — the same injector, the same content, resolved once instead of repeatedly.
> (Bakir, Q22 — hard invariant.)
>
> **I5.** Scheduled jobs and proactive delivery keep working across the change.
> (Bakir, Q22 — hard invariant.)
>
> **I6.** A persisted prompt is never reused across owls or across `session_id`s. The key is
> `(session_key, owl_name)` and the entry is bound to the current incarnation.

Note what is deliberately **not** an invariant: recall parity. Bakir accepted a recall regression
explicitly (Q24 — "memory is weak anyway"), so no recall-regression gate blocks this item.

## Configuration

**No configuration was added, and that is deliberate.**

The draft proposed a `session.prompt` block with a `profile_source` key. The profile
is read from `~/.stackowl/USER.md` via `StackowlHome.home()` and nothing needed to
be configurable to make the item work — so the key was not invented. A setting with
one possible value is a setting nobody can use and everybody has to reason about.

If a second location is ever genuinely needed, `memory/user_profile.py`'s
`default_profile_path()` is the single place it would be threaded through.

**There is no `enabled` flag, and that is deliberate.** This draft originally specified one
(`enabled: false` restoring the per-turn rebuild as a "rollback path"), which contradicts the
decision recorded in `progress.yml` on 2026-07-25:

> `migration: Cut over immediately and restart the platform. No dual path, no flag.`

A flag here is not free: it is precisely the second assembly path Bakir rejected when he also
rejected approach B ("stable prefix + live suffix — keeps per-turn retrieval latency and leaves two
assembly paths alive permanently"). Keeping both alive would mean every later item in this domain
has to reason about which one is live, and the measurements this whole wave exists to produce would
depend on an invisible setting. Rollback is `git revert`, which costs a restart and no permanent
complexity.

Corrected 2026-07-27, before implementing against this section — the drift was found by re-reading
the decision record rather than the doc.

### Two behaviours became unconditional, and both are configuration in spirit

Neither is a settings key, but both are decisions a reader will otherwise assume
were oversights and "fix" back.

**The call protocol** (`DEBT-22`). `assemble` calls `build_stable_base_prompt(lean=lean)`
with no `describe_tool_protocol` argument, so the `ACTION:` protocol ships on every
turn. It used to be dropped on a tool-free turn. A frozen prompt cannot express a
per-turn conditional at all: a session opening on a chat turn would have carried a
protocol-less prompt for its whole life and lost tool use until the next rollover.
The imitation defence that conditional existed for did not go away — it moved to
`volatile_turn_context(capabilities_offered=False)`, which states the prohibition on
the turn that is actually tool-free.

**The capability banner** (`DEBT-24`, found in `cleanup`). `CapabilityManifest.probe`
is now called with `tools_enabled=True` unconditionally. It previously received
`state.intent_class not in TOOL_FREE_CLASSES`, which was correct while the prompt was
rebuilt per turn and became a **session-long falsehood** once it was frozen: a
conversation opening with "hi" froze a prompt missing the device-access line — the one
written to stop the owl claiming it is a cloud model that cannot reach the user's
machine — and daily rollover kept it missing for up to a day. Measured with `shell`
registered: 579 chars vs 336. The banner asserts *platform* capability, which is a fact
about the session, not the turn.

Both are the same lesson, and `base_prompt.py` records it where the next person will
look: if a new fact is true of **this turn** rather than of the session, it belongs in
`volatile_turn_context`, never in the frozen prompt.

There is **no invalidation log line**, because there is no invalidation *event*:
`prompt_store.load` returns `None` when the stored row belongs to a different
`session_id`, so a rollover is a read-time miss followed by an ordinary
`cold_build`, not a discard. The old table's `prompt_invalidated` row described a
mechanism that was never built.

`exit` is `info`, not `debug`, deliberately: at debug these per-part sizes vanished
entirely — 0 of 17403 live log lines carried them — which is why prompt composition
was unmeasurable before `D01.6`.

Failure paths all log at `error` with `exc_info`, one per degradable part:
`prompt cache read FAILED`, `persona injection FAILED`, `existing-owls block FAILED`,
`skill catalogue FAILED`, `base prompt build FAILED`, `capability manifest FAILED`,
`user profile FAILED`, `undelivered banner FAILED`, `prompt freeze FAILED`.

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| Persona injection fails at cold build | exception in injector | Logged `error`, prompt built without persona (today's behaviour) | A less characterful reply for that session |
| Profile file missing or malformed | read/parse | Empty profile, logged `error`; the session still works | It knows less about them until fixed |
| Persisted prompt unreadable after restart | rehydrate | Cold rebuild, logged `warning` | Nothing — one slower first turn |
| Prompt hash differs mid-session | `D01.6` invariant query | **Bug.** Alerts via the invariant test, not at runtime | Nothing directly; caught in validation |
| Owl switched mid-lane | key mismatch | New key, cold build for that owl | Nothing — correct behaviour |

## What `cleanup` and `test` changed after the freeze shipped

Recorded here because `PROCESS` forbids quiet drift between the design and the code.

**Removed** — each verified to have zero callers across the tree before deletion:
`operational_adapter()`, `build_base_prompt()` and `build_base_prompt_now()` from
`base_prompt.py`, plus `_GLOBAL_CATALOG_K` in `assemble.py`. By then the adapter held a
second verbatim copy of every string in the stable and volatile tiers, so the same
prompt text was being maintained in two places — the file's own comment said to delete
it once both callers had moved, and both had. `build_base_prompt_now()` had no callers
even before this item.

**Kept, deliberately** — `skills/skill_relevance.py`, `assign_tiers()` and the two
score floors are orphaned but were **not** deleted. Bakir rejected the proposal to
remove them and the evidence agreed: the scorer's input is still computed every turn
(`classify.py` → `delivery_gate.py`), and `skill_view.py` still *writes* focus
hysteresis whose only reader is that scorer. That is a half-wired feature, not
finished orphan code, and deleting the reader would strand a live writer permanently.
Tracked as `DEBT-25` and handed to `D05.4`, whose progressive disclosure is a sibling
of this machinery — `X2` names the *budgeter* as the mechanism that should go, not
skill tiering.

**Fixed** — `DEBT-24`, described under Configuration above: a regression this item's own
freeze introduced.

**The limitation that qualifies this document** — `DEBT-27`. The freeze engages only for
lanes that arrive through channel ingress. `assemble` gates both the cache read and the
freeze write on a non-empty `session_id`, which is minted by
`sessions/ingress.py::resolve_turn_session` — a function with exactly one caller,
the gateway path. Every background and scheduled lane therefore cold-builds on every
call: measured live, **1 cached vs 51 cold_build**. Invariant I1 still holds and the
provider-side cost win still applies, because each owl reproduces a byte-identical
prompt. What is not being realised for those lanes is the *latency* half — the window
probe, the profile read and the catalogue read have not left the critical path. This
contradicts a recorded decision (background work was an explicit target, `D01.7`
brainstorm), so it is a gap against intent rather than a scope boundary.
**The `session_id` guard itself is deliberate and must not be "fixed" by deleting it**:
every background lane shares the empty key, so dropping it would serve one owl's frozen
prompt to every other background owl. The fix is to give those lanes a real session
identity. Handed to `D01.7`.

- Prior art: `hermes-agent/agent/system_prompt.py` and its three-tier stable/context/volatile split.
  **Adopted:** build once per session, move on-demand depth to tool calls, and defer background
  changes to the next boundary.
  **Adopted and then CORRECTED:** this line previously read "freeze even the *volatile* tier",
  and that adoption was the single worst error in the design. Volatile means volatile. A clock
  cannot be frozen — for a session bounded by daily rollover it would tell the model a time up to
  ~24h stale, defeating the exact purpose the timestamp serves. Neither can a show-once banner, nor
  a "no capabilities *this turn*" instruction, nor a capability claim that is true only of some
  turns. Four separate findings were the same mistake in different fields (the undelivered banner,
  per-turn recall, `DEBT-23`, `DEBT-24`), which is why the tiers are now **named functions** with
  the per-turn one delivered alongside the turn: naming them gives every future per-turn fact a
  correct home instead of the next one being smuggled into the system prompt and quietly costing
  the cached prefix.
  **Diverged:** we persist rather than hold the prompt on a cached agent object (our core
  exec-replaces itself constantly); we key on owl as well as session (they have one agent); and we
  enforce stability with a measured hash invariant rather than by review discipline. Hermes has no
  equivalent of `prompt_hash` — they rely on reviewers catching cache-breaking changes, which is
  exactly the kind of guarantee we prefer to assert.
