## Why this exists

**The map asks the wrong question, because the answer already shipped.** It asks whether
deferred-by-default is acceptable UX for StackOwl. StackOwl has *been* deferred-by-default
since `D01.1`, silently: the system prompt is frozen for the life of a session and **nothing
in the tree can clear it**. Edit an owl's persona mid-conversation and that conversation
never sees the change.

That is proven, not asserted. `tests/pipeline/test_d011_frozen_prompt_gateway_integration.py`
mutates an owl's persona between turn 1 and turn 2 and asserts turn 2 does **not** see it:

```python
# line 342 — the assertion, and its failure message
assert _PERSONA_AFTER not in systems[1], (
    "I1 FAIL (and the freeze is not engaged): turn 2 picked up the persona "
    "change made mid-conversation, which means the prompt was REBUILT ...")
```

Structurally the same: nothing outside `sessions/prompt_store.py` references
`session_prompts`, the store only ever `INSERT`s / `UPSERT`s (never deletes), and an owl edit
does not touch `session_id`. The only release is a rollover minting a new incarnation — and
`D01.7` rolls daily at 04:00 or after idle, so "next session" can be twelve hours away.

So this item is not "should we defer?". It is **the invalidation seam `D01.1` never built**,
plus a decision about who is allowed to be surprised.

**The economics decided it, against the original recommendation.** A cache miss on the
~2712-token frozen prompt costs roughly **4c** against the `D01.6` baseline (40 calls,
180,712 input tokens, $2.85). A confused user re-editing costs roughly **57c per turn** —
about 13× more. And the retry loop is documented in `pipeline/steps/assemble.py` already: the
model kept retrying `owl_build` with name variants ("Brain" → "Researcher Brain" →
"research_brain") until the owls block was added to stop it. **Silence causes retries, and
retries cost more than the miss.** Silent deferral is therefore the *expensive* option.

## Model

The rule is not deferred-vs-immediate. It is **who is surprised**.

| Actor | Change | Applies | Why |
|---|---|---|---|
| Human, at a keyboard | `/owl edit`, skill install, permission change | **Immediately** (next turn) | Someone is waiting and expecting an effect; surprise costs ~13× the miss |
| Owl, mid-task | `tool_build`, skill create, self DNA edit | **Next turn boundary** | The autonomy loop must not stall until 04:00 — but never mid-turn, or Law 1 breaks |
| Machine, unattended | nightly DNA evolution, background curator writes | **Deferred to rollover** | Nobody is waiting; deferral is free |

**Deferred changes need no machinery at all.** A rollover mints a new `session_id`, the
stored row stops matching, and the next turn cold-builds. `D01.1`'s self-enforcing design
already applies them. No pending queue, no listener, no table.

### Interface

Two explicit methods on `SessionPromptStore`, beside `load`/`save`:

| Method | Clears | Called from |
|---|---|---|
| `invalidate_owl(*, owl_name, cause) -> int` | that owl on **every lane** | `owls_command._edit`, `owl_build` (3 rebuild sites) |
| `invalidate_all(*, cause) -> int` | every frozen prompt | `SkillIndexStore.set_enabled` |

**Where each trigger hooks, and why there.** The skills trigger is bound to the **write** in
`SkillIndexStore.set_enabled`, not to the `/skill` command, so a future writer reaching the
catalogue by another route still invalidates — the reasoning that put cache marking at one
chokepoint in `D01.2`, and the exact gap its cleanup stage found in the stream path.

**`owl_build` was named as a trigger and never wired. [ADDED]** The design listed owl
self-extension among the triggers but did not say where it hooks; implementation filled the
`session_prompt_store` gap in that path's `StepServices` so it *could* reach the store, and
then nothing called it. Cleanup found the seam reachable and unused — "registered but never
wired", one item after `D01.2` found the same shape. It matters more here than for the slash
command: an owl that rewrites its own specialty mid-task and does not invalidate keeps
reasoning under the persona it started the session with, so the autonomy loop silently ignores
its own change until 04:00. Now wired at all three rebuild sites through one helper.

Two names rather than one optional argument: the dangerous case must not be the default.
Both return the row count, for the log line.

**Blast radius is per-owl, not per-lane.** You edited the *owl*, not one conversation, so
`secretary` on Telegram, CLI and two incident lanes all rebuild. Anything narrower lets the
same owl silently disagree with itself across channels — the harder bug to diagnose.

`invalidate_all()` is **global across principals**, and that is deliberate. `session_prompts`
has no `owner_id` (migration `0102`, "NO owner_id, DELIBERATELY" — the parent `sessions`
table has none either). The skills catalogue and capabilities block are machine-wide facts,
so every prompt containing them genuinely *is* stale after an install.

## Lifecycle

```
 human edits an owl                     owl self-extends            nightly evolution
        │                                      │                            │
        ▼                                      ▼                            ▼
 persist the change                    persist the change           persist the change
        │                                      │                            │
        ▼                                      ▼                            │
 await invalidate_owl(cause=…)          await invalidate_owl(…)             │  (nothing)
        │  DELETE … WHERE owl_name = ?         │  at the TURN boundary      │
        ▼                                      ▼                            ▼
 confirmation returned                 next turn starts             04:00 rollover
        │                                      │                            │
        └──────────────┬───────────────────────┘                            │
                       ▼                                                    ▼
              next turn: load() misses ──► cold build ──► save()   new session_id ⇒ same
                       │                                            miss, same cold build
                       ▼
              cause consumed by cache_audit ⇒ "changed as requested" at info
```

**Ordering is guaranteed by the call stack, not by scheduling.** The command `await`s
invalidation before returning its confirmation, and the next turn cannot begin until the user
has that reply. There is no race to test for because none exists.

**This is why the EventBus was rejected**, despite `owls_command.py:379` already emitting a
(dead, unsubscribed) `owl_edited` event. `EventBus.emit` runs *sync* handlers inline — but
invalidation must `await` a DB write, and only *async* handlers may await, and those are
"scheduled on the running loop". Scheduled is not ordered.

**An in-flight turn always finishes on the prompt it started with.** One rule for both
actors — human edits and owl self-changes behave identically — which is what keeps Law 1
("nothing mutates past context") true by construction.

## Invariants

> **I1.** Invalidation never affects a turn already in flight. It changes only what the
> *next* turn builds.
>
> **I2.** A change made by a human is visible to the next turn on every lane that owl serves.
> This is the item's entire user-visible promise, and the assertion currently FAILS by design
> (`D01.1` proves it), so the test for it is guaranteed to be able to fail.
>
> **I3.** A failure to invalidate never rolls back or fails the change itself. The edit
> persisted; losing the cache clear is logged at `error` and the turn proceeds. Mirrors
> `D01.2`'s I3.
>
> **I4.** Invalidation is idempotent and safe when nothing matches. Background lanes never
> froze a prompt (`DEBT-27`: they have an empty `session_id`), so a delete clears 0 rows and
> costs nothing — and becomes meaningful automatically once `DEBT-27` lands, with no change
> here.
>
> **I5.** Enforcement never depends on prompt freshness. A revoked permission is refused at
> dispatch however stale the prompt is — **but only while the owl registry stays live.**
> If the registry is ever cached per session to match the prompt freeze, this silently
> becomes false. See "The load-bearing condition" below.

## Configuration

**None.** This item adds no settings. There is no enable flag and no `--now`/`--later` pair:
under the model above, a human change is simply immediate, so there is nothing to opt into.

## Observability

| Point | `msg` | `_fields` |
|---|---|---|
| exit | `[prompt] invalidate: exit` (**info**) | `cause, scope, owl, rows` |
| failure | `[prompt] invalidate: no store wired — the change will not apply until rollover` (**error**) | `cause, owl` |
| audit | `[cache] breakpoints: prompt part changed as requested` (**info**) | `session_key, owl, parts, cause` |

`info`, not `debug`, deliberately — `D01.6` logged the diagnostics it needed at debug and they
appeared in **0 of 17403** live log lines.

This is the missing half of `D01.2`'s audit: that one names *which part* changed, this names
*what caused* the rebuild. Together they answer "why did this cost me a cache miss" from the
JSONL alone.

```bash
cat ~/.stackowl/logs/stackowl.jsonl \
  | jq -r 'select(.msg=="[prompt] invalidate: exit")
           | "\(.fields.cause) scope=\(.fields.scope) owl=\(.fields.owl) rows=\(.fields.rows)"'
```

### The clash this creates, and how it is resolved

`D01.2`'s `audit_prompt_parts` warns whenever a prompt part changes between cold builds.
After this item, **every deliberate edit produces exactly that** — so editing a persona would
emit a warning about a change the user just asked for. That is the same cry-wolf failure the
`D01.2` validate stage caught, arriving from the other direction.

The `cause` is therefore threaded through: an explained change logs at `info` as "changed as
requested"; an **unexplained** change stays a `warning`. The audit keeps doing the one job it
exists for — catching invalidators nobody asked for.

**How the cause travels, which the design did not specify. [ADDED]** It lives in
`infra/prompt_invalidation.py`, and both halves of that placement are load-bearing:

- **`infra/`, not beside either user.** `sessions/prompt_store.py` records the explanation and
  `pipeline/cache_audit.py` consumes it, and `sessions` must not import `pipeline`. Both may
  import `infra`. Exactly the layering that put `prompt_metrics` there.
- **A module-level map, not a `ContextVar`.** The two halves happen in *different turns* — the
  invalidation while handling a slash command, the audit during the *next* turn's cold build.
  A ContextVar is per-async-context and would be empty by then. It is the right tool for
  `prompt_metrics` (one turn) and the wrong one here.

The explanation is **consumed once**: one invalidation explains one rebuild, so a single edit
cannot blind the audit for the life of the process. The pending map is FIFO-bounded at 256 —
an explanation never consumed means the predicted rebuild never happened, and evicting fails
toward `warning`, the safe direction for an audit.

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| No store wired at a call site | `services.session_prompt_store is None` | Logged `error`; the edit still succeeds | Nothing — but the change waits for rollover |
| DB delete fails | exception in `invalidate_*` | Logged `error`, swallowed (I3) | Nothing — the edit persisted |
| Nothing to invalidate | 0 rows | Normal (I4) | Nothing |
| Change made while a turn is in flight | not detected, by design | The turn finishes on its own prompt (I1) | The *next* reply reflects the change |
| Registry cached per session (hypothetical) | — | **None — I5 silently breaks.** See below | Stale enforcement |

### The load-bearing condition

`I5` holds because `pipeline/authz_compose.py` computes `owl.bounds(now) ∩ creation_ceiling`
— live, at dispatch — and its docstring states the fail-closed contract plus *"task_envelope
is intentionally excluded from enforcement (E2-S3) … the hard boundary must not depend on an
LLM-derived hint."* Presentation is not authorisation.

**This is written down because it is fragile.** If anyone ever caches the owl registry per
session to mirror the prompt freeze, enforcement becomes as stale as the prompt and `I5`
fails with no test to catch it. Any future item that proposes caching the registry must read
this paragraph first.

### Prior art, and where we deliberately diverge

**The map is wrong about Hermes, and this is the third such correction in the program.** It
states that "any command that would mutate system-prompt state … takes effect next session by
default, with `--now` for immediate. This is the canonical pattern, documented as such."

Hermes *does* have that contract, named and reused — `hermes_cli/skills_hub.py` carries
`"--now invalidates prompt cache immediately (costs more money). Default: defer to next
session to preserve cache"`, and `agent/coding_context.py:37` describes the `/coding` flip as
"the same contract as ``/skills install`` vs ``--now``". But it covers **skills and `/coding`
only**. Everywhere else the gateway calls `_evict_cached_agent(session_key)` at **56 call
sites**, applying the change at the next *message* with no deferral and no cost message. And
no file under `docs/` describes the deferral at all, so "documented as such" is not right
either.

**Adopted:** the insight that prompt-mutating changes have a cost worth naming, and that a
cache-preserving default is a legitimate product decision rather than an oversight.

**Diverged, with reasons:**

1. **We invalidate rather than evict.** Hermes drops a cached *agent object*; we delete a
   *persisted row*. Ours survives the `os.execv` that StackOwl performs on every code change
   — the same divergence `D01.1` recorded for the freeze itself.
2. **Human changes are immediate; theirs defer.** Their `--now` exists because deferral is
   their default. Ours is inverted on measured grounds: the retry loop deferral causes costs
   ~13× the cache miss it saves, and StackOwl has that loop on record.
3. **We have an actor distinction they cannot have.** Hermes runs one agent with no
   self-extension, so "an owl changed its own state mid-task" has no equivalent. The
   next-turn-boundary rule is ours.
4. **One rule for in-flight turns, not two.** Both a human edit and an owl self-change let
   the current turn finish on its own prompt. Hermes' eviction can land mid-conversation.

### How the two Laws hold

**Law 1 — per-conversation prompt caching is sacred.** Invalidation never touches a turn in
flight; it only changes what the *next* turn builds, so nothing mutates past context. Worth
stating plainly, though: this makes invalidation the **second** sanctioned way a frozen
prompt's life can end early, alongside compression. A reader who assumes rollover is the only
release will be wrong.

**Law 2 — the core is a narrow waist.** Nothing is added to the model's tool surface. No new
core tool, no plugin, no MCP server, no new module — one method pair on an existing store,
one line in an existing `set_services` call, and call sites that already exist.
