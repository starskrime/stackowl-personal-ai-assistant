## Why this exists

`D01.1` froze the system prompt; `D01.2` placed cache markers; `D01.3` measured
that the **tools array** changes anyway — 15 events across 5 `(lane, owl)` pairs,
with the tool *count* itself oscillating in 4 of 5. On the Anthropic wire `tools`
renders at **position 0**, so a moving array invalidates marker 1 and everything
downstream, every turn.

## The actual defect

`to_provider_schema` runs **two** stages, and only the second is wrong:

```
 profile / pins / hydrated
        │
        ▼
 ToolPresentation.select(...)        "deterministic, self-healing"   ← STABLE
        │
        ▼
 if budget is not None:
     rank_candidates(request_text=…)  ordered by LEXICAL RELEVANCE   ← THE DEFECT
     fit_items(window − fixed_cost)   greedy fit                     ← keep this
        │
        ▼
 presented set   (overflow → tool_search, already)
```

**Defect A — the ordering signal is the query.** `rank_candidates` orders the
discretionary set "by lexical relevance to `request_text`", so a different
question yields a different order, a different greedy fit, and therefore a
different array.

**Defect B — the BUDGET moves too, and this one was missed by the brainstorm.**
Found by reading the call site rather than the map:

```python
# execute.py:1100 — recomputed EVERY turn
_fixed_cost = _est_tokens(state.system_prompt) + sum(
    _est_tokens(getattr(m, "content", "")) for m in state.history
)
# context_budget.py:41
return window - fixed_cost_tokens
```

`fixed_cost` includes **the conversation history**, which grows on every turn. So
the tool-token budget *shrinks monotonically as the session proceeds*, and
`fit_items` admits fewer candidates — **even if the ordering is perfectly
stable.** When history is trimmed or compacted the budget recovers and the tool
comes back.

That is the missing explanation for the most striking part of D01.3's
measurement: the tool **count** oscillated in 4 of 5 pairs
(`5 → 4 → 5 → 5 → 5`, `4 → 4 → 3 → 4`). An ordering defect alone reshuffles a
fixed-size array; it does not change its length. Defect B does.

**Both are ordering/sizing problems, not capability losses.** Nothing is
unreachable — the prefix simply never repeats. But fixing only Defect A would
have left `I1` unmet and the item would have shipped looking correct and
measuring unchanged.

## The design

**Decide the presented set once per session, from a stable signal.** Two changes,
one per defect, and nothing else moves.

| | today | after |
|---|---|---|
| ordering signal (A) | lexical relevance to *this query* | measured usage for *this owl* |
| when the fit runs (B) | every turn, against a shrinking budget | **once per session**, memoized |
| `fit_items` algorithm | greedy size-fit | **unchanged** — same function, called less often |
| window awareness | `window − fixed_cost` | **kept**, but evaluated at the session's first turn |
| overflow | `tool_search` | **unchanged** |
| guaranteed set | never evicted | **unchanged** |

The learned core is not an addition bolted onto a port — it is the **direct
substitute** for `request_text` at the same seam. A stable input where an unstable
one used to be.

### Why memoization, and not "just remove history from fixed_cost"

Dropping `state.history` from `_fixed_cost` would stabilise the budget, and it is
the smaller diff. It is **rejected**: the budget's purpose is to stop a
small-window model being handed more schemas than it has room for, and on turn 40
the history *is* the room. A budget that ignores it would be stable and wrong,
overshooting exactly when the window is tightest. `I3` says window-awareness must
survive; this would keep the call and hollow out the meaning.

Memoizing keeps the measurement honest and moves *when* it is taken: at the
session's first turn, where `D01.1` already establishes the frozen prompt and
`D01.4` already provides the invalidation seam. It is also Hermes' shape —
`agent_init.py:1386` builds the array once and the loop never rebuilds it —
arrived at from our own constraint rather than copied.

**Memo key:** `(session_key, owl, protocol, window)`. Protocol and window are in
the key because `build_tool_schemas` is deliberately re-invoked per escalation
tier — `execute.py:1113` states a fast and a powerful tier "can speak different
wire protocols and have different context windows". A memo keyed on the session
alone would hand an Anthropic-shaped array to an OpenAI-protocol tier. Each tier
gets its own stable array; each is stable across turns, which is what the cache
requires.

**Not memoized:** the `restrict_to` path (`execute.py:1126`). A planned envelope
is per-task by construction and already routes through the deterministic
`select()`, not through the budgeter. It has neither defect.

**Also not memoized: the depth>0 exclusion** (`execute.py:1144`). Spawn/delegate
tools are stripped *after* the schemas are built, and `delegation_depth` is a
property of the turn, not the session. It must stay outside the memo or a
delegated child's exclusion would be cached onto its parent's lane.

### The one deliberate exception: tool_search hydration

`I1` and `I2` genuinely collide here, and the collision is worth stating rather
than resolving by omission.

FX-07 promotes a `tool_search` hit "into the NEXT turn's presented schema"
(`tool_search.py:158`) via a session-scoped hydrated set. That is a mid-session
change to the array — precisely what `I1` forbids. Under a naive memo the
promotion would silently stop working: the model would search, find the tool, and
never receive it.

**Resolution: the hydrated set is part of the memo key, so a hydration
invalidates.** One cache miss, at the moment the model discovers a tool it needs.

That is the right trade, for three reasons. It is **bounded** — the hydrated set
is monotonic within a session and only grows on an explicit `tool_search`, so the
number of invalidations is the number of discoveries, not the number of turns. It
is **caused**, not incidental — the prefix changes because the toolset genuinely
changed, which is the one thing a cache invalidation is *supposed* to mean. And
the alternative is worse: silently dropping promotion would trade a rare, useful
cache miss for a permanently broken bridge.

Hermes does not face this because their bridge *dispatches* (`tool_call`) rather
than promoting into the schema, so their array never changes. Ours promotes,
which is better for the model — the tool arrives natively next turn — and costs
one rebuild. We keep ours and pay.

### The learned core

- **Signal:** frequency × success, recency-weighted, grouped from
  `task_outcomes.(owl_name, tool_sequence)` — already recorded, already complete.
- **Cold start:** the owl's declared capability preset — which already exists
  (`owl_build_infer.infer_capability`, `manifest.capability_profile`) and is
  already the authz basis. Nothing new is invented for a new owl.
- **Recomputed at session boundaries only.** Never mid-session. This is the load-
  bearing constraint: it changes exactly where `D01.1` already permits change, and
  `D01.4`'s `invalidate_all` is the seam that applies it.
- **Demotion:** unused for N *rollovers* — session-boundary count, not wall-clock,
  so an owl that runs rarely is not punished for being idle.
- **Never deletes.** Learning only moves a tool between core and bridge. A demoted
  tool is still discoverable and still promotable by `tool_search`.
- **Respects `max_tools`.** An unbounded learned core would grow back into the
  window pressure the bridge exists to relieve.

### Where the signal comes from — and why nothing is stored

Three candidates were checked against the live database rather than assumed:

| Candidate | Verdict |
|---|---|
| `infra/tool_outcome_ledger.py` | **No** — turn-scoped, does not persist |
| `tool_heuristics` (34 rows) | **No** — has `tool_name`, `mean_quality`, but **no owl**; and it is outcome *prediction*, not usage |
| **`task_outcomes` (10,311 rows)** | **Yes** — `owl_name` + `tool_sequence` + `success` + `quality_score` + `captured_at`, zero write gap |

The read helper also exists. `outcome_store.list_successful_with_sequence`
(`outcome_store.py:501`) already returns exactly this shape — scored,
quality-filtered, non-empty-`tool_sequence` outcomes carrying `owl_name` — and is
already in use by `SkillSynthesizerHandler`. The positives-only gate exists too:
`is_positive_signal` (`outcome_store.py:76`), which `ToolOutcomeMiner` calls and
which additionally excludes a user-Disliked approach. **I5 is inherited, not
re-implemented.**

**So no table is added and no migration is written.** The aggregation is a
group-by over ≤500 rows performed once at a session boundary. Persisting it would
create a fourth store overlapping three existing ones, which is precisely the
duplication `X2` exists to remove — the item would reintroduce its own bug class.

**Two parameter details the implement stage must not inherit blindly** (read, not
assumed — both are on `list_successful_with_sequence`):

1. `min_quality=0.75` is a *skill-synthesis* threshold. "Good enough to base a new
   skill on" is a stricter bar than "this owl actually uses this tool." Ordering
   wants the looser one.
2. `limit=500` with `ORDER BY captured_at ASC` returns the **oldest** 500 in the
   window. For a recency-weighted signal that is the wrong end of the range. Either
   pass a window narrow enough that the limit cannot bind, or add an owl-scoped
   DESC variant — do not silently reuse the default and call the result recent.

### What ToolOutcomeMiner does and does not give us

`learning/tool_outcome_miner.py` already scans these outcomes and writes
`tool_heuristics` on a daily schedule (`scheduler/handlers/tool_outcome_miner_handler.py`).
It is not reusable here, for a reason worth stating rather than restating as a
gap: **it buckets by `(tool, failure_label)` and discards `o.owl_name`, which is
sitting on the outcome it is iterating** (`tool_outcome_miner.py:122`). Its
question is "does this tool tend to succeed?" — global, predictive. Ours is "does
*this owl* reach for this tool?" — per-owl, descriptive.

Adding `owl_name` to its bucket key was considered and **rejected**: it would
split a 34-row table's rows per owl and change what its read surface means
(`find_for_tool`, `list_all` — both keyed on tool, by design), to serve a consumer
that does not need the result persisted at all.

### Where membership lives — the one brainstorm question left open

Brainstorm closed with "where does toolset membership live — the tool's own
declaration, the owl manifest, or both, and which wins?" unanswered. **The tree
answers it, so no new decision is taken here.** `base.py:82-86`:

- **The tool declares its group.** `toolset_group: str | None` — one group name,
  set by the tool itself.
- **The owl's manifest selects groups.** `capability_profile` lists group names;
  "a tool joins the presented set when its `toolset_group` is in that profile".

So: both, at different ends, and neither "wins" — the tool declares *what it is*,
the owl declares *what it wants*, and presentation is the intersection. Adding a
manifest-side per-tool override would create a second way to express membership
and a precedence rule to go with it; there is no requirement here that needs one.

`toolset_group` is also explicitly **not** `consent_category` (grouping, not
consent) and **not** `capability_tag` (same-kind-of-result, used for self-healing
substitution). Three adjacent fields; this item touches only the first.

### tool_search results are filtered by the owl's envelope

Not for security — `execute.py:430` confirms a tool can be *"visible but still
DENIED"*, and dispatch enforces `compute_effective_bounds` regardless. For
**efficiency**: an unfiltered search advertises dead ends the model will call and
be refused for, burning a 15–35s round-trip and real money each time. Presentation
and authorisation stay separate mechanisms; the search surface simply stops
suggesting the impossible.

## Invariants

> **I1.** The presented tool array is byte-stable for the life of a session,
> **for a given (owl, protocol, window, hydrated-set)**. This is the item's entire
> purpose; `D01.2`'s position-0 marker is worthless otherwise. The qualifiers are
> not weasel words — each names a thing that legitimately differs (an escalation
> tier's protocol, its window) or legitimately changes (a discovery). Turn count
> and question wording are not on that list, and today they both are.
>
> **I2.** No tool is ever unreachable. Overflow stays discoverable via
> `tool_search` and promotable into the next turn — as it already is today.
> Learning may move a tool between core and bridge; it may never remove one.
> **`I2` beats `I1` where they collide:** a hydration invalidates the memo rather
> than being dropped to preserve stability.
>
> **I3.** Window-aware fitting survives, and survives *meaning what it meant*.
> `fit_items` is still called with a budget measured from the real window and the
> real fixed cost — it is called once per session instead of once per turn. Keeping
> the call while removing history from the measurement would satisfy the letter of
> this invariant and defeat it: the budget would be stable and wrong exactly when
> the window is tightest.
>
> **I4.** The core changes only at a session boundary. A mid-session change would
> re-break `I1`.
>
> **I5.** Learning reads only positive signal. Inherited from `is_positive_signal`
> rather than re-implemented — the standing operator directive is that the
> platform never learns "tool X fails under Y", and a second copy of that filter
> is a second place for it to drift. The same gate already excludes a user-Disliked
> approach.
>
> **I6.** No new table. The item adds no migration and no store. Persisting a
> fourth per-tool aggregate alongside `task_outcomes`, `tool_heuristics` and the
> turn-scoped ledger would recreate `X2` — the duplication this item exists to
> resolve.

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| Learned core grows past the window | `max_tools` cap | Overflow to bridge | Nothing |
| Owl's role changes; core is stale | recency weighting | Adapts over N rollovers | Briefly suboptimal ordering |
| Outcome query fails or returns nothing | empty result at rollover | Fall back to the capability preset (the cold-start path — it must be a live fallback, not just a first-run branch) | Nothing |
| An owl has outcomes but all below the quality bar | empty result | Same fallback | Nothing |
| Core recomputed mid-session | **would break I1** | Must be prevented by construction, not by check | Cache miss every turn |
| Memo key omits protocol/window | — | **Not detected.** An escalation tier would receive the other tier's wire shape | Malformed tool schemas on the escalated call |
| Memo key omits the hydrated set | — | **Not detected.** FX-07 promotion silently stops working | The model searches, finds a tool, and never gets it |
| Memo survives a session boundary | `cache_audit` stays silent, wrongly | Keyed on `session_key`, so a new session cannot hit it | A learned demotion never takes effect |
| History-derived budget left per-turn | `cache_audit` still fires on `tool_count` | — | Defect B unfixed; the item looks done and measures unchanged |

### Prior art, and where we deliberately diverge

Hermes builds `agent.tools` **once** at init from `enabled_toolsets` /
`disabled_toolsets` and never rebuilds it (`agent_init.py:1386`), with overflow
deferred behind `tool_search` / `tool_describe` / `tool_call` above a
`threshold_pct` of the context window (`tools/tool_search.py`).

**Adopted:** nothing, in the end — we already had the equivalent. The value of
reading them was **diagnostic**: it showed the target shape clearly enough to
reveal that our defect was one ordering argument, not a missing subsystem.

**Diverged — and this is the item's whole contribution:** their toolsets are
static, human-edited configuration, because they have **one agent**. We have owls,
an authz envelope, two months of per-owl outcome history and `D01.4`'s
invalidation seam, so the core set can be **learned per owl from measured usage**
rather than configured. They cannot do this — there is no per-agent identity to
learn against, so a human edits the list.

**One thing of theirs we should not copy:** `dynamic_schema_overrides` — a
callable re-evaluated on every `get_definitions()` so a description can reflect
live config. It makes the schema config-dependent, which is a cache-stability risk
they absorb with a config-mtime fingerprint in their memo key. Given this item
exists to *stop* the array moving, importing a mechanism that moves it would be
precisely backwards.

### How the two Laws hold

**Law 1 — per-conversation prompt caching is sacred.** This item is what finally
makes it true for position 0. The learned core changes only at session boundaries,
which is where `D01.1` already sanctions change.

**Law 2 — the core is a narrow waist.** No new model-facing tool: `tool_search`
already exists and is already presented. No new table either (`I6`). What changes
is one argument to `rank_candidates` and where its value comes from — invisible to
the prompt and invisible to the schema.
