## Why this exists

StackOwl HAD exactly one session identifier and **it never changed**. `/reset` deleted the
transcript, but nothing ever started a new session. There was no boundary, so there was no moment
at which anything could be refreshed. (Past tense as of this item — see "What is built" below.)

That blocks more than one item. "Build the prompt once per session" (`D01.1`) is meaningless
without a session that begins. "New facts apply next conversation" (Bakir, Q7) never arrives if
there is no next conversation. "Archive yesterday's transcript and summarise it into memory"
(Q17) has no trigger. The background-review fork (`D09.1`) and the skill curator (`D09.3`) both
want an idle moment that we cannot currently detect.

One missing concept is holding up five items.

## Model

The central idea, borrowed directly from Hermes: **split identity in two.**

| | What it is | Format | Changes when |
|---|---|---|---|
| `session_key` | The conversation **lane** — deterministic, derived from where the message came from | `owl:{owl}:{channel}:{chat_type}[:{chat_id}][:{thread_id}][:{participant_id}]` | Never |
| `session_id` | This **incarnation** of the lane | `YYYYMMDD_HHMMSS_<8hex>` | Every reset |

A reset keeps the key and mints a new id. The key is how we find your conversation; the id is
which run of it you are in. Before this item StackOwl conflated them, which is exactly why it
could not reset.

**We prefix the key with the owl.** Hermes has one agent; we have owls, and switching owl mid-lane
means a different persona and therefore a different prompt. The owl belongs in the key.

### The rename — what the model cost to make true

The table above was aspirational when this document was written. StackOwl's existing `session_id`
**was the lane, not the incarnation**: `channels/telegram/adapter.py` minted it as `str(user_id)`,
`channels/base.py:81 resolve_target()` treated it as the delivery address, `gateway/turn_registry.py`
keyed turn concurrency on it, and `memory/sqlite_bridge.py` scoped conversation facts by it.

So adopting the model meant renaming the concept in place, not adding one beside it. Bakir chose
the full rename over the cheaper alternative (leave `session_id` as the routing identifier and call
the new concept `incarnation_id`) after being shown the measured cost:

| | |
|---|---|
| Occurrences | 1,715 in 173 `src/` files + 1,757 in 445 `tests/` files |
| Tables | 7 (`cost_records` 61,858 rows, `task_outcomes` 8,029, `retry_queue` 3,802, `turn_decisions`, `message_ledger`, `conversations`, `thread_registry`) |
| Not renamed | `parliament_sessions.session_id` (a debate id) and browser page sessions — the same word, three unrelated concepts |

`session_id` naming three different things is why this could not be a find-replace. The rename
excluded `src/stackowl/parliament/` and `src/stackowl/tools/browser/` wholesale, and five
mixed-domain files were done by hand. **mypy strict found the seam**: after the mechanical pass it
reported exactly four errors, every one of them at a parliament/lane boundary
(`ParliamentSession.session_key` did not exist; `PipelineState(session_id=…)` no longer did either).
Zero new errors remain against the 78-error pre-existing baseline (`DEBT-8`).

One consequence is permanent and worth stating: **historical rows keep bare chat ids as their lane
value.** A composite key (`owl:brain:telegram:dm:12345`) needs the owl and channel, and neither was
ever stored on those rows, so there is nothing to backfill from. Rows written before the cutover
identify a lane by chat id; rows after it identify it by composite key.

### SessionEntry

| Field | Type | Default | Meaning |
|---|---|---|---|
| `session_key` | `str` | — | The lane. Primary key. |
| `session_id` | `str` | — | Current incarnation. |
| `owl_name` | `str` | — | Which owl owns this lane. |
| `channel` | `str` | — | Originating channel, for delivery routing. |
| `created_at` | `datetime` | — | When this incarnation began. |
| `updated_at` | `datetime` | — | Last activity. Drives idle expiry. |
| `chat_id` | `str \| None` | `None` | The channel-NATIVE send target. Stored rather than derived: a composite lane key is not parseable into a chat id, and on Slack the lane never was one. `None` for channels with no per-lane destination (CLI). |
| `identity_key` | `str \| None` | `None` | Who this lane belongs to. Stamped at ingress, where the identity is already resolved. Required because the sweeper fires at 4 AM with no ingress context to re-derive it from, and because a summary filed under the owl-prefixed lane is a summary recall cannot see. |
| `message_count` | `int` | `0` | Inbound messages on this incarnation, incremented in `resolve_for`. Renamed from `turn_count`, which counted nothing (see below). Migration `0096`. |
| `completed_turns` | `int` | `0` | Turns that produced a reply, incremented at turn end beside the transcript write. Kept separate from `message_count` because the difference between them is a real health signal. |
| `parent_session_key` | `str \| None` | `None` | *(design — part 7)* For a runner lane, the conversation that caused it. Its summary is attributed to the parent, so background work gets its own frozen prompt without fragmenting the story of the conversation that asked for it. |

**`turn_count` counted nothing.** It was minted at 0, reset to 0 on rollover, persisted, read back, and published in the `session.rollover` payload — and no code path ever incremented it. Live proof: the only existing lane read `turn_count=0` while its transcript held 4 messages. Any consumer gating on it read a constant. It is renamed rather than repaired because the column is three days old, nothing outside `sessions/` reads it, and this item exists precisely because a name that lied about what it held cost a 571-file rename.

### State flags

Five booleans forming a state machine, evaluated on every inbound message.

| Flag | Set by | Effect on next access |
|---|---|---|
| `suspended` | `/stop`, or 3 consecutive restart failures on this lane | Hard wipe — force a new `session_id` |
| `resume_pending` | Unclean shutdown, or drain timeout mid-turn | **Preserve** the `session_id`; the transcript continues |
| `was_auto_reset` + `auto_reset_reason` | Policy expiry | Consumed **once** to show a visible notice: "new conversation — previous one ended (idle/daily)" |
| `is_fresh_reset` | Explicit `/new` | Kept distinct from `was_auto_reset` so an intentional reset never produces a misleading "expired" message |
| `expiry_finalized` | Background sweeper, after hooks ran | Prevents redundant finalisation across restarts |

## Lifecycle

```
 inbound message
        │
        ▼
 build session_key from (owl, channel, chat_type, chat_id, thread, participant)
        │
        ▼
 ┌──────────────────────┐
 │ key exists?          │── no ──► create fresh entry
 └──────────┬───────────┘
            │ yes
            ▼
 ┌──────────────────────┐
 │ 1. suspended?        │── yes ─► force reset, new session_id
 └──────────┬───────────┘
            ▼
 ┌──────────────────────┐
 │ 2. resume_pending?   │── yes ─► PRESERVE session_id, continue transcript
 └──────────┬───────────┘          (cleared after the next successful turn)
            ▼
 ┌──────────────────────┐
 │ 3. policy expired?   │── yes ─► auto-reset, reason = idle | daily
 └──────────┬───────────┘          run the rollover hook (see below)
            ▼
 ┌──────────────────────┐
 │ 4. return existing,  │
 │    bump updated_at   │
 └──────────────────────┘
```

**The priority order is behaviour, and it is the thing most likely to regress.** `suspended` beats
`resume_pending` beats policy, always. A hard wipe must never be overridden by a soft recovery.

### The rollover hook

When step 3 fires, before the new incarnation starts:

1. End the old `session_id` in the DB with reason `idle` or `daily`.
2. Archive the transcript — it stays queryable (see `D11.2`).
3. Emit `session.rollover` on the `EventBus`.

Step 3 is the seam. `D09.1` (background review) and `D09.3` (curator) subscribe to it rather than
inventing their own idle detection. Q17's "summary into memory" is a subscriber too. **Three items
converge here instead of building three schedulers** — this is dedup target X3, resolved by
architecture rather than by cleanup.

### What the boundary actually does with memory *(design — part 5)*

The obvious build here is wrong, and it was nearly built. StackOwl already has a dormant handler
(`memory/extraction_handler.py`) that reads a lane's `messages` rows, runs `FactExtractor`, and
stages the results — the Q17 summary, apparently already written and merely unwired. Wiring it up
looks like the highest rung on the ladder: extend existing code, and revive a dead feature while
you are there.

It is a duplicate. `memory/conversation_miner.py` **already does that job** — the same
`FactExtractor`, over the per-turn records `turn_persist` stages, with semantic dedup at 0.92
cosine, run by the `DreamWorker`, promoted into `committed_facts` where recall reads. It is not
theoretical: the live database holds **98,435 `conversation_fact` rows** against 8,093 raw
`conversation` rows. The dormant handler is a *third* path over the same content, differing only in
which table it reads. Wiring it to the rollover would have had one extractor mine one conversation
twice into one table.

So the boundary's job is narrower than "summarise the conversation":

1. **Trigger the miner.** It is idempotent, so the boundary simply gives it a good moment instead of
   waiting out its interval. It is triggered *unscoped* — `staged_facts` records the person
   (`source_ref`), not which incarnation a fact came from, so "mine the run that just ended" is not
   expressible today. Stated as a limitation rather than dressed up; stamping `session_id` onto
   `staged_facts` is the fix if it ever matters.
2. **Write one narrative artifact** — what was decided, what went wrong. This is the genuinely
   missing thing. The miner produces atomic facts *about the user* (Q14's first category, already
   covered) and no account of a conversation's decisions or failures. Standard tier, per Q19.
   Staged under `identity_key` with its own `source_type`, so the existing promoter commits it and
   recall finds it — no new retrieval path.

**Cost gate.** Every rolled lane that has transcript rows gets the call, and the model itself
decides whether anything was worth keeping. Q14's structural pre-gate is withdrawn: the signal it
would have gated on (`turn_count`) was dead, and non-chat runners write no transcript, so a silent
lane already costs nothing.

**A gate the design did not know about, found while building it.** Staging the summary is not
enough to make it recallable. The promoter requires **corroboration** — `reinforcement_count >= 3`
for most source types, `>= 1` for `conversation_fact` — which is the right rule for an *extracted*
claim, and the wrong one for an *authored* artifact. A summary is written once and never
re-derived, so its count stays 0 for ever: it would have sat in `staged_facts` permanently, written
and logged and never recalled, with no observable symptom because every intermediate step reports
success. `fact_promoter.AUTHORED_ONCE_SOURCE_TYPES` now exempts it from corroboration **but not
from the confidence gate**, and the eligibility predicate — previously two hand-copied duplicates
"kept in lock-step by review" — is one shared string with a test asserting the two agree.

**Delivery.** `session.rollover` → a scheduler job keyed `rollover:{lane}:{ended_incarnation}`, so
one boundary can never be summarised twice → a `DurableTask` row. The task row is a **checkpoint
record driven by the handler**, not a goal fed to the ReAct kernel; the kernel is an agent loop and
this is one call. That job-plus-task shape is heavier than a bare job and was chosen deliberately
(see *Related*).

## Invariants

> **I1.** `session_key` never changes for the life of a lane. Anything that would change it
> creates a different lane.
>
> **I2.** A reset always mints a new `session_id` and never reuses one. Ids are monotonic per lane.
>
> **I3.** Priority order is `suspended` → `resume_pending` → policy → existing. Exactly one branch
> executes per message.
>
> **I4.** A lane with a running background process, an in-flight durable task, or an active
> objective is **never** expired. Borrowed from Hermes, and it matters more for us because
> autonomy is a headline feature: an agent working overnight must not have its session cut.
>
> **I5.** An auto-reset is always visible. `was_auto_reset` produces a user-facing notice exactly
> once. A boundary the user cannot see is a boundary they will experience as amnesia.
>
> **I6.** No transcript is destroyed by a rollover. The old incarnation is ended and archived,
> never deleted. (`/reset` deleting history is a separate, explicit user action.)

**I6 was unfalsifiable when it was written, and finding that out is part of this item.** Reading
the live path for the ingress wiring turned up that the `conversations` and `messages` tables
(migration `0002`) have **no `INSERT` site anywhere in `src/`**. Both are empty in the live
database, against 61,858 `cost_records` and 109,380 `staged_facts`. There was no transcript for a
rollover to preserve or destroy.

Six subsystems read those tables and have therefore been operating on an empty result set:

| Reader | What it believes it is doing |
|---|---|
| `owls/evolution.py:92` | fetching excerpts to evolve owl DNA |
| `memory/extraction_handler.py:22` | extracting facts from a session's messages |
| `tools/knowledge/session_search.py:71` | searching past conversations |
| `tools/knowledge/transcripts.py:50` | reading a transcript back |
| `tools/knowledge/session_access.py:137` | resolving a session's owner, used for authz |
| `tools/scheduling/cron_helpers.py:20` | resolving the owl that owns a cron job |

The de-facto transcript is `staged_facts` (`source_type='conversation'`, `source_ref` = the lane).
Bakir's call was to fix it inside this item rather than book it as debt: the turn-end transcript
writer lands with the ingress wiring, keyed by lane **and** incarnation, which is what finally
makes I6 a testable statement instead of a wish.

## Configuration

```yaml
session:
  reset_mode: both          # none | idle | daily | both      (default: both)
  at_hour: 4                # int 0-23, LOCAL time            (default: 4)
  idle_minutes: 1440        # int, 24h                        (default: 1440)
  notify_on_reset: true     # bool — surface the boundary     (default: true)
  group_sessions_per_user: true    # isolate group chats per user
  thread_sessions_per_user: false  # threads shared by default
  max_age_days: 0           # prune entries older than N days; 0 = never
```

**On `at_hour` — resolved, signed off 2026-07-25.** Bakir chose midnight in Q16; Hermes defaults
to 4 AM on the reasoning that a session running at 1 AM is mid-thought and midnight guillotines it,
whereas at 4 AM nobody is talking. **Bakir accepted 4 AM**, superseding his earlier answer. It
ships configurable, so midnight stays reachable for anyone who wants it — the default is 4.

Per-channel overrides go under `channels.<name>.session`, matching Hermes' per-platform policy.

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| Core exec-replaces mid-turn | no clean-shutdown marker at boot | Lanes touched in the last 120s marked `resume_pending`; the transcript continues on next message | Nothing — conversation resumes |
| Same lane interrupted 3× | restart counter per lane | Lane force-`suspended`, clean slate | "Starting a fresh conversation — the previous one could not be recovered" |
| Rollover fires during an active job | `I4` check | Expiry skipped, retried next sweep | Nothing |
| Clock jump / timezone change | policy evaluation | Idle check uses monotonic elapsed where possible; daily uses local wall clock and tolerates a one-off double boundary | At most one extra reset notice |
| Rollover hook subscriber throws | hook wrapper | Logged at `error`; the rollover still completes | Nothing — the boundary is not blocked by a subscriber |

**Divergence worth stating:** Hermes' agent cache is in-memory (LRU 128, 1 h TTL) because their
gateway restarts rarely. **Our core exec-replaces itself on every code change**, so an in-memory
cache would be discarded constantly during development. Session entries are therefore **persisted**,
and the `SessionPrompt` that `D01.1` builds on top is persisted too. We already have drain +
durable recovery to build the resume path on.

### Where Hermes had no answer to port

Two of this slice's questions were taken to the teacher first. Neither had an answer, and the
reasons are worth recording, because "Hermes does not do this" is otherwise indistinguishable from
"we forgot to check".

**Identity scoping — they cannot have an answer.** `get_memory_dir()` returns
`get_hermes_home()/"memories"`; `MEMORY.md` and `USER.md` are single profile-global files loaded
into the system prompt (`tools/memory_tool.py:55`, `225-226`). Nothing is keyed by person or by
session. Hermes is a single-user agent, so "which person do these facts belong to" never arises.
The teacher default is rebutted **by absence** — this is one of the sixteen areas where StackOwl is
already ahead, and `identity_key` on the lane row is ours.

**Non-chat lanes — they have none.** `build_session_key` has exactly two branches, `dm` and
group/channel, and both require a chat platform (`gateway/session.py:1074-1134`). Delegated work
*inherits* the ambient key (`tools/delegate_tool.py:2976-3009` reads `get_current_session_key()`,
falling back to the durable `AIAgent.session_id`), background processes are session-scoped by that
same inherited key (`tools/process_registry.py:1777`), and cron is an external managed service that
fires a **delivery into a chat**, never a session of its own. Their model is: a session is a
conversation with a human, and everything else borrows the conversation that caused it.

**We diverge for autonomous work, and follow them for cron.** Objectives, delegated subagents,
durable recovery and the shadow validator get their own lanes, so background work earns its own
frozen prompt — the `D01.1` win, which their inheritance model forfeits. A `parent_session_key` link
keeps the summary attributed to the conversation that asked, so the divergence costs one column and
not the coherence of the story. Cron follows Hermes: it runs on the lane of the chat it delivers to,
falling back to a synthetic `owl:{owl}:cron:{job}` only when there is no single target. That is
deliberately **two rules where Q9 said one** — cron is a delivery, an objective is work — and it is
written down here so a later reader does not "fix" it into one.

### An accepted cost

The rollover enqueues a scheduler **job** *and* the job creates a `DurableTask`. Bakir was shown
that this is two queue mechanisms for one unit of work, that a `DurableTask` is an agent ReAct
kernel with checkpointing while a summary is one call that either happens or is retried whole, and
that it makes dedup target `X1` (two work queues) harder to resolve later. He reaffirmed it for the
crash semantics. Recorded so it reads as a decision with a known price rather than an oversight.

## What is built, and what is not

Built and live: the lane/incarnation split; the reset policy and its priority order; the store
with its derived write-only mirror; the `session_key` rename across the tree (migration `0093`);
the send target on the lane (`0094`); the incarnation on `TraceContext`, `PipelineState` and
`cost_records` (`0095`); ingress resolution; the visible boundary notice; the turn-end transcript
writer; `session.rollover` on the `EventBus`; `/new` (with the old in-flight verb moved to
`/queue`); and the `conversation_sweep` job that makes the boundary a clock event.

**Not yet built**, and deliberately named rather than implied. Items 1–4 are designed and approved
(2026-07-25, 24 questions) and are slice 3b parts 4–7, in this order:

1. ~~**Part 4 — the lane row tells the truth.**~~ **BUILT** (migration `0096`): `identity_key` stamped
   at ingress, `turn_count` → `message_count` (bumped in `resolve_for`), and `completed_turns`
   (bumped at turn end, and never for a floored turn — the gap between the two counters is the
   signal that a lane is failing to answer).
2. ~~**Part 5 — the boundary's memory work**~~ **BUILT** (`memory/rollover_summary_handler.py`,
   migration `0097`): the miner trigger and the narrative artifact, as designed above.
   `FactExtractionJobHandler` is deleted; `FactExtractor` stays. **End-to-end is unproven** — the
   only enabled provider's host stopped resolving on 2026-07-26 (`DEBT-10`), so the paid call is
   proven against a real database and not against the live gateway.
3. **Part 6 — two of the four never-expire conditions** (Q12). `conversation_sweep._is_busy`
   enforces a running background process and a pending clarify; an in-flight durable task and an
   active objective are not checked, because neither `tasks` nor `objectives` stores a
   `session_key`. Part 6 adds it and stamps it at creation.
4. **Part 7 — Q9, every runner gets a lane.** `resolve_for` has exactly one caller today
   (`startup/orchestrator.py:1924`, chat ingress), so cron jobs, delegated subagents and objectives
   have no lane at all and Q9 is unimplemented. Part 7 adds `parent_session_key` and routes them
   through it.

Beyond this slice:

5. **`resume_pending` recovery** — the flag, its policy branch and its persistence all exist and
   are tested, but nothing SETS it yet. The crash-recovery path from Q6 (synthesise a message
   event and auto-continue) is unbuilt, so today an interrupted turn is simply lost rather than
   resumed.
6. **Context-full as a trigger** — `ResetReason.CONTEXT_FULL` exists and `reset_notice` handles
   it; the compression side that would fire it belongs to `D03.2`.
