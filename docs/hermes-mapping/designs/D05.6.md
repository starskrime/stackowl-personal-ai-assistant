## Why this exists, measured

A description naming another tool — *"restores what `edit` changed"*, *"use
`transcripts` for past conversation content"* — is a useful routing hint **while
that tool is present**. When it isn't, the same sentence instructs the model to
call something it cannot see.

| | measured |
|---|---|
| schemas naming another tool | **40 of 77** |
| total references | 78 (42 cross-group) |
| …that **cannot** dangle (target in the base set, or same capability) | 47 |
| **…that genuinely can dangle** | **31**, across 22 referrers and 14 targets |

Targets that can vanish include `edit`, `git`, `process`, `delegate_task`,
`send_message`, `clarify`, `transcripts`, `session_search`.

The sharpest case: **`undo_write` is in the never-evicted base set**, so it is
always presented — and it advertises `edit`, which is *not* in the base set and is
evictable by the budget. On a narrow owl profile the model is told to rely on a
tool it has not been given.

### This item is a consequence of D05.3

Worth stating plainly. Before capability gating, every registered tool was
presented on every turn, so a cross-reference was **always** valid and this was a
latent wording issue. `D05.3` made tools genuinely disappear.

Of the four references to a capability-gated tool, all four are browser→browser
and therefore safe — and `browser_vision` → `browser_navigate` is safe *only*
because `D05.3` gated `browser_vision` after a test caught that `toolset_group`
is not a reliable proxy for a dependency. Left ungated, it would have been the
first real dangling reference this item exists to prevent.

## The design

```
select / fit  →  FINAL presented set
        │
        ▼   _emit()  ← new single exit, shared by all three paths
        │
        ├─ for each tool: strip sentences naming an ABSENT tool
        │     • only names in the CATALOG count (not English words)
        │     • same-capability targets are EXEMPT (they vanish together)
        │     • the FIRST sentence is never dropped
        ▼
   schemas  →  D05.2 memo stores the ALREADY-STRIPPED array
```

**Placement is load-bearing.** Stripping happens inside `to_provider_schema`,
before the memo caches the result, so descriptions stay byte-stable for the
session rather than varying per turn. A capability flip already invalidates that
memo (`D05.3`), so a returning tool gets its hints back with **no new
invalidation path**.

`to_provider_schema` previously had three separate `return [_schema_for(t) …]`
exits. They now share one `_emit()`, because the strip needs the final presented
set — which is not known until the list is complete.

### Two exemptions, both necessary

1. **Only registered names count.** `memory`, `process`, `wait`, `git` and `edit`
   are all real tool names *and* ordinary English words. Matching prose would
   strip sentences that were never references.
2. **Same-capability targets are exempt.** If `browser` is down, `browser_click`
   and `browser_snapshot` are *both* absent, so the hint can never dangle.
   Stripping it would remove useful in-toolset guidance for no safety gain.

### The flaw a test found

Sentence-level removal was chosen with its bluntness accepted — `read_logs`'
ANTI-LANE sentence also carries a still-valid *"durable facts (use memory)"* hint,
and that half goes with it.

**The test found a worse case the decision hadn't anticipated.** `undo_write`
opens:

> *"Undo the most recent file write/**edit** by restoring the file's pre-image."*

`\bedit\b` matches inside `write/edit`, so the blunt rule deleted the tool's own
**definition**, leaving a schema that described only its `token` argument and
never said what the tool does.

**Rule added: the first sentence is never dropped.** It states what the tool *is*;
later sentences elaborate or route. The trade is explicit — a first sentence
mentioning an absent tool in passing keeps that word, which is prose rather than
an instruction to call it, and far less harmful than a tool whose schema no longer
says what it does.

## Invariants

> **I1.** A presented schema never names a tool that is absent from the same
> presented set — except in its first sentence (`I3`) or under an exemption.
>
> **I2.** A description is never emptied. If every sentence referenced an absent
> tool, the original is returned: the description is what `tool_search` ranks on
> and what the model chooses by, so an empty one breaks the tool far more
> thoroughly than a stale hint.
>
> **I3.** The first sentence is never dropped. Losing a routing hint is the
> accepted cost of sentence-level stripping; losing the definition is not.
>
> **I4.** Descriptions stay session-stable. The strip runs before `D05.2`'s memo
> stores the array, never per turn.
>
> **I5.** A strip failure never costs a turn its tools. The call is wrapped; any
> exception falls back to the raw description.

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| Sentence splitter mis-splits (`e.g.`, decimals) | — | Conservative regex: it under-splits, so a bit more prose is stripped, never a reference left behind | A slightly shorter description |
| A useful hint is lost with its sentence | — | **Accepted** — the stated cost of this approach | `read_logs` loses its "use memory" half |
| Every sentence references an absent tool | `I2` | Original returned, warning logged | Nothing |
| The stripper raises | `I5` | Raw description used, error logged | Nothing |
| A new tool name is also a common English word | **Not detected** | Only catalog names match, so it would strip real prose containing that word | Over-stripped description |

The last row is this design's standing liability: `edit`, `process`, `wait`,
`memory` and `git` are already both. The catalog check bounds the damage to
*registered* names, but a future tool called `list` or `run` would strip a lot of
innocent prose.

### Prior art, and where we deliberately diverge

`AGENTS.md` states a hard rule: a schema description *"must not mention tools from
other toolsets by name… causing the model to hallucinate calls to non-existent
tools"*, and says cross-references are added dynamically in
`get_tool_definitions()`.

**The rule is much stronger than the mechanism.** The actual enforcement is one
hardcoded string-replace, for one tool:

```python
desc.replace(" For simple information retrieval, prefer web_search or "
             "web_extract (faster, cheaper).", "")
```

plus a single test on `x_search`. It breaks the moment anyone rewords that
sentence.

**Adopted:** the rule, and the reasoning behind it — which is correct and well
argued in their own docs.

**Diverged:** the mechanism is generic and driven by the presented set rather than
per-tool string surgery. We can afford that because `to_provider_schema` already
computes the presented set; they strip in a place that does not know it as
precisely. We also add two exemptions their approach has no way to express
(catalog-only matching, and same-capability targets).

**Not adopted: a registration-time lint.** It was considered — StackOwl already
has a `_lint_description` seam that warns on thin descriptions — and rejected as a
*replacement*: registration cannot know what will be presented, so it would flag
all 31 references forever, including the ones that are correct whenever their
target is present.

### How the two Laws hold

**Law 1 — per-conversation prompt caching is sacred.** The strip runs once per
session, inside the memo build. A description changes only when the presented set
changes, which is already an invalidation point.

**Law 2 — the core is a narrow waist.** Nothing added to the model's tool surface.
This makes the existing surface honest rather than larger.
