# Bookends — the Frame Around a Hit From the Middle

**Item.** D11.3 · Session-search shapes — `PARITY`
**Last verified.** 2026-09-04, commit `HEAD`

## Why this exists

The Ask is a build instruction, not a question: *"Adopt bookends — cheap and clearly
useful."* The reference platform attaches the first and last three messages of a session to
a search result.

**Measured before building it**, across all nine daily logs (2026-08-28 → 2026-09-04):

| mode | invocations |
|---|---|
| `discover` | 16 |
| `browse` | 2 |
| `scroll` | **0** |

Control for that count: 1,765 `skill_view` mentions in the same files, so the instrument
reads. **The live log alone would have said zero** — it rotates daily and was 46 minutes old
when this was measured, and the control was zero in it too. A zero whose control is also
zero measures the instrument, not the system.

**A correction to the entry's implied shape.** `browse` does not list sessions. All three
modes are scoped to one session (`WHERE c.session_key = ?`); browse pages through a single
session's messages with LIMIT/OFFSET. So bookends are not a session picker. They are the
frame for a `discover` hit — five matches from the middle of a two-hundred-turn session,
with nothing to say what the session was about or whether it ever resolved.

That is also why they go on `discover` and not elsewhere: it is 16 of the 18 recorded uses,
and it is the only mode whose output is inherently un-anchored.

## Model

| Constant | Meaning | Value |
|---|---|---|
| `_BOOKEND_TURNS` | Turns of frame at each end | `3` |
| `_HEAD_SQL` | First turns, ascending, LIMIT-bounded | — |
| `_TAIL_SQL` | Last turns, descending, LIMIT-bounded | — |

Three is small on purpose: this is context for a hit, not a second result set, and every
turn added is tokens spent on a question the caller did not ask.

**`_HEAD_SQL` is bounded rather than reusing `_ORDERED_SQL`**, which has no `LIMIT` because
`scroll` needs the whole index to locate an anchor. A bookend must never be able to read a
session's entire history.

## Lifecycle

1. `discover` runs its FTS (or LIKE fallback) and renders the matches.
2. **Only if there were matches**, fetch `2N+1` head rows.
3. `2N` or fewer → the caller can already see the whole session; emit no frame.
4. Otherwise render `head[:N]` as *session opens* and the reversed tail as *session closes*.

Step 2's `2N+1` answers "is there a middle?" without a `COUNT`. Step 3 exists because a
short session would otherwise be printed twice — and on a two-turn session that reads as
four turns.

Bookends **decorate a result; they never manufacture one**. No matches, no frame.

## Invariants

- A bookend is redacted exactly like any other turn.
- A bookend is labelled, never mixed into the match list.
- No matches → no frame.
- A session with no middle → no frame.
- A bookend failure never costs the caller the matches.

## Configuration

None. Ships ON — the Ask calls it cheap and clearly useful, and a context feature nobody
enables is decoration.

## Observability

- `session_search.execute: exit` — INFO, fields `success`, `turns`, `duration_ms`. `turns`
  counts **matches**, not bookends: it is the answer to "how much did you find", and
  inflating it with frame would make the tool overstate itself.
- `session_search: bookends failed — returning matches unframed` — WARNING.

```bash
# Which modes are actually used? (the live log rotates daily — read them all)
grep -h 'session_search.execute: entry' ~/.stackowl/logs/stackowl*.jsonl \
  | python3 -c 'import sys,json,collections; print(collections.Counter(
      json.loads(l)["fields"].get("mode") for l in sys.stdin))'
```

## Failure modes

| Failure | What happens | What notices |
|---|---|---|
| Bookend query fails | Matches returned unframed | The WARNING |
| Session shorter than 2N | No frame | `test_a_short_session_is_not_printed_twice` |
| Frame bypasses `_render` | **A secret leaks** | `test_the_frame_is_redacted_like_every_other_turn` (mutation-proven) |
| Frame unlabelled | Reads as extra matches | `test_the_frame_is_labelled_not_mixed_into_the_matches` |

**The redaction row is the one that matters.** `_render` applies `redact_secrets` to every
turn. A bookend reaching the output by any other path would leak from the two turns *most*
likely to carry a credential — where a task is set up, and where it is signed off. Rendering
through `_render` is the design, not a convenience.

## Verification

```bash
# 1. Both directions, the short-session case, the no-match control, and redaction.
uv run pytest tests/tools/knowledge/test_a_match_from_the_middle_gets_its_frame.py -q
#    expect: 5 passed

# 2. The tool's existing contract is unchanged.
uv run pytest tests/tools/knowledge -q
#    expect: 205 passed
```

Both RUN on 2026-09-04, not trusted. Mutation-proven twice: disabling the call kills three
tests, and replacing `_render` with a hand-rolled formatter leaks the key and kills the
redaction test.

**OPEN — no bookend has been emitted in production.** It fires on the next `discover` with a
hit, which needs real traffic. Closing query:

```bash
grep -c 'session opens' ~/.stackowl/logs/stackowl*.jsonl
```

Note that the tool logs its exit, not its output, so this closes on the *tool result* rather
than the log — the honest closing check is a `discover` run against a long session.
