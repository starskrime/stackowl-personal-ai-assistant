# Execution backends — what confines code here, and what actually limits it

> **Status:** live (local); remote/cloud backends not built — see Decision
> **Map item:** D06.1
> **Source:** `src/stackowl/sandbox/` (21 modules + `ptc/`), `tools/code/execute_code.py`,
> `tools/system/shell.py`
> **Config:** `sandbox.bwrap_enabled`, `sandbox.docker_enabled` in `stackowl.yaml`
> **Last verified:** 2026-09-05, against commit `<pending>`

## Why this exists

The map's gap reads *"No remote/cloud execution. The ABC exists — the implementations do
not."* **The second sentence is misleading and worth correcting before anyone plans work
from it.** Two implementations exist, are wired, and are exercised: `BwrapSandbox` and
`DockerSandbox` behind `SandboxBackend`, selected by `SandboxSelector` (bwrap-primary,
Docker when the code needs network), with a capability probe that runs on every boot.
Both binaries are installed on this host. What is genuinely absent is *remote* — SSH,
Modal, Daytona — which the reference platform has and StackOwl does not.

**The Ask is "does runs-anywhere matter, or is the Jetson + local the target?" and the
measurement answers a sharper question first: adding backends would not change how much
code runs here, because the backend is not the binding constraint.**

## Model — two execution paths, deliberately different

| | `execute_code` | `shell` |
|---|---|---|
| confinement | bwrap or Docker, 6 invariants | **none — host subprocess by design** |
| consent | always-ask (recorded operator decision) | catastrophic shapes only |
| live calls | **1** | **205** |
| interpreter launches | n/a | **33 detected, logged, NOT gated** |

The asymmetry is deliberate at every step and is documented where it lives.
`sandbox/base.py`'s invariant 1 states it outright — *"Never execute un-isolated on the
host. If isolation cannot be established, refuse — never degrade to a bare subprocess
(that is what `shell` already is)."* `shell`'s own docstring declares the
maximum-autonomy model. Neither is an oversight.

## What the numbers say about the Ask

**The confined path is gated shut whenever it matters most.** Measured across every
retained log: `execute_code` consent decisions are **27 deny, 1 allow**. All 27 refusals
are on the `rca` lane with the same reason — *"always-ask and no human is attached"*. The
single allow came through Telegram, where a human approved it, and it then ran
successfully on bwrap (`exit_reason: ok`). **So the sandbox works. It is almost never
reached.**

**And the ungated path is where code actually runs.** This was measured and root-caused on
2026-09-01: the gate was keyed on a tool NAME while the risk belongs to a CAPABILITY, and
`shell` invoked an interpreter 110 times out of 153 (72%) unattended. `CODE_EXECUTION` +
`launches_an_interpreter` were added as the one source for "does this call execute code",
so a third interpreter-running tool cannot silently miss the rule. `shell.py:653` now
detects and logs it — 33 occurrences, 7 of them today — and the line says plainly that it
is **"not gated as code_execution"**. It is a marker, not a control, the same shape and
the same honest wording as D12.8's untrusted-content fence.

**So a remote backend would add a sixth place to run code that the consent policy already
refuses to run unattended, while the path that does run code unattended is not confined at
all.** Backends are not the constraint.

## What a remote backend would have to satisfy

Recorded so the work is cheap whenever it is wanted. `SandboxBackend` is a keystone
contract, not a thin interface — a remote implementation must uphold all six invariants,
and three are materially harder off-host: **caps-or-refuse** (enforce every cap in
`spec.caps` or refuse; no uncapped run), **env allowlist-from-empty** (the child inherits
only `spec.env_allow`, so credentials must not cross the boundary to reach the remote),
and **never raise from `run()`** (network failure becomes a structured `ExecResult`, not
an exception). `ptc/` — the confined tool-callback channel — additionally assumes a local
socket, so a remote backend either forgoes PTC or tunnels it.

## Decision

**Not built, and not filed as debt.** The Ask is product intent and is escalated as
ESC-150 rather than defaulted here. Building SSH/Modal/Daytona backends now would be
scaffolding for a capability that today's policy declines to use unattended — the dead
seat the standing rule forbids. **The trigger to reopen is an answer to ESC-150**, or the
consent posture changing so that confined execution can be granted without a human.

## Failure modes

**A zero here is a policy outcome, not a broken sandbox.** `execute_code`'s single call
proves the local path works end to end. Reading its low usage as "the sandbox is broken"
would be exactly wrong, and the 27 denials name their own reason.

**The confinement investment is aimed at 0.5% of code execution.** That is the honest
ratio (1 confined call against 205 shell calls, 33 of which launched an interpreter). It
is not a defect — it is the cost of the maximum-autonomy model — but it is the number that
should inform any further spend on backends.
