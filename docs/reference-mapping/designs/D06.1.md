## Why this exists

The map's gap reads *"No remote/cloud execution. The ABC exists — the implementations do
not."* **The second sentence is misleading and worth correcting before anyone plans work
from it.** Two implementations exist, are wired, and are exercised: `BwrapSandbox` and
`DockerSandbox` behind `SandboxBackend`, selected by `SandboxSelector` (bwrap-primary,
Docker when the code needs network), with a capability probe that runs on every boot.
Both binaries are installed on this host. What is genuinely absent is *remote* — SSH,
Modal, Daytona — which the reference platform has and StackOwl does not.

**The Ask is "does runs-anywhere matter, or is the Jetson + local the target?" and the
measurement answers a sharper question first: adding backends would not change how much
code runs here, because the backend is not the binding constraint.**

## Model — two execution paths, deliberately different

| | `execute_code` | `shell` |
|---|---|---|
| confinement | bwrap or Docker, 6 invariants | **none — host subprocess by design** |
| consent | always-ask → **unattended-grant carve-out since 2026-09-05** | catastrophic shapes only — destruction by PATH, and since 2026-09-10 removal by PACKAGE |
| live calls | **1** (was 1) | **628** (was 544, was 205) |
| interpreter launches | n/a | **87 detected, logged, NOT gated** (was 45, was 33) |
| sandbox assemblies | **1,094**, of which **1** ever ran | n/a |

*Re-measured 2026-09-10 across every retained log. The confined side has STILL not moved
— 1 call, in the whole record — while the unconfined side has doubled again. Every
conclusion below gets stronger, not weaker, which is the only reason a re-measurement is
worth writing down.*

**And the second gated class, added 2026-09-10.** `is_catastrophic` asked only about
destruction that names a PATH, so `apt purge -y systemd`, `pip uninstall -y stackowl` and
`systemctl disable --now stackowl` all ran silently — the package manager resolves the
file list itself, so there was no path for the predicate to read. That is a different
question from this document's subject (code execution) and it does not move any number
here; it is recorded in the row above because a reader comparing the two columns is
entitled to know what "catastrophic shapes" now means. See DEBT-287.

The asymmetry is deliberate at every step and is documented where it lives.
`sandbox/base.py`'s invariant 1 states it outright — *"Never execute un-isolated on the
host. If isolation cannot be established, refuse — never degrade to a bare subprocess
(that is what `shell` already is)."* `shell`'s own docstring declares the
maximum-autonomy model. Neither is an oversight.

## What the numbers say about the Ask

**The confined path is gated shut whenever it matters most.** Measured across every
retained log: `execute_code` consent decisions are **27 deny, 1 allow**. All 27 refusals
are on the `rca` lane with the same reason — *"always-ask and no human is attached"*. The
single allow came through Telegram, where a human approved it, and it then ran
successfully on bwrap (`exit_reason: ok`). **So the sandbox works. It is almost never
reached.**

**And the ungated path is where code actually runs.** This was measured and root-caused on
2026-09-01: the gate was keyed on a tool NAME while the risk belongs to a CAPABILITY, and
`shell` invoked an interpreter 110 times out of 153 (72%) unattended. `CODE_EXECUTION` +
`launches_an_interpreter` were added as the one source for "does this call execute code",
so a third interpreter-running tool cannot silently miss the rule. `shell.py:653` now
detects and logs it — 33 occurrences, 7 of them today — and the line says plainly that it
is **"not gated as code_execution"**. It is a marker, not a control, the same shape and
the same honest wording as D12.8's untrusted-content fence.

**So a remote backend would add a sixth place to run code that the consent policy already
refuses to run unattended, while the path that does run code unattended is not confined at
all.** Backends are not the constraint.

## What a remote backend would have to satisfy

Recorded so the work is cheap whenever it is wanted. `SandboxBackend` is a keystone
contract, not a thin interface — a remote implementation must uphold all six invariants,
and three are materially harder off-host: **caps-or-refuse** (enforce every cap in
`spec.caps` or refuse; no uncapped run), **env allowlist-from-empty** (the child inherits
only `spec.env_allow`, so credentials must not cross the boundary to reach the remote),
and **never raise from `run()`** (network failure becomes a structured `ExecResult`, not
an exception). `ptc/` — the confined tool-callback channel — additionally assumes a local
socket, so a remote backend either forgoes PTC or tunnels it.

## Decision — reopened 2026-09-07 because both of its own triggers fired, and re-argued

This section used to read: *"The trigger to reopen is an answer to ESC-150, or the consent
posture changing so that confined execution can be granted without a human."*

**Both fired on 2026-09-05, and this page went two days without knowing.** Bakir answered
ESC-150 — *grant confined runs unattended, and notify each time* — and `caa01d3d` shipped
it: `runs_confined()` keys on the CONTRACT a tool holds, not on its consent category, so
`execute_code` is exempt while `claude_code` (same category, HOST executor, by its own
docstring) is not. The live validate went into `progress.yml` under a D06.1-named key and
never reached the document, which is the fifth-surface failure with the item's own name on
the commit that caused it.

**So the question is genuinely reopened, and the answer is still no — on stronger
evidence than before.** Reopening a decision means re-arguing it, not restating it:

| what the old Decision rested on | today |
|---|---|
| the policy declines confined runs unattended | **it no longer does** — that premise is gone |
| confined runs: 1 | **1** — the carve-out is live and has not yet been exercised |
| `execute_code` consent: 27 deny / 1 allow | **27 / 1, unchanged** — no grant since the carve-out |
| unconfined interpreter launches: 33 | **45** |
| sandbox assemblies | **950**, one of which ran |

The premise that carried the old argument is gone; a different one carries the same
conclusion. A remote backend would add a sixth place to run code on a path that has
executed code **once, ever**, while the path that executes it routinely is unconfined by
design and now does so 45 detected times. **Backends were never the constraint, and
removing the consent constraint did not make them one** — which is exactly the prediction
this document made, now tested rather than asserted.

**The new reopen trigger is a firing, not an answer.** The carve-out is live and
unexercised: the moment `execute_code` is granted unattended and RUNS, confined execution
stops being a 1-in-950 path and the ratio below has to be re-taken. Until then this stays
not built and not filed as debt.

**And the notification half was briefly dead, which is measured rather than assumed.** The
boot audit reported `DANGLING event subscription 'consent.confined_execution_granted' —
subscribed but NO module declares it as a publisher` **ten times**, 2026-09-05T23:22Z
through 2026-09-06T01:50Z: the publisher existed, the declaration a hundred lines away did
not. It was fixed by lifting `declared_event_publishers()` out of a function body where no
test could reach it, and the two most recent boots (2026-09-07T14:10Z and 18:37Z) both
report **0 dangling over 38 handlers** — a real denominator, not a silent zero.

## Failure modes

**A zero here is a policy outcome, not a broken sandbox.** `execute_code`'s single call
proves the local path works end to end. Reading its low usage as "the sandbox is broken"
would be exactly wrong, and the 27 denials name their own reason.

**The confinement investment is aimed at ~2% of code execution — and the 0.5% this
section used to state was the wrong denominator, not a stale one.**

The old sentence read *"0.5% of code execution … (1 confined call against 205 shell
calls, 33 of which launched an interpreter)"*. 1/205 is indeed 0.5%, but **205 is SHELL
CALLS, not code executions** — the same sentence says only 33 of them launched an
interpreter. The share of *code execution* that was confined was 1 of 34, **2.9%**: six
times what the headline claimed. The number was computed against the population that was
easy to count rather than the one the sentence named, which is this programme's most
expensive habit turned on its own summary line.

Re-measured 2026-09-07, with both denominators stated so neither can be mistaken for the
other:

| denominator | value | confined share |
|---|---|---|
| **code executions** (1 confined + 87 interpreter launches) | 88 | **1.1%** |
| shell calls (the old, wrong denominator) | 628 | 0.16% |
| sandbox assemblies (built, then unused) | 1,094 | 0.09% |

*Re-measured 2026-09-10. The confined share HALVED without anything being confined less —
the numerator has been 1 since this document was written and every denominator grows. A
share whose numerator never moves is a statement about the denominator, and quoting its
trend as a change in confinement would be the same denominator error this section exists
to record.*

Every one of these is small and the conclusion is unchanged — it is not a defect, it is
the cost of the maximum-autonomy model. But **which** small number it is matters to
anyone judging further spend, and the corrected one is an order of magnitude off the
number that was on this page. The same figure was repeated in `D06.3` and in
`progress.yml`; both are corrected in the same change, because fixing one copy of a
number is not fixing the number.
