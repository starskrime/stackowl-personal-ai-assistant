# The Session Store, and a Column That Was Recorded One Table Over

**Item.** D11.1 · Session store — `PARITY`
**Last verified.** 2026-09-04, commit `68ad3615`

## Why this exists

D11.1 asks nothing — it is a parity claim to verify. The reference platform's session store
is named as `SessionDB`, SQLite **WAL**, source tagging per session, and model config
recorded per session. Three properties, each measurable.

| property | verdict | evidence |
|---|---|---|
| WAL | **parity** | `PRAGMA journal_mode=WAL` in the pool, and `wal` in the live file header |
| source tagging per session | **parity** | `sessions.channel` — telegram 107, cli 13, rca 3 |
| model config per session | **ahead** | `cost_records`, 130,420 rows, `model` 100% populated, per CALL |

We also set `foreign_keys=ON` and `busy_timeout=15000` — the latter raised from 5000 after a
measured writer-contention burst where a confirmed-live liveness heartbeat failed both
attempts.

**The map said 90 migrations. There are 135.** Corrected.

## The measurement I got backwards first

`messages` has a `model` column. It is populated in **0 of 3,841 rows**. Read alone, that
says we are *behind* on the third property: a column nobody fills.

That was the wrong table. `cost_records` holds **130,420 rows with `model` populated in
every one**, alongside provider, input/output tokens, cost, TTFT and prompt hash, and
carries `trace_id`, `conversation_id`, `session_key` and `owl_name` to join back to the
turn. The model that served every call is recorded, richly, and more finely than the
reference's per-session config.

This is the same mistake this programme already paid for once: `committed_facts` was empty,
"the archive has no writer" was reported, and 361 real memories were sitting in
`staged_facts` one table over. **An empty table is a question, not an answer** — and the
question is *where did the writes go*, not *is the feature missing*.

**Two per-connection pragmas nearly went into this document as facts, too.** A first pass
read `busy_timeout` and `foreign_keys` off a fresh read-only Python connection and got
`5000` and `0` — Python's defaults, not the platform's. Only `journal_mode` is persistent in
the file header. For per-connection settings the pool source is the authority; a connection
I opened measures me.

## The defect

`messages.model` is the losing half of **two copies of one rule** (`CLAUDE.md` shape 3), and
it is dead on every axis measured:

| axis | measurement |
|---|---|
| rows populated | 0 of 3,841 |
| readers | **0** — every SELECT over `messages` names `id, role, content, created_at` |
| writers | 1 INSERT, handed `None` by its only caller |
| test fixtures | 9 of 10 already omitted the column; the 10th passed a literal `NULL` |

**It could not have been filled from the path that writes it.** `PipelineState` carries no
field naming the model that answered — only `model_window`. The caller had nothing to pass.

**And filling it would have been lossy.** 130,420 model calls against 3,841 recorded
messages is roughly 34 calls per message. A single `model` string on a message cannot
represent that without a rule for which of the 34 counts, and a summary that can disagree
with the ledger is worse than no summary.

**What made it possible?** A column added for a fact that a purpose-built ledger already
owned, and no reader to notice the difference. Migration 0110 removed a column for the same
reason and states the rule in one sentence: *"Two writers to one fact is how fields
drift."* That drop removed a column populated in 169 of 170 rows. This one removes a column
populated in none, so it deletes no information at all.

## Lifecycle

Migration `0136_drop_the_unfilled_message_model.sql` — `ALTER TABLE messages DROP COLUMN
model`. The `model` parameter is removed from `TranscriptStore.record_turn` in the same
change, along with the column in its INSERT and the two test fixtures that named it.
Retiring means the code, the parameter, the tests and the schema, together.

## Configuration

None. A migration runs on every boot through the same idempotent runner as the other 135.

## Observability

- `transcript.record_turn: exit` — INFO, fields `session_key`, `conversation_id`,
  `rows_written`. Unchanged.

```bash
# Which model served a given turn — the surviving, populated home for the fact.
sqlite3 ~/.stackowl/workspace/stackowl.db \
  "SELECT model, COUNT(*) FROM cost_records WHERE conversation_id = ? GROUP BY 1;"
```

## Failure modes

| Failure | What happens | What notices |
|---|---|---|
| A fixture still names `model` | `table messages has no column named model` | The package run — it caught 11 at once |
| The migration silently no-ops | Column survives | `test_messages_no_longer_carries_a_model_column` (mutation-proven) |
| The drop takes the only copy | — | `test_the_fact_still_has_exactly_one_home` |
