## Why this exists

The reference platform integrates Modal and Daytona: persistent sandboxes that hibernate
when idle and wake on demand. Its marketing claim — *"costs nearly nothing between
sessions"* — **is** the feature. The map records StackOwl as having none of it, and asks
whether that matters to this deployment story.

**It does not, and three independent pieces of evidence say so.** None of them is a
preference, so this was answered rather than escalated: handing back a question the
operator's own recorded rules already settle is the cost the escalation queue exists to
avoid.

## The architectural answer: there is nothing to hibernate

Hibernation is a solution to a problem created by PERSISTENCE. A sandbox that survives
between sessions holds state, occupies a machine, and bills for it — so you pay to make it
sleep. **StackOwl's sandboxes do not survive at all.**

`docker_argv.py` builds `docker run --name <container>` per call, and the comment there
records why there is deliberately no `--rm`:

> "Removal is instead guaranteed by the backend's `docker rm -f` in a `finally` — so the
> container survives just long enough to be inspected, then is always reaped. **No
> container is ever left behind.**"

So a sandbox exists for the duration of one `execute_code` call. There is no idle
sandbox, and therefore no idle cost to eliminate. The reference platform's feature answers
a question this architecture never asks.

## The economic answer: the idle cost is electricity, not billing

"Costs nearly nothing between sessions" is a claim about per-second cloud billing. This
platform runs on one always-on Jetson. Between sessions it costs the same as it costs
during them, and hibernating a sandbox that does not exist would save nothing measurable.

## The policy answer: both integrations are commercial SaaS

Modal and Daytona are hosted services. Two standing rules already govern this, and the
programme's own record cites them in those words — *"no vendor names in shipped code"* and
*"self-hosted/open-source only"*. Adopting either would put a vendor name in `src/` and a
third party in the execution path, which is the shape both rules exist to refuse.

## What already covers the real version of this need

**Leaked artifacts are reaped, and it runs.** `sandbox_sweep` (`scheduler/assembly.py`,
every 10 minutes, **executions in the retained logs in the low thousands and rising** —
1,225 on 2026-09-05, 1,470 on 2026-09-08; a SHAPE, not a pinned count, because a cadence
that keeps running falsifies any number written here as a side effect of working) removes
scratch dirs under
`~/.stackowl/sandbox/`, `stackowl-sbx-*` containers and bwrap cgroup scopes older than
`SANDBOX_ARTIFACT_TTL_S` (1h, ~120× the 30s max wall time so a live run is never reaped).
That is the genuine local analogue: not "hibernate the idle thing", but "nothing idle
should exist, and anything a crash left behind is collected".

## Failure modes

**Hibernating the PLATFORM is a different feature, and it is incompatible with this one's
design.** If the idea is read as "suspend StackOwl itself when nobody is talking to it",
that breaks the thing the platform is: an always-on loop. The scheduler dispatches
`health_sweep` every 5 minutes and `sandbox_sweep` every 10, proactive delivery and the
durable task loop run unattended, and a suspended platform delivers none of it. That is
not a gap to close — it is a property to protect.

**The trigger to revisit.** If StackOwl is ever deployed to per-second-billed infrastructure
where the *whole process* idles between conversations, the economics change and this should
be re-asked. Nothing in the current deployment story points that way, and D06.1 already
recorded that remote execution is not the binding constraint here.

```bash
# per-call lifecycle: no container survives a call
grep -n "docker rm -f\|No container is ever left behind" src/stackowl/sandbox/docker_argv.py

# the local analogue, and that it actually runs
grep -c '"msg": "\[scheduler\] sandbox_sweep.execute: exit"' ~/.stackowl/logs/stackowl*.jsonl  # 1225

# no vendor integration was added — as an IMPORT or a DEPENDENCY, not a substring.
# A naive `grep -rin "modal|daytona"` returns 17 and every one is a FALSE POSITIVE:

grep -inE "\bmodal\b|daytona" pyproject.toml | wc -l                            # 0
```
