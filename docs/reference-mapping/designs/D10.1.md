# The Skill Format, and the Directory That Was Never Looked At

**Item.** D10.1 · Skill format — `PARITY`
**Last verified.** 2026-09-04, commit `3790aa09`

## Why this exists

The map recorded D10.1 as parity: both platforms use a single `SKILL.md` with YAML
frontmatter, compatible with the wider agent-skills convention. That much held. What did
not hold was the half of "format" that nobody writes down — **where the file has to be**.

Measured 2026-09-04: **40 `SKILL.md` files on disk, 39 registered on the last boot.** The
fortieth, `~/.stackowl/skills/trending-research-owl/`, had been there since 2026-06-27 —
**69 days** — and had produced **zero** log lines in that time. Not a rejection, not a
warning. Silence.

It was not rejected because it was never a candidate. `load_all` scans by joining each
known source onto the root:

```python
for source in _VALID_SOURCES:          # builtin, installed, user, learned
    source_dir = skills_root / source
```

That iterates the set of directories the loader **expects**. An iteration over the expected
set can never notice an unexpected member. The `skill invalid — skipping` warning, marked
in the source as *"B5 — never silent"*, is real and correct — and it only ever covered
files the loader **found**. A skill it never looks at cannot fail loudly.

**What else does that same cause reach?** Any enumeration of an allow-list over a
filesystem, and more generally the same family as this programme's grep rule: *a zero
proves the pattern did not match, not that the thing is absent.* You only ever see what
you enumerate. The fix is to walk the other direction — from what is actually on disk —
and report the difference.

**What put the file there is NOT established.** `migrate_legacy_skills` (`paths.py:449`)
relocates `legacy.iterdir()` wholesale when the skills root moved out of the
model-writable workspace, which would preserve a flat top-level directory exactly like
this one. That is a plausible origin and a live shape, but it is **not evidence for this
file**: the legacy tree is gone and the log carrying that migration has rotated. Recorded
as unproven rather than asserted. It does not change the fix, because the fix targets the
silence, which is the durable cause whatever wrote the directory.

## Model

| Field | Meaning | Default |
|---|---|---|
| `_VALID_SOURCES` | Source dirs scanned under the skills root | `get_args(SkillSource)` |
| `_SKILL_MD_FILENAME` | The one required file in a skill dir | `SKILL.md` |
| `_MAX_SKILL_DEPTH` | `<source>/<name>/` or `<source>/<category>/<name>/` | `2` |
| `_OWL_TRUSTED_SOURCES` | Sources whose `owls.yaml` is honoured | `{builtin, user}` |

`_VALID_SOURCES` was a literal tuple restating the manifest's `SkillSource` Literal —
**two copies of one rule**. They agreed, which is why this was a cheap dedup and not a
defect; had they diverged, a source in the loader only would fail every skill under it at
validation, and a source in the manifest only would make those skills unreachable with no
error at all. It is now derived with `get_args`.

## Lifecycle

1. Seed builtins (idempotent copy into `builtin/`).
2. **Report strays** — skill-shaped dirs under the root that are in no source dir.
3. Scan each source dir, load each skill, warn-and-skip on an invalid one.

Step 2 **reports**; it does not adopt. `source` is a trust input — it is forced from the
directory *"so frontmatter can't lie"*, and owl loading is gated on it. Adopting an
unplaceable directory would hand a skill a trust level nobody assigned it, which is a
larger defect than the one being fixed. Where the file should go is the operator's call
(ESC-127); making it visible is not.

## Invariants

- A `SKILL.md` on disk is either **loaded** or **named in the log**. Never neither.
- A stray is never loaded, at any source, under any layout.
- `_VALID_SOURCES` and `SkillSource` cannot diverge — one is derived from the other.
- A non-skill directory under the root (`notes/`, an empty dir) is not reported. Only
  skill-shaped strays count, or the warning becomes noise and stops being read.

## Configuration

None. The check is unconditional and ships ON — a report that has to be enabled is a
report nobody enables.

## Observability

- `[skills] loader.load_all: SKILL.md outside any source dir — not loaded` — **WARNING**,
  fields `paths`, `count`, `valid_sources`. WARNING, not DEBUG: production runs at INFO,
  and this is the only evidence the invariant above holds.
- `[skills] loader._load_one: registered` — INFO, one per loaded skill. The denominator.

```bash
# Does the arithmetic reconcile on the current boot?
grep -c '"msg": "\[skills\] loader._load_one: registered' ~/.stackowl/logs/stackowl.jsonl
grep 'outside any source dir' ~/.stackowl/logs/stackowl.jsonl | tail -1
find ~/.stackowl/skills -name SKILL.md | wc -l    # must equal loaded + strays
```

## Failure modes

| Failure | What happens | What notices |
|---|---|---|
| Skill in no source dir | Not loaded | The WARNING, every boot |
| Unknown frontmatter key | `extra="forbid"` → skill skipped | `skill invalid — skipping` |
| A key we ourselves retired | Dropped, skill still loads | DEBUG (deliberate — 142 of 169 files carried `summary`; 142 warnings a boot trains an operator to stop reading warnings) |
| Skills root unreadable | Strays return empty | The `cannot scan skills root` WARNING |

The `extra="forbid"` policy is the parity risk worth naming: a skill authored elsewhere in
the wider convention that carries a key we do not model (`platforms:`, `metadata:`) fails
to load **entirely**. That is loud and recoverable today, and it is the right default for
a typo — `descrption:` becomes a named error instead of a silently ignored key. It is
recorded here because it bounds the "compatible with the wider convention" claim: we read
that convention's *shape*, not its *whole vocabulary*.
