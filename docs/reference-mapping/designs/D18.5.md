# The Gap Was Dead, The Mechanism Was Misquoted, And The Detector Was Voiding Itself

**Item.** D18.5 · Test isolation — `PARTIAL`, wave 9, order 88.
**Ask.** "Would subprocess-per-file isolation fix our hang?"
**Answer.** There is no hang, and subprocess isolation would make things worse. What
was actually broken is that the full run — this programme's only cross-pollution
detector — disqualified its own verdict in **53% of completed runs**.

## Three of the item's premises are false, and one of them is a lesson

**1. "Our full suite is not runnable."** It runs constantly. `~/.stackowl/logs/` holds
20 suite logs spanning 2026-09-03 23:53 → 2026-09-05 05:11 — roughly one run every
1.7 hours — and today's completed green: `11994 passed, 18 skipped, 0 failed in
1856.98s, rc=0`. Durations across 17 completed runs: 1731s–1937s, median ~30:08. The
runtime is stable and predictable, which is precisely why nobody is deterred.

**2. "xdist workers."** The reference platform **explicitly dropped xdist**, and its
runner carries a docstring section titled *"Why drop xdist entirely?"* — *"xdist's
persistent workers accumulate state across files, which is exactly the leakage we
wanted to fix."* It is not in their dependencies at all.

**3. And where that error came from is the lesson.** Their own contributor guide
still describes the runner as using xdist. The doc is stale relative to the code it
describes, and this map entry copied the doc. **A claim sourced from the reference's
DOCUMENTATION is not evidence about the reference's BEHAVIOUR** — that applies to
every remaining item in this programme, not just this one.

## What was actually wrong

`scripts/full_suite.sh` fingerprints `src` and `tests` before and after a run, so a
verdict names the tree it is about. That check was added on 2026-09-04 after a
30-minute run returned `3 failed` about a tree that never existed at any instant.

**The fix chosen then was to LABEL the moving run, and its own numbers condemn it.**
Measured across every log kept: **9 of 17 completed runs — 53% — printed `SUITE TREE
CHANGED … this verdict is about NO SINGLE TREE`.** A detector that voids its own
verdict more than half the time is not a detector, and the label only ever helped
someone who noticed it and spent another 30 minutes by hand. Nine times, nobody did.
That is repairing WHAT happened and leaving WHY alone: the loop that edits while the
suite runs was never going to stop, so the suite is what had to adapt.

A moving run now **re-runs itself once** against the tree as it then stands, and says
`SUITE TREE STILL` when the verdict is about a single tree. Bounded at one retry, so
continuous editing reports plainly instead of looping. Proven behaviourally: touching
a source file mid-run produced `TREE CHANGED` → `RETRY` → `TREE STILL (attempt 2)` →
`DONE rc=0`.

**And the completion stamp could be skipped.** `SUITE DONE` was the last statement
inside a `set -euo pipefail` region, below a fingerprint call that runs through a
pipe — so any failure there exited before the stamp. One kept log proves it happened:
`full-suite-20260903-235313.log` ends with `1 failed, 11856 passed … in 1767.71s` and
no `SUITE DONE`, so the documented collector reports a run that finished 29 hours
earlier as still going. It is now written from an EXIT trap, which cannot be skipped.

## The one parity clause that was not vacuous, and what it caught

Of the reference runner's CI-parity block, the credential-unsetting half has almost
nothing to bind to here: exactly one credential-shaped variable exists in the
environment (the harness's own), and every operator secret is a `file:` reference
under a home `conftest` already redirects. **TZ was different, and it earned itself
immediately.**

Pinning `TZ=UTC` exposed `_next_local_hour_iso` in `scheduler/assembly.py`:

    now = datetime.now()                                  # NAIVE — host local time
    candidate = now.replace(hour=hour, minute=0, ...)
    return candidate.astimezone(UTC).isoformat()          # assumes the HOST zone

**The root cause is not the timezone — it is that this was a SECOND implementation.**
`compute_next_run` in `scheduler_helpers.py` had always resolved
`settings.system.timezone` for exactly this computation, and its docstring says the
scheduler "shares the SAME tz the quiet-hours clock uses". So every seeded job's
FIRST run was computed one way and every SUBSEQUENT run another — `CLAUDE.md` shape
3, two copies of one rule, with the wrong copy in the seeding path.

The duplicate carried two defects, both measured:

* **Timezone.** On this box the host zone and `system.timezone` share an offset, so
  it looked correct. On the ordinary self-hosted shape — a server running UTC — a
  09:00 America/Chicago check-in was seeded for 09:00Z: **04:00 for the operator.**
* **Minutes, silently dropped.** It took an HOUR only, so `daily@04:30` was seeded to
  fire at 04:00. Three schedules did this, and the call site's own comment already
  warned that a ":30" offset "would compute the identical 05:00 first-run timestamp
  for both".

**So it was deleted, not taught.** `_first_run_for(schedule)` passes the schedule
STRING to `compute_next_run`, so first and later runs share one code path and there
is no second hour to keep in step. Retired means deleted: the helper is gone, so is
`_daily_schedule_hour` (its only caller went with it), so is the now-dead `next_hour`
parameter across all 11 call sites, and so is the landmine comment about dropped
minutes — a note that outlives its mine sends the next reader hunting a defect that
no longer exists.

## What was rejected, and why, so it is not re-proposed

* **Subprocess-per-file isolation** — it would multiply interpreter startup across
  ~1,000 files, and its only unique power is detecting cross-test pollution, which is
  exactly what the shared-process sequential run is valued for. It does not detect
  leakage; it makes leakage invisible. The reference chose immunity over detection
  deliberately; we need the detection.
* **xdist** — the reference dropped it for our exact reason.
* **Unsetting credential variables** — nothing to bind to (see above).
* **A copied-snapshot run**, which would make the tree immutable by construction and
  is genuinely stronger than a retry. Rejected *for now* because imports resolve
  `stackowl` from an editable install, so a snapshot only takes effect by redirecting
  `PYTHONPATH` — subtly different from what production imports, in the one tool this
  programme trusts most. A wrong verdict from a mis-wired snapshot is worse than a
  late one. Recorded in the script itself so it is not re-proposed cheaply.

## Verification

```bash
uv run pytest tests/test_the_suite_verdict_is_about_one_tree.py \
              tests/test_a_schedule_honours_the_configured_timezone.py -q   # 7 passed
uv run pytest tests/scheduler -q                                            # 548 passed
# the retry path, behaviourally:
( sleep 12; touch src/stackowl/paths.py ) &
STACKOWL_SUITE_LOG=/tmp/t.log ./scripts/full_suite.sh tests/plugins
grep '^SUITE' /tmp/t.log     # TREE CHANGED -> RETRY -> TREE STILL (attempt 2) -> DONE
```

All RUN on 2026-09-05, not trusted. **Mutation-proven**, each restored from a file
copy and re-run green: un-trapping the verdict, defaulting TZ instead of pinning it,
reverting the scheduler to the host zone (3 failures), and dropping the schedule's
minutes (1).
