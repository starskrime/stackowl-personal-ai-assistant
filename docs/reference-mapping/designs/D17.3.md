# External Security Scanner — Two of Three Threats Are Structurally Answered

**Item.** D17.3 · External security scanner — `MISSING`
**Last verified.** 2026-09-05, commit `HEAD`

## Why this exists

The Ask: *"worth it, or does our sandbox make it redundant?"* The reference platform runs an
external binary that scans commands for content-level threats — **homograph URLs**,
**pipe-to-interpreter**, **terminal injection** — with the exit code as the verdict, JSON
stdout enriching but never overriding, and auto-install from GitHub releases with SHA-256 and
cosign verification.

**Nothing was built.** Whether to take a third-party binary is the operator's call
(**ESC-135**). What this item did was answer the three threats it names, one at a time.

## Threat 1 — pipe-to-interpreter: structurally impossible

`ShellTool` runs `create_subprocess_exec` with **`shell=False`** (ARCH-75). Its own docstring
states the consequence: *"pipes/redirects/chaining are inert."*

`curl … | sh` is not detected here. **It cannot be expressed.** There is no shell to
interpret the `|`, so the argv is passed to `curl` as literal arguments. That is strictly
stronger than a scanner that pattern-matches the shape, and it cannot be bypassed by an
encoding the scanner did not anticipate.

A scanner for this threat would be redundant.

## Threat 2 — homograph URLs: not covered, and the threat model differs

`infra/net/ssrf_guard.py` is **resolve-then-validate**: it resolves the host and rejects if
any resolved IP is loopback, private, link-local, carrier-grade NAT, or multicast. There is
no IDN/punycode normalisation and no homograph detection — measured, that grep is empty.

But a homograph attack is a **phishing** control: it protects a *human* who misreads
`аmazon.com` (Cyrillic а) as `amazon.com`. Our reader is the model, which sees bytes, and the
guard's question is not "does this domain look like another one" but "where does it actually
resolve" — which a homograph domain answers honestly.

Not covered. Not obviously needed. Recorded as an open question rather than a gap, because
asserting either way would be a claim about attacker behaviour I have not measured.

## Threat 3 — terminal injection: a narrow, real exposure

`channels/cli_adapter.py:70` composes `RichLog(highlight=True, **markup=True**, wrap=True)`.
With markup enabled, `[...]` sequences in the content are interpreted as Rich markup rather
than shown.

**Scoped honestly before calling it a hole:** that widget's own docstring says *"Minimal
Textual app — RichLog + Input. **Used in tests / fallback only**"*, and what reaches it
(`self._app.write(chunk.content)`) is assistant response text, not raw tool output. So the
path is a fallback CLI mode, and untrusted content reaches it only if the model echoes it.

Real, narrow, and — this is the point — **ours to fix structurally** if it is worth fixing:
escaping markup on untrusted content at the render boundary is a few lines in our code. It is
not an argument for a third-party binary.

## What the rule adopted two items ago already says

D16.4 (2026-09-04): *third-party products ship as plugins, not in the core tree.* An external
scanner binary — auto-installed from GitHub releases, verified with SHA-256 and cosign — is
exactly that category. So even a "yes" answer to this Ask lands at rung 4, a plugin, not in
`src/`. The policy answers half the question before the risk appetite is even consulted.

## What was decided

Nothing built. Two of the three threats the scanner targets are already answered — one
structurally and more strongly than a scanner could, one by a guard that asks a different and
more reliable question. The third is a narrow display-layer exposure in a fallback path with
a cheap in-house fix.

## Verification

```bash
# 1. Pipes are inert: exec-only, and no shell=True KEYWORD anywhere.
python3 -c '
import ast, pathlib
t = ast.parse(pathlib.Path("src/stackowl/tools/system/shell.py").read_text())
print([n.lineno for n in ast.walk(t) if isinstance(n, ast.Call)
       for kw in n.keywords if kw.arg == "shell"
       and isinstance(kw.value, ast.Constant) and kw.value.value is True] or "none")'
#    expect: none
#
# AST, NOT GREP, and the first draft of this line got it wrong: `grep -c shell=True`
# returns 1, because line 1's own docstring says "never shell=True (ARCH-75)". A text
# scan cannot tell a module promising something from a module doing it — the same
# assertion-versus-mention problem D16.6 hit, caught here by running the section
# instead of trusting it.

# 2. No homograph/IDN handling in the URL guard.
grep -niE "punycode|idna|homograph|xn--" src/stackowl/infra/net/ssrf_guard.py
#    expect: no output

# 3. The markup-enabled widget, and its stated scope.
grep -n "markup=True" src/stackowl/channels/cli_adapter.py
sed -n '58p' src/stackowl/channels/cli_adapter.py
#    expect: RichLog(... markup=True ...) and "Used in tests / fallback only"
```

All three RUN on 2026-09-05, not trusted.
