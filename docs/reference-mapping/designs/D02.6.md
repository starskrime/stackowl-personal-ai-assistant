three of its members are vendor-named and one of its two classification paths is
English substring matching, the answer was **"full taxonomy, rules kept — status

That is what shipped — **half of it. [CORRECTED 2026-09-07.]** Every reason worth

stands. The other half does not: `ProviderConfig.quirks` was to carry anything

**`quirks` was DELETED on 2026-08-20 (`7234f3cd`), by Bakir's call, as a write with

## What was actually broken, measured

The classifier already existed and was already structural. Two real defects sat
inside it, and neither was visible until the taxonomy forced someone to name each
status separately.

### 1. The whole 4xx range collapsed to `AUTH`

```python
if 400 <= status <= 499:
    return FailureCause.AUTH   # ← 402, 404, 408, 413 all land here
```

A **413 payload-too-large** was therefore indistinguishable from a bad API key.
We trim proactively before every call but had **no reactive path** if a provider
rejects on size anyway — so the one failure whose fix is "send less" was handled
by a policy of "do not retry, it is a credential problem."

### 2. The structural status check admitted only 429 and 5xx

```python
# before
if isinstance(status, int) and (status == 429 or 500 <= status <= 599):
    return _cause_for_status(status)
```

The comment above it read *"works across SDKs that expose `status_code`"*. The
condition said otherwise: any other status, on any exception outside the three
probed SDK hierarchies, fell through to `NOT_A_FAULT` — no cause, no action.
**The docstring and the code disagreed, and the docstring was the one people
read.** Widened to every status ≥ 400.

Floored at 400 deliberately: `_cause_for_status` falls through to `TRANSPORT` for
anything unrecognised, and `TRANSPORT` **is** a breaker fault. Widening past that
line would start tripping the circuit breaker on exceptions that merely happen to
carry a status attribute. Pinned by a test.

### 3. Found while verifying: a live 400 mislabelled as a credential failure

Not planned work — it fell out of reading production logs for evidence the
classifier fires at all.

```
2026-08-04T23:43:24Z  ERROR  stackowl.engine
  "[resilient_round] provider request/credential failure (non-429 4xx) —
   blind retry will not self-heal this"     provider=NeraAiRaw  exc_type=BadRequestError
```

Counted across all rotations: **461 occurrences over 15 days** (46 on 07-21, 43 on
07-22, a 342-spike on 07-29, still 5 on 08-04). The preceding log lines identify
the caller: `dream_worker` → `conversation_miner.mine_all`, `trace_id: null` — a
background job, which is why nobody noticed.

A 400 is **our malformed payload**, not our credentials. The log line pointed a
reader at the API key for a request-construction bug, and carried no detail to
diagnose from. Split into `BAD_REQUEST`, with the provider's own words logged
(truncated to 200 chars, matching the SQL rule — a rejection can echo the payload
back).

> The recovery action is **unchanged** — `ABORT` either way. This buys nothing at
> runtime and everything at 2am. That is the honest description of the fix.

## The taxonomy

| status | cause | action | why that action |
|---|---|---|---|
| — | `NOT_A_FAULT` | `NONE` | control flow or our own bug |
| — | `TRANSPORT` | `RETRY` | connection dropped; a retry can self-heal |
| 5xx | `SERVER_5XX` | `RETRY` | upstream blip |
| 408 | `TIMEOUT` | `RETRY` | transient |
| 429 | `RATE_LIMIT` | `BACKOFF` | quota-aware cooldown already implemented |
| 529 | `OVERLOADED` | `BACKOFF` | saturation — back off harder than a plain 500 |
| 402 | `BILLING` | `ROTATE_CREDENTIAL` | this credential is spent |
| 413 | `PAYLOAD_TOO_LARGE` | `COMPRESS` | shrink, never blind-retry |
| 404 | `MODEL_NOT_FOUND` | `FALLBACK_MODEL` | bad model id; another will do |
| 400 | `BAD_REQUEST` | `ABORT` | our payload; a retry sends the same bad request |
| other 4xx | `AUTH` | `ABORT` | nothing here self-heals |

`RECOVERY_FOR_CAUSE` is a **dict, not an if-tree**, so a new cause cannot be added
without someone stating what to do about it — pinned by
`test_every_cause_states_what_to_do_about_it`.

## Where the actions actually fire

A taxonomy nobody consults is decoration. This is the `D05.2` lesson: M1 survived
there because 19 module tests passed while the module was **unwired**.

**`is_cascadable_fault` (`llm_gateway.py`) now consults `recovery_for`.** A cause
prescribing `FALLBACK_MODEL` or `ROTATE_CREDENTIAL` cascades to the next tier.
`is_provider_fault` says False for both — correctly: the provider is healthy, this
request is simply unusable against it — so **a 404 bad-model-id or a 402
out-of-credit used to dead-end at the user with other tiers sitting idle.**
Climbing the ladder *is* that recovery: the next tier is a different model behind
a different credential. Nothing else in the process can perform either action.

**`COMPRESS` has no actuator, and the ladder does not pretend it does.** Climbing
a tier does not make a payload smaller. The cause is named, logged, and left
un-actuated — recorded as `DEBT-39` rather than faked. Pinned by
`test_a_413_does_not_cascade_because_nothing_can_compress_yet`.

## The one deliberate breaker change

`_BREAKER_FAULTS` is now **derived** — a cause counts against the circuit breaker
iff its action is `RETRY` or `BACKOFF` (i.e. we believe the provider itself is
unhealthy) — rather than a hand-listed triple that could silently drift from the
action map. Mutation M15 proves the derivation matters.

That changes exactly one input: **a 408 now counts.** It previously reached `AUTH`
through the 4xx catch-all and did not. A status-less `TimeoutError` always
counted; treating an HTTP timeout as a credential problem was never intended, it
fell out of the collapse. Every other status is unchanged, pinned by
`test_breaker_faults_change_in_exactly_one_place`.

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| Bad model id (404) | status | cascade to next tier | an answer, from a higher tier |
| Provider out of credit (402) | status | cascade to next tier | an answer, from a higher tier |
| Payload too large (413) | status | **none — `DEBT-39`** | the error, honestly |
| Malformed request (400) | status | abort | the error, and a log line naming the payload |
| Bad credential (401/403) | status | abort | the error, honestly |
| Provider saturated (529) | status | backoff + breaker | a retry, then a tier climb |
| A cause added with no action | `I3` | abort | the error, honestly |

**The document diagnosed its own unfalsifiable check and filed it as a

**The cause was PLACEMENT, not the level.** A decision about which recovery to
attempt was attached to the routine 4-point EXIT line, whose level is set by a
logging convention — exits are DEBUG — rather than by the value of what it carries.
The convention is right; the load-bearing field was on the wrong line. The
classification now emits its own INFO record and the exit line stays DEBUG, pinned
in both directions.

Volume was measured before the line was written: ten days of logs carry **81**
`[resilient_round]` records out of 580,225. Not a firehose.

```bash

grep -h '"msg": "\[resilient_round\] fault classified"' ~/.stackowl/logs/stackowl*.jsonl \
  | python3 -c 'import sys,json;[print(json.loads(l)["fields"]["cause"],"->",json.loads(l)["fields"]["recovery"]) for l in sys.stdin]'
```

**Still not proven live: the rare causes firing.** 402/404/408/413/529 had never
appeared in 15 days when this was written and have still not appeared. That remains
a statement about our providers, not about the code, and no amount of waiting
conjures a 413. What changed is that the claim is now falsifiable at all.

**A reader trap, worth one line.** The taxonomy table below lists action MEMBER
names; the log carries their VALUES, and they differ in one place —
`ROTATE_CREDENTIAL` is logged as `rotate`. The new tests derive the expected value
from `RECOVERY_FOR_CAUSE` rather than spelling it out, which is how that mismatch
was found.

### Prior art, and where we deliberately diverge

`agent/error_classifier.py` — a 22-member failure taxonomy with a status-code path
and a message-substring path, feeding a failover policy.

**Adopted:** the taxonomy itself — the insight that "provider failed" is not one
thing, and that naming the cause is only useful if each cause carries an action.
The specific causes (billing, model-not-found, payload-too-large, overloaded)
are real incident knowledge we would otherwise have learned the expensive way.

**Diverged:** no message matching; no vendor-named members; `_BREAKER_FAULTS`
derived from the action map rather than listed. [CORRECTED 2026-09-07 — this said
their three members "become `ProviderConfig.quirks` entries". They became nothing:
`quirks` was deleted 2026-08-20 as a write with no reader, and the coverage those
members represented is carried by status codes, which is where it was always real.]

**Not adopted:** their failover *policy* object. Ours already has one — the
breaker, the limiter, and `LLMGateway`'s tier escalation. X9 said "compose, do not
add a second"; the classifier feeds those three.

### How the two Laws hold

**Law 1 — per-conversation prompt caching is sacred.** Untouched. This is a
fault-path-only change; no prompt, schema, or tools array moves. A cascade to a
higher tier already rebuilt the request before this item existed.

**Law 2 — the core is a narrow waist.** No new model-facing surface. The taxonomy
is internal; the model never sees a `FailureCause`.
