# Session Export & Recap — and What the Archive Does Not Contain

**Item.** D11.4 · Session export & recap — `MISSING`
**Last verified.** 2026-09-04, commit `HEAD`

## Why this exists

The Ask — *"Product feature or nice-to-have?"* — is product intent and stays the operator's
(**ESC-130**). Nothing was built. What this item did was make that question answerable, and
in doing so found something larger than the feature it was asking about.

## The gap is real, and two near-misses are not it

`session_export_md`, `session_export_html`, `session_recap`, `session_filters`,
`session_listing` — none exist. Confirmed by search, and by two names that look like hits
and are not:

- `/sessions` exists — in `browser_command.py`. **Browser** sessions.
- `/resume` exists — in `owls_command.py`. Resuming an **owl's cadence**.

Neither has anything to do with conversation export. A grep that stopped at the name would
have reported parity.

## What the archive actually covers

The map says `export/` is "full-archive backup". It is a curated five-table export, and
measured on the live database:

| exported table | rows |
|---|---|
| `committed_facts` | **0** |
| `staged_facts` | 230 |
| `owl_dna` | 11 |
| `parliament_sessions` | **0** |
| `audit_log` | 11,257 |

| NOT exported | rows |
|---|---|
| `conversations` | **1,107** |
| `messages` | **3,841** |
| `sessions` | **123** |

**The conversation history is in no export, at any granularity.** D11.4 reads as a gap in
*formatting and convenience* — markdown, HTML, recap. The measurement says the gap is prior
to that: there is no supported path by which the operator gets their transcript out of the
platform at all.

Two of the five exported tables are also empty. `parliament_sessions` has no rows.
`committed_facts` has none because it is the **unwired target of a promotion step that never
runs** — `staged_facts` holds the live 230 — which is why this item does **not** remove it
from the export. A destination waiting for its writer is a different thing from a retired
table, and `test_c7_f131_export_scope.py` (a sanitization merge-gate) depends on it being
exported.

## Demand, measured

Across all nine daily logs (2026-08-28 → 2026-09-04):

| path | invocations |
|---|---|
| `session_search` | 18 (discover 16, browse 2, scroll 0) |
| `transcripts` tool | **0** |
| operator-run export | **0** — all 8 `[export] backup.backup: exit` lines are the migration runner's automatic pre-migration backup |

**The `transcripts` zero is about demand, not reach.** Its INFO line
(`transcripts.execute: entry`) was confirmed in source before counting, and the tool is
registered: live discovery over `stackowl.tools` finds 79 tool classes and `transcripts` is
among them. A static grep said the opposite — `TranscriptsTool` has no reference outside its
own file — which is exactly the trap `CLAUDE.md` names, since this codebase wires tools
dynamically.

**And a raw count would have said 3,353.** Grepping `transcript` across the logs matches
`transcript.record_turn: exit` (1,515, the *writer*, firing every turn), two pipeline
persistence messages, and 168 lines about **voice transcription** — a different sense of the
word. Not one of them is the tool. The honest number is zero.

## What was decided

Nothing was built. The item is `MISSING` and stays so.

That is not deferral of the diagnosis: the diagnosis is above and complete. What waits is a
decision only the operator can make, and it is now two questions rather than one — the
feature, and the prior question of whether transcripts belong in the archive at all. Putting
3,841 user messages into a portable archive is a privacy-relevant scope change, and no
recorded decision says it was ever intended. `test_c7_f131_export_scope.py` governs
*sanitization* scope, not table selection, so it does not settle it either.
