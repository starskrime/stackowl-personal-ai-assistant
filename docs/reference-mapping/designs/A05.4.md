## Why this exists

**The item's own gap was measurably false, and correcting it is what made this
small.** A05.4 originally read *"cron jobs are invisible unless the operator
queries the database by hand"*. Measured against the tree on 2026-09-11,
`tools/scheduling/cronjob.py` declares **eight** actions — create, watch, list,
update, pause, resume, remove, run — which is every verb this item asks for.
Built as written, A05.4 would have rebuilt a working tool.

What is actually missing is narrower: **every one of those verbs needs somebody
at a chat prompt.** The operator asked for "a web dashboard where customer
control platform, agents, crons", and there is no view of the set from anywhere
that is not a conversation. So the smallest complete thing that ships this ON is
one read route on the door A05.1 already built.

**And the real work was the guard, not the route.** With one route, the origin
check, the token check and the READ check sat inline in `_handle_health`, and
that was honest. The second route is precisely the moment that becomes two
copies of one rule — and the moment a handler can be written that performs two
of the three checks and looks finished.

**What was already swept, and what was not.** A05.1 built
`test_every_route_handler_calls_authenticate` derived from the router rather than
hand-listed, so the TOKEN check already reached every registered route; that test
now follows the delegation instead of looking for the literal. What was pinned to
one handler by name was the ORIGIN ORDERING — `test_order_is_origin_then_token`
read `_handle_health`'s source, so a second route checking the token first, or
omitting the origin check entirely, would have passed it untouched. This
distinction is recorded because an earlier draft of this document stated the
broader, wrong version, and running the derived test path is what corrected it.

## The ladder rung

**Extend what runs.** No new store, no new reader, no new setting, no second
engine. `list_jobs()` is the method `cronjob.py`'s own `list` calls; this route
calls the same one on the same live `JobScheduler` the scheduler subsystem
already owns, injected from `SchedulerComponents` exactly as the health
aggregator is.

**Law 1 — nothing duplicates logic that already runs work.** The route issues no
SQL; a test asserts the whole `control_plane` module contains no `SELECT`,
`INSERT`, `UPDATE` or `DELETE`. Two readers of one table is how a dashboard and
a chat turn come to disagree about what is scheduled.

**Law 2 — the core stays narrow.** One handler and one guard, on a surface that
already exists.

## Model

`GET /api/v1/schedules` → `200` with

```json
{"wired": true,
 "schedules": [{"job_id": "...", "handler": "...", "schedule": "0 7 * * *",
                "enabled": true, "status": "pending",
                "last_run_at": "...", "next_run_at": "...",
                "failure_count": 3, "last_error": "db is locked"}]}
```

Every field name was read off `Job.model_fields` rather than off the table, so
the payload cannot drift from the model the scheduler returns.

**`failure_count` and `last_error` are not decoration.** A list that shows a job
exists but not that it has been failing is the shape A05.5 names — a surface
that answers, and leaves the reader worse off than silence would have.

**`jobs` carries no `owner_id` column** (asked of the live schema, 2026-09-11:
`job_id handler_name schedule idempotency_key last_run_at next_run_at status
retry_count created_at failure_count last_error enabled replay_missed
primary_channel params target_channels target_addresses retry_at
circuit_broken_at claimed_at`). There is therefore no per-owner predicate to
apply here, and none is implied by its absence. If that table ever gains one,
this route must gain the predicate in the same change.

## Lifecycle

The route is registered in `ControlPlaneServer.run()` beside `/api/v1/health`,
served by the same `SupervisedTask`, and dies with it. It holds no state.

## Invariants

1. **Every registered route reaches `_guard`, and `_guard` authenticates.** Both
   halves are asserted: the chain could otherwise be satisfied by a guard that
   had quietly stopped checking. Derived from `run()`'s own `add_get(...)` calls,
   never from a list written in a test.

   **Amended 2026-09-11 (DEBT-308), with one structural exemption.** A browser
   cannot put an `Authorization` header on a top-level navigation, so the page
   itself has to be servable without one. The sweep now admits an unguarded
   handler **only if it touches no `self.` attribute at all** — a property of the
   code rather than a name on an allowlist — and a companion assertion fails if
   NO route is guarded, so the carve-out cannot swallow the rule. `GET /` is the
   only route that qualifies, and it returns a constant.
2. **No handler performs `check_origin`, `authenticate` or `.may(` itself.**
   This is the half the sweep above cannot see: a handler can reach the guard
   AND still carry its own partial copy of the decision.
3. **Origin before token.** A browser request from another origin may carry a
   valid credential, so checking the token first authenticates an attack before
   rejecting it. Asserted twice: by reading `_guard`'s source, and by behaviour
   — a request with a valid token and a foreign Origin gets 401.
4. **403 and 401 stay different answers.** One says *who are you*, the other
   says *not you*; collapsing them makes `granted` decorative.
5. **A missing collaborator confesses.** No scheduler wired → `503` and
   `"wired": false`, never an empty list. A read failure that looks like an
   empty store is itself a mapped item (A06.6).

## Configuration

None. The route inherits `control_plane.bind_address` and `control_plane.port`,
and the credential A05.1 resolves. Nothing here can be turned off
independently — it ships ON with the surface.

## Observability

`[control_plane] server.schedules: entry` and
`[control_plane] server.schedules: exit — served` at **INFO**, the latter
carrying `principal_id`, `schedules` (the count) and `duration_ms`. Every
refusal is a **WARNING** naming which of the three checks refused.

The guard's refusal lines carry the route name, so `server.health` and
`server.schedules` remain distinguishable in the log after the extraction — a
shared helper that logged one name would have made two routes indistinguishable,
which is the observability cost of de-duplication and is why the route is a
parameter.

Nothing here is DEBUG. This deployment has written **zero** DEBUG records in
677,108, so a DEBUG line is a claim nothing can settle.

## Failure modes

| What fails | What happens | What notices |
|---|---|---|
| No credential can be resolved | The server refuses to bind at all (A05.1's I1) | `server.run` ERROR, and the reachability census |
| Scheduler not injected | `503`, `"wired": false`, WARNING naming the missing collaborator | The WARNING, and the caller's own status code |
| `list_jobs()` raises | Propagates to aiohttp as a 500; `SupervisedTask` accounts the failure | The supervisor, and the absent `exit — served` line |
| A route is added without the guard | The tripwire fails by name | `./scripts/tripwires.sh` |

## What this deliberately does not do

**It does not write.** Create, update, remove and run-now are the rest of A05.4
and are not built here. A read route is complete on its own — it closes the
"see them as a set" half of the gap, and shipping it does not imply the write
half exists.

**It does not add a second reader, a cache, or a projection.** The set is
whatever the live scheduler says it is, computed per request. `list_jobs()`
returns every row ordered by `job_id`; if that ever becomes too large to serve
whole, the bound belongs in the scheduler, where the chat surface would get it
too.
