# One Key, Zero Failures — And Two Things I Nearly Called Dead

**Item.** D04.3 · Credential pool & rotation — `MISSING`, wave 10, order 95.
**Ask.** "Do you run multiple keys per provider today?"
**Answer.** No, measurably. The pool is declined; what shipped is the gap the
measuring actually found.

## The Ask, answered

Four providers are configured and **one is enabled** — `NeraAiRaw`, with **one**
`api_key`, a `file:` reference. The other three are local endpoints with no key at
all. And the model permits nothing else: `ProviderConfig.api_key` is `str | None`,
never a list.

**Demand for rotation is zero, and the first measurement of it was wrong.** A raw
`grep -c` over the logs reported 271 hits for "429", 250 for "401" and 262 for
"403" — suspiciously alike, and they were: the samples show
`(640in/429out tokens)`. Those are token counts. Parsing the JSON and matching only
message text across **502,215 records in 9 log files** leaves exactly **two**
distinct auth-or-rate-limit messages: a 400 payload rejection (twice, our own
malformed request) and — 569 times — `[scheduler] credential_rotation handler
registered`.

**Not one rate-limit event. Not one auth failure. Ever.** A pool for a deployment
with one key and no failures is decoration.

## The map's `MISSING` is too flat

The map credits the reference with "the error classifier can decide 'rotate
credential' as a distinct action from 'fall back to another provider'". **That half
is already here**, and its own docstring says it was deliberately ported: `AUTH`
(401/403), `RATE_LIMIT` (429 — "back-pressure, not an outage"), `BILLING` (402 —
*"credit exhausted; rotate, do not retry"*), `PAYLOAD_TOO_LARGE`, `TIMEOUT`,
`BAD_REQUEST`, `SERVER_5XX`, each mapped to a `RecoveryAction`, and pinned by
`tests/providers/test_failure_taxonomy.py`.

So the classifier exists and is arguably richer than the reference's — the ported
version deliberately dropped their English-substring matching and their
runtime-specific member names. **Only the pool is missing, and there is nothing to
put in it.** `BILLING`'s comment names "rotate" as the action for a mechanism that
does not exist, which is honest about intent rather than a defect.

## Two things I nearly called dead, and checked

**`credential_rotation` is a name collision.** A handler by that name is registered
on every boot — 569 times in the logs — and has **zero rows** in `jobs`. It is not
this item's subject at all: its docstring says "session liveness check for persistent
profiles", opening a browser profile and checking whether a *web login* still holds.
And it is **not dead**: `cronjob.py:520` passes `handler_name=handler` generically, so
it is reachable on demand exactly as `assembly.py:1557` documents. `CLAUDE.md`'s rule
that "the zero-row table is the QUESTION, never the answer" is what stopped a wrong
deletion here.

**`FailureCause` appears zero times outside its own module** — which looked like the
write-with-no-reader shape found twice already this week. It is not: the retry loop
*is* its consumer, `classify_failure_cause` is used ten times inside, and a dedicated
test file pins the taxonomy. Legitimate encapsulation.

Both were checked before concluding, and both would have been wrong.

## What shipped instead

Secrets are referenced as `file:/…/.secrets/<name>.key`, and `_from_file` read
whatever was there **without ever looking at the mode**.

Measured: the operator's own secrets are correct — `700` on the directory, `0600` on
every one of six keys — so **the new check is silent on his box**, which is what a
healthy guard looks like. The failure it exists for is the invisible one: a restore,
a `cp`, an editor writing a fresh file, or an archive extracted without modes,
leaving a key readable by every process on the machine. The platform would read it,
work perfectly, and never mention it.

Three decisions, each borrowed from an item that earned it:

* **It warns and still returns the secret.** A world-readable key is already exposed;
  refusing to start does not un-expose it and takes the platform down to report
  something stopping cannot fix — D18.9's rule, that you fail closed only when
  refusing *prevents* the harm.
* **It is silent when the mode is right.** A guard that fires on the correct case is
  one its reader learns to ignore — D18.7, where a cross-platform checker sat unread
  for months because it flagged correct code.
* **An unmeasurable mode is not an exposure.** If `stat` raises, the secret still
  resolves and the check says nothing. "I could not check" and "it is exposed" are
  different claims.

It is POSIX-guarded, because mode bits do not carry this meaning on Windows and
`scripts/boundaries/b4.py` — gated since D18.7 — exists to stop that assumption being
made silently.

## Verification

```bash
uv run pytest tests/config/test_a_secret_file_that_anyone_can_read_says_so.py -q  # 7 passed
uv run pytest tests/config tests/setup -q                                         # 168 passed
uv run python - <<'EOF'
import logging, glob, os
logging.basicConfig(level=logging.WARNING)
from stackowl.config.secret_resolver import SecretResolver
for k in sorted(glob.glob(os.path.expanduser("~/.stackowl/.secrets/*.key"))):
    SecretResolver.resolve(f"file:{k}")
EOF
#   expect: no output — all six real secrets are 0600
```

All RUN on 2026-09-05, not trusted. **Mutation-proven**, each restored from a file
copy and re-run green: removing the mode check (4 failures), and making it refuse
rather than warn (5).
