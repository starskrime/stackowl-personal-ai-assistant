# Config vs. Secrets — Adopting the Rule Verbatim Would Have Been Wrong

**Item.** D18.1 · Config vs. secrets discipline — `MISSING`
**Last verified.** 2026-09-05, commit `HEAD`

## Why this exists

The Ask: *"Adopt the split? It makes config discoverable and prevents env sprawl."* The
reference platform's rule is hard — `.env` is secrets only, and **every** behavioural setting
lives in `config.yaml`.

**The premise was measured before adopting, and it does not hold.**

## All 18 environment variables, and why each is environmental

| class | why | variables |
|---|---|---|
| bootstrap | read before Settings can exist — you cannot read `config.yaml` to learn where `config.yaml` is | `DATA_DIR`, `HOME`, `LOG_DIR`, `PID_FILE`, `CONFIG_FILE`, `YAML`, `CORE_SOCKET`, `MODEL_CACHE_DIR`, `TEST_MODE` |
| host-specific | a property of the machine, not the user; one config file deploys to several hosts | `CONTEXT_CEILING`, `BROWSER_OFFLINE` |
| terminal convention | the `NO_COLOR` / `prefers-reduced-motion` family, where env is the conventional home | `REDUCED_MOTION`, `NO_GLYPHS` |
| logging bootstrap | logging configures before Settings loads | `LOG_LEVEL`, `LOG_RETAIN_DAYS` |
| deployment secret | read at import, before `SecretResolver` (which needs config) exists | `FINGERPRINT_SECRET` |
| unwired | the in-tree vendor integration nothing registers (D16.4) | `HEADLESS_OAUTH` |

`CONTEXT_CEILING` is the clearest case, and its own docstring says it: *"Set
`STACKOWL_CONTEXT_CEILING` **ONLY** to opt into a host-specific cap (e.g. to bound KV-cache
RAM on a constrained inference server)."* Moving that into `stackowl.yaml` would put a
machine's RAM limit into a file that ships between machines.

**There is no behavioural sprawl to migrate.** Adopting the rule verbatim would have moved
settings that are correctly environmental.

## And the secrets half is already answered, more strongly

There is no `.env` at all. `config/secret_resolver.py` resolves a **reference** —
`keychain:<service>`, `file:<path>`, or a bare env name — so the config file holds a pointer,
never a value, and the strongest option is the OS keychain rather than a dotfile. The
reference platform's rule is "keep secrets in `.env`"; ours is "keep a pointer, and prefer the
keychain".

## So what was actually missing

Not a migration. **Today's discipline is held by the authors who happened to write each of
these carefully, and nothing asks the question when the next one is added.** A behavioural
setting introduced tomorrow as a bare `os.environ.get` would look exactly like the eighteen
that are correct, and no one would notice.

`tests/test_a_new_env_var_has_to_justify_itself.py` asks it automatically: every
`STACKOWL_*` name in `src/` must be classified with one of five reasons, and **"behavioural"
is deliberately not a valid reason** — a behavioural setting has a home, and it is not the
environment.

Set equality in both directions, for the reason D16.2 records: a list that outlives its
subjects stops describing anything.

## Verification

```bash
uv run pytest tests/test_a_new_env_var_has_to_justify_itself.py -q   # 3 passed
python3 - <<'EOF'
import re, pathlib
n = set()
for p in pathlib.Path("src/stackowl").rglob("*.py"):
    n |= set(re.findall(r"STACKOWL_[A-Z0-9_]+", p.read_text(errors="ignore")))
print(len(n))
EOF
#    expect: 18
```

Both RUN on 2026-09-05, not trusted. Mutation-proven: a bare
`os.environ.get("STACKOWL_RETRY_DELAY_S")` fails the guard by name, with the message naming
the five legitimate reasons so the next author can classify or move it.
