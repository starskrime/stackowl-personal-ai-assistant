# D08.1 · Two-file curated memory

> **Verdict:** `DIVERGENT` · **Track:** decide · **Priority:** P1 · **Wave:** 4
> **Dedup target:** `X4` — extraction pipeline vs curated two-file layer. Resolved here.
> **Absorbs:** `D08.3` (memory-write nudges) — see R6Q24.
> **Brainstorm:** 27 questions, 7 rounds, 2026-08-08.

## The item changed shape once it was measured

It was scoped as *"add a legible two-file layer in front of the pipeline"*. Measurement on the live
database turned it into something else: **the pipeline behind it is not a sophisticated memory
system that costs too much. It is a machine that writes down its own diagnostics.**

| measured 2026-08-08 | |
|---|---|
| committed facts | **88,631** (9.75M chars) |
| mention a trace id or `failure_class` | **32,880 — 37.1%** |
| about the platform's own subsystems | 18,606 — 21.0% |
| never reinforced | 43,503 — 49.1% |
| Hermes' *entire* memory budget | **3,575 chars** |

The most-reinforced fact in the whole store is `"Today's date is 2026-07-15"` — three weeks stale,
reinforced **157 times**, with at least six variants. `reinforcement_count` measures how often a
topic came up, not whether it matters: the rest of the top twelve is news headlines at 115–130 each,
including the same story stored twice under two phrasings.

### Root cause, and why the date matters

Writes exploded on **2026-08-05** from ~300–600/day to 9,000–14,400/day. That is the day ADR-19's
autonomous loops shipped.

`fact_extractor.extract()` takes `session_key` **and never consults it.** `MACHINE_LANE_PREFIXES`
(`"goal-"`, `"incident-"`) exists in `sessions/models.py` and is used by the brief — but not here.
So every incident-recovery and retry conversation is mined into durable memory *about the user*.
Confirmed in the data: the newest `staged_facts.source_ref` values are `incident-bf64c33824f9`,
`retry-0b2d9b2d`, `incident-6b8986fbd402`.

The extractor's volume scaled with the platform's autonomy because nothing told it the platform
was talking to itself.

### The reader with no writer

`load_user_profile()` runs on **every prompt build**. `~/.stackowl/USER.md` **does not exist**, and
nothing in `src/` writes it. D01.1 deliberately removed per-turn fact recall from the prompt — for
a good reason, Law 1 — and replaced it with a file that has no writer.

**So the system prompt has carried zero curated memory since D01.1 landed.** Not degraded memory:
none. That is the actual gap this item closes.

## Retrieval was never the weak link

Worth stating plainly, because it is the obvious objection and it was raised during the brainstorm
(R7Q27): the semantic store is real and fully populated. All 89,031 facts carry embeddings in
SQLite's `committed_facts.embedding`, mirrored into a **229 MB LanceDB** table, alongside an FTS5
index — and `memory(action='search')` already does hybrid vector + BM25 recall.

Semantic search over a corpus that is 37% trace IDs returns trace IDs. **Better vectors cannot fix a
bad corpus.** That is why this item removes the *write* path and keeps search untouched.

*(A caveat found on the way: 1,319 facts were embedded with `hash-v1-384d`, the degraded hash
fallback, not a real model. They are not semantically findable in any meaningful sense.)*

## Design

### The two files

| | path | scope | budget |
|---|---|---|---|
| user profile | `~/.stackowl/memory/USER.md` | global | **1,375 chars** |
| agent notes | `~/.stackowl/memory/<owl>.md` | per owl | **2,200 chars** |

Placement was voted (R7Q26) as the standing rule requires. Budgets are Hermes' numbers adopted
as-is (R2Q7), the same call as D10.2's 60-character description cap.

**Per-owl agent notes** because session lanes are already per-owl (`owl:secretary:telegram:dm:…`).
The user is the same person to every owl; what an owl learned doing its job is its own. A shared
bounded file would have owls silently evicting each other.

**Files, not curated DB rows.** Re-examined mid-brainstorm at Bakir's challenge and re-confirmed
(R7Q27). A marked subset of `committed_facts` would keep one storage engine and preserve semantic
search over the curated set — genuinely attractive — but it forfeits this item's stated gap:
*legible, and editable by the user in a text editor*. The store is **look-up**: the model must know
to ask, it costs a tool call, and results vary per query, which is why they cannot live in a
cache-stable prompt. The file is **always-known**.

### Writing

One tool, not two (R2Q5) — `memory` already exists with `add/search/get/forget`, and a second
memory tool is exactly the fork `X4` forbids. It gains a `target`:

```
memory(action='add', target='user'|'<owl>', durability='permanent'|'until_changed', content=…)
memory(action='search', …)      # spans files AND store — retrieval is one question
memory(action='forget', target=…)  # destructive, so it must say where
```

**Durability is required and recorded in the entry** (R4Q14, R5Q20). `transient` is not an accepted
value, so `"Today's date is 2026-07-15"` has nowhere to go. Recording it in the entry — not just
validating it — gives consolidation a principled eviction order: `until_changed` before `permanent`,
rather than evicting by age, which is what let 43,503 unreinforced facts survive.

**The budget is hard and the agent consolidates** (R1Q3). At capacity, `add` REFUSES and tells the
model to merge or remove and retry *in this turn*, bounded by a per-turn failure cap so a fragile
write cannot loop the turn to budget exhaustion. Forgetting becomes the agent's problem against a
visible limit — the same decay pressure the skill catalog turned out to need.

**Every write is scanned** with the existing skill security scanner (R3Q11). This item *creates* an
agent-writable prompt-injection surface; shipping it unscanned and pointing at D08.4 would be
filing a ticket about a hole we just made.

### Reading

The prompt carries a **frozen snapshot** bound to `session_id`, the conversation incarnation
(R2Q6). Mid-session writes hit disk and the live state immediately; the prompt does not change
until the next `/new`. Law 1 holds.

**The staleness was measured and accepted, not assumed** (R3Q9). The main Telegram lane has had
**two incarnations in its entire life**, so a fact written today may not reach the prompt for weeks.
Bakir accepted this with the refresh made explicit — the write confirmation must say *"this reaches
the prompt on your next /new"*, or the agent will appear to ignore what it just learned.

### What is removed

The write path goes; search stays (R6Q23). Retired outright rather than filtered first (R6Q21) —
a lane filter on code being deleted is wasted work:

- `fact_extractor` — the root cause
- `fact_promoter`, `fact_reinforcer` — 12,200 promotions in one day, feeding nothing
- `contradiction_detector` — `fact_rejections` is **empty**; it has never rejected anything
- `trust` scoring — one real value across the corpus (86,329 `self` vs 102 `untrusted`)
- the dream-worker phases that drive them

Kept: the store, its embeddings, LanceDB, FTS5 and `MemoryBridge.recall`, so `memory` can still
look things up.

**All existing facts are deleted** (R5Q19, R6Q22 — *"delete it"*). A routine pre-change DB backup
is taken, as before every migration; no separate archive was wanted. `USER.md` starts empty
(R4Q15): distilling from this store would import the noise the item exists to escape.

### D08.3 comes with it

With extraction retired, the turn-counter nudge is the **only** thing that will ever prompt a write
(R6Q24). Shipping the files and the tool without it means zero writes a day, not a handful. Same
call as pulling D10.2 forward to unblock D09.3.

## Acceptance

Corrected by Bakir (R7Q25): *"my numbers was not a rule it was a guess. agent may write more or
less but definitely not 14,400 per day."* So acceptance **does not hardcode a rate**:

1. Both files exist and contain entries the agent wrote.
2. The assembled system prompt demonstrably carries them — verified by measuring the built prompt,
   not by the code path existing. This is the check D01.1 missed.
3. The write rate is bounded by the **budget**, not by a number.
4. The old path is gone: fact writes collapse from 14,400/day by orders of magnitude.

## Failure modes

| if | then |
|---|---|
| the file cannot be read | degrade to absent and log; a missing profile costs context, never a reply |
| the file cannot be written | the tool returns the failure to the model; it must not floor the turn |
| the budget binds and the model cannot consolidate | bounded retries, then a terminal "save skipped" — a failed memory side effect must never suppress the user's answer |
| the security scan refuses content | the write is refused with the reason; nothing reaches the file |
| an owl has no notes file | absent is the ordinary case, logged at debug |

## Divergences from the reference platform, stated

- **Per-owl agent notes.** Hermes has one agent and one `MEMORY.md`. We have owls with their own
  DNA and their own lanes, so agent notes are per-owl while the user profile stays global.
- **`~/.stackowl/memory/` rather than the working directory.** All runtime state lives under
  `StackowlHome`; theirs sits beside the project.
- **We delete an existing corpus.** Hermes never had one to delete. This is a one-off consequence
  of having shipped an extraction pipeline first.
