# Confinement depth — two cages, and the one that ran silently

> **Status:** live
> **Map item:** D06.3 · Confinement depth (`AHEAD`)
> **Source:** `src/stackowl/sandbox/` — 20 modules + `ptc/`; the cages are
> `bwrap.py` (primary) and `docker.py` (network tier)
> **Config:** `sandbox.bwrap_enabled` / `sandbox.docker_enabled` in `stackowl.yaml`,
> both `default=True`, both hot-reloadable
> **Last verified:** 2026-09-06, against commit `0eca53b6` — Verification section RUN

## Why this exists

The map records the gap in the reference platform's favour nowhere here: they have
Docker/Singularity isolation and no seccomp or cgroup layer of their own; we have seccomp
filters, cgroup limits, mount planning, scratch dirs, a host-wide concurrency governor and
a privileged tool channel. The Ask answers itself — *"Keep. Ours is genuinely stronger."*

**It is stronger, and the item still found something.** All six capabilities exist as
dedicated modules and all six are wired. What none of them did was leave a record when they
WORKED. Measured 2026-09-06 across every retained log: the sandbox is assembled and probed
on every boot — 812 assemblies, 814 probes and climbing — and has **run once**. Nothing
recorded how that run ended, because the only outcome logged below INFO was success.

## Model — two cages, deliberately not the same cage

The map's one-line summary lumps the capabilities together. They are split across two
backends on a security argument, and confusing them is the main risk to a reader.

| | `BwrapSandbox` — **primary** | `DockerSandbox` — network tier |
|---|---|---|
| selected when | always, unless the code needs network | `spec.network` true, or bwrap unavailable |
| privilege model | rootless **user namespace** | **rootful** daemon |
| seccomp | **none, deliberately** | `--security-opt seccomp=<profile>`, **mandatory** |
| network | `--unshare-net`; `network=True` is REFUSED | `--network=none` default, `bridge` on opt-in |
| resources | cgroup-v2 `memory.max` + `pids.max` | `--memory` / `--memory-swap` / `--cpus` / `--pids-limit` |
| env | `--clearenv` then allowlist only | no host env, allowlisted names forwarded |
| privilege drop | `--unshare-all`, `--cap-drop ALL`, no setuid | `--cap-drop=ALL`, `no-new-privileges`, non-root `--user` |

**Why bwrap has no seccomp filter and that is not a hole.** `docker.py` states the argument
in its own header: the host's Docker daemon is rootful, so a container escape could reach
host root, "which makes the restrictive seccomp filter load-bearing and MANDATORY here
(unlike the rootless bwrap backend, **where a userns already contains an escape**)". Two
different threat models, two different mitigations. A reader who takes "we have seccomp" as
a property of every run will draw the wrong conclusion about the primary path.

Shared caps (`limits.py`): `DEFAULT_MEM_MIB = 2048`, `DEFAULT_PIDS = 256`,
`DEFAULT_WALL_TIME_S = 30`, `MAX_CONCURRENT_SANDBOXES = 3` — the governor's bound exists so
N concurrent runs cannot exceed N × 2048 MiB and OOM the host.

## Lifecycle

```
execute_code
    │
    ├─ consent ──▶ DENY (27 historical) or ONCE
    │              since ESC-150 an unattended CONFINED run is auto-granted
    ▼
SandboxSelector.select(spec)
    ├─ network requested ──▶ Docker      ("chose Docker (network requested)")
    ├─ bwrap available   ──▶ bwrap       ("chose bwrap (rootless primary)")
    ├─ bwrap unavailable ──▶ Docker      ("chose Docker (bwrap unavailable, no-network)")
    └─ neither           ──▶ REFUSE      ("no sandbox backend available")
    ▼
backend.run(spec)
    ├─ scratch made, code written, PTC channel started (optional)
    ├─ argv built (bwrap+cgroup scope, or hardened docker run)
    ▼
  outcome ──┬─ wall-time exceeded  ── INFO
            ├─ cgroup recipe refused ── ERROR   (caps-or-refuse)
            ├─ OOM-killed           ── INFO
            ├─ killed by signal     ── INFO
            └─ completed            ── INFO   ← was DEBUG until 2026-09-06
    ▼
  finally: container `docker rm -f` / scratch removed; cgroup scope reaped by systemd
```

**Ordering is behaviour**: the network check precedes availability, so a network-requiring
spec never silently lands on the no-network backend.

## Invariants

The seven `SandboxBackend` invariants, as both backends' docstrings state them:

1. **Never un-isolated.** Every run goes through a cage; any setup failure REFUSES with a
   structured `ExecResult` rather than degrading to a bare host process — "that is what
   `shell` already is".
2. **Caps-or-refuse.** Every cap in `spec.caps` is enforced or the run refuses. On bwrap the
   cgroup recipe exits non-zero if a mandatory cap cannot be written.
3. **Deny-all network** unless explicitly granted, and bwrap refuses `network=True` outright.
4. **Env allowlist-from-empty** — the child inherits nothing; only `spec.env_allow` names cross.
5. **Never raise** — every failure is a structured `ExecResult`.
6. **No host FS** — a minimal read-only runtime plus the run's own RW scratch; `/home`,
   `~/.stackowl` and `/etc` are absent.
7. **No privilege escalation** — rootless userns, or cap-drop + no-new-privileges + seccomp.

**I8 (added by this item).** A run that COMPLETES is recorded at INFO, naming the backend
and the caps it enforced. Invariants 2 and 7 are otherwise assertions rather than evidence:
a `caps_applied` that nothing prints cannot be checked at 2am.

## Configuration

| Key | Type | Default | Hot reload | Notes |
|---|---|---|---|---|
| `sandbox.bwrap_enabled` | bool | `True` | yes | False ⇒ Docker-only |
| `sandbox.docker_enabled` | bool | `True` | yes | False ⇒ bwrap-only; network code refuses. **Docker here is rootful — disable for the tightest blast radius.** |

If both are false, code execution is unavailable and the selector says so. There is no
"unconfined" setting, and adding one would break invariant 1.

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| A mandatory cap cannot be written | cgroup recipe exit code | REFUSE — never a mis-reported ok | "the sandbox refused" with the cap named |
| Memory cap breached | cgroup `oom_kill` counter | `reason="oom"` | "exceeded its memory cap" |
| Run exceeds 30s | wall-time kill | process tree terminated | "wall-time exceeded" |
| bwrap missing | boot capability probe | selector routes to Docker | nothing — transparent |
| Both backends unavailable | selector | structured refusal | "no sandbox backend available" |
| Container or scratch leaks | `sandbox_sweep`, every 10 min | reaped after `SANDBOX_ARTIFACT_TTL_S` | nothing |

**The honest ratio, and it is the failure mode that matters most.** D06.1 measured
`execute_code` at **1 allow / 27 deny**, every refusal "always-ask and no human is
attached", while `shell` — unconfined by design — ran 205 times and launched an interpreter
33 detected times. All of this depth is aimed at roughly 0.5% of the code this platform
executes. That is the cost of the maximum-autonomy model rather than a defect, and ESC-150
(2026-09-05) is the change that lets the confined path be reached unattended at all.

## Verification

```bash
# 1. The subsystem's own suite.
uv run pytest tests/sandbox -q
#    expect: 0 failed
#    (A SHAPE, NOT A COUNT. This step runs over a whole package, so any new
#     test anywhere falsifies a pinned number — the document would rot as a
#     side effect of the programme working. Measured 2026-09-06: this line
#     read 172 passed and the truth was 172 — right only because nobody had added a sandbox test.)

# 2. Both binaries present on this host.
uv run python -c "import shutil; print('bwrap', shutil.which('bwrap'), '| docker', shutil.which('docker'))"
#    expect: both paths, not None

# 3. Live — assembled constantly, RUN once, and the GC runs.
./scripts/log_since.sh 2026-08-28 'sandbox.capability] probe: exit'   # rises per boot
./scripts/log_since.sh 2026-08-28 'chose bwrap'                       # 1
./scripts/log_since.sh 2026-08-28 'chose Docker'                      # 0
./scripts/log_since.sh 2026-08-28 'no sandbox backend available'      # 0
./scripts/log_since.sh 2026-08-28 'sandbox_sweep.execute: exit'       # 1247
```

**Measured 2026-09-06:** 172 passed; both binaries present; probe 814, then 1 / 0 / 0 /
1247. The probe count is deliberately NOT pinned to a number — it increments on every boot
(it read 813 and then 814 minutes later during this very verification), so a fixed
expectation there would be stale before the next reader ran it. What must hold is the
SHAPE: the probe fires every boot, exactly one backend choice has ever been made, none
were Docker, and no boot has ever found itself without a backend.

**The closing query for I8 is OPEN**, and honestly so — the INFO line shipped today and the
single historical run predates it:

```bash
./scripts/log_since.sh 2026-09-06 'sandbox.bwrap] run: exit'   # 0 today
```

A confined run must occur before this can return anything. That is the same shape D06.1
recorded: the cage works and is almost never reached.
