## Why this exists

Two things arrived at the same seam and must be done in one pass.

**One:** `MemoryBridge` serves two masters. A **live conversation half** — `store`,
`retrieve`, `recent_conversation_turns`, `clear_session`, `health` — that is load-bearing
in `turn_persist` and `classify` every single turn. And a **dead fact half** — `stage`,
`recall`, `delete`, `list_staged`, `find_committed_by_prefix` — left behind by the
extraction pipeline D08.1 retired. 31 files outside `src/stackowl/memory/` name the
bridge — though see the Design section, where measurement showed only **3** of them
actually use the live half and **none** use both.

**Two:** the last live consumers of `fact_promoter` are the three channel approve/reject
callbacks (telegram 185 lines, slack 145, discord 114), and those callbacks sit *inside the
same orchestrator try-blocks as consent and clarify*. Breaking that block breaks consent
buttons on every channel at once. D08.1 stopped deliberately at this boundary rather than
open it in a session tail.

So `fact_promoter`, `contradiction_detector`, `pruner`, the DreamWorker's five phases and
the three callbacks travel together, and the orchestrator block is opened **once**,
carefully, with a consent smoke test after.

## What the reference platform actually does

Read from `agent/memory_provider.py` (315 lines), `agent/memory_manager.py` (1,241),
`tools/memory_tool.py` (1,258) and `plugins/memory/`, which ships eight providers —
byterover, hindsight, holographic, honcho, mem0, openviking, retaindb, supermemory.

A single `MemoryProvider` ABC with a declared lifecycle:

| hook | when | required |
|---|---|---|
| `name` | identity | yes |
| `is_available()` | at init, decides activation — *"should not make network calls"* | yes |
| `initialize(session_id, **kw)` | once at startup; may create resources | yes |
| `system_prompt_block()` | prompt assembly — **static text only** | no |
| `prefetch(query, session_id)` | before each call, returns recall text | no |
| `queue_prefetch(...)` | after a turn, warms the next one | no |
| `sync_turn(user, assistant, ...)` | after each turn, non-blocking write | no |
| `get_tool_schemas()` / `handle_tool_call()` | model-facing surface | schemas yes |
| `on_turn_start` / `on_session_end` / `on_session_switch` / `on_pre_compress` / `on_delegation` / `on_memory_write` | opt-in hooks | no |
| `get_config_schema()` / `save_config()` | setup UX | no |
| `backup_paths()` | extra paths for backup | no |
| `shutdown()` | clean exit | no |

**The two design decisions worth stealing, and why:**

1. **One external provider at a time, enforced by the manager** — the docstring says
   plainly it exists *"to prevent tool schema bloat and conflicting memory backends."*
   That is Law 2 applied to memory: eight providers may exist, but only one may put tools
   on the wire. A memory subsystem that lets every backend register schemas grows the waist
   by exactly the amount Law 2 forbids.

2. **`system_prompt_block()` is STATIC, and recall is a separate `prefetch()`** — stated
   explicitly: *"This is for STATIC provider info... Prefetched recall context is injected
   separately."* This is Law 1, discovered independently. StackOwl paid for the same lesson
   in D01.1, where per-turn `memory_context` was measured as the single largest source of
   prompt instability. Their interface has the split baked into its shape so a provider
   author cannot get it wrong; ours enforces it by where the call site sits.

## What StackOwl already has

Checked before proposing anything, per the standing rule.

- **A whole plugin subsystem already exists** at `src/stackowl/plugins/`: `registry.py`,
  `manifest.py` (`PluginManifest`, pydantic), `local_loader.py`, `remote_install.py`,
  `verify.py` (`PluginVerifier`, signature checks), `capabilities.py`, `context.py`,
  `index.py`. **D08.2 must extend this, not build a second plugin mechanism** — that would
  be the exact duplication `X4` and PROCESS.md's anti-duplication rule exist to prevent.
- **The curated two-file memory from D08.1 is already the `builtin` provider in all but
  name** — it has a static prompt block, a tool surface, budgets and a frozen snapshot.
- **`MemoryBridge` already has the seam**, it is simply not drawn: the live half and the
  dead half are separate method groups on one class.

## Design — SETTLED

**Footprint ladder: rung 1 (extend existing code) for the split, rung 4 (plugin) for
providers. Explicitly NOT rung 6 — no new core tool.** The existing `memory` tool stays the
single model-facing surface and providers contribute behind it, so the waist does not grow
however many providers ship. 77 tools are already registered; that number is the reason
the cap below counts what plugins ADD rather than the total.

**Law 1 holds** because the active provider set and its tool schemas are resolved ONCE at
session start and frozen for the incarnation. Nothing about memory changes the toolset or
the system prompt mid-conversation. This is the same shape D08.1 used for its curated
snapshot, and the same one the reference platform reaches by splitting a static
`system_prompt_block()` from a volatile `prefetch()`.

**Law 2 holds** because provider-contributed schemas are capped at 6, enforced centrally,
and a surplus provider is REFUSED at activation rather than silently dropped.

### Slice A — draw the line inside MemoryBridge

Split the protocol into a live `ConversationStore` and the fact half, then repoint the
readers. Does not touch the orchestrator, so **ESC-1 does not block it.**

| File | Change |
|---|---|
| `src/stackowl/memory/bridge.py` | split the protocol; live half is `store`, `retrieve`, `recent_conversation_turns`, `clear_session`, `health` |
| `src/stackowl/memory/sqlite_bridge.py` | widen `_trim_turns` beyond `source_type='conversation'` |
| `src/stackowl/tools/knowledge/memory.py` | `search` repointed at the curated files, substring |
| `src/stackowl/brief/assemblers.py` | drop the `recall` and `list_staged` call sites |
| `src/stackowl/tools/browser/tools.py` | drop the `recall` call site |

**MEASURED 2026-08-14, and it corrects this document's own opening figure.** Of every file
outside `src/stackowl/memory/` that names the bridge: **3** use only the live half
(`turn_persist`, `classify`, `commands/reset` — all now moved), **11** use only the dead
half, **16** merely mention it in annotations, and **0 use both**.

The halves were already disjoint at file level, so the split costs 3 files, not 31. The
"31 files, so this cannot be done casually" framing under *Why this exists* counted files
that MENTION `MemoryBridge`, which is a different question and overstated the work by an
order of magnitude. Seam-by-seam was still the right method — it is how the disjointness
was discovered rather than assumed — but the caution it was bought with turned out to be
unnecessary here.

### Slice B — the orchestrator block, opened once

**Seams 1-2 DONE 2026-08-14; seam 3 blocked on ESC-4.** ESC-1 is resolved and the consent
suite is green, which was the gate.

- **Seam 1** — Telegram's handler (185 lines), which turned out to have no constructor
  anywhere: never registered, zero risk.
- **Seam 2** — the wired Slack (145) and Discord (114) handlers, their orchestrator wiring,
  and `_SlackMemoryBridgeComposite`, which existed only to feed them. Both blocks excised
  cleanly: consent and clarify register as separate statements *before* the memory lines, so
  the shared try-block was never logically entangled — only positionally.
- **Seam 3** — `fact_promoter`, `contradiction_detector`, `pruner` and the DreamWorker's
  five phases. BLOCKED: this document and `progress.yml` both said the callbacks were the
  promoter's last consumers. They are not. `tui/widgets/memory_review_panel.py` calls
  `force_promote` — a fourth approve/reject surface, unreachable in production but with
  tests inside Story 8.5's overlay suite. See ESC-4.

The consent suite was measured either side of every seam: 95 before, 95 after seam 1, 104
after seam 2. That was the discipline the whole slice existed to justify.

### Slice C — MemoryProvider as a plugin kind

`PluginManifest.type` gains `"memory_provider"` — one added value to a frozen `Literal`,
after which the existing loader, verifier, index and remote-install path apply unchanged.
A separate memory-provider registry was rejected as the parallel-mechanism duplication
PROCESS.md forbids.

- Several providers may be installed; the active set is resolved once per session.
- Provider-contributed tool schemas are capped at **6** in total.
- Over the cap ⇒ the surplus is REFUSED at activation and logged at INFO. Never a silent drop.
- D08.1's curated memory is registered as `builtin`: **exempt from the cap and
  non-removable.** It is expressed through the interface so the interface is exercised by a
  real implementation, but it can never be deactivated — D08.1 shipped the two files as a
  guarantee, not an option.

### What is deliberately NOT done

`recall()` keeps working over `committed_facts`; the table stays present and empty because
a table that returns nothing is honest while a missing one errors at every call site. What
changes is that nothing user-facing depends on it any more.


## Invariants

Numbered and testable. Each needs a test before the item closes; **I5 must exist FIRST**,
because it is the only one that guards the slice B edit.

> **I1.** Provider-contributed tool schemas never exceed the ceiling (default 6). The
> built-in curated memory is exempt and is not counted.
>
> **I2.** The active provider set and its tool schemas are resolved once per session and do
> not change for the life of that incarnation. (Law 1.)
>
> **I3.** A provider whose schemas would breach the ceiling is REFUSED at activation and the
> refusal is logged at INFO. It is never silently dropped, and never partially loaded.
>
> **I4.** A provider that raises never costs the user a reply — memory degrades, the turn
> completes.
>
> **I5.** Consent and clarify behaviour on all three channels is unchanged before and after
> slice B.
>
> **I6.** The built-in curated memory cannot be deactivated by any configuration.
>
> **I7.** Every row in `staged_facts` is subject to a bound, whatever its `source_type` —
> not only `conversation`. (The gap measured during this item's brainstorm.)

## Failure modes — draft

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| a provider is unavailable at init | `is_available()` | it is not activated; `builtin` continues | nothing |
| a provider raises mid-turn | the call site's guard | log ERROR, continue without it | their answer, unaffected |
| slice B breaks a consent callback | the consent smoke test | **do not ship the slice** | — |
| two providers both claim active | the registry's one-active check | refuse to start the second, log ERROR | a clear startup error |
