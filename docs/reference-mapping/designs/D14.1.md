## Why this exists

The map's Ask: *"Add surface flags to our `CommandMeta`? Small change, removes per-channel
special-casing."* The reference platform's `CommandDef` carries `cli_only`, `gateway_only`
and a `gateway_config_gate` dotpath, so adding an alias there is a one-tuple change.

**The answer is no, and the reason is a measurement rather than a preference.**

## Model

One registry, and every consumer derives from it.

| Consumer | How it gets its list | Filters by surface? |
|---|---|---|
| Telegram menu (`build_bot_commands`) | passed the registry's commands | **no** — coerces names to Telegram's limits, drops duplicates |
| Slack slash bridge | reads the registry | no |
| `/help` | reads the registry, groups by `CommandMeta.group` | no |
| `find_command` | reads the registry | no |
| TUI autocomplete | `command_names` / `command_infos` from the registry | no |

`grep` for a hardcoded command list across `src/` — `KNOWN_COMMANDS`, `COMMAND_LIST`,
`_COMMANDS = `, `commands = [` — returns **nothing**. There is no second roster anywhere.

**So there is no per-channel special-casing to remove.** `cli_only` / `gateway_only` flags
would be a seat for a problem this codebase does not have, which is the dead scaffolding the
standing rule forbids. `CommandMeta` carries `grammar`, `subcommands`, `args`, `examples`
and `group`, and nothing has yet needed more.

## The rule that keeps the registry honest, and where it was one case short

`test_tier_meta.py` names it the "honesty guarantee": **the subcommands declared in meta are
exactly the ones `handle()` actually implements** — no fabricated extras, nothing
dispatchable left undeclared. It matters because the declaration is what `/help`, the
Telegram menu and autocomplete render; a meta that disagrees with the parser advertises
commands that fail and hides commands that work.

Measured 2026-09-06:

| | count |
|---|---|
| command classes | **34** |
| of those, declaring subcommands (where the rule means anything) | **14** |
| of those, carrying a `tests/commands/test_*_meta.py` guard | **13** |
| **uncovered** | **`preferences_command`** |

Nothing had gone wrong. `/preferences` declares `list` and `remove`, and `handle()`
dispatches exactly `remove`, `list` and bare-→-`list`. **That is why it went unnoticed:** the
rule was kept by thirteen people remembering to write a file, and a rule kept by memory is
one case short the moment someone forgets. Writing a fourteenth file would have left the
identical hole for the fifteenth command.

## Invariants

1. **Every command that declares subcommands has a meta guard.** Enforced structurally, by
   discovery, not by a roster — a hand-maintained list here would be the very thing this
   item abolishes.
2. **No command declares a duplicate subcommand name** — a shadowed name is unreachable.
3. **Every subcommand carries a summary** — it is what `/help` and autocomplete render.
4. **Declaring subcommands means `grammar == "verb"`** — the other grammars do not offer
   subcommands to completion, so they would be unreachable.

Invariants 2–4 hold across all 34 commands today; they are regression locks, hoisted from
the assertions the thirteen per-command files each made privately.

## Configuration

None. Commands are registered in `commands/assembly.py`; their metadata is declared on the
class. There is no flag, no allowlist and no per-channel gate.

## Observability

The registry is a boot-time structure, not a runtime event; its correctness is asserted by
tests rather than watched in logs. The Telegram menu derivation does log when it drops
something, and those two lines are the only place a command silently fails to appear:

| Line | Level | When |
|---|---|---|
| `[telegram] commands: dropped uncoercible command name` | WARNING | a name is empty after coercion |
| `[telegram] commands: duplicate command name skipped` | WARNING | two commands coerce to one Telegram name |

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| meta declares a subcommand `handle()` does not dispatch | the per-command guard | — | `/help` advertises a command that errors |
| `handle()` dispatches something undeclared | the per-command guard | — | a working command absent from help and autocomplete |
| A new command with subcommands ships with no guard | **`test_every_command_meta_is_guarded.py`** | — | nothing, until one of the two above happens |
| Two commands coerce to one Telegram name | `build_bot_commands` | second is skipped | one command missing from the Telegram menu |

**A known and deliberate exception.** `provider_command.py` documents eight subcommands
(`add-pick`, `add-token`, `add-model`, `add-tier`, `menu`, `edit-menu`, `edit-field`,
`model-add-execute`) omitted from its metadata tuple on purpose — internal steps of guided
flows, reachable only via generated buttons. Its own comment names the cause: *"there is no
`hidden` flag on `SubCommand`"*. That is a real gap in the metadata vocabulary and it is
**recorded, not built**: the omission costs nothing today (those steps are meant to be
unlisted, and the per-command guard is written against the declared set), and adding a
`hidden` flag would touch every consumer to serve one command. The trigger to build it is a
second command needing the same trick.

* **Prior art and where we diverge.** The reference platform's surface flags exist because
  its CLI and gateway genuinely dispatch different sets. Ours do not — every consumer
  presents everything the registry holds — so the flags would encode a distinction this
  platform has not made. If a command ever must be hidden from one surface, this is the
  shape to copy; until then it is a field nothing would set, and a feature ships ON or not
  at all.
