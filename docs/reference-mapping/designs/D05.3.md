## Why this exists, measured

Not a hypothetical. On this box, right now:

| | measured |
|---|---|
| tools registered | **77** |
| total schema cost | **18,061 tokens** |
| browser tools | **25** |
| browser schema cost | **2,652 tokens — 14% of the entire tool surface** |
| browser runtime in this process | **not running** |
| browser tools presented anyway | **all 25** |

Every turn pays 2,652 tokens to advertise a capability that cannot execute, and
invites the model to call it. That is the gap the map describes, quantified
without needing a synthetic scenario.

## What already exists — the item is a link, not a subsystem

`ADR-6`'s **`HealableResource`** (`infra/resilience.py:47`) is a Protocol with
exactly the four things this item needs:

```python
class HealableResource(Protocol):
    @property
    def available(self) -> bool: ...              # the gate
    @property
    def unavailable_reason(self) -> str | None: ...  # the reason
    async def ensure_available(self) -> None: ...    # the heal
    def register_on_recycled(self, cb) -> None: ...  # the invalidation hook
```

**Ten subsystems already implement it:** the browser runtime, the Telegram /
Slack / Discord / WhatsApp adapters, LanceDB, Kuzu, the embedding registry,
providers, the db pool, and the MCP client.

Health is further along still. `BrowserContributor.health_check()` already
returns `"unavailable: {reason}"`, and `health_sweep` already collects every
contributor periodically and already has a heal path.

**So the availability signal exists, the heal exists, and the invalidation hook
exists. The only missing piece is the link from any of them to tool
presentation.** This is the same shape as `D05.2`, where the usage signal had been
recorded for two months and only the consumer was missing — except that here it
was caught *before* designing rather than three corrections in.

## The design

```
 ToolManifest.requires_capability = "browser"
        │
        ▼
 infra/capabilities.get("browser")  ──►  HealableResource | None
        │                                      │
        │                                .available  ─────►  gate
        │                                .unavailable_reason ─►  why
        │                                .remedy (NEW, optional) ─►  fix
        │                                .ensure_available()  ──►  heal
        │                                .register_on_recycled ──►  invalidate
        ▼
 ToolPresentation  ──►  present / omit
 tool_search       ──►  list, annotated UNAVAILABLE + reason + remedy
 dispatch          ──►  refuse with reason + remedy
```

Resolution must be **lazy**: `ToolRegistry.with_defaults()` registers all 77
tools at import time, long before any runtime is constructed. Subsystems
self-register into `infra/capabilities` as the orchestrator builds them.

### Placement — voted, not chosen

`infra/capabilities.py`, beside `infra/resilience.py` which defines the protocol
it serves, and in the same layer as `hydrated_tools.py` and `presented_tools.py`.
Rejected: `StepServices` (pipeline-layer — `tools/` would reach *up* into the
pipeline to answer a presentation question) and `HealthAggregator` (holds
*status*, not the resources, so `ensure_available` and `register_on_recycled`
would be unreachable through it).

### Gating rules

1. **Gate on `available` only.** `HealthStatus` has three states but `available`
   is a bool, and *degraded* means working-but-slow. Hiding a working tool for
   being slow removes capability the agent could still use.
2. **Protected tools are never gated.** `_DEFAULT_BASE ∪ _DEFAULT_ALWAYS` are
   presented regardless. See the invariant and its stated cost below.
3. **Absent from the schema, present in `tool_search`.** Zero token cost, but an
   owl can still *discover* the capability and report what is blocking it. A
   capability an owl cannot see is one it can never ask to have enabled.
4. **Dispatch refuses.** A hidden tool is still dispatchable by name — that is
   how `tool_search` overflow stays callable — so the precondition is checked at
   dispatch rather than letting the tool's own code fail deep with an opaque
   error.

### Flake suppression — adopted wholesale, and we need it more

Hermes caches a check for 30s **and** suppresses a failure within 60s of the last
success, serving the last-good `True` and logging a warning. That grace window is
scar tissue: their incidents #21658/#5304, where one timed-out `docker version`
under load silently stripped a whole toolset mid-session and a `delegate_task`
subagent then reported *"Tool read_file does not exist."*

**StackOwl is more exposed than they are, not less** — our probes run on a Jetson
under load. Losing 25 tools to a single slow probe is exactly the silent
capability loss this repo has a standing rule against.

### Detection — push and poll, because neither covers both directions

| Event | Detected by |
|---|---|
| A resource is recycled | `register_on_recycled` — instant, free, no polling |
| A capability *appears* (API key added, Docker started) | `health_sweep` re-probe |

`register_on_recycled` fires on **recycle**, not on "became available for the
first time". Using it alone would mean adding an API key does nothing until
rollover; using only the poll would leave a built hook unused and make recycles
wait for the next sweep.

### Heal: at boot, everything, no consent

Operator decision, taken against the recommendation to gate large or `sudo`
installs behind consent. **Consistent with the tree rather than new risk:**
`browser_probe` already auto-fetches the 622 MB Camoufox binary at boot today
(`fetch_if_missing=True`), and the standing rule is that the agent installs heavy
dependencies itself. This extends existing behaviour.

Stated plainly so the cost is visible: **boot can now perform large downloads and
privileged installs without asking.**

## Invariants

> **I1.** A tool whose capability is unavailable is not in the presented schema —
> unless it is protected (`I2`).
>
> **I2.** Protected tools are never availability-gated. `_DEFAULT_BASE ∪
> _DEFAULT_ALWAYS` are presented even when their capability is down, so a probe
> bug can never leave an owl with an empty toolbox.
> **Stated cost:** with no network, `web_fetch` stays visible and will fail when
> called. That is the accepted price of the guarantee, not an oversight.
>
> **I3.** Nothing becomes unreachable. A gated tool remains listed by
> `tool_search` with its reason, and remains dispatchable — dispatch refuses with
> the reason rather than the tool vanishing from the world.
>
> **I4.** A transient probe failure never strips a tool. Within the grace window
> of a recent success, the last-good verdict is served and the failure is not
> cached.
>
> **I5.** An availability change invalidates `D05.2`'s presented-set memo. Without
> this the gate would be evaluated once per session and a newly-configured
> capability would not appear until rollover.
>
> **I6.** Gating is **presentation and precondition, never authorization**.
> `compute_effective_bounds` remains the only access-control boundary. An
> available tool is not thereby permitted; an unavailable one is not thereby
> denied.

## Blast radius — measured, and smaller than "map everything" sounds

The operator chose to map **every** capability rather than browser alone. I
flagged that a Kuzu/LanceDB blip could then hide the agent's memory tools,
against the standing rule about never silently disabling features. Measured

## Configuration

**None added.** The TTL and grace window ship as module constants, mirroring

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| Probe flaps under load | grace window | Last-good verdict served, warning logged | Nothing |
| Probe genuinely down past the grace window | — | Tools gated, reason surfaced | The agent reports the blocker and its remedy |
| Capability appears mid-session | `health_sweep` | Memo invalidated, tool presented next turn | The tool starts working |
| Capability recycled | `register_on_recycled` | Memo invalidated immediately | Nothing |
| **Memo not invalidated on a flip** | — | **Not detected.** The gate is evaluated once per session and a new capability never appears | "I added the API key and nothing happened" |
| **A capability name with no registered resource** | — | Must fail OPEN (present the tool), not closed | Nothing — a typo must not silently delete a toolset |
| Boot heal downloads 622 MB on a metered link | — | **Not prevented** — consent was declined by decision | A slow first boot |

The fail-open row is load-bearing: a misspelled `requires_capability` must
present the tool, never hide it. Fail-closed would turn a typo into a silently
missing toolset, which is the exact class of bug this item exists to end.

### THE ITEM WAS INERT ON THIS BOX, and only the restart showed it

The most important thing validate found, and a green suite would never have.

`resolve()` fails **open** on an unregistered name — correct, and the reason a
typo cannot delete a toolset. But the orchestrator registered the browser
capability only *inside* the branch that constructs the runtime, and **the
gateway role skips that branch**. So on this box the gateway registered nothing,
gated nothing, and presented all 25 browser tools.

**The gate was correct, wired, fully tested — and completely inert.**

Fixed by registering an `_UnavailableCapability` stub on the skip path. "There is
no browser in this process" is a real availability verdict and has to be stated
as one; fail-open is for names nobody has an answer for, not for ones we do. Its
`ensure_available()` raises rather than pretending to heal, because a process
that does not host a subsystem cannot start it and a silent success would report
a repair that never happened.

### What is proven live, and what is not

**Proven:**

- the corrected skip message — `browser runtime skipped — this process runs the
  gateway role; the browser is hosted by core` — which no longer contradicts the
  probe's `binary=True` two lines earlier
- `[presented_tools] capability changed — dropping every memoized tool array`:
  the registration fired and the capability → memo invalidation chain works **end
  to end in production**

**Not proven: the gating itself.** Zero turns have run since the restart, so no
schema has been built and `[capabilities] resolve: capability UNAVAILABLE` has

### Prior art, and where we deliberately diverge

Hermes gates with a per-tool `check_fn` predicate, TTL-cached on the function
object, plus a declarative `requires_env` list. A failing check makes the tool
**absent from the schema entirely**.

**Adopted:** the shape (absent, not annotated), the TTL, and — most valuable —
the **60-second failure-grace window**, which is the part their code comments
show was learned from an outage rather than designed up front.

**Diverged:**

1. **A capability name, not a callable.** They have no availability layer to
   point at, so each tool carries its own predicate. We have ten
   `HealableResource` implementations already reporting exactly this, so 25
   hand-written browser callables would be 25 wrappers around an existing fact.
2. **We keep gated tools discoverable.** They disappear entirely; ours remain in
   `tool_search` with their reason. This matters because StackOwl owls are
   expected to *extend themselves* — an owl that cannot see a capability can
   never ask for it to be enabled, which their single-agent design never needs.
3. **We heal.** Their `check_fn` only reports. `ensure_available()` already
   exists on all ten of our resources, so an unavailable capability can attempt
   its own repair rather than staying unavailable until a human notices.
4. **A reason and a remedy, not a bool.** A direct consequence of (2): a tool the
   model can still see needs to explain itself.

**Not copied:** `requires_env`. A declarative env-var list is a second, weaker
availability mechanism next to the one we already have, and `HealableResource`
subsumes it — a subsystem that needs an env var can report that as its reason.

### How the two Laws hold

**Law 1 — per-conversation prompt caching is sacred.** Gating changes the tools
array, which `D05.2` just stabilised, so it is bound to the same seam: the gate
is evaluated when the memo is built, and an availability change invalidates it.
The array still changes only for a real, caused reason.

**Law 2 — the core is a narrow waist.** No new model-facing tool. `tool_search`
already exists and gains an annotation, not a sibling.
