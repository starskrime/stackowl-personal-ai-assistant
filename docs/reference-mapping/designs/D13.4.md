## Why this exists

The reference platform ships `acp_adapter/`, an ACP server letting VS Code, Zed and
JetBrains drive the agent, with its own auth, edit approval, permissions, provenance and
event model. The Ask: *"Is coding-in-editor part of the vision, or is StackOwl a life/ops
assistant?"*

**That is vision, and it is not answered here.** What the measurement can do — and what an
answer should rest on — is say what this platform actually does with its hands today.

## Model — 29,142 tool uses, and what they were

Measured 2026-09-06 from `task_outcomes.tool_sequence`, the same store the platform's own
`usage_report` reads: **84 distinct tools, 29,142 total uses.**

| Group | Uses | Share |
|---|---|---|
| **Research** (`web_search` 9,831 + `web_fetch` 6,850) | **16,681** | **57%** |
| **Coding tools, all of them** | **4,788** | **16.4%** |
| everything else (memory, browser, tool_search, lessons, delivery, …) | 7,673 | 26% |

And the coding group does not mean what the label suggests:

| Tool | Uses | What it is |
|---|---|---|
| `shell` | 3,088 | running commands — ops |
| `read_file` | 942 | reading — ops or research |
| `search_files` | 453 | reading |
| `write_file` | 228 | authoring |
| `execute_code` | 42 | confined execution (see D06.1) |
| `apply_patch` | 20 | authoring |
| `edit` | 10 | authoring |
| `claude_code` | 4 | delegating to a coding agent |
| `run_tests` | 1 | authoring workflow |
| `git` | **0** | never invoked, ever |

**Authoring — the thing an editor integration exists to serve — is 258 uses, 0.9% of all
tool activity.** `git` has never been called once. `claude_code`, the one tool whose entire
purpose is driving a coding agent, has four uses.

So the platform reads, searches the web, runs shell commands and remembers things. It edits
files rarely and versions them never.

## The instrument, because the obvious query was wrong twice

This number was hard to get right and the wrong versions were confident:

1. **`grep '"tool": "X"'` over the logs** put `run_claude_code_demo` top — a tool the
   platform's own report lists as NEVER INVOKED. The field name was right and the line
   type was wrong: they are `registry.register: thin tool description` warnings, not tool
   invocations.

   **This document's first account of WHY was itself unmeasured, and it was wrong.** It
   said those lines were "emitted at boot for every registered tool". Re-measured
   2026-09-06: every one of the 640 such lines carries the SAME message and names
   **exactly one tool**. The warning fires for a tool whose description is too thin for
   `tool_search` to rank — not for every tool — so the count is ONE dead tool multiplied
   by 640 boots, not many tools multiplied by a few.

   That correction matters more than the arithmetic. Read the first way, 629 was boot
   noise to be ignored. Read correctly, it is a single learned tool with zero invocations
   in 29,142 recorded tool uses, occupying a slot in the presented set and announcing
   itself on every boot since June — which is precisely the accumulation
   `LearnedToolLoader` was built to make visible, and whose retirement it deliberately
   leaves to the operator. The lesson generalises: **when you catch your instrument
   lying, measure the lie too.** Explaining a wrong number with a guess produces a second
   wrong number that is harder to spot, because it now arrives wearing a correction.
2. **`[pipeline] execute: tool dispatch ok`** returned **0**, because it is logged at DEBUG
   (`execute.py:2314`) and production runs at INFO. The logs cannot answer this question at
   all.

The authoritative source is the store — `task_outcomes.tool_sequence` — which is exactly
what `usage_report` reads, and its own SQL carries `owner_id = ?` because "the scope changes
the ANSWER, deliberately: a tool used only by another principal now reads as never-invoked
for this one."

## Invariants

1. **Tool usage is counted from the store, never from the logs.** The dispatch line is DEBUG
   and the registry lines mention every tool name on every boot.
2. **A capability's presence is not its use.** Nine coding tools exist; one of them accounts
   for 64% of the group and `git` for none of it.

## Observability

No change. Note for a future reader: if per-tool usage ever needs to be answerable from logs

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| Counting tool usage from the logs | nothing — it returns a confident wrong number | use `task_outcomes.tool_sequence` | — |
| Reading "coding tools: 16.4%" as "it codes" | — | read the split: 3,088 of it is `shell` | — |

## Verification

```bash
# The authoritative count, from the store the platform's own report reads.
uv run python -c "
import sqlite3
from stackowl.db.pool import default_db_path
c = sqlite3.connect(str(default_db_path()))
rows = c.execute('SELECT je.value, COUNT(*) FROM task_outcomes t, json_each(t.tool_sequence) je '
                 \"WHERE t.tool_sequence NOT IN ('', '[]') GROUP BY je.value ORDER BY 2 DESC\").fetchall()
d = dict(rows); tot = sum(d.values())
auth = sum(d.get(k, 0) for k in ('write_file','apply_patch','edit'))
print('total', tot, '| authoring', auth, '| git', d.get('git', 0), '| claude_code', d.get('claude_code', 0))"
#    expect: total 29142, authoring 258, git 0, claude_code 4

# The trap: the log-based count is wrong, and this is what it says. Note the GLOB —
# stackowl*.jsonl is every retained day; stackowl.jsonl alone is only today, and the
# two differ by an order of magnitude. A count is not a count until its window is
# stated, which is the same lesson DEBT-125 paid for with a date bound.
# SHAPE, NOT A PINNED COUNT. This number grows by one on every boot, so an `expect:
# 629` goes stale by simply leaving the platform running — it read 640 three days later.
# What is stable, and what the trap actually is, is that the lines are ALL one message
# about ONE tool.
grep -ah '"tool": "run_claude_code_demo"' ~/.stackowl/logs/stackowl*.jsonl \
  | grep -c 'thin tool description'
#    expect: the same count as the line above it — every hit is the WARNING, none is a
#    tool invocation, for a tool the platform's own report lists as never invoked
```

**Measured 2026-09-06:** total 29,142; authoring 258; `git` 0; `claude_code` 4; the log trap
returned **629** across the full glob (and 26 for today alone — the first draft of this
very command used the narrow one and disagreed with its own prose). **Re-measured
2026-09-06: 640, every one of them the thin-description WARNING, naming exactly one
tool** — which is why the expectation above is now a shape rather than that number.

## Decision

**Not built, and the decision is escalated rather than defaulted — under ESC-152, not as a
new entry.** An ACP server is surface #4 by another name, and ESC-152 already asks "do you
want a non-terminal surface, and if so which?". An editor plug-in is one specific answer to
that question, so it belongs there with this measurement attached rather than as a second
place to decide the same thing.

What the measurement says, stated plainly for whoever answers it: **an editor integration
serves authoring, and authoring is 0.9% of what this platform does.** That is not an
argument that coding does not matter — 4,788 coding-tool uses is real work — but the shape
of that work is *reading and running*, which an editor does not improve, rather than
*writing in a project*, which it does.
