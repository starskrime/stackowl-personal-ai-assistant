## The measured gap

Over the retained window: **219** feedback classifications — 203 neutral, 3
positive, and **17 NEGATIVE at 0.9–1.0 confidence**. They produced **8 preference
notes and zero procedural knowledge**. All 17 fall on 2026-08-28 between 00:17 and
05:25: one long dissatisfied session from which the platform learned nothing
reusable.

## Why the map's Ask cannot be answered as written

The Ask is *"adopt the prompt design directly?"* — and it cannot be a copy-paste,
because the two systems trigger from different **inputs**:

* **Ours** — `skills/synthesizer.py` clusters `TaskOutcomes` by exact
  `tool_sequence`. The input is *what the agent did*.
* **Theirs** — `agent/background_review.py` reviews the **conversation**. The
  input is *what the user said*.

A prompt that says "user corrected your style, update the relevant skill" has
nothing to read when its input is a tool-sequence cluster. D09.2 therefore needs a
vehicle that sees conversations.

## The vehicle, and why not the others

**Chosen: the rollover-summary handler.** It already runs once per conversation
boundary, off a durable job row on the existing scheduler, and it already reads
the full transcript and makes exactly one standard-tier call with it. That is the
same position as the reference's `on_session_end`, on a loop that already exists —
which is what the standing "find the existing loop and extend it" rule requires.

Rejected: D09.1's background review fork is the faithful port but is **blocked on
ESC-41**; routing feedback into the synthesizer keeps the wrong input.

## The cost decision, stated plainly

The transcript is **already being sent** on that call. So the review is added to
the EXISTING prompt as one more field in the JSON it already returns, and costs
**output tokens only — no additional API call**. A separate review call would have
cost roughly 43 extra standard-tier calls a day at current rollover volume. Given
the standing concern about burning tokens, that was not a close decision.

**The summary must not be able to regress.** The new field is OPTIONAL: if it is
absent, empty, or unparseable, `_parse_summary` behaves exactly as before. The
summary path has 273 staged artifacts behind it and is not being put at risk to
add a second feature to the same call.

## Positive framing — the operator's condition

The reference prompt's primary signal is user frustration, which collides with the
standing rule that self-learning stores **wins, never failures**. Bakir's
resolution: store the **corrected behaviour**, never the correction.

    NOT   "was too verbose in the VPN explanation"
    BUT   "answer directly; no preamble"

The prompt therefore asks for an instruction to a future session, phrased
positively, in the imperative — never a description of what went wrong.

## Scope of THIS slice, and what is deliberately left

**In:** extraction of the corrected behaviour at the session boundary, INFO
evidence, and persistence to the owl's curated memory — which is injected into the
system prompt every turn, so the next session genuinely starts already knowing.

**Out, and named rather than implied:** writing a `SKILL.md`. The synthesizer's
skill-write path is `security_scan_gate → consent → write → store.upsert`, a
consent-gated pipeline that is its own build. Routing corrections into it is slice
2. Shipping slice 1 to curated memory is not a substitute for that — it is the
half that changes behaviour without touching a gated write path from a background
job.
