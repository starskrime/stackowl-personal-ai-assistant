## Why this exists

`D01.2` placed the prompt-cache markers and `D01.3` measured that the **tools array**
moves anyway. On the Anthropic wire `tools` renders at position 0, so an array that
varies between turns of one conversation invalidates every downstream breakpoint. This
item was originally "Progressive tool disclosure" — the reference platform's mechanism
for deferring non-core tools. That mechanism **provably cannot fire here** (tools are
2.87% of a 262,144-token window against a >10% trigger, and it defers only MCP and
plugin tools while zero plugins are installed), so Bakir re-scoped it on 2026-08-21:
**give the presented tool array one owner.**

The re-scope rested on a measurement — "the array changes 13 times a day across four
lanes". **That measurement was wrong, and this document is largely the correction.**
The instrument that produced it compares arrays across a boundary where no shared
prefix ever existed, so it reports an invalidation of a cache that was never held.

## Model

Three identifiers decide what "the array changed" can even mean. Confusing them is the
whole defect, so they open the document.

| Identifier | What it names | Lifetime | Shares a cached prefix? |
|---|---|---|---|
| `session_key` | the **lane** — a chat, a goal, a durable task target | forever | **No.** Many conversations, many owls, many non-conversational runs share one. |
| `conversation_id` | the **conversation** (D01.7 incarnation), minted at ingress | until reset/rollover | **Yes.** This is the unit a provider-side prompt cache is held across. |
| `trace_id` | one turn, or one retry of one turn | one turn | No — it is finer than the cache. |

`PipelineState.conversation_id` is `""` for turns that never passed through ingress. Its own
field comment states the rule this item needs: *"they have a lane but no conversation
run, and saying so honestly beats inventing one."* Scheduler handlers, retry-queue runs,
self-heal `-fix` runs, goal execution and delegated children all carry `""`.

### Who owns the array

`ESC-18` recorded that "three mechanisms decide which tools the model sees, none of them
owning the question". Measured, that is not right. `to_provider_schema` has exactly **two
production callers, both in `execute.py`**, and they are the two branches of one
`if restrict_to is not None`. A single owner already exists.

| Branch | Fires when | Path | Memoized | Observed size |
|---|---|---|---|---|
| **A — plan** | `state.task_envelope` set, or `banned_capabilities` non-empty, or a bounded owl with no DNA profile | deterministic `select()` | no | 6–7 tools |
| **B — budget** | otherwise | ranked + greedy-fit, capped at `tool_count_cap` | yes (`presented_tools`) | 22–36 tools |

The owner's *result* is a pure function of its arguments. One argument is not stable
across turns: `budget.fixed_cost_tokens` is `est(system_prompt) + est(every history
message)`, which grows every turn. `to_provider_schema`'s own docstring says so — *"the
caller memoizes the result rather than this method pretending to be pure across turns it
cannot see."*

**That is the design flaw in one sentence: an input that changes the RESULT is not in the
memo KEY.** The memo is therefore not a cache — it is the sole holder of the stability
invariant, while `infra/presented_tools.py` documents losing it as *"never a correctness
issue"*.

## Lifecycle

```
turn ─► execute._run_with_tools
         │
         ├─ restrict_to ?  ── yes ─► to_provider_schema(select)      ── branch A
         │                            (never memoized)
         └─ no ─► make_key(session_key, owl, provider, protocol,
                           window, hydrated)
                     │
                     ├─ hit  ─► serve memo             (ignores the budget entirely)
                     └─ miss ─► rank + fit(basis) ─► put()
                                        ▲
                                        └── budget_basis(key, measured):
                                            stamped on the first tool turn,
                                            reused after ⇒ the miss reproduces
                                            the hit
         │
         └─► audit_tools_stability(session_key, schemas, owl, conversation_id=…)
                                   ◄── compares within one CONVERSATION;
                                       silent when there is no conversation_id
```

Before D05.4 the miss path read the turn's own `fixed_cost`, which grows every turn and
was not in the memo key — so the memo was the only thing holding Law 1, and every wipe
was a capability change.

Priority order where several conditions fire on one turn, as the code has it:
`task_envelope` → `banned_capabilities` (rewrites `restrict_to`) → effective-bounds
narrowing (only when `restrict_to is None and profile is None`) → depth>0 spawn-tool
exclusion (applies to both branches, after).

The memo is dropped wholesale on any capability flip (`_on_capability_change`), on an
owl edit, and by LRU past 256 entries. The **basis** survives the first of those and not
the other two — see slice 2's lifetime table, which is where the fix lives.

### The budget has never bound here

Since the eviction message started naming the constraint that actually bound
(2026-08-21T13:44:11Z), **36 of 36 evictions were `tool_count_cap` and 0 were the token
budget.** A constant cap is stable across turns, which is why the array is stable in
practice despite the impure input **on this deployment**. It re-arms on any small-window
backend, which is exactly what `D04.1` is about.

That is why no window-relative **quantizer** was built: sizing machinery to a constraint
that has bound zero times here would repeat the mistake this item was re-scoped to
escape. What ships is smaller — the basis is stamped once and reused, so the miss path
does what the hit path already did. Writing that as a test first is what showed it was
not dormant at all: see slice 2.

### The envelope/budgeter split is not the defect

Recorded on 2026-08-21 as `THE_ACTUAL_CAUSE`: a turn with a planned envelope presents
6–7 tools and one without presents 23–36, inside a single lane. Both halves of that are
true and the conclusion does not follow. `task_envelope` is set only by
`task_runner`/`store`/`recovery`, and every one of those runs carries `session_id == ""`.
So branch A and branch B never alternate **within one conversation** — they alternate
within one *lane*, which is a bucketing artifact of the instrument, not a prefix
invalidation. Since ESC-29 the narrowing is also a real least-privilege boundary, so
presenting fewer tools on an enveloped run is correct rather than a Law 2 violation.

## The design

Three slices. Slice 1 ships first, because it is what makes slices 2 and 3 falsifiable.

### Slice 1a — key the audit on the conversation

`audit_tools_stability` takes `conversation_id` and keys on `(conversation_id, owl)`. An empty
`session_id` means there is no conversation and therefore no prefix to invalidate: no
comparison is made and nothing is logged.

This is the same fix the module has already applied once at the wrong granularity. Its
own comment records adding `owl` to the key because *"an audit that cries wolf on every
multi-owl lane trains its reader to ignore it"*. Lane-keyed, it cries wolf on every
multi-session lane and every non-conversational run: 121 of 122.

Nothing is lost. Per-run array sizes stay answerable from
`[pipeline] execute: context budget`, which carries `tools_count` at INFO on every turn.

### Slice 1b — report the delta, not two hashes

`_tools_hashes` stores the digest alongside the previous **name set**. The WARNING then
carries `added` and `removed` instead of `prev_hash`/`hash` alone, so the next real
event is self-diagnosing. Bounded: the entry is a set of ≤ `tool_count_cap` short
strings, in a map already capped at 512 entries (now conversations, not lanes).

### Slice 2 — a memo miss must reproduce the memo hit

**Written as a test first, and it went red.** The design above expected a pinned
invariant with no mechanism behind it, on the grounds that the budget has never bound in
production. That was true and it was not the whole question. With the real registry, the
real budgeter and only the AI provider mocked, at a 16,000-token window:

```
turn 1                                    66 tools
_on_capability_change("browser")          ← the production trigger, 62×/day
turn 2, history 40 messages longer        53 tools
lost: heartbeat_respond, mixture_of_agents, note_applied_lesson, objective,
      owl_schedule, pdf, process, read_logs, run_tests, search_files,
      send_message, session_search, sessions_send
```

A three-second subprocess bounce silently amputates thirteen capabilities mid-conversation,
`objective` and `send_message` among them. So a mechanism ships.

**`presented_tools.budget_basis(key, measured)`** stamps the fixed-cost figure on the
session's first tool turn and returns the stamp thereafter. The array is fitted against
the conversation's basis, not the turn's.

This changes **no behaviour on the hit path** — a memo hit already ignores the budget
entirely — so it is not a new policy, it is the miss path being made to agree with the
hit path. Chosen over two alternatives:

| Alternative | Why not |
|---|---|
| Quantise the basis into window-relative buckets | More machinery for a constraint that has bound 0 times in 36 measured evictions. Pinning is what the hit path already does. |
| Narrow `_on_capability_change`'s scope instead | Fixes the trigger, not the amputation. Any other invalidation — LRU eviction, restart, owl edit — would still shrink the array. |

Lifetimes are deliberately different, and that difference is the fix:

| Event | Memo | Basis | Why |
|---|---|---|---|
| capability flip (`_on_capability_change`) | dropped | **kept** | "this array may be stale", not "this conversation is over" |
| rollover / `clear(session_key)` | dropped | dropped | a new incarnation starts from a fresh history |
| owl edit (`clear_owl`) | dropped | dropped | the system prompt changed, and it is half the fixed cost |
| tool_search discovery (`hydrated`) | key changes → rebuild | **kept** | a discovery adds a tool; it does not change how much room the history leaves |

### Slice 3 — out of scope, recorded

`_on_capability_change` drops **every** memoized array platform-wide on any capability
flip, justified by *"Capability flips are rare"* — measured false: 950 all-time, 62 in
one day, 100% of them `browser`, from a ~3-second subprocess recycle. That is a
wrong-EVENT defect (a transient bounce is not a capability change) compounded by a
wrong-SCOPE one (all sessions, not the affected ones). It costs 284 needless rebuilds a
day. With slice 2 shipped the basis survives that wipe, so a needless rebuild costs CPU
and no longer costs the array — it is a cost defect now, tracked as
`DEBT-D054-BROWSER-FLAP` rather than folded in.

There is a coupling worth stating before anyone takes it: the browser wipe is currently
the **only** thing causing the learned usage ranking to be recomputed, because the memo's
horizon is the lane rather than the conversation (`DEBT-D054-MEMO-HORIZON`, raised as
ESC-31). Fixing the flap without answering that would freeze the ranking for the life of
every lane.

### One confusion, three stores

Every defect found in this area reduces to using `session_key` — the **lane** — where a
**conversation** is meant. It is worth seeing together, because converting one store and
not the others leaves the platform half-right:

| Store | Keyed on | Its own stated intent | Status |
|---|---|---|---|
| `cache_audit._tools_hashes` | was the lane | "between turns" of a conversation | **fixed here** |
| `presented_tools._memo` | the lane | *"a new session must recompute"* | ESC-31 |
| `hydrated_tools._by_session` | the lane | *"survive ACROSS turns of the same session"* | ESC-31b |

The third is measured and not theoretical: on one lane in one day, 29 `tool_search` calls
carried no `session_id` (retry, self-heal, goal execution) and 26 carried one. They share
a hydration bucket, so a tool discovered by a background run is promoted into the next
interactive turn's roster. The same store also drops **32% of all discoveries** — 59 of
185 calls have an empty `session_key` and `record()` returns early — so FX-07's promotion
silently does not happen on a third of its traffic.

## Invariants

> **I1.** A `tools array CHANGED` warning is emitted only when two turns of the **same
> `session_id`** presented different arrays. A run with no `session_id` never emits one.
>
> **I2.** Rebuilding the presented array for one conversation, with the same
> `(owl, provider, protocol, window, hydrated)` and any history length, yields the
> identical array. A memo miss costs time, never the prefix.
>
> **I2a.** A capability flip drops the memo and **keeps** the basis. A rollover or an owl
> edit drops both.
>
> **I3.** The warning names which tools entered and which left. A change is never
> reported as two opaque hashes alone.
>
> **I4.** Branch A (`restrict_to`) and branch B (budget) are never both reachable within
> one `session_id` — an enveloped run has no conversation. Violated only if a durable
> task ever acquires a `session_id`, which would then be a genuine capability change and
> is correctly reported by I1.

## Observability

- `[cache] breakpoints: tools array CHANGED — position 0 invalidated this turn` —
  **WARNING**, fields `session_id`, `owl`, `prev_hash`, `hash`, `tool_count`, `added`,
  `removed`. After slice 1 this is an acceptance test, not a diagnosis: it should stay
  silent for any conversation with two or more tool turns.
- `[pipeline] execute: context budget` — INFO, every tool turn, carries `tools_count`,
  `system_prompt_tokens`, `history_tokens`, `model_window`.
- `[pipeline] execute: presented tools — rebuilt` — **INFO** (promoted from debug by this
  item), fields `owl`, `protocol`, `window`, `tools`, `scored_tools`,
  `fixed_cost_measured`, `fixed_cost_basis`. This is the evidence for I2: on a rebuild
  mid-conversation the two fixed-cost figures diverge and `tools` must not. Its sibling
  `presented tools — memo hit` stays at debug — it fires on every turn.
- `registry.to_provider_schema: eligible tools NOT presented — …` — INFO, names the
  constraint that bound (cap vs budget).
- `[presented_tools] capability changed — dropping every memoized tool array` — INFO,
  carries `capability` and `dropped`.

```bash
# I2 — rebuilds where the basis held: measured != basis, and the array did not move.
jq -c 'select(.msg|test("presented tools — rebuilt"))|{ts,owl:.fields.owl,
       tools:.fields.tools,measured:.fields.fixed_cost_measured,
       basis:.fields.fixed_cost_basis}' ~/.stackowl/logs/stackowl*.jsonl

# Every genuine within-conversation change, with what moved:
jq -c 'select(.msg|test("tools array CHANGED"))|{ts,owl:.fields.owl,sid:.session_id,
       n:.fields.tool_count,added:.fields.added,removed:.fields.removed}' \
  ~/.stackowl/logs/stackowl*.jsonl
```

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| Array genuinely changes mid-conversation | the WARNING above, now with the delta | none — reported, never corrected | one lost cached prefix; no functional change |
| Memo wiped by a transient capability flip | `[presented_tools] capability changed`, `dropped` count | rebuild; under I2 reproduces the same array | nothing |
| Budget binds and shrinks the array | eviction line naming *the turn's token budget* | the basis is stamped once, so the array is fitted to the conversation's first turn and does not shrink further | fewer tools presented than an unbudgeted turn; overflow still reachable via `tool_search` |
| History outgrows the stamped basis late in a long conversation | not detected here — it is the compressor's job | context compression, which is Law 1's one sanctioned exception | nothing; the array holds |
| Schema unserialisable, stability unmeasured | `tools array not serialisable` at ERROR | audit skips the turn; the turn proceeds | nothing |
| An expected change (owl edit) reported as a violation | not detected — `take_expected_change` is consumed by the prompt audit only | none | a WARNING with no cause; tracked, not fixed here |

## Standing watch

Two invariants are proven by test and have **not** been observed in production, and
the distinction is kept rather than blurred. `I1` and `I2` both need a multi-turn
interactive lane whose memo is invalidated mid-conversation; every rebuild since the
fix shipped is a distinct `incident-*` lane seen exactly once, so neither has had a
discriminating opportunity.

**Bakir's call, 2026-08-21:** close the item on the integration-test evidence and keep
these as a standing watch. The reasoning he accepted: the test drives `execute.run`
with the **real** `ToolRegistry`, the **real** budgeter and the **real** memo,
mocking only the AI provider — which is this repo's own mandated bar for proof — and
the production code path is confirmed live (30 records carrying `fixed_cost_basis`).
Holding an item open on a traffic shape nobody controls blocks it indefinitely.

The counter-argument, kept because it is real: `D01.1` shipped a reader against a file
nothing wrote and its test passed continuously because the test wrote the file itself.
That is not this case — nothing here is self-supplied — but the standing watch exists
so the difference stays checkable rather than argued.

Run the two queries in Verification below whenever this subsystem is touched. Pass is
a **non-zero rebuild count** with zero unbounded warnings, and at least one record
where `measured != basis` with `tools` unchanged.

**Watch reading, 2026-08-22** (bounded to boot `2026-08-22T15:27:19Z`):

| Check | Result | Reading |
|---|---|---|
| `I1` — no warning without a conversation | **0 warnings over 15 rebuilds** | **PASS**, and for the first time with a non-zero denominator. The 2026-08-21 reading was 0-over-0, which proved nothing. |
| `I3` — a warning names its delta | 0 warnings emitted | vacuous — no record could fail to carry `added`/`removed` |

One fact from the re-run that supersedes an earlier note: `tools` is **not** constant at
40. `incident-8ebb22112452` rebuilt at `tools=19` for `verifier` and `hypothesis` while
`rca_gatherer` on the *same lane* rebuilt at 40. That is per-**owl** profile narrowing,
not per-turn drift, and it is exactly what an invariant keyed on `(conversation, owl)`
predicts. A bare "tools=40 on every rebuild" would now read as stale.

### `I2` is not waiting on traffic. It is waiting on a shape this design does not produce.

Widening the window from *this boot* to *every record since the line was promoted to INFO*
(2026-08-21 onward, **233 rebuilds**) changes the diagnosis, and the change is worth more
than the check:

* **220 of the 233 rebuilds carry no `conversation_id` at all.** Only 13 do.
* **Zero `(conversation_id, owl)` pairs appear more than once.** Not "few" — none. So a
  *within-conversation* rebuild, which is the only thing `I2` as phrased can observe, has
  not happened once in two days.
* Three records DO read `measured != basis`, so **the basis mechanism is demonstrably
  live** — it is being reused:

  | ts | lane | conversation | owl | tools | measured | basis |
  |---|---|---|---|---|---|---|
  | 01:45:21 | `owl:secretary:telegram:dm:…` | *none* | `scout` | 23 | 5929 | 5459 |
  | 01:47:51 | `owl:secretary:telegram:dm:…` | *none* | `scout` | 24 | 7333 | 5459 |
  | 14:40:23 | `owl:secretary:telegram:dm:…` | `20260822_094020_…` | `secretary` | 23 | 6403 | 5909 |

  All three are the **same lane across different conversations**, and in all three `tools`
  changed anyway. The stated pass — `measured != basis` *with `tools` unchanged* — is
  therefore still unmet.

The reason is structural, not statistical: `memo_key` is built from
`state.session_key` (`pipeline/steps/execute.py:1415-1425`) — **the lane** — so the memo
and the basis it carries persist *across* conversations on one lane and are never
re-derived *within* one. A check phrased on within-conversation reuse cannot be satisfied
by a mechanism keyed on the lane. That is `ESC-31`/`ESC-31b` exactly ("should the memo AND
the hydration set key on the conversation rather than the lane — three stores, one
confusion"), now with a measurement attached rather than a suspicion.

**So the watch stands, and its wording is the thing to revisit when ESC-31 is answered** —
not the traffic. Recorded here rather than reopening the item, because the item closed on
the integration-test bar and this does not disturb that: the basis is provably reused, the
array is provably rebuilt, and what is unproven is narrower and now named.

## Verification

> **Read `stackowl*.jsonl`, not `stackowl.jsonl` — this is not a convenience.** At UTC
> midnight the log rotates: the gateway reopens the new file while the **core keeps an open
> descriptor on the rotated one** and goes on writing there
> (`project_gateway_core_dual_log_writer_bug`, recorded 2026-07-18, still unfixed; verified
> at the fd level on 2026-08-23 — core pid writing `stackowl-2026-08-22.jsonl`, 1,236 lines
> after 00:00Z, against 24 in the current file). A query pinned to the single filename is
> blind to the core after any midnight, returns 0, and looks exactly like a check that
> passed. That is the 0-over-0 trap wearing a filename, and it silently invalidated a
> night's worth of watch readings before it was caught.

**The log field was renamed `session_id` -> `conversation_id` on 2026-08-21**, so every query below reads `(.conversation_id // .session_id)` to span the cutover — records written before it still carry the old name, and a query that sees only one of them silently halves its own denominator. THE FIELD WAS RENAMED; the queries did not forget.

**Every log query below is also bounded to the current incarnation.** The JSONL is
append-only for the whole day, so an unbounded query mixes records written under the
OLD contract with records written under the new one and reports failure forever —
a check that cannot pass, which is the same defect as one that cannot fail. Running
this section is what caught that: the first draft asked for 0 and got 12, all of
them from before the fix went live. Take the boot timestamp first and bound on it:

```bash
# The current core's boot — every query below is scoped to it.
BOOT=$(jq -rc 'select(.msg|test("plugins. boot"))|.ts' \
        ~/.stackowl/logs/stackowl*.jsonl | tail -1)
echo "scoped to $BOOT"

# I1 — no warning on a run without a conversation. Expect 0.
# READ THE DENOMINATOR WITH IT: 0 warnings over 0 rebuilds is no opportunity, not
# success. The second query is the denominator and must be non-zero for the first
# to mean anything.
jq -rc --arg b "$BOOT" 'select(.ts>$b)|select(.msg|test("tools array CHANGED"))
  |select((.conversation_id // .session_id)==null)|.ts' ~/.stackowl/logs/stackowl*.jsonl | wc -l
jq -rc --arg b "$BOOT" 'select(.ts>$b)
  |select(.msg|test("presented tools — rebuilt"))|.ts' \
  ~/.stackowl/logs/stackowl*.jsonl | wc -l

# I3 — every warning names the delta. Each line must carry added/removed.
jq -c --arg b "$BOOT" 'select(.ts>$b)|select(.msg|test("tools array CHANGED"))
  |.fields|{added,removed}' ~/.stackowl/logs/stackowl*.jsonl

# I2 — the basis held across a rebuild. Pass needs at least one row where
# measured != basis; all-equal means every key was stamped for the FIRST time and
# the invariant has not been exercised yet, which is OPEN, not PASS.
jq -c --arg b "$BOOT" 'select(.ts>$b)
  |select(.msg|test("presented tools — rebuilt"))
  |{lane:.session_key,owl:.fields.owl,tools:.fields.tools,
    measured:.fields.fixed_cost_measured,basis:.fields.fixed_cost_basis}' \
  ~/.stackowl/logs/stackowl*.jsonl

# I1/I3 — the audit's contract (24 tests)
uv run pytest tests/pipeline/test_cache_audit.py -q

# I2/I2a — rebuild idempotence, real registry + real budgeter (21 tests)
uv run pytest tests/pipeline/test_d052_tools_array_is_wired_stable.py \
              tests/infra/test_presented_tools_memo.py -q
```
