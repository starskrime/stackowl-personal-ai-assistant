# Skill Ownership per Persona, and the Protection Nobody Could Engage

**Item.** D10.7 · Skill ownership per persona — `AHEAD`
**Last verified.** 2026-09-04, commit `a0f720c5`

## Why this exists

The map calls this AHEAD on the strength of three things — `owls/skill_ownership.py`,
per-owl `tool_presets`, and pinned skills — and asks only to keep them, noting they seed
toolsets (D05.2). Two of the three are genuinely exercised. The third could never be
turned on.

**Ownership is real.** 29 `skill_ownership` rows across six owls:

| owl | skills owned |
|---|---|
| `verifier` | 8 |
| `secretary` | 8 |
| `rca_gatherer` | 4 |
| `scout` | 4 |
| `jobmarket` | 3 |
| `mailbutler` | 2 |

The **only** writer is `failure_outcome_miner`, at two call sites: it attaches a skill to
the owl that failed, both to the live registry (so this process presents it immediately)
and to the durable row (so the next boot does). Nobody attaches skills by hand.

**`tool_presets` is real.** Imported by six modules — `owl_build`, `owl_build_infer`,
`owl_build_authz`, `builder`, `presentation`, and `authz_compose`, which cites it by name
when explaining why an owl can always reach `owl_build`.

## The defect

`pinned` had **three readers and no writer**:

```
store.set_lifecycle_state   UPDATE skills SET lifecycle_state = ? ... AND pinned = 0
consolidation.py            pinned members of a merge cluster, twice
lifecycle.py:218            if row.pinned
```

Each reader protects something real: a pinned skill is not archived by lifecycle decay and
is not discarded by a merge. `store.set_pinned` exists and works. Its callers were
**seven, every one of them a test** — zero in `src/`.

**The empirical check agrees without any grep: 0 of 39 skills were pinned, and that number
could not change.** That matters, because a grep for writers is exactly the instrument this
programme has watched lie. The sibling flags `suspended` and `resume_pending` looked
writerless under the same regex and are not — they are written as part of a row upsert. The
row count is what separates the two cases.

**What makes this more than a dormant flag.** `/skill dedupe`'s own help text tells the
operator *"a pinned member wins outright"*. A user-facing command documented a lever that
did not exist. That is the `/quiet` finding (D15.6) inverted: there, a command recorded an
override nothing read; here, a command promises a mechanism nothing can set.

**What made it possible?** The enforcement and the control were built in different places
and only the enforcement was reachable. The `WHERE ... AND pinned = 0` clause lives beside
the retirement query, where it belongs; the means to set the flag belongs to a command
surface nobody went back to. A guard whose *control* has no home ships as decoration —
`CLAUDE.md` shape 5, and its D03.4 example is the same story with a result cap.

## The second finding — duplicates concentrate per owl

D10.3 measured that the 25 learned skills are roughly eight concepts. Ownership shows
where that lands:

| owl | skills | twin pairs at ≥0.90 |
|---|---|---|
| `verifier` | 8 | **4** |
| `rca_gatherer` | 4 | 1 |

The `verifier` owl's skill set is dominated by restatements of one capability. And
`owl_drive_thresholds` computes each skill's retirement threshold from the owning owl's
drive — so a family split across seven names splits the very decay signal that would
retire it. The duplication is self-reinforcing, which is why D10.3's mint-time gate was
necessary but is not sufficient for what already exists (**ESC-128**).

## Model

| Verb | Effect |
|---|---|
| `/skill pin <name>` | `pinned = 1` — curator will not archive, merge will keep |
| `/skill unpin <name>` | `pinned = 0` — decay and merge apply again |

Both declared in `_SKILL_META` **and** dispatched, together. `test_skill_meta.py` already
enforces that pairing, because `menu` once dispatched while undeclared and `/help` could
not see it.

Same shape as `_set_enabled`: a metadata toggle, so it does not route through
`record_skill_mutation` (the content-mutation chokepoint) and its audit row carries no
before/after hash.

## Configuration

None. Ships ON. Unpin exists in the same change as pin — a protection you cannot release
is a different bug from one you cannot engage, and shipping half would have created it.

## Observability

- `[commands] skill.pin: exit` / `skill.unpin: exit` — **INFO**, fields `name`, `pinned`.
- An audit row per toggle, `op` = `pin` / `unpin`, `actor` = `user:pin` / `user:unpin`.

```bash
# Has the operator ever pinned anything, and what is protected right now?
sqlite3 ~/.stackowl/workspace/stackowl.db \
  "SELECT name FROM skills WHERE pinned = 1;"
```

## Failure modes

| Failure | What happens | What notices |
|---|---|---|
| Pin a name that matches nothing | `✗ /skill pin: no skill matching …` | The reply |
| Verb declared but not dispatched | — | `test_skill_declares_all_subcommands` |
| Verb replies success but writes nothing | — | The end-to-end dispatch test (mutation-proven) |
| Pinned skill blocks a needed merge | Merge keeps it | `/skill unpin` |
