## Why this exists

The map counts six surfaces on the reference platform (classic CLI, Ink/React TUI over
JSON-RPC, Electron desktop, web dashboard embedding the real TUI over a PTY WebSocket, an
ACP server for editors, and the messaging gateway) against three here. The Ask is product
intent — *"Which surfaces matter? A dashboard is often what makes a platform feel real to
non-terminal users."* — so it is escalated rather than answered here.

**What this item could settle is what the three actually carry, and the answer was that the
platform cannot tell two of them apart.**

## Model — what exists, and what one name covers

| Surface | Built | Channel name | Turns carried |
|---|---|---|---|
| Textual TUI | `tui/` (10 modules) | **`cli`** | not separable — see below |
| Headless CLI | `channels/cli_adapter.py` | **`cli`** | not separable |
| Telegram | `channels/telegram/` | `telegram` | **65** |
| Slack | `channels/slack/` | `slack` | **0** |
| Discord | `channels/discord/` | `discord` | **0** |
| WhatsApp | `channels/whatsapp/` | `whatsapp` | **0** |

**THE cli/MESSAGING SPLIT THIS TABLE DRAWS BY HAND IS NOW MACHINE-READABLE** (2026-09-08,
`bc1f7a75`). `ChannelAdapter.implicitly_addressable` declares whether a surface can reach a
recipient with no explicit target: **True** for the single-terminal ones (CLI, and the base
default), **False** for all four messaging adapters, which carry a per-message target. It
was added because a caller could not tell them apart and guessed — a recovered answer was
reported delivered and dropped, and three others reached whichever chat had spoken last.
The distinction was always in this table; nothing in the code could be asked for it.
| *(autonomous, not a surface)* | RCA / scheduled lanes | `rca` | 112 |

**`cli` is two surfaces, and it has to be.** `CLIAdapter` (the 4-zone Textual TUI) and
`HeadlessCliAdapter` (no terminal at all — `start.sh` launches with stdin at `/dev/null`)
both answer `channel_name == "cli"`. That string is the **routing identity**: consent
provenance reads it through `_gateway_channels()`, the clarify gateway registers the
adapter under it, proactive delivery addresses it, and `tools/browser/sessions.py` branches
on it. Renaming to report better would be a security-relevant change made for a reporting
reason.

So `ChannelAdapter.surface` was added **alongside** `channel_name`, never instead of it:

| Adapter | `channel_name` | `surface` |
|---|---|---|
| `CLIAdapter` (fullzone) | `cli` | `tui` |
| `CLIAdapter` (legacy/raw) | `cli` | `raw` |
| `HeadlessCliAdapter` | `cli` | `headless` |
| `SocketChannelAdapter` | *the proxied channel* | `socket:<channel>` |
| every other adapter | *its own* | **the same** — the default |

**`cli` is in fact THREE bindings, and the live log is what found the third.**
`orchestrator.py:2110` binds `SocketChannelAdapter(core_conn, channel_name="cli")` in the
split-process **core** role — the branch most boots on this deployment actually take. Under
the base default it reported a bare `cli`, which reads as "a cli surface with nothing to
add" when the truth is that no terminal is attached to that process at all. That distinction
is not cosmetic: it is why boot markers appear in PAIRS in these logs (gateway + core), and
that pairing has made more than one count in this programme read as double what it was.

The default is `channel_name`, not a placeholder: for Telegram the surface *is* Telegram.
A default of `"unknown"` would make an adapter that forgot to answer look identical to one
that genuinely has nothing to add.

## Lifecycle

```
stackowl start
     │
     ├─ split-process CORE ────▶ SocketChannelAdapter  surface="socket:cli"
     │                            (no terminal here at all; the gateway holds the channel)
     │
     ├─ stdin.isatty() false ──▶ HeadlessCliAdapter    surface="headless"
     │                            (INFO: "stdin is not a TTY … no Textual TUI")
     │
     └─ stdin.isatty() true  ──▶ TuiAssembly.build()
                                  └─▶ CLIAdapter(tui_components, event_bus)
                                        _mode="fullzone"  surface="tui"
     ▼
  both register as "cli" with the clarify gateway AND the ChannelRegistry
     ▼
  INFO: "[startup] gateway: starting CLI adapter"  { surface: … }
```

`surface` is **derived** from the `_mode` the constructor already chose. A second
independently-set string would be free to disagree with the behaviour it names.

## Invariants

1. **`channel_name` never varies by surface.** Both cli surfaces answer `cli`; routing,
   consent provenance and delivery depend on it.
2. **`surface` is derived, never assigned separately** — it reads the same `_mode` the
   constructor decided on.
3. **Every adapter has an honest answer.** The base default returns `channel_name`, so
   there is no "unknown" state that hides a missing override.

## Configuration

None. The CLI surface is selected structurally by `stdin.isatty()` — there is no flag,
because a flag could disagree with the terminal that is actually attached. Messaging
adapters are enabled by their own credentials being configured.

## Observability

| Line | Level | `_fields` |
|---|---|---|
| `[startup] gateway: starting CLI adapter` | INFO | **`surface`** |
| `[startup] gateway: stdin is not a TTY — starting the CLI channel HEADLESS …` | INFO | — |
| `[cli] CLIAdapter.init: ready` | DEBUG | `session_key`, `mode` |

```bash
# Which surface has this install actually been booting?
cat ~/.stackowl/logs/stackowl*.jsonl \
  | jq -r 'select(.msg == "[startup] gateway: starting CLI adapter") | .fields.surface' \
  | sort | uniq -c
```

**Before this item that query was impossible and the answer was a subtraction**: 815
`starting CLI adapter` lines minus 195 "stdin is not a TTY" lines implied 620 TUI boots. A
fact reachable only by knowing which two numbers to subtract is not a fact the record
carries.

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| No terminal attached | `stdin.isatty()` at boot | headless adapter; the channel still exists for clarify + proactive delivery | An INFO line telling them to run from a terminal |
| A new adapter omits `surface` | — | base default returns `channel_name` | Nothing; the answer is still honest |
| Textual on a redirected stdin | *fixed 2026-08-14* | headless adapter | — |

That last row is why the split exists at all: with stdin at `/dev/null`, Textual's input
thread busy-waits on EOF and the gateway sat at **100.3% CPU** — a whole core, spent being
useless.
