# The Install Path We Already Had, and the Sidecar Nobody Gated

**Item.** D10.4 · Skills Hub — `MISSING`
**Last verified.** 2026-09-04, commit `HEAD`

## Why this exists

D10.4's Ask — *"Distribution is how a platform gets adopted. In scope?"* — is product
intent, and stays the operator's (**ESC-129**). Everything around it is measurable, and
measuring it corrected the entry and found a live defect.

**"No install path from outside" is wrong.** Two user-typable commands exist:

```
/skill add <local-path>        install_from_local_path
/skill add --url <url>         install_from_git_url | install_from_archive_url
```

`git clone --depth=1` for a repo, download-and-extract for `.tar` / `.tar.gz` / `.zip`,
both landing in `skills/installed/`, both already defending against oversized downloads
(`_MAX_ARCHIVE_BYTES`) and zip-bomb expansion (`_MAX_EXTRACTED_BYTES`), both writing an
audit row with a restorable snapshot.

What is genuinely absent is the hub *around* that path: no `SkillSource` abstraction over
repos, no lockfile, no quarantine directory, no taps, and no static analysis of what was
installed. `installed/` is empty — the path has never been used.

## The defect

A skill directory may carry two extension sidecars. Until 2026-09-04 they were trusted
differently, and the asymmetry ran the wrong way:

| sidecar | what it is | gated on |
|---|---|---|
| `owls.yaml` | **declarative** — registers agents | `source in _OWL_TRUSTED_SOURCES` |
| `tools/*.py` | **executed** — `exec_module`, then every `Tool` subclass instantiated and registered | `tools_dir.exists()` |

The declarative artifact was gated by provenance. The executable one was not gated by
provenance at all.

**A guard exists and answers a different question.** D05.1's actuator refuses to exec skill
tool modules when the skills tree sits *inside the model-writable workspace*. That is about
whether the **model** can write what we run. It says nothing about whether a git URL can,
and for `installed/` it is explicitly a no-op — its own comment reads *"normally a no-op:
the two trees are siblings under ~/.stackowl"*.

**And no scan covered it.** `gated_skill_write` runs `security_scan_gate` HARD and fails
closed on a scanner crash — but only on the agent's own authoring path, and only over the
**SKILL.md text**. `skill_helpers.py`, which is what `/skill add` uses, references the scan
gate **zero times**.

**What made this possible?** Two constants for one rule. `_OWL_TRUSTED_SOURCES` named the
owl case rather than the *principle* — which sources may extend the running process — so
when the second sidecar arrived there was nothing for it to be measured against, and
"trusted source" silently meant "trusted for owls". A rule named after its first caller
does not generalise to its second.

**What else does that reach?** The same vocabulary was restated in **four** places: the
manifest `Literal`, the loader tuple, `skill_command._VALID_SOURCES`, and that command's
`choices=` tuple. D10.1 collapsed two of them and reported the dedup done; D10.4 found the
other two. All four agreed, so nothing was broken — the cost was that "I deduped it" was
recorded as true when it was half true.

## Model

```python
_TRUSTED_EXTENSION_SOURCES = frozenset({"builtin", "user"})
_OWL_TRUSTED_SOURCES = _TRUSTED_EXTENSION_SOURCES   # the same object, not a copy
```

`builtin` is code we shipped; `user` is code the operator placed by hand. Not `learned`
(the model wrote it — precisely what D05.1's actuator exists to keep out of `exec_module`)
and not `installed` (a URL did).

## Lifecycle

1. Load and validate `SKILL.md`. The skill itself always loads.
2. `tools/` present → **trusted source?** import and register, else refuse and warn.
3. `owls.yaml` present → **trusted source?** register, else refuse and warn.

A refused sidecar never fails the skill. Refusing the *skill* would turn a provenance
question into an outage, which is the mistake `_drop_retired_keys` already records.

## Configuration

None. Ships ON. **Zero live impact, measured before the change**: all 39 registered skills
report `tools: 0`, and no `tools/` directory exists under any source on disk.

## Observability

- `[skills] loader: refusing tools/ from untrusted source` — **WARNING**, fields `source`,
  `skill`, `skipped` (how many `.py` files). A refusal nobody can see is indistinguishable
  from a skill that had no tools.
- `[skills] loader: refusing owls.yaml from untrusted source` — WARNING, unchanged.

```bash
grep -E 'refusing (tools/|owls.yaml) from untrusted' ~/.stackowl/logs/stackowl.jsonl | tail
```

## Failure modes

| Failure | What happens | What notices |
|---|---|---|
| Installed skill ships `tools/` | Skill loads, tools refused | The WARNING, every boot |
| Learned skill ships `tools/` | Same | The WARNING |
| Builtin/user skill ships `tools/` | Registered as before | The existing collision + idempotency tests |
| Skills tree inside the workspace | D05.1 refuses *all* tool exec | Its own ERROR line |

## Verification

```bash
# 1. Both directions, both untrusted sources and both trusted ones.
uv run pytest tests/skills/test_the_executable_sidecar_is_gated_like_the_declarative_one.py -q
#    expect: 5 passed

# 2. The existing tool-loading contract is unchanged.
uv run pytest tests/skills -q
#    expect: 484 passed

# 3. Nothing on disk loses a tool.
find ~/.stackowl/skills -maxdepth 4 -type d -name tools    # expect: no output
```

All three RUN on 2026-09-04, not trusted. Check 3 is the one that licensed the change: the
gate is only safe to ship ON because there is nothing for it to break.

`tests/skills/test_loader_tool_collision.py::test_reload_same_skill_tool_is_idempotent`
changed its fixture source from `learned` to `user`. Its subject is idempotent
re-registration and the source was incidental — the collision test beside it already used
`user`. Recorded here because a fixture edited to make a new guard pass is exactly how a
guard gets quietly weakened, and this one was not.
