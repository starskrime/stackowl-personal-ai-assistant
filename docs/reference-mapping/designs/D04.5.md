# It Survives. The Explanation Did Not.

**Item.** D04.5 · Tier escalation — `AHEAD`, track `keep`, wave 10, order 97.
**Ask.** "Keep. Confirm it survives."
**Answer.** It survives, verified three ways. What was missing is that a refused
escalation left no trace at all.

## Confirmed, not assumed

The mechanism is a same-turn `ESCALATE` sentinel: a tool's circuit breaker opens, the
pipeline sets a one-bit turn-scoped flag, the provider ReAct loop reads it and returns
the sentinel, and the gateway re-runs the turn on a stronger tier.

**The part worth confirming is the gate in front of it,** and its docstring records
what it cost to learn:

> "25 escalations, all landing on the same (NeraAiRaw, neraai-v1-raw). Each made the
> provider DISCARD a finished attempt — 14, 15, 16 and 19 tool calls in four of those
> turns — return the ESCALATE sentinel, and hand the gateway a turn it had to re-run
> before anything could be delivered. `on_escalate` also reset the tool-outcome
> ledger, so the re-run was blind to what the first attempt had already learned."

`can_escalate` used to mean "this is not the last rung" — a fact about the LADDER, not
about the TARGET. `_can_escalate_meaningfully` asks the real question: is there a
higher tier that resolves somewhere *else*?

Verified on 2026-09-05:

1. the gate exists and asks that question;
2. on the live configuration it answers **False** — `describe_tier_ladder()` returns
   `NeraAiRaw/neraai-v1-raw` on all three rungs, and `tier_ladder_is_degenerate()` is
   `True`;
3. **both** provider loops honour it, and six test files exercise the area, one of them
   named `test_escalation_that_changes_nothing_is_visible.py`.

So the answer to "confirm it survives" is yes, and the deployment it protects is
exactly the degenerate one it was written for.

## What did not survive: the explanation

The pipeline logs `"[pipeline] execute: circuit open — requested tier escalation"` at
INFO when a tool's breaker opens. Measured across every kept log: **12 such requests,
and zero lines recording the outcome.** All twelve are 2026-08-28 to 08-31, on
`web_fetch`, `shell` and `owl_build`.

Someone asking "why didn't that turn escalate?" found a request and silence. The
honest answer — every rung resolves to the same model, so there is nothing stronger to
reach — is precisely the fact D04.4 had to make visible for the ladder itself, one
item earlier. **A no-op that says nothing is the shape this programme keeps paying
for.**

## Why the fix is one function and not two if-statements

Both provider loops open-coded `if can_escalate and escalation_requested():`. Adding
the decline message to each would have been **two copies of one rule** — the shape
that made the vendor sniff wrong in D04.2, and one of the four `CLAUDE.md` lists as
accounting for nearly every real defect here.

`escalation_signal.escalation_allowed(can_escalate=…)` is now the single place that
answers "should this turn escalate", and therefore the single place that can say why
not. Both providers ask it; a test asserts neither open-codes the decision again.

Three properties, each earned from a different item:

* **Silent when nothing asked.** A line on every turn that never wanted to escalate
  would drown the one that did — D18.7, where a guard that fires on the healthy case
  is one its reader learns to ignore.
* **Said once per turn.** A tool loop can ask many times and the answer never changes;
  repeating it per step turns one fact into a burst.
* **It says WHY**, not just that it declined. A decline with no reason is the same
  silence in a different font.

## Housekeeping: an escalation whose premise expired for the wrong reason

`escalation_check` reported ESC-114 EXPIRED — "which ceiling should bind on a long
research sweep". Its check asked whether the token cap or the step cap dominates, and
flipped to "steps dominant again **{'steps': 1}**": a verdict on a denominator of one.

Measured properly, budget-cap events went 30 (08-28) → 7 (09-02) → **zero on 09-03 and
09-04** → 1 (09-05). But the ceilings did not stop binding — **the workload dropped**:
owl/goal-lane calls fell from 708 a day to 29, a 24× fall, while the jobs that drive
them still exist. **Closing it as resolved would have recorded a fix that never
happened.** Its check now measures whether any ceiling is binding often enough to
judge, so it stays quiet while the lane is idle and asks for a re-read when real
sweeps return.

**My replacement check was wrong twice before it was right**, and both are worth
keeping. The first used sweep VOLUME with a threshold of 100 calls over two days —
which reported "active again" for a 24× reduction. The second referenced
`glob.glob(...)` results as if they were `Path` objects, so it raised `AttributeError`
into a suppressed stderr and the queue printed `(no output)`. **A premise check that
errors is a check that never fires**, which is the same failure as a DEBUG-only
acceptance line: run the closing query before you need it.
