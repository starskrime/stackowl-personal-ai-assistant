# Dependency Pinning — a Ceiling on Every Dependency, a SHA on Every Action

**Item.** D17.5 · Dependency pinning policy — `MISSING`
**Last verified.** 2026-09-05, commit `HEAD`

## Why this exists

The Ask is two words: *"Cheap. Adopt?"* The reference platform's policy has four clauses,
established after a real supply-chain compromise and reinforced after a worm campaign:
every dependency needs an upper bound, git URLs pin to a 40-char SHA, GitHub Actions pin to a
SHA, and CI-only pip installs pin exactly.

## Measured before adopting

| | |
|---|---|
| dependencies in `pyproject.toml` | 44 |
| with an upper bound | **2** (`playwright`, `pypdf`) |
| `uses:` lines in `.github/workflows` | 8 |
| pinned to a commit SHA | **0** |
| pinned to a mutable tag | **8** (`@v4`, `@v2`, `@v5`) |
| git-URL dependencies | 0 |
| CI-only `pip install` lines | 0 |

**Two clauses were vacuous** — nothing to bind — and are recorded so nobody re-adopts them as
work. A test asserts they *stay* vacuous, because the day a `git+` dependency appears is the
day that clause stops being free.

## The action half is the sharper one

`uv.lock` is committed, so an install today is already reproducible. That is why the
dependency clause is about the **resolution** step, not the install: an unbounded `>=` means
the next `uv lock --upgrade` accepts a brand-new major, including a release published minutes
ago by whoever compromised the maintainer.

**A lockfile does not cover CI actions at all.** `actions/checkout@v4` is whatever that tag
points at when the job runs, executing with the repository's credentials. That is exactly the
worm-campaign shape, and it was our largest unbounded surface.

## How the bounds were chosen

**From the LOCKED version, not from the floor.** For each dependency, the ceiling is the next
major above what `uv.lock` already resolved — so the existing lock satisfies every new
specifier by construction and nothing is re-resolved.

Verified: `uv lock --check` resolves 210 packages, and the lock diff contains **zero**
`version =` changes. The only movement is the `[package.metadata] requires-dist` block, which
is uv recording the project's own declared specifiers.

One exception, stated: `discord.py` has no entry in the lock (it is in an optional group), so
its ceiling comes from the declared floor's major — `>=2.3,<3`.

Action SHAs were resolved from the live API, dereferencing annotated tags to their commit —
`astral-sh/setup-uv@v5` is an annotated tag, and pinning the tag object rather than the
commit would have pinned nothing useful. Each pin keeps `# v4`-style comment, and a test
requires it: a bare 40-character SHA is unreadable, and the next person cannot tell an
upgrade from a downgrade without it.

## Invariants

- Every dependency specifier carries `<` (or `==`).
- Every `uses:` names a 40-hex commit SHA.
- Every pinned action carries a version comment.
- No `git+` dependency and no CI `pip install` appears — the vacuous clauses stay vacuous.

## Verification

```bash
uv run pytest tests/test_every_dependency_and_action_is_bounded.py -q   # 4 passed
uv lock --check                                                        # Resolved 210 packages
git diff uv.lock | grep -c '^[+-]version = '                           # 0
grep -rhoE "uses: \S+" .github/workflows/ | sort -u                    # all @<40 hex>
```

All four RUN on 2026-09-05, not trusted. Mutation-proven both ways: removing `rich`'s ceiling
and reverting one action to `@v4` each fail the guard by name.
