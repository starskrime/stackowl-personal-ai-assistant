## Why this exists

Bakir, 2026-08-10, verbatim:

> "DreamWorker should be in platform. because i am not going to create a next chatbot which
> does no interaction. thats why i am thinking to build jarvis which will dream and rethink
> about his life, his abilities, his growing, learning, improving and etc things."

**Nothing in the platform said any of it.** The agent reflects on every turn — 6,419
reflections promoted to 5,769 lessons — and evolves its own DNA (586 artifacts). What no
surface could do was compare the platform *to itself*. `AutonomicHealth` reports current
counts, `Learning` reports the last 24 hours, `SystemSpend` reports tokens. Not one of them
can say **"I am better at this than I was."**

## Model

**One assembler, two windows, five sentences.** The section compares the last 7 days against
the 7 before, over the same owner-scoped tables the rest of the brief reads.

| Concept | Meaning | Source |
|---|---|---|
| `_GROWTH_WINDOW_DAYS` | 7 — the comparison window, and the offset of the baseline | `assemblers.py:731` |
| `_GROWTH_MIN_FAILURES` | 5 — a capability is only reported if one side reaches this | `assemblers.py:735` |
| success rate | `SUM(success) / COUNT(*)` over `task_outcomes` | `_window()` |
| capability failures | `failed_capability` counts, **success = 0 only**, `failure_class <> 'stop'` | `_failures_by_capability()` |
| step-cap hits | `success = 0 AND failure_class = 'stop'` | `_step_cap_hits()` |
| skills learned | `COUNT(*) FROM skills WHERE loaded_at > now − 7d` | inline |

**It is deterministic on purpose, and that is the whole design.** The obvious way to build
"dreaming" is to hand a model its own history and let it narrate. That produces a paragraph
about growth whether or not any growth happened — the overclaim this platform has spent weeks
learning not to make. Every number here is measured and the sentence is *assembled* from it,
so the brief cannot report improvement on a week that got worse.

## Lifecycle

```
morning_brief fires (daily@08:00 local = 13:00 UTC)
        │
        ▼
GrowthAssembler.assemble(ctx)
        │
        ├─ read: this window, prior window, failures both sides, step-caps, skills
        │        └─ any read raises ──▶ omitted=True, WARNING, brief continues
        │
        ├─ prior_tot == 0 or this_tot == 0 ──▶ omitted=True, INFO
        │     "no prior week, no comparison" — a baseline of zero would report
        │     spectacular growth forever
        │
        ▼
   compose, in this order:
     1. overall success, this week vs last, with the verb chosen by the delta
     2. capabilities that IMPROVED        (optional)
     3. capabilities that got WORSE       (optional, never suppressed)
     4. the step cap, on its own line     (optional)
     5. skills learned this week          (always)
        │
        ▼
   BriefSection(key="growth", omitted=False) ──▶ brief ──▶ proactive delivery
```

**Ordering is behaviour.** "Worse" is emitted immediately after "improved" and is never
conditional on there being good news to balance it.

## Invariants

1. **A week with no baseline is omitted, never estimated.** `prior_tot == 0` returns
   `omitted=True`; inventing a zero baseline would report infinite improvement forever.
2. **A regression is always reported when present.** A self-assessment that only lists
   progress is the overclaim shape wearing a friendly voice.
3. **Only genuine failures count as capability failures.** `success = 0` is required: a row
   can name a `failed_capability` on a turn that SUCCEEDED — the capability stumbled and the
   recovery ladder got there anyway — and counting those reports a regression the user never
   experienced.
4. **Step exhaustion is never attributed to a tool.** `failure_class = 'stop'` means the turn
   ran out of room; the capability named is whatever was in flight. It gets its own sentence.
5. **A failed read omits the section, never the brief.** One section may not kill the report.
6. **Everything is owner-scoped.** Every query carries `owner_id = ?`; this is a tenancy
   surface like any other.

## Configuration

**None, deliberately.** There is no `growth:` key in `stackowl.yaml` and no flag. The window
(7 days) and the reporting floor (5 failures) are constants in the module, and the section
runs whenever the brief runs. A feature ships ON; an operator switch here would be an
opt-out for a report the operator asked for.

The brief itself is scheduled as the `morning_brief` job — measured on the live table:
`schedule='daily@08:00'`, `enabled=1`, next run `2026-09-06T13:00:00+00:00`.

| `[brief] growth: not enough history to compare — omitting` | INFO | `this_turns`, `prior_turns` |

| `[brief] growth: assembled` | INFO | `success_now`, `success_prior`, `improved`, `regressed`, `skills_learned`, `step_cap_now`, `step_cap_prior` |

Both omit paths are at INFO or above on purpose: a section that silently vanishes from the
brief is indistinguishable from one that was never built.


## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| A table is missing or unreadable | `except` around every read | `omitted=True`, WARNING logged | The brief, minus this section |
| Fewer than two weeks of history | `prior_tot == 0 or this_tot == 0` | `omitted=True`, INFO logged | The brief, minus this section |
| A capability moved by fewer than 5 failures | `_GROWTH_MIN_FAILURES` | Not reported | Nothing — noise suppressed |
| The week genuinely got worse | Nothing to detect; it is reported | None wanted | "I got WORSE at: …" |

**Three correctness faults were found and fixed within hours of first shipping**, all of the
same shape — a count that was not made of what it claimed:

* Counting every row naming a `failed_capability` read `web_fetch` 27 → 48, of which 22 and
  37 were on turns that **succeeded**. Honest figures: 5 → 11.
* Then excluding `failure_class='stop'` took `web_fetch` from 5 → 11 to **0 → 0** — it had
  never failed as a capability at all. `browser_navigate`'s 12 → 3 "improvement" went the
  same way. **Every per-capability movement the first night reported was step exhaustion
  wearing a tool's name.**
* The step-cap sentence says "stopped before finishing", not "ran out of steps", because the
  ceiling that actually fires has moved: steps 30/5/4/2/0 across 08-28…09-02 while tokens
  went 0/0/8/8/7. Recent breaches are the 500,000-token input cap, not the 20-step one.

## Related

* **Prior art: none, and that is the point.** This is the first item in the `N` namespace —
  a native idea, not a gap against someone else's architecture. The reference platform has no
  self-comparison surface to diverge from; it reports current state, as ours did before this.
* **It is NOT D09.1.** That item's gap is "learning is not tied to the moment the lesson
  exists, and does not see the live conversation" — per-turn review with a conversation in
  front of it. Dreaming is periodic and reflexive: the agent thinking about *itself* when
  nobody is talking to it. Different trigger, different subject.
* **It deliberately did not fill the `DreamWorker` seat.** That handler and its 30-minute
  schedule were deleted on 2026-09-01 under "retired means deleted", and nothing should
  re-create them: the brief already runs daily, guards each section, and delivers through one
  seam measured reaching the operator. A job waking every 30 minutes to do nothing produces
  run records that read as a healthy loop — the failure ADR-19 exists to kill.
* Sibling sections in the same file: `AutonomicHealth` (current state), `Learning` (last 24h),
  `SystemSpend` (tokens), `ConcludedIncidents`.
