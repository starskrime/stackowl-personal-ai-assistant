## Why this exists

Bakir's ESC-16 answer (2026-08-17): **yes to lifecycle hooks, as a SEPARATE capability-gated
extension point rather than a property every plugin gets; no to pip entry points.**

The measurement behind the question (2026-08-15) is what shapes the design:

- **Six extension points exist**, discovered by `issubclass` against `_ABC_NAMES`: `Tool`,
  `JobHandler`, `SlashCommand`, `ChannelAdapter`, `OwlSource`, `MemoryProvider`.
- **Zero lifecycle hooks exist.** All six reference hook names were grepped for across `src/`
  and none appears anywhere.
- **Zero plugins are installed.** The directory is empty and the `plugins` table has 0 rows.
  The whole surface — loader, manifest, capabilities, verify, remote install — had never once
  run in anger. It was proven end to end for the first time on 2026-08-16 with a throwaway
  probe.

That last number is the one that disciplines this document. We are widening a surface that has
one day of real use, so the design deliberately does the smallest honest thing.

## Model

### One ABC, one capability

A seventh entry joins `_ABC_NAMES`:

```
"LifecycleHook": "stackowl.plugins.hooks"
```

and one capability joins `capabilities.py`:

```
LIFECYCLE_HOOKS: Final = "lifecycle_hooks"
```

A plugin that subclasses `LifecycleHook` **without** `lifecycle_hooks` in its manifest
`capabilities` fails to load, loudly, through the existing `PluginContext._require` path that
already raises `PluginCapabilityDeniedError`. No new permission machinery: the gate that exists
for `tool_registry` is the gate used here.

**Why one capability and not six** (one per hook point): the manifest already lists the hook
points the plugin implements, so the operator sees exactly what it observes at grant time.
Six capabilities would express the same fact twice, and two writers to one fact is how they
drift — the shape this tree keeps paying for.

### The six hook points

Ported as SHAPES from the reference platform, not as code:

| hook | fires | receives |
|---|---|---|
| `on_session_start` | a conversation lane opens | session key, owl name, channel |
| `pre_tool_call` | before a tool dispatches | tool name, arguments |
| `post_tool_call` | after a tool returns | tool name, `ToolResult` |
| `pre_llm_call` | before a provider call | model tier, message count |
| `post_llm_call` | after a provider returns | tier, token counts, latency |
| `on_session_end` | a lane finalises | session key, reason |

### OBSERVE ONLY — the decision that keeps this small

**A hook cannot change anything.** It receives a read-only view, returns `None`, and its return
value is discarded. No veto, no argument rewriting, no tool substitution.

This is the deliberate v1 boundary, and it is worth stating why, because a veto is the obvious
next thing to want:

- A veto on `pre_tool_call` is the single largest trust surface in the item — third-party code
  deciding whether the agent may act. `D17` owns security, and this platform's rule is that
  presentation is never authorization.
- Nothing currently in flight needs it. Zero plugins exist; inventing a control surface for a
  population of zero is exactly the over-architecting Bakir ruled out on 2026-08-17.
- Observe-only cannot break a turn. That property is what lets hooks ship before a real plugin
  ecosystem exists to prove them.

Veto is recorded as a **non-goal for v1**, to be raised as its own escalation if and when a
real plugin needs it.

## Lifecycle

1. **Load.** `LocalPluginLoader` sees a `LifecycleHook` subclass defined in the plugin's own
   module (the `__module__` guard shipped 2026-08-16 already prevents a plugin registering a
   class it merely imported).
2. **Gate.** The manifest must grant `lifecycle_hooks`, else `PluginCapabilityDeniedError`.
3. **Register.** The instance is added to a process-wide `HookRegistry`, keyed by hook point —
   so dispatch is a dict lookup, never a scan of every plugin.
4. **Dispatch.** Each call site awaits the registry, which fans out to the hooks registered for
   that point.
5. **Unload.** `unload()` drops the plugin's hooks, mirroring how it drops its classes today.

## Invariants

- **I1 — a hook never changes what the model sees.** Hooks are observe-only, so the presented
  tool array is untouched. This is Law 1: the array is frozen per incarnation, and a hook that
  could add or remove a tool mid-conversation would invalidate the prompt cache on every turn.
- **I2 — a hook costs zero tokens.** A hook is not a model tool and never enters the waist.
  This is Law 2 exactly: grow the product at the edges, never at the waist.
- **I3 — a failing hook never costs the turn.** Every dispatch is wrapped; an exception is
  logged at ERROR with the plugin name and swallowed. The turn proceeds as if the hook were
  absent.
- **I4 — a hook cannot hang the turn.** Dispatch is bounded by a timeout. A hook that exceeds
  it is abandoned, not awaited.
- **I5 — a repeatedly failing hook is DISABLED, not merely logged.** After N consecutive
  failures the hook is disarmed for the process and the operator is told. This is the standing
  self-healing rule: if it degrades, something must notice and act, not file the debt.
- **I6 — an ungranted hook does not run.** Enforced at load, not at dispatch, so a denied
  plugin never reaches a call site.

## Configuration

No new `stackowl.yaml` section. Per-plugin, in its own `plugin.yaml`:

```yaml
capabilities: [lifecycle_hooks]
```

The hook points a plugin implements are derived from the methods it overrides and surfaced to
the operator at grant time — declared by construction rather than by a second list that can
disagree with the code.

## Observability

At INFO, because production runs at INFO and a DEBUG line does not exist when it is needed:

- `[plugins] hooks.register: exit` — plugin, hook points, count
- `[plugins] hooks.dispatch: hook failed` (ERROR) — plugin, hook point, exception
- `[plugins] hooks.disable: exit` (WARNING) — plugin, consecutive failures (I5)

Dispatch itself is NOT logged per call: `pre_tool_call` fires on every tool of every turn, and
an INFO line there would drown the log it lives in.

## Failure modes

| failure | caught by | user sees | how we notice |
|---|---|---|---|
| Hook raises | dispatch wrapper (I3) | nothing; turn completes | ERROR with plugin + hook point |
| Hook hangs | dispatch timeout (I4) | nothing; turn completes | ERROR naming the timeout |
| Hook fails repeatedly | failure counter (I5) | a notice that it was disabled | WARNING at disable |
| Plugin declares hooks without the grant | load-time gate (I6) | plugin fails to install | `PluginCapabilityDeniedError` |
| Plugin imports someone else's hook class | `_defined_here` guard | nothing registered | already shipped + proven |

## Related

- **Map items:** `D16.1` (this) → blocks `D16.3` → blocks `D04.1`. The chain is why the hook
  table must be decided ONCE: `D04.1` arrives expecting one discovery mechanism, and a second
  hook path added later for providers is the duplication that dependency exists to prevent.
- **Escalations:** `ESC-16` (answered 2026-08-17 — gated hooks, no pip entry points).
- **Prior art, and where we deliberately diverge:** the reference platform lets any plugin
  declare hooks and additionally discovers plugins through pip entry points. We take neither.
  Hooks are a gated extension point because a hook runs on every tool and model call; pip
  discovery is refused because installing a plugin should stay an explicit act by the operator
  — the directory IS the consent.

### Scope carried into implement

Found by being the first user of this surface (2026-08-16), and belonging to this item:

1. **`_register_classes` calls `obj()` with no arguments**, so any extension point needing
   constructor arguments cannot be a plugin at all. A hook may need config, so this is now
   load-bearing rather than cosmetic.
2. **`Tool` requires `name`, `description` and `parameters` as separate abstract properties**,
   so implementing `manifest` alone — the obvious guess, since `ToolManifest` exists — fails.
   It is the first thing a plugin author writes and the first thing that breaks.
3. **`ToolResult.duration_ms` is required with no default**, so the obvious
   `ToolResult(success=True, output=...)` raises. The author is made to supply a timing number
   they have not measured, while the platform times calls itself in two places
   (`tools/base.py:268`, `execute.py:992`). **Recommendation: give it a default of `0.0` and let
   the platform's own measurement win** — an author-supplied duration is a second writer to a
   fact the platform already owns.

## Where the implementation disagreed with this design

PROCESS.md's rule: the design and the code may diverge, provided it is VISIBLE.
Four things changed while building it, and each is here rather than only in a
commit message.

**1. The gate the design leaned on did not exist.** This document said an ungranted
hook plugin "fails to load, loudly, through the existing `PluginContext._require`
path". MEASURED 2026-08-19: `PluginContext` has ZERO construction sites in `src/` —
only tests build one — and `manifest.capabilities` was parsed by the manifest model
and read by nothing. Every capability was declared and enforced nowhere: a plugin
with `capabilities: []` still had its Tool registered into the live tool registry.

So the gate is now real, and GENERAL rather than hook-only: `capabilities.require()`
is the single check, `CAPABILITY_FOR_EXTENSION_POINT` maps each of the seven points
to the capability an operator must grant, and `LocalPluginLoader` calls it before
registering anything. `PluginContext._require` calls the same function, because two
copies of a permission rule is how the two end up disagreeing. Gating hooks alone
would have left six ungated siblings — an actuator wired on one path in seven, which
is the first failure shape in PROCESS.md.

Two capabilities were added: `lifecycle_hooks`, and `memory_provider` — which D08.2
slice C never got, the same omission as its missing registry slot (fixed in
`fed6968d`). This is safe to start enforcing only because zero plugins are installed.

**2. The LLM hook payload is smaller than the table above promised, deliberately.**
The design said `pre_llm_call` receives "model tier, message count" and
`post_llm_call` "tier, token counts, latency". Neither is available at the seam that
is actually shared. `LLMGateway`'s docstring claims every LLM consumer goes through
it; measured 2026-08-19, roughly twenty call sites call
`provider.complete()`/`complete_with_tools()` directly, so a hook there would fire on
some paths only. The shared site is `ModelProvider._resilient_round`, which every
concrete provider wraps EVERY remote round in — and it knows the provider and the
protocol, not the ladder tier or the message list.

So the payload is `provider`, `protocol`, `ok` and a `duration_ms` measured by the
bracket itself. Token counts stay with the cost pipeline (`cost_records`), which
already owns them; an author-supplied copy in a hook payload would be a second writer
to a fact the platform already records — the same argument that settled
`ToolResult.duration_ms`.

**3. Session hooks ride the boundary the platform already has.** `on_session_end` and
`on_session_start` fire from `SessionStore.resolve_for` on exactly the condition that
publishes `session.rollover` and tells the USER a conversation ended — END before
START, so a consumer summarising the conversation that just closed is never handed
the new one first. An ESC-13 RESTART, which mints a fresh `session_id` because the
process that froze the prompt is gone, deliberately fires NEITHER: it is not a
conversation boundary, the user is not told about it, and a start with no matching end
would be an observer's view of something the platform does not believe happened.

**4. Two of the three carried scope items changed shape.** `ToolResult.duration_ms`
already defaults to `0.0` (shipped in `b6f5e9c5`, with `Tool.__call__` stamping its
own measurement over a zero). `Tool` now derives `name`/`description`/`parameters`
from `manifest` when a subclass declares only that — filling ABSTRACT slots only, in
`__init_subclass__`, so a subclass of a concrete tool keeps its parent's fields and a
class declaring neither still fails loudly at instantiation. And `obj()` construction
is unchanged: nothing passes configuration to a plugin's constructor because there is
nothing to pass — `PluginManifest` carries `config_schema` (a shape) and no config
VALUES, and no store holds any. The loader now STATES that contract instead of
letting a raw `TypeError` about a missing positional argument reach the author.

**5. Boot was reading the download catalogue, not the installed plugins.** Found
2026-08-19 by installing an actual plugin and watching it not load.
`load_installed_plugins` iterated `PluginIndex` — `plugin-index.yaml`, whose
`PluginIndexEntry` carries `name`/`url`/`version`/`sha256` and NO path — so every
entry would have been skipped as "no install path recorded" and an absent catalogue
file reported "no plugins installed" forever. Boot now walks
`~/.stackowl/plugins/*/plugin.yaml`, which is Bakir's ESC-16 answer rather than a
convenience: pip entry points were refused so that installing a plugin stays an
explicit act, and the directory IS the consent. The operator's `/plugins disable` is
honoured at boot for the first time; a plugin with no registry row is hand-placed
rather than disabled and still loads; a registry that cannot be read decides nothing.

still owes.

### And the three dispatchers that skipped the chokepoint

Wiring `pre/post_tool_call` into `Tool.__call__` surfaced three call sites running
`tool.execute()` directly — `mcp/server.py`, `tools/interaction/_batch_support.py` and
`sandbox/ptc/dispatch.py` — which therefore skipped verification, the acceptance
authority, exception wrapping and the hooks. Fixed in `08e3b20e`: all three now call the
tool and decide with `is_trustworthy_success()`. It is recorded here because it is a
result of this item's work, not of its design: a hook point is a good way to discover
which paths are not the path.
