## Why this exists

D16.3 asks "which categories are worth an ABC?" The brainstorm measured the answer as
**none** — every category with 3+ implementations already has its ABC, and every
category without one has 0–2. Bakir's call (2026-08-20) was nonetheless to build the
context-engine ABC, and running the architect stage against the real code turned that
into a sharper and better-evidenced design than the item's own framing.

**The reference platform's context-engine ABC is the wrong object to copy.** Theirs is
a swappable whole-engine interface: 4 abstract methods, and exactly **1**
implementation. By their own meta-rule — *"when 3+ contributions integrate the same
category, design the ABC"* — it does not clear the bar, and copying it would add our
tenth ABC below that threshold.

**But our own numbers clear the bar on a different axis.** `assemble.run()` composes
**seven** contributors:

```
base            build_stable_base_prompt()          owls/base_prompt.py
capabilities    CapabilityManifest.probe().render() pipeline/capability_manifest.py
persona         DNAPromptInjector.inject()          owls/dna_injector.py
owls_block      (owl roster)                        assemble.py, inline
skills_block    SkillInstructionInjector.render()   skills/instruction_injector.py
profile         (curated memory)                    assemble.py, inline
stable_context  (memory blocks from classify)       state.stable_context
```

Seven implementations of one concept, composed by hardcoded import. That is the
contributor axis, and it clears 3+ twice over.

**And the list is maintained THREE times in one function, and has already drifted.**

| list | what it drives | contents |
|---|---|---|
| `parts = [...]` (`assemble.py:408`) | the composed prompt, and its ORDER | 7 parts |
| `audit_prompt_parts({...})` (`assemble.py:~425`) | D01.2 cache-invalidation audit | the same 7 |
| the `assemble: exit` log `_fields` | D01.6's per-part size diagnostic | **6 of the 7**, plus 2 non-parts |

`capabilities_len` is absent from the log. Confirmed on live data, not read off the
source — across all 18 `assemble: exit` lines the retained log holds, the `_len` fields
are `base, persona, banner, owls, skills, profile, stable_context, memory, system`.
`capabilities` is a real part (measured at 579 chars in the code's own comment) whose
size has never once been recorded, while `banner` and `memory` — which are **not** in
the composed prompt — are logged on every turn.

The comment directly above that log line says:

> *"INFO, not DEBUG. These per-part sizes are the diagnostic D01.6 exists to obtain,
> and at debug level they vanished entirely: 0 of 17403 lines in the live log carried
> them, which is why prompt composition was unmeasurable."*

D01.6 moved those sizes to INFO precisely so composition would be measurable. One part
is still unmeasurable, because a second hand-maintained list forgot it. This is
CLAUDE.md defect shape #3 — two copies of one rule — sitting inside the function this
item was going to abstract anyway, at three copies rather than two.

**So the design is not "adopt their ABC". It is: make the seven-item list exist once.**

## Model

### One concept, discovered rather than invented

Every one of the seven already obeys the same contract in `assemble.run()` today:

- it has a **stable name** (used as the audit key and the log field prefix);
- it **renders to a string**, and an empty string means "contribute nothing";
- it is **fail-open** — each is individually wrapped in `try/except` that logs at ERROR
  and degrades to `""`, because "no-hidden-errors: never let prompt-building crash the
  turn";
- it holds a **fixed position** in the composed order.

That contract is not being introduced. It is being *named*.

```python
class PromptContributor(Protocol):
    name: str
    async def render(self, ctx: PromptContext) -> str: ...
```

| field | type | default | meaning |
|---|---|---|---|
| `name` | `str` | — | audit key AND log field stem (`{name}_len`). One string, three uses. |
| `render` | `async (PromptContext) -> str` | — | `""` contributes nothing. Never raises past the dispatcher. |

`PromptContext` is a read-only view of what the seven actually read today —
`state`, `services`, `owl_name`, `lean` — and nothing else. It is deliberately narrower
than `PipelineState`: a contributor that can reach the whole state can reach
`state.intent_class`, and D01.1 already paid for that once (a per-turn conditional
frozen into a session-long prompt).

### Why a Protocol and not an ABC

`LifecycleHook` is listed in `_ABC_NAMES` and is **not an ABC** — its own module says
"Nothing here is abstract". The table already tolerates a non-ABC, and a Protocol costs
an implementer nothing: the four contributors that are currently plain functions stay
plain functions. Structural typing is what lets this be a deduplication rather than a
rewrite.

## Lifecycle

```
COLD BUILD (once per session_key+owl_name — D01.1 slice 5, the freeze)
   │
   ├─ CONTRIBUTORS: tuple[PromptContributor, ...]   <- THE ONE LIST
   │        order is the composed order; position is behaviour
   │
   ├─ for each: render() ──┬─ ok  ─────────► rendered[name] = text
   │                       └─ raises ──────► log ERROR, rendered[name] = ""
   │                                          (turn proceeds — existing contract)
   ├─ compose   "\n\n".join(t for t in rendered.values() if t)
   ├─ audit     audit_prompt_parts(rendered)          <- derived, not re-listed
   └─ log       {f"{name}_len": len(t) for ...}       <- derived, not re-listed
                                                          I1 cannot drift again
WARM PATH (every subsequent turn of the incarnation)
   └─ prompt is read from the frozen store; NO contributor runs. Unchanged.
```

**Priority order is the composed order, and it is behaviour.** `base` before
`capabilities` before `persona` is not arbitrary — it is the cached prefix (Law 1).
Reordering the tuple changes `prompt_hash` and invalidates every session's cache, so
the tuple's order is an invariant, not a style choice.

## The rung, and the one it is not

**Rung 1 — extend existing code.** A module-level tuple and a dispatcher inside the
step that already does this work.

> **SUPERSEDED 2026-08-21 — Bakir's call on E2: "everything, including prompt
> contributors."** It DOES join `_ABC_NAMES`, as the eighth point, **capability-gated**
> exactly as `lifecycle_hooks` is (D16.1's pattern): a plugin declaring a contributor
> without the grant fails to load, loudly. The reasoning below is kept rather than
> deleted, because every risk it names is still real and a future reader should see what
> was traded for extensibility — this was a decision, not an oversight. The mitigation
> is the capability gate plus the per-contributor fail-open the dispatcher already has.

**The original argument for keeping it internal.** Becoming the eighth plugin extension
point is a strictly heavier commitment than being an internal seam:

- it is a **one-way door on first install** — reversible today (the `plugins` table has
  0 rows), and permanently not, the moment one third party registers against it;
- it means third-party code composes the **system prompt**, which is the single largest
  trust surface in the platform — larger than a tool, because it is not gated by
  consent and rides every turn of the session;
- seven extension points already exist and **zero plugins have ever been installed**,
  so there is no evidence an eighth is wanted;
- and *who may extend which category* is exactly open escalation **E2**, unanswered.

E2 came back "yes, everything". So the promotion happens — and the three-table change
is exactly the shape that failed once before (D08.2 added `MemoryProvider` to two of
three, so registration silently hit `continue`). The bidirectional tests in
`tests/plugins/` are what make that impossible to repeat, and the eighth entry must
satisfy them before it ships.

## Invariants

> **I1.** Every contributor that reaches the prompt also reaches the cache audit and the
> exit log, with the same name. The three are derived from one tuple, so they cannot
> disagree. *(Today they do: `capabilities_len` is missing.)*
>
> **I2.** A contributor that raises contributes `""` and never fails the turn. The
> failure is logged at ERROR naming the contributor.
>
> **I3.** For identical inputs the composed prompt is **byte-identical** to the
> pre-change prompt, including `prompt_hash`. A prompt that changes shape silently
> invalidates every live session's cache (Law 1).
>
> **I4.** The contributor tuple's ORDER is part of the contract. Order changes are
> prompt changes.
>
> **I5.** A contributor is not a `Tool` and never enters the presented tool array
> (Law 2).
>
> **I6.** No contributor reads per-turn state. The prompt is frozen per incarnation, so
> a per-turn conditional becomes a session-long falsehood — the D01.1/DEBT-22 lesson,
> enforced by `PromptContext` carrying no volatile fields.

| invariant | held by | proven in |
|---|---|---|
| I1 | audit + log dicts are comprehensions over `CONTRIBUTORS` | `test_one_list_composes_audits_and_logs.py` |
| I2 | dispatcher `try/except` per contributor | `test_a_failing_contributor_never_costs_the_turn.py` |
| I3 | golden-prompt comparison against the pre-change composer | `test_the_prompt_is_byte_identical.py` |
| I4 | the tuple's order asserted explicitly | `test_one_list_composes_audits_and_logs.py` |
| I5 | `PromptContributor` is not `Tool`; tool array unchanged across a build | `test_a_contributor_never_reaches_the_waist.py` |
| I6 | `PromptContext` has no per-turn field to read | `test_a_contributor_cannot_read_the_turn.py` |

I3 is the migration's whole safety story and is written FIRST.

## Configuration

None. No `stackowl.yaml` key is added, moved or renamed. The contributor list is code,
because its order is behaviour and an operator reordering the cached prefix by editing
YAML would invalidate every session's prompt cache with no way to see why.

## Observability

At INFO, because production runs at INFO:

- `[pipeline] assemble: exit` — gains `capabilities_len`, and gains it *by construction*
  rather than by someone remembering. Field set becomes exactly `{name}_len` for the
  seven, plus the existing non-part fields.
- `[pipeline] assemble: contributor failed` (ERROR) — contributor name + exception.

```bash
# Which parts compose the prompt, and did any go missing?
grep -h 'assemble: exit' ~/.stackowl/logs/stackowl*.jsonl \
  | jq -c '.fields | with_entries(select(.key|endswith("_len")))' | tail -5
# PASS: seven *_len keys matching the contributor names, capabilities_len among them.
```

Glob the ROTATED logs — `stackowl.jsonl` rotates daily, and querying only the current
file is how a working feature reads as "never fired" (the D08.3 lesson).

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| One contributor raises | dispatcher try/except (I2) | that part is `""`; others compose | a slightly shorter prompt; nothing else |
| Every contributor raises | same | `system_prompt=None`, as today | existing degraded path, unchanged |
| A contributor returns non-`str` | dispatcher coerces + logs ERROR | treated as `""` | nothing |
| Contributor added to the tuple, forgotten elsewhere | **impossible by construction** (I1) | — | — |
| Order changed accidentally | I4 test + `prompt_hash` moves | test fails before ship | — |

  implementation. We take the *idea* that context assembly is a named category and
  reject the *object*: our evidence is seven contributors and one engine, so we build
  the contributor interface and no engine. We also decline their plugin discovery for
  this category, on the grounds that third-party code composing the system prompt is a
  larger trust surface than a gated tool, and that seven extension points with zero
  installed plugins is not evidence for an eighth.
