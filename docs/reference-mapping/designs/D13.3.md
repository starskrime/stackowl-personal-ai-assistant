# TUI transport — we already split, at a different seam and for a better reason

> **Status:** live — no change needed; the map's description of our side was incomplete
> **Map item:** D13.3 · TUI transport (`DIVERGENT`)
> **Source:** `src/stackowl/ipc/` (frames, codec, connection, client),
> `src/stackowl/channels/socket_adapter.py`, `src/stackowl/config/runtime_settings.py`
> **Config:** `runtime.split_process` (default **True**), `runtime.socket_path`
> **Last verified:** 2026-09-06, against commit `097c73af` — Verification section RUN

## Why this exists

The reference platform runs newline-delimited JSON-RPC over stdio between Node and Python:
TypeScript owns the screen, Python owns sessions, tools, model calls and slash logic. The
Ask: *"In-process is simpler and works. Any reason to split?"*

**The question contains a false premise about our own side, and correcting it is the
answer.** The map recorded us as "Textual in-process, plus an EventBus for live progress".
That describes the mono path. We already run a two-process split, it is ON by default, and
it is what this deployment is running right now.

## Model — the same transport, a different seam

`ipc/__init__.py` states it in one sentence:

> "Local IPC transport for the gateway<->core two-process split. A **DURABLE gateway**
> process holds client connections (TUI, channels) and a **RESTARTABLE core** process runs
> the agent logic; they talk over a local unix-domain socket using **newline-delimited JSON
> frames**."

| | Reference platform | StackOwl |
|---|---|---|
| transport | newline-delimited JSON-RPC over **stdio** | newline-delimited JSON frames over a **unix socket** |
| seam | **language** — TypeScript owns the screen | **lifecycle** — the gateway outlives the core |
| what crosses it | screen events ↔ agent logic | `ingress`/`steer`/`stop`/`clarify_reply`/`query_running` → core; `chunk`/`send_text`/`progress_event`/`clarify_ask`/`running_state`/`hello`/`restart_notice`/`goodbye` → gateway |
| why | one language per concern | **the core exec-replaces itself on code change while the gateway keeps the user's connection** |

**Ours is the stronger reason, and it is the one that makes self-modification safe.** A
platform that rewrites its own code has to restart to load it; if the process holding the
user's connection is the same one being replaced, every self-improvement drops the
conversation. The split exists so `CodeWatcher` can exec-replace the core while the gateway
holds the socket — which is why `runtime.split_process` defaults True and its own
description says "the durable gateway holds the TUI while the core can be restarted on code
change".

The core is deliberately unaware of any of it: `socket_adapter.py` — "In the split, the core
runs the *entire* existing pipeline unchanged; its only [job is the bridge]". The frames
"mirror the existing in-process seams … with no semantic change", so the same code runs
either way.

## Lifecycle

```
   user ──▶ gateway process (DURABLE)                 core process (RESTARTABLE)
              ├─ CLIAdapter / Textual TUI    ingress ──▶  the entire pipeline,
              ├─ Telegram / Slack / …        steer   ──▶  unchanged and unaware
              └─ SocketChannelAdapter ◀── chunk, progress_event, clarify_ask …
                        │
                        └── holds the connection while CodeWatcher
                            exec-replaces the core beneath it
```

`split_process=False` collapses this to one process and the same code path runs; the frames
were designed to mirror the in-process seams precisely so that stays true.

## What remains in-process, and the one time it cost something

Textual runs inside the **gateway**, and that is the only "in-process" left. It has cost
exactly one measured incident, recorded in `HeadlessCliAdapter`'s own docstring:

> "measured on the live box 2026-08-14: the gateway sat at **100.3% CPU** — a whole core,
> continuously — and a py-spy profile put ~95% of it in Textual's Linux input driver."

The cause was a busy-wait on EOF: `start.sh` launches with stdin at `/dev/null`, a `select()`
on which is always ready, so the input thread woke, read nothing, and selected again forever.
**The fix was a role split, not a process split** — `HeadlessCliAdapter` keeps the `cli`
channel and its contract while dropping the terminal. Splitting the screen into another
process would not have helped: the busy-wait would simply have burned a core over there.

## Invariants

1. **The core runs the entire pipeline unchanged.** The split is a transport, not a second
   implementation — the same guarantee D13.2 adopted as a written rule.
2. **Frames carry only JSON-serialisable scalars**, mirroring `IngressMessage` and
   `ResponseChunk`, so no callable or asyncio object can cross the boundary.
3. **`split_process=False` remains a working path**, and the frames were shaped to make the
   two modes semantically identical rather than merely similar.

## Configuration

| Key | Default | Notes |
|---|---|---|
| `runtime.split_process` | **True** | two processes over a local socket; False forces the single-process compat path |
| `runtime.socket_path` | `None` | derives from the StackOwl home run dir |
| `runtime.auto_restart.*` | — | only takes effect when `split_process` is true |

## Observability

The split is visible in the boot line's `surface` field, added by D13.1 for a different
reason and useful here: the core reports `socket:cli` and the gateway `headless`.

```bash
cat ~/.stackowl/logs/stackowl.jsonl \
  | jq -r 'select(.msg == "[startup] gateway: starting CLI adapter") | .fields.surface' \
  | sort | uniq -c
```

Before D13.1 the two processes were indistinguishable in the logs, which is why boot markers
appeared in pairs and made several counts in this programme read as double what they were.

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| The core dies or is replaced | the gateway's connection handling | `restart_notice` / reconnect; the gateway holds the client | a pause, not a dropped session |
| A frame fails to decode | `FrameDecodeError` in the codec | structured error, connection not corrupted | — |
| Textual busy-waits with no TTY | *fixed 2026-08-14* | `HeadlessCliAdapter` | — |
| Both processes' logs look identical | *fixed by D13.1* | `surface` on the boot line | — |

## Verification

```bash
# The split exists, is the default, and states its own reason.
grep -n "split_process" -A 8 src/stackowl/config/runtime_settings.py | grep -E "default|durable"
#    expect: default=True, and "the durable gateway holds the TUI while the core can be restarted"

head -8 src/stackowl/ipc/__init__.py
#    expect: newline-delimited JSON frames over a unix-domain socket

# It is what this deployment is actually running.
cat ~/.stackowl/logs/stackowl.jsonl \
  | jq -r 'select(.msg == "[startup] gateway: starting CLI adapter") | .fields.surface' \
  | sort | uniq -c
#    expect: both socket:cli (core) and headless (gateway)
```

**Measured 2026-09-06:** `default=True` with that description; the docstring as quoted; the
live log alternates `socket:cli` and `headless`.

## Decision

**No change.** The split the Ask asks about exists, is on by default, uses the same transport
family, and is drawn at the seam that matters for a self-modifying platform. Splitting the
*screen* into a third process would buy the language separation we do not need — we are
single-language by design — at the cost of another boundary to keep semantically identical.

The map's verdict `DIVERGENT` stands, but the divergence is the **seam**, not the transport,
and the map's description of our side has been corrected.
