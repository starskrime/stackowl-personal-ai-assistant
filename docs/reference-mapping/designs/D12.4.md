> `src/stackowl/channels/telegram/adapter.py`, `src/stackowl/config/progress_settings.py`

> **Last verified:** 2026-09-06, against commit `b78670d6` — Verification section RUN

## Why this exists

The reference platform bridges sync agent callbacks to async delivery in
`gateway/stream_consumer.py`: queue the deltas, then **progressively edit a single
message** through the edit transport, rate-limited and buffered. The Ask: *"Do we
edit-in-place, or post successive messages? (Affects flood-control, which has bitten us.)"*

**We edit in place, and we have since before the question was asked. The defect was that
nothing could tell you so.**

## Model — one mutating status message, one clean answer

`TelegramProgressView` is a per-turn state machine over exactly one Telegram message. Its
own docstring states the shape: a turn's progress chunks drive a SINGLE message that edits
through states ("Working on it…" → "Searching the web…" → "Writing your answer…"), backed by
a re-issued typing indicator, collapsing to a "✓ done in 34s" footer once the answer lands
as a separate, clean message. It is wired at `adapter.py:513`, constructed on the first
chunk whose `kind == "progress"`.

| | Reference platform | StackOwl |
|---|---|---|
| what streams | model deltas, buffered | **semantic progress states**, not deltas |
| the transport | progressive edit of one message | progressive edit of one message |
| rate limit | buffered + rate-limited | `edit_min_interval_s`, coalesced |
| the answer | edited into the same message | a **separate** message; status becomes a footer |
| turn that fails | — | `abort()` — an honest failure footer |

**The one place we genuinely post successive messages is a long ANSWER.** Telegram caps a
message at 4096 characters, so `TelegramMessageSplitter` splits past it and `send_text`
dispatches N parts. That is the successive-messages half of the Ask, and `part_count` is
the number flood control actually spends.

## The finding — the mechanism was fine, the evidence was impossible

Measured 2026-09-06 across the full retained window (10 files, 555,598 records, 1,159 from
the telegram module):

| line | count | why |
|---|---|---|
| `adapter.send_status` (creates the one mutating message) | **0** | its success path logged **nothing**; only a DEBUG on flood-ban and a WARNING on failure |
| every line `progress_render.py` emits | 4 kinds, **all WARNING** | each on a failure branch |
| `adapter.edit_message: edit failed — fail open` | **4 (ERROR)** | the *only* production trace of edit-in-place |
| `adapter.send_text: decision split` (`part_count`) | **0** | logged at DEBUG; production runs at INFO |

So the sole evidence that in-place editing existed was evidence of it **failing**. D12.4's
own closing check had already walked into this: bounding the grep reported CLOSEABLE on
those four hits, and *"counting a FAILURE as evidence that in-place editing works is the
denominator error twice in one day."*

**That is why this item sat at six stages with an empty record.** Not because the work was
skipped — because no volume of traffic could ever have answered its Ask, so there was
nothing honest to write down. A zero here meant "impossible", not "not yet".

This is the D08.1 defect, and the programme has now paid for it three times: D08.1's fourth
acceptance check, D11.3's frame that was rendered and logged nowhere, and this.

## What shipped

**One INFO line per turn**, at teardown where `settle()` and `abort()` already converge:

```
[telegram] progress.turn: streaming summary
  outcome=settled|aborted|never_shown  messages_sent=1  edits_applied=5
  edits_suppressed=6  typing_calls=2  progress_events=7  api_calls=8  elapsed_s=34
```

Per **turn**, not per edit: at ~1 edit/sec a 50s turn would emit fifty lines to state one
ratio. `messages_sent` against `edits_applied` is the edit-in-place answer; `api_calls` is
the flood-control answer; `edits_suppressed` is the rate limiter's own work made visible.

**And the never-shown branch reports too.** `settle()` used to return early when no status
was ever displayed. That is the flicker guard *working*, and `api_calls=0` is the number
that proves it — logged only on the branch that showed something, the cheapest turns would
have been the invisible ones.

**`decision split` promoted DEBUG → INFO**, because `part_count` is the other half of the
same Ask, hidden by the same cause.

## Invariants

1. **One status message per turn.** `messages_sent` is 0 or 1, never more; a value above 1
   would mean the edit transport had been abandoned for successive posting.
2. **Observability never breaks a turn.** The summary is wrapped like every other call in
   this module — progress is best-effort by design, and a summary that could raise would
   turn an observability line into a way to lose a turn.
3. **Both halves of the Ask stay answerable at INFO**, guarded by
   `tests/channels/telegram/test_the_streaming_path_says_what_it_did.py`.

## Configuration

| Key | Default | Notes |
|---|---|---|
| `progress.telegram_edit_min_interval_s` | 1.0 | stays under Telegram's ~1 edit/sec cap |
| `progress.flicker_guard_ms` | — | a sub-guard turn never flashes a status |
| `progress.typing_reissue_interval_s` | 4.0 | Telegram clears typing after ~5s |
| `progress.tick_interval_s` | 3.0 | ticker cadence across event-less gaps |
| `progress.elapsed_after_s` | 10.0 | when the counter appears |
| `progress.reassure_after_s` | 30.0 | when the phrase switches to reassurance |

Nothing was added. The mechanism already shipped ON.

## Observability

The per-turn summary above, plus `adapter.send_text: decision split` with `part_count`.
Together they answer the Ask from the logs alone: one message edited N times for the
status, one-or-N messages for the answer, and the total Bot API calls both spent.

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| An edit fails | `edit_message: edit failed — fail open` (ERROR) | fail open; the answer is delivered independently | the status stops updating; the answer still arrives |
| A turn ends without an answer | `abort()` | an honest failure footer | "failed after Ns" instead of a status stuck ticking |
| Flood ban | `send_status` skips outright while banned | best-effort | no status; the answer path has its own guard |
| The streaming path goes silent again | the summary line disappears | — | nothing, which is the point |

The third row is the incident this design already survived: a ~10h `RetryAfter` ban caused
by every send path hammering with no backoff. The status path now skips outright during a
known ban rather than spending one call and one traceback per 3s tick.

## Verification

```bash
uv run pytest tests/channels/telegram/test_the_streaming_path_says_what_it_did.py -q
#    expect: 7 passed

uv run pytest tests/channels -q
#    expect: 0 failed

# Both halves of the Ask are emitted at INFO, asked of the LOGGERS not the file.
uv run python -c "
import ast, pathlib
for f, needle in (('progress_render.py', 'progress.turn: streaming summary'),
                  ('adapter.py', 'send_text: decision split')):
    t = ast.parse((pathlib.Path('src/stackowl/channels/telegram')/f).read_text())
    lv = {n.func.attr for n in ast.walk(t)
          if isinstance(n, ast.Call) and isinstance(n.func, ast.Attribute) and n.args
          and isinstance(n.args[0], ast.Constant) and needle in str(n.args[0].value)}
    print(f, sorted(lv))"
#    expect: progress_render.py ['info'] and adapter.py ['info']
```

**Measured 2026-09-06:** 7 passed; 664 passed / 0 failed; both lines report `['info']`.

**Mutation-proven, because a guard that cannot fail is decoration.** Three mutants, each
verified applied and then restored from a file copy: the summary demoted to DEBUG — the
exact defect this item exists to fix — took **5 of 6** tests red; dropping the
`edits_suppressed` counter took 1; restoring `settle()`'s early return took 1. Final re-run
240 passed.

## Decision

**Edit-in-place, confirmed and now evidenced — no change to the mechanism.** The map's
verdict `PARTIAL` was right about the record and wrong about the code: our StackOwl line
said "`ResponseChunk` with `kind=answer|progress` and a progress renderer", which describes
the plumbing and not the behaviour. We do what the reference platform does, at the same
seam, with the same rate limiting, plus an honest failure footer they have no equivalent
for.

The gap was never the streaming design. It was that a subsystem observable only through its
failure branches cannot be reasoned about, defended, or closed.
