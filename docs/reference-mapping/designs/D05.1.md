# Registry & auto-discovery — and an executable tree inside a writable one

> **Status:** live — shipped ON, no flag
> **Map item:** `D05.1` (wave 2) — verdict **corrected `PARITY` → `PARTIAL`**
> **Source (to change):** `tools/registry.py` (`with_defaults`), `paths.py` (`skills_dir`), `skills/loader.py`
> **Source (new):** `tools/_infra/discovery.py` — AST-prefiltered discovery
> **Migration:** a one-shot, idempotent move of `~/.stackowl/workspace/skills` → `~/.stackowl/skills`
> **Config:** none · **Ladder rung:** 1 — extend existing code
> **Last verified:** 2026-08-03, against commit `0d6954f6`

> **⚠ THIS ITEM WAS RE-VERDICTED AND WIDENED.** The map called it `PARITY` with a
> "small" gap. Both halves of its StackOwl description are wrong, and the item
> contains a live security hole. Details below rather than in a footnote.

## The map is wrong about us

> *"**StackOwl.** `tools/registry.py` with auto-discovery…  **Gap.** Small: no
> `dynamic_schema_overrides`, no AST prefilter."*

**There is no auto-discovery.** `ToolRegistry.with_defaults()` was 61 explicit
imports and 60 `registry.register(...)` calls (measured, not estimated). The only dynamic
registration paths in the tree are:

1. `LearnedToolLoader` — reads **declarative JSON specs**, and its docstring
   explicitly refuses to execute model-authored Python "(it runs arbitrary code
   at boot)".
2. **`SkillLoader`** — globs `tools/*.py` under the skills tree and calls
   `importlib` `exec_module()` on each. This *is* StackOwl's auto-discovery, and
   it does exactly what the other loader refuses to do.

Two loaders, opposite positions on the same question, and only one wrote down why.

## The security hole, confirmed by running it

Skills live **inside the tree `write_file` is confined to**:

```python
>>> resolve_in_workspace("skills/evil/tools/pwn.py")
PosixPath('/home/boss/.stackowl/workspace/skills/evil/tools/pwn.py')
>>> StackowlHome.skills_dir()
PosixPath('/home/boss/.stackowl/workspace/skills')
```

and `skills/loader.py:290-299` `exec_module()`s every `tools/*.py` it finds
there at boot.

**So any tool that can write the workspace gets arbitrary Python executed at next
start.** `write_file` is a base, always-presented tool, not consent-gated as
consequential. After `D05.5`, sandboxed PTC code can call `write_file` too — so a
script can escape the sandbox with a **one-reboot delay**, partly bypassing the
escape fence that item built the day before.

The realistic chain on a personal box is not an attacker with shell — it is
**fetched web content influencing what the model writes**, which then executes at
the next restart.

**Measured before proposing a fix: 420 skills on disk, ZERO ship a `tools/*.py`.**
The capability is entirely unexercised. That makes relocation the conservative
option, not the cautious-sounding one.

### The fix: move the executable tree out of the writable one

```python
# paths.py
- return cls.workspace() / "skills"      # inside write_file's confinement
+ return cls.home() / "skills"           # a sibling of it, not a child
```

**Skill installation is unaffected**, and this was checked rather than assumed
because it was the operator's first question. `skill_manage`, `synthesize_skills`,
`SkillLoader`, the scheduler, the orchestrator and builtin-seeding **all** resolve
through `StackowlHome.skills_dir()` and write with a direct `Path.write_text()`.
**None goes through `write_file`'s guard.** The location was never load-bearing
for installation — only for the hole. The only hardcoded `workspace/skills`
strings are in five **docstrings**.

Rejected: a path-guard rule refusing `.py` writes under `skills/**`. It is a rule
someone must re-apply for every future executable tree — which is precisely how
this hole appeared. Structure beats policy here.

## Auto-discovery

Adopted (operator decision, against my recommendation to keep the explicit list —
my argument was reviewability, and the ergonomics won).

**Hermes' technique, a different target.** Their AST predicate looks for a
top-level `registry.register(...)` *call*, because their tools self-register.
Ours are `Tool` *subclasses* that `with_defaults()` instantiates, so their
predicate would match **nothing** in our tree. Port the design, never the code.

```
glob tools/**/*.py
   │
   ▼  AST: does the module define a top-level class inheriting Tool?
   │     (helpers, schemas, _infra never imported)
   ▼  import the survivors
   │
   ▼  issubclass(obj, Tool) and not abstract   ← the real check
   │
   ▼  instantiate
```

**Verified equivalence, not a leap of faith.** Prototyped against the live tree:

| | |
|---|---|
| modules matched by the AST predicate | **61** |
| helper modules never imported | 69 |
| instantiable `Tool` subclasses found | **77** |
| registered but not discovered | **0** |
| discovered but not registered | **0** |

Exact parity with the hardcoded list. The 18 browser subclasses come free:
`_BrowserTool(Tool)` is itself top-level in the same module, so the file matches
and every subclass in it is found by `issubclass`.

### The defect this design would have shipped

`with_defaults()` does not merely instantiate — it **shares dependencies**:

```python
_undo_store = UndoStore()                    _plan_store = PlanStore()
registry.register(EditTool(store=_undo_store))       TodoTool(store=_plan_store)
registry.register(ApplyPatchTool(store=_undo_store)) UpdatePlanTool(store=_plan_store)
registry.register(UndoWriteTool(store=_undo_store))
```

Every one of those constructors accepts `store=None` and falls back to building
**its own**. So naive discovery — `obj()` for everything it finds — would compile,
import, register 77 tools, pass a smoke test, and leave **`undo_write` silently
unable to undo anything `edit` did**, because they would no longer share a store.

That is the `D05.3` lesson recurring (a sweep that looks complete and isn't),
caught at architect this time rather than by a test.

**Design consequence — discovery yields CLASSES, wiring stays explicit:**

- 72 tools: discovered and auto-instantiated (11 of them have optional
  constructor params and are listed in `_DEFAULT_CONSTRUCTIBLE` to record that
  their defaults are what `with_defaults` always passed).
- **5 tools in 2 groups**: `edit`/`apply_patch`/`undo_write`, `todo`/`update_plan`
  — constructed by an explicit wiring table that owns the shared instance.
- `LearnedShellTool` is the only class with a *required* constructor arg and is
  deliberately **not** discoverable this way; it is registered per-spec by
  `LearnedToolLoader`.

**And a guard, because the failure is silent:** discovery must **refuse to
auto-instantiate** any class whose constructor takes a parameter unless it is
named in the wiring table. Adding a shared-dependency tool and forgetting the
table then fails loudly at boot instead of quietly breaking undo.

## Declined: `dynamic_schema_overrides`

The map's headline ask, and the one thing it correctly identifies as missing.
**Declined**, consistent with what `D05.2` already shipped.

It makes a tool's description a function of live config, so the tools array moves
whenever config does — the exact instability `D05.2` spent two items removing. I
had already written in that doc that importing it would be *"precisely
backwards"*; adopting it now would be arguing against my own shipped work without
new evidence.

**Measured, not asserted:** 13 of 77 schemas state a numeric limit, and
`delegate_task` — the very tool Hermes rewrites dynamically — has a purely
generic description here with no limits in it. The problem the mechanism solves
is one we do not currently have. Their limits are per-install user config; ours
are mostly module constants.

If a StackOwl schema ever does misstate a live setting, the seam already exists:
`D05.3` invalidates `D05.2`'s memo on a capability change, and a config change
could use the same path.

## Invariants

> **I1.** No executable tree lives inside a model-writable one. The reason
> `skills_dir()` moves rather than gaining a write rule.
>
> **I2.** Discovery must reproduce the current registered set exactly. Verified
> empirically before implementation: 77 found, 0 missing, 0 extra.
>
> **I3.** A tool with constructor parameters is **never** auto-instantiated. It is
> either in the explicit wiring table or discovery fails loudly. Silently giving
> a tool a private dependency is the `undo_write` bug.
>
> **I4.** Helper modules are never imported. That is the AST prefilter's whole
> purpose — 69 of 130 modules under `tools/` define no tool.
>
> **I5.** The tools array stays a function of the session, not of config
> (`D05.2`). This is why `dynamic_schema_overrides` is declined.

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| A shared-dependency tool added without wiring | **`I3` guard — loud boot failure** | Add it to the table | Boot refuses, with the class named |
| A `.py` dropped in `tools/` becomes model-callable | — | **Accepted** — that is the point of discovery | A new tool appears |
| Skills migration runs twice | idempotent move | No-op | Nothing |
| Skills migration interrupted half-way | — | **Not detected.** Must copy-then-swap, never move-in-place | Some skills missing |
| A skill relies on `tools/*.py` | — | **None on this box — 0 of 420 use it** | — |
| Discovery imports a module with an import-time side effect | — | **Not detected.** The AST gate reduces but does not eliminate this | Slower or surprising boot |

Row 4 is why the migration copies to the new location and only removes the old
one after a successful verify — a half-completed `move` would lose skills.

Re-measured every load-bearing claim in this document. Three hold. One did not.

| claim | 2026-08-03 | 2026-08-30 |
|---|---|---|
| no skill ships a `tools/*.py` | 0 of 420 | **0 of 21** — denominator moved, numerator did not |
| the relocation closed the exec hole | asserted | **verified by running the original probe** |
| the registry discovers 77 tools | 77 | **77** |
| AST prefilter imports 61 modules | 61 of 130 | **61 of 116** — the 61 holds, the denominator drifted |
| the invariant is asserted at startup | claimed in this doc | **nothing called it** |

The corpus fell from 420 to 21 because the operator purged the learned skills on
2026-08-29. That moves the denominator of the "unexercised exec path" claim but not
its conclusion: still zero skill tool modules anywhere in the tree.

### The defect

`skills_dir_is_outside_workspace()` shipped described as *"the security property
this item exists to establish, expressed as something CHECKABLE rather than as a
comment"*, and `skills_dir()`'s docstring stated *"Verified by
`skills_dir_is_outside_workspace`, which the startup path asserts"*. Measured: its
only references anywhere in `src/` were that docstring and `__all__`. Nothing
called it. The property was, precisely, a comment.

This is not cosmetic. The function encodes a case nothing else can see:
`STACKOWL_DATA_DIR` relocates `workspace()` but not `home()`, so
`STACKOWL_DATA_DIR=~/.stackowl` silently makes the workspace the **parent** of the
skills tree and restores arbitrary-code-execution-at-boot. Nothing would have
noticed.

### The fix — an alarm and an actuator

**Alarm.** `StackowlHome.ensure_exists()` now logs the invariant on every boot:
INFO on the healthy path, ERROR with remediation when the trees overlap. INFO on
*success* is deliberate — production runs at INFO, and an invariant that speaks
only when broken can never be confirmed to have run at all. It lives in
`ensure_exists()` because that method's own comment already calls it "the one
place every process calls on the way up".

**Actuator.** `SkillLoader._load_tools()` now refuses to `exec_module()` any skill
tool module while the invariant is false. Reporting a hole does not close it.

`M8` unwires the actuator and only `test_the_loader_REFUSES_to_exec_when_the_trees_overlap`
dies; `M9` unwires the boot check and only
`test_boot_reports_the_invariant_on_the_HEALTHY_path` dies. One mutation, one
test, no overlap. The counterweight — `test_the_loader_still_execs_on_the_healthy_path`
— writes a real `.py` that touches a marker file on import and asserts the marker
**exists**, because a fence that always refuses is not a fence, it is an outage,
and a 0-of-21 denominator means nothing else would have caught that.

### The migration destroyed 419 skills before it worked

Recorded here because the design doc is where the next person looks. See
`INCIDENT-2026-08-03-skills-migration` in `progress.yml` for the full account.

``ensure_exists()`` creates ``skills/{builtin,installed,user,learned}`` **before**
the migration runs. The first version skipped any entry whose destination already
existed — treating those four freshly-created **empty** directories as "already
migrated" — and verified only that each *name* existed at the target. Four empty
dirs satisfied that, verify passed, and ``rmtree`` deleted the source.

Fully recovered: the ``skills`` table stores ``body_text`` and ``manifest_json``,
so all 421 rows were rewritten to disk. **The data survived because a cache
happened to hold the source of truth. That was luck, not design.**

The fix is two lines of principle: ``copytree(dirs_exist_ok=True)`` because an
existing destination means *partially* migrated, and **verify by counting files**
because a name check passes on an empty directory. Both are pinned by
``test_migration_survives_ensure_exists_having_precreated_the_subdirs``, which
reproduces the real precondition rather than a synthetic one.

### Prior art, and where we deliberately diverge

Hermes globs `tools/*.py`, cheap-text-prefilters for `"registry"` and
`"register"`, AST-parses the survivors for a **top-level `registry.register(...)`
call**, then imports only those. `ToolEntry` carries `check_fn`, `requires_env`,
`max_result_size_chars` and `dynamic_schema_overrides`.

**Adopted:** the discovery technique — prefilter, then import only real tool
modules — and the reason for it (helpers must never be pulled in by accident).

**Diverged:**

1. **A different AST target**, because our tools are subclasses rather than
   self-registering calls. Their exact predicate matches nothing here.
2. **Explicit wiring survives discovery.** They have no shared-dependency
   construction; we have two groups of it, and auto-instantiating them would
   silently break undo. Discovery yields classes; wiring stays code.
3. **`dynamic_schema_overrides` declined** — see above. This is the only item in
   the programme so far where we have deliberately *not* adopted the thing the map
   named as the gap, and the reason is our own prior work rather than taste.
4. **`requires_env` not adopted.** `D05.3` already covers availability through
   `HealableResource`, and a declarative env-var list would be a second, weaker
   mechanism beside it.

### How the two Laws hold

**Law 1 — per-conversation prompt caching is sacred.** Protected by *declining*
`dynamic_schema_overrides`. Discovery runs once at boot and changes no schema.

**Law 2 — the core is a narrow waist.** Unchanged: discovery alters *how* the
same 77 tools reach the registry, not how many the model sees.
