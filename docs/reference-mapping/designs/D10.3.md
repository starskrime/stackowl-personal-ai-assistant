# Active vs. Optional Skills — the Wrong Instrument for the Real Problem

**Item.** D10.3 · Active vs. optional skills — `MISSING`
**Last verified.** 2026-09-07, commit `3203353c` — all three checks re-run (5 passed;
663 passed, 0 failed; 10 of 25) and the closing query re-run on the GLOB, where it still
returns exactly 2. (Previously 2026-09-06/`c27dbde7`, and 2026-09-04/`6a2bdb02` when it
was still OPEN.)

## Why this exists

D10.3 asks one question: *"Do we have enough skills for this split to matter yet?"* The
reference platform ships 69 active skills and 111 optional ones, and the split exists to
keep heavy-dependency and niche skills out of the default set.

**The answer is no — and measuring it showed the premise is wrong in a way that matters
more than the answer.** We have 39 registered skills: 14 builtin, 25 learned. Not enough
for a split by any reading. But those 25 learned skills are **roughly eight concepts**:

| family | n | members |
|---|---|---|
| VERIFIER | 7 | `rca-evidence-verifier`, `rca_evidence_brief_verifier`, `verify_rca_evidence`, `verify-incident-hypothesis`, `evidence-brief-verifier`, `incident_hypothesis_evidence_check`, `evidence_verifier_rejection` |
| GATHERER | 3 | `evidence_brief`, `rca_evidence_brief`, `incident-evidence-brief` |
| OWLS | 2 | `owl-name-collision-check`, `owls-list` |
| OWLBUILD | 2 | `incident_owl_build`, `incident_owl_build_stop` — **byte-identical descriptions** |

Every one of these was confirmed by reading its `description` and `when_to_use`, not
inferred from its name. The seven VERIFIERs all say the same thing: *use when acting as
the verifier owl in a fixed-stage incident RCA, judging a hypothesis against an evidence
brief.*

So the split is the wrong instrument. Splitting a catalogue whose problem is redundancy
produces a redundant active set and a redundant optional set. **The catalogue does not
need dividing; it needs to stop growing sideways.**

## Model

The mint-time duplicate gate had three rungs, and every one of them is **lexical**:

| rung | question it answers | blind to |
|---|---|---|
| `_cluster_already_covered` | did we learn this from the same traces? | the same lesson from new evidence |
| `base_name` | is this a `-N` variant of something we hold? | rearrangements, separators |
| `canonical_key` (ESC-52) | is this the same name, rearranged? | synonyms and supersets |

All three are *true answers to lexical questions*. `verify_rca_evidence` and
`evidence-brief-verifier` share no tokens at all, so no arrangement of their letters will
ever make them equal.

**That is the root cause, and it is a ladder, not a bug.** `base_name` missed
rearrangements, so `canonical_key` was added. `canonical_key` misses synonyms, so the
obvious next move is a fourth lexical rule — and it would be blind to the fifth family.
Each fix extended the lexical family instead of changing the KIND of question asked.

**What else does that cause reach?** Every "have I already got one of these?" decision made
by comparing names. `owl-name-collision-check` is itself a learned skill *about* doing this
for owls — the platform learned the problem exists and filed it as a skill.

The instrument for the other kind of question was already built, populated and unused:
`store.semantic_recall` does cosine over enabled skills, and **39 of 39 skills carry an
embedding**. Built but not wired — shape 5 in `CLAUDE.md`.

## Lifecycle

1. `_cluster_already_covered` — same traces? stop.
2. `base_name` / `canonical_key` — same name, any arrangement? reinforce.
3. **`_semantic_twin` — nearest learned skill ≥ `_SEMANTIC_TWIN_MIN`? reinforce.**

The third rung feeds the **same** reinforce-and-audit action as the second: revive the
skill, write a `reinforce` audit row, mint nothing. One mechanism with a new input, not a
second gate — the standing rule against a second engine applies inside the learning loop
as much as outside it.

Narrowed to the **learned** corpus, the same population the lexical rungs read. A proposed
lesson resembling a *builtin* skill is a different question with nothing to reinforce, and
is deliberately out of scope.

## Configuration

`_SEMANTIC_TWIN_MIN = 0.90`. Ships ON; there is no flag.

**Measured, not chosen.** Over all 741 pairs of the live corpus on 2026-09-04:

| population | n | range |
|---|---|---|
| confirmed duplicate pairs | 26 | 0.828 – 0.952 |
| everything else | 715 | max **0.875** |

The distributions **overlap**, so no threshold separates them cleanly, and this one is set
for precision over recall: at 0.90 it catches 6 of 26 known duplicate pairs and flags
**zero** non-duplicates. At 0.85 it would catch 21 and flag 5.

The asymmetry is the whole argument. A missed duplicate sits in the catalogue where it can
be seen and merged. **A wrongly suppressed skill is a capability that never existed, and
nothing reports it** — the same reason D10.1's stray detector reports instead of adopting.

## Failure modes

| Failure | What happens | What notices |
|---|---|---|
| No embedder wired | Semantic rung returns `(None, None)`; lexical rungs unaffected | A dedicated test — the new rung must never become a prerequisite for the old ones |
| Embedder raises | Caught, logged, fall through to mint | The WARNING |
| No `embed_text` from the caller | Rung skipped without an embedding call | A test asserts the embedder is not even reached |
| Threshold too low | A real skill is never minted | **Nothing.** This is why 0.90, not 0.85 |
