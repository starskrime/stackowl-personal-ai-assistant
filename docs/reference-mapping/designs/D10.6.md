# Skill Catalogue Rendering

> **Status:** live
> **Map item:** D10.6
> **Source:** `src/stackowl/skills/instruction_injector.py` (361 lines)
> **Config:** none user-facing — module constants only (see Configuration)
> **Last verified:** 2026-09-02, against commit `cf4a7842`

## Why this exists

The skill catalogue is how the model learns what it can already do. It is injected into the
frozen system prompt under a character cap, and the corpus grows faster than the cap.

**The old behaviour was a cliff.** Entries were rendered at full width —
`description — when_to_use` — and placed in order until the budget ran out. Everything after
that point fell to a bare name in the catalogue index. So a handful of skills carried a rich
blurb and the rest carried no retrieval signal at all, decided by **position** rather than by
anything meaningful.

Measured in production on 13 consecutive live turns before the fix: `skills_len` sat at
**3,875 of the 4,000 cap** every time. The cap was not theoretical — it bound every turn.

## Model

| Tier | Renders | Set by |
|---|---|---|
| `FULL` | name + the skill body | never sent in by `assemble`; reachable only by explicit request |
| `SUMMARY` | `- name: description — when_to_use` (lean: `- name: description`) | everything `assemble` passes |
| `CATALOG` | bare name in a comma list | reached only by **demotion** inside `render` |

Two budgets a reader will confuse:

| Name | Value | What it bounds |
|---|---|---|
| `_DEFAULT_CAP` | 4,000 | the whole rendered block |
| `catalog_reserve` | `min(sum(len(name)+2), cap × 0.25)` | floor under the index, so names can never be starved by text |
| `text_budget` | `cap − catalog_reserve` | what SUMMARY and FULL entries share |
| `_SUMMARY_BUDGET_RESERVE` | 800 | chars FULL may not consume, so SUMMARY is not starved |

## Lifecycle

```
render(owl, tiered, cap)
  ├─ catalog_reserve = min(Σ name costs, cap × CATALOG_RESERVE_SHARE)
  ├─ summary_cost    = Σ full-width cost of every SUMMARY entry
  ├─ lean_summaries  = summary_cost > cap − catalog_reserve − |_STANDING|   ◄── ONE decision
  └─ for each entry, in relevance order:
        FULL    → fits? place : demote to SUMMARY
        SUMMARY → fits (at the chosen fidelity)? place : demote to CATALOG
        CATALOG → bare name, trimmed only if the index itself overflows
```

**Priority order, and it is the whole design:** fidelity is decided **once, before placement**.
Deciding it per entry helps exactly one — the entry straddling the boundary — because the
budget is spent in order and everything after it is already out of room. Measured: the
per-entry version moved 11 descriptions to 12; the global version moved it to 19.

## Invariants

> **I1.** No skill is ever removed entirely — it degrades to a bare name, never to nothing.
> **I2.** Fidelity is chosen once per render, not per entry: no entry keeps `when_to_use`
> while another is reduced to a bare name.
> **I3.** A corpus that fits at full width keeps its `when_to_use` — no gratuitous trimming.
> **I4.** The rendered block never exceeds `cap`.
> **I5.** Going lean never *reduces* the number of entries carrying a description.
> **I6.** `_entry` never reads `when_to_use` directly; the trimming rule lives in one place.

All six map to tests in `tests/skills/test_the_catalogue_degrades_evenly_not_alphabetically.py`.

## Configuration

| Constant | Value | Meaning |
|---|---|---|
| `_DEFAULT_CAP` | 4,000 | total render budget |
| `CATALOG_RESERVE_SHARE` | 0.25 | share reserved for the name index |
| `_SUMMARY_BUDGET_RESERVE` | 800 | chars FULL may not take from SUMMARY |
| `WHEN_TO_USE_CATALOGUE_CHARS` | 80 | per-entry trim of the trigger clause at full width |
| `_FENCE_OVERHEAD` | derived | charged once per section, not per untrusted entry |

None are user-facing keys. `_DEFAULT_CAP` in particular is a constant nobody has measured a
justification for — recorded here so the next reader knows it is a default, not a finding.

## Observability

- `[skills] injector.render: rendering summaries LEAN — the corpus does not fit at full
  width…` — INFO, `_fields`: `owl`, `summary_cost`, `cap`.
- `skill injection: pinned skills exceed budget — some demoted to summary` — WARNING.
- `[pipeline] assemble: exit` carries `skills_len`, which is the rendered size per turn.

```bash
cat ~/.stackowl/logs/stackowl.jsonl \
  | jq -c 'select(.fields.skills_len != null) | {ts, skills_len: .fields.skills_len}'
```

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| Corpus exceeds cap at full width | `summary_cost` vs budget | Every summary renders lean | More skills visible, no trigger phrasing |
| Corpus exceeds cap even lean | per-entry fit check | Overflow demotes to bare names | Names still present, no description |
| Index itself exceeds its reserve | catalogue trim loop | Trims the tail, states the count | "…and N more" |
| Pinned skill will not fit | `pin_demoted` | Demoted to summary, logged WARNING | Pinned skill loses its body |

Nothing fails closed here and nothing raises: the worst case is a shorter blurb.

#    expect: entries carrying a description > 12, and present == total
uv run python - <<'PY'
import sqlite3, types
import stackowl.skills.instruction_injector as I
c = sqlite3.connect("file:$HOME/.stackowl/workspace/stackowl.db?mode=ro", uri=True)
rows = c.execute("select name,description,when_to_use,source from skills").fetchall()
S = lambda n,d,w,s: types.SimpleNamespace(name=n, description=d or "", when_to_use=w or "", source=s or "agent")
out = I.SkillInstructionInjector().render(
    "secretary", [(S(*r), I.SkillTier.SUMMARY, False) for r in rows], cap=I._DEFAULT_CAP)
lines = [l for l in out.splitlines() if l.startswith("- ")]
print("chars", len(out), "entries_with_text", len(lines),
      "present", sum(1 for r in rows if r[0] in out), "/", len(rows))
PY

# 4. Live (OPEN): the lean path firing on a real turn.
grep -c "rendering summaries LEAN" ~/.stackowl/logs/stackowl.jsonl

## Related

- Map items: `D10.2` (description cap), `D09.3` (summary column removal), `ESC-10` (deleted
  `skill_relevance.py`), `ESC-46` (`synthesize_skills` out of the guaranteed set).
- **Still blocked, and not addressed here:** *which* skills should be visible. That needs live
  traffic to say whether the per-query reader already reaches what the frozen catalogue drops.
  This item makes the degradation **even** rather than alphabetical, which is worth having
  whichever way that question resolves.
- **Prior art and where we diverged.** The reference platform renders every skill at a uniform
  short width (~85 chars, `SKILL_PROMPT_DESC_LIMIT = 60`), groups by category so the category
  line amortizes shared context, and states the rule outright: *never remove entries entirely —
  agent-created skills are the model's project*. We adopted the uniform-width instinct and the
  never-remove rule. We did **not** adopt category grouping: our catalogue is ordered by
  measured value (`-n_executions`), and grouping would silently reorder it by something other
  than that score, which is a property `_fence_runs` already protects deliberately.
