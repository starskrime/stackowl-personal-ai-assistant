## Why this exists

**The operator's verdict, 2026-09-12, verbatim:** *"Dashboard not an enterprice
level and modern on hitech view. Start the bmad desing to work on desing also make
it mobile optimized looks like app bit an website."*

The eight read surfaces were correct and nobody would show them to anyone. The gap
was MEASURED rather than restated, which matters because the obvious reading —
"nobody thought about mobile" — is false: `viewport` and `prefers-color-scheme`
were both already there. What was missing was narrower and more fixable.

| measured 2026-09-12, before any of this | value |
|---|---|
| CSS vs JS in a 22,980-byte page | **2,307** vs 15,558 bytes |
| CSS custom properties vs distinct hex colours | **8** vs 16 — half the palette bypassed its own tokens |
| media queries, for the whole responsive story | **1** |
| `<table>` elements vs inline SVG | **9** vs **0** |
| manifest / `theme-color` / web-app-capable / app icon | **absent, all four** |
| `prefers-reduced-motion` | absent, so any animation would be unconditional |

Those four absences in the fifth row ARE the difference between a page and an app:
they are why it could not be installed, had no home-screen icon, and kept browser
chrome. The rest is the absence of a design system.

**And one more thing was wrong that no amount of styling would have fixed.** Eight
panels stacked on one scroll is a document. A phone showing eight tables end to end
is not an app with a bad theme; it is a web page, and the operator's word for that
was "website".

## Model

### One enumeration, and everything derived from it

`PANELS` is the single list. It has been the single list since A05.2 shipped three
hand-written enumerations and updated one of them, and every surface added since
reads from it rather than beside it.

| field | type | what it decides |
|---|---|---|
| `id` | string | the `<section id=… hidden>` it renders into, and the fetch/hide/forget sweeps |
| `path` | string | the `/api/v1/` route it reads; the route↔page bijection is over this |
| `render` | function | the renderer that unhides its own section |
| `dest` | string | **the destination LABEL** — added 2026-09-12 |

`dest` is deliberately a LABEL and not an id with a label beside it. A
`DESTINATIONS` array would be a second enumeration, and this page has already paid
twice for one. Everything a destination needs is derived from that one string:

```
dest: "Work"   ->  element id   "dest" + lowercase   ->  destwork
               ->  button text  the string itself    ->  WORK
               ->  rail order   order of first appearance in PANELS
```

So the only way to add a destination is to give a panel a `dest` nothing else uses,
and the only way to rename one is to change it in the one place it is written.

### The two kinds of hidden, which are not the same question

This distinction is what let the app shell ship without rewriting four behavioural
guards, and it is the part a future reader is most likely to break.

| element | `hidden` means |
|---|---|
| `<section id="X" hidden>` | **this panel has no data** — its fetch failed, or the operator signed out |
| `<div class="dest" id="destX" hidden>` | **this is not the destination you are looking at** |

A browser hides a section inside a hidden wrapper, which is the app behaviour. The
headless harness has no parent/child hiding, so a section's `hidden` still answers
only the first question there — which is why
`test_a_healthy_platform_renders_every_section` still asserts that a healthy
platform renders **all eight**, and still means what it meant before the shell
existed.

## Lifecycle

```
  load page
      |
      v
  sessionStorage has a token? --no--> "sign in to read the platform"
      |                                     |
     yes                          sign in --+
      |                                     |
      v                                     v
  load(token): Promise.allSettled over PANELS       <-- ONE failure is ONE panel,
      |                                                  never the page (A05.2)
      +--> each fulfilled panel: render(), section.hidden = false
      +--> each rejected  panel: section.hidden = true, named in the status line
      |
      v
  no panel answered? --yes--> status line is the failures, and the shell never appears
      |
      no
      v
  buildRail()        once, idempotent
  rail.hidden = false
  showDest(CURRENT || destinations()[0])            <-- exactly ONE destination
      |
      v
  click a rail button -> showDest(label)
      |
      v
  "sign out" -> every section hidden, every wrapper hidden, rail hidden
```

**Priority order, where it can fire together.** `showDest` is the only thing that
sets a wrapper's `hidden`, and it sets ALL of them on every call — so the invariant
"exactly one" cannot be broken by a partial update. The rail is built once and
never rebuilt; `CURRENT` survives a re-`load()`, so a refresh does not throw the
operator back to Overview.

## Invariants

> **I1.** Exactly one destination wrapper is visible once data has loaded.
> Guard: `test_ONE_destination_is_shown_at_a_time`.
>
> **I2.** The destinations `PANELS` names and the wrappers the markup declares are
> the SAME SET, both directions. A wrapper with no panel is an empty screen; a
> panel whose `dest` has no wrapper is a panel nobody can ever reach.
> Guard: `test_the_destinations_are_a_BIJECTION_with_the_panels`.
>
> **I3.** Every destination opens from its own button, and the rail's marked tab is
> the destination on screen.
> Guard: `test_EVERY_destination_opens_from_its_own_button`.
>
> **I4.** The rail is never written in the markup — it is a mount point the script
> fills from `PANELS`.
> Guard: `test_the_rail_is_not_written_in_the_MARKUP`.
>
> **I5.** "Sign out" hides every section, every wrapper AND the rail.
> Guards: `test_forgetting_the_token_hides_EVERY_section`,
> `test_forgetting_the_token_takes_the_SHELL_too`.
>
> **I6.** No panel's payload is read by its POSITION in `PANELS`.
> Guard: `test_the_status_line_reads_its_counts_BY_ID`.
>
> **I7.** The page has exactly one `<script>` block.
> Guard: `test_the_page_has_exactly_ONE_script_block`.
>
> **I8.** The page makes no external request of any kind.
> Guard: `test_nothing_is_fetched_from_another_host`, in
> `test_the_dashboard_is_a_page_a_person_can_open.py`.

**I6 and I7 are both traps rather than regressions**, and both are recorded here
because neither is visible from the source.

I6: `load()` read `results[1]` and `results[2]` for the status line — a positional
index into `PANELS`. That was correct only while the array stayed in the order it
was first written in, and **grouping the panels into destinations reorders it**.
The status line would then have reported the config payload's `schedules`. MEASURED
before the fix: under the old test fixture, where every route answered the same
empty payload, the positional and by-id readings produce the byte-identical string
`0 schedules · 0 settings` — so no assertion over that fixture could ever have told
them apart. The fixture now answers `/schedules` with three and `/config` with two.

I7: the guard that EXECUTES this page extracts its script with a NON-GREEDY
`<script>(.*?)</script>`. A second block would hand that whole file a FRAGMENT, and
every test in it would go green having run nothing. A05.10's own record named this
as an outstanding hazard; it costs one assertion to stop being one.

## Configuration

None. This document's subject has no settings, and that is deliberate: a dashboard
whose appearance is configurable is a dashboard with two appearances to test. The
viewer's own `prefers-color-scheme` and `prefers-reduced-motion` are the only
inputs, and both are honoured without a stored preference.

## Observability

The page is client-side; what a 2am reader can see is what the SERVER recorded.

| `msg` | when | `_fields` |
|---|---|---|
| `[control_plane] server.index: exit — page served` | every page load | — |
| `[control_plane] server.run: exit — listening` | boot | `bind`, `port` |
| `[control_plane] server.run: the dashboard login is still the DEFAULT admin/admin` | boot, while unchanged | `bind`, `reachable_off_this_machine`, `remedy` |

There is no client-side telemetry and none is planned: a page that phoned home
would violate the no-external-request constraint, and the only thing it could
report is which tab someone opened.

```bash
# Is anyone actually opening it, and from where is it reachable?
./scripts/log_since.sh 2026-09-12 'server.index: exit'
cat ~/.stackowl/logs/stackowl*.jsonl | jq -c 'select(.msg | startswith("[control_plane] server.run")) | {ts, msg, f: ._fields}'
```

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| One `/api/` route 503s | `Promise.allSettled` per panel | the other seven render | that panel's section hidden, the route named in the status line |
| Every route fails | `ok.length === 0` | none — the shell is not built | the failures, joined; no empty app |
| A route answers `wired: false` | the renderer's own branch | renders the reason | "no db wired" in that panel, not an error |
| A panel's `dest` has no wrapper | **I2**, at test time | — | *fails closed at CI; unreachable panel never ships* |
| The session expires | 401 from the route | the panel hides | status line carries the HTTP status |
| Operator signs out | explicit | everything hides | a bare sign-in form — no table, no rail |
| The browser has no `clip-path` | `@supports not` | square 1px border | a panel with a border instead of a chamfer |
| `prefers-reduced-motion` | media query | animation durations collapse to 0.01ms | a still page |

The row worth reading twice is the fourth: it is the only one whose recovery is
"this cannot ship", and that is deliberate. An unreachable panel is silent by
construction — it renders into a container the rail never shows, and every existing
guard would still report it visible — so a test is the ONLY place it can be caught.

## What is NOT built, named so the gap is legible

**Naming a gap is not closing it, and this document says so because A05.1 learned
it the expensive way** — two gaps named under exactly such a heading survived into
production precisely because the record said, truthfully, that someone had thought
about them.

* **Record rows with a detail surface.** Nine tables are still nine tables. The
  responsive-table trick (`display:block` + `td::before{content:attr(data-label)}`)
  was proposed and REFUTED by measurement: agents has 13 columns with `bounds` and
  `creation_ceiling` at **262 characters**, so a label:value stack for one row is
  13 lines and roughly 800px of phone screen. The record-row design stands and is
  not built.
* **A synthesis layer.** 43 columns across 8 tables on first paint, and no verdict
  anywhere above them. `/api/v1/health` has a measured **612ms floor** across 14
  samples and a structural worst case of 15s, so a blocking hero rollup would sit
  behind the slowest probe — whatever is built here must not await it.
* **Paging and search.** `lessons` holds 5,964 rows and its route returns 50
  (**0.8%**) while `SqliteLessonsStore.search` already exists and is not wired to
  it. Six of eight routes have no row cap and NO route accepts a query parameter.
* **A remembered destination.** `CURRENT` survives a re-`load()` within the tab and
  nothing more; a reload opens Overview.
