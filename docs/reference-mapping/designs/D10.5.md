## Why this exists

**Not for the reason the map gives.** D10.5's gap line reads "Direct Law 1 violation, and it
also means the model cannot be pointed at a skill on demand." Both halves were measured false
on 2026-08-29 and the map has been corrected in place:

| claim | measured verdict |
|---|---|
| Law 1 violation | **FALSE.** `skills_len` varies in **0 of 403 lanes** over four days (only 4159 or 0) while **304 of those same lanes** vary `prompt_hash` — the instrument detects variation, skills never cause it. Independently: **0 `prompt_hash` changes across 54 multi-turn conversations.** Fixed by D01.1 slices 4b+5 and ESC-10. |
| Model cannot reach a skill | **FALSE.** `skill_view` is in the guaranteed tool base with a reachability probe, and ran **391 times in 7 days**. |
| Reference never puts skills in the system prompt | **FALSE.** It carries a name + 57-char-description index there. Only **bodies** stay out — exactly our posture. |

What survives is narrower and real: **`/skill` has twelve verbs that MANAGE skills and not one
that USES one.** `/skill show X` renders the body *to the operator's screen*; the model never
sees it. The operator's only working route today is to type "follow the X skill and do T" and
hope the model chooses to call `skill_view`.

It matters because of the corpus. The catalogue is capped at 4,000 chars
(`skills/instruction_injector.py:12`), so of **180 enabled skills, 16 are presented and 163 are
dropped on every turn** — 2,604 `catalog truncated by budget` WARNINGs in the retained logs.
Over seven days the model loaded **five distinct skills**, all from the visible head; 174 were
never loaded once. A human naming a skill needs no catalogue, which makes this the only route
that reaches the other 163.

**Stated plainly, because the panel split on it and averaging would hide the finding: this is
an ERGONOMICS item wearing a capability item's gap line.** It is worth twenty lines because it
costs twenty lines. It is not the capability work, and it must not be counted as such — the
corpus item (why 174 skills are unreachable and `skills_list` has never once been called) is
tracked separately in `ESC-58`.

## Model

| concept | meaning |
|---|---|
| **skill catalogue** | names + descriptions in the frozen system prompt. Unchanged by this item. |
| **skill body** | the SKILL.md procedure. Arrives as a **tool result** from `skill_view`, never in the system prompt and never as the turn's input text. |
| **turn prompt** | `SlashCommand.build_turn_prompt(args) -> str \| None`. Returning a string makes the gateway re-run the message as though the operator had typed that text. **Synchronous by contract.** |
| **activation tag** | the `[/skill use]` prefix. Load-bearing — see Invariant I4. |

## Where the implementation diverged from this design, and why

**The design said inject the body. The implementation STEERS instead**, returning a short
directive that names the skill and tells the turn to load it with `skill_view`. Recorded here
per `PROCESS.md` ("say so in the commit, and correct the document"), because three things only
became visible while building it:

1. **`build_turn_prompt` is synchronous** (`orchestrator.py` calls it without `await`), and
   resolving a name is an `await store.get(...)`. Injecting would have required widening a
   seam every command implements, to serve one verb.
2. **`learn_prompt`'s module doc states the house rule**, and it is not a style note: *"It
   gathers nothing, calls no model, touches no database and writes no skill... That restraint
   is the entire design."* A command that read the skill store would be a second read path
   beside `skill_view` — the same shape Bakir's 2026-08-17 rule forbids.
3. **It deletes defect 1 outright rather than mitigating it.** Steering keeps the body a TOOL
   RESULT, so it never becomes `state.input_text` and `turn_persist` never sees it. No
   `input_is_synthetic` flag was needed, and `PipelineState` did not grow a field.

**What this trades away, said plainly.** The reference platform pastes the body verbatim,
which *guarantees* the model sees it; steering means the model is told to load the skill and
could in principle not do so. The trade is taken because the reference pays for that guarantee
twice — it needs `extract_user_instruction_from_skill_message` plus byte-identical marker
constants purely to **undo** its own expansion so its memory layer does not embed skill bodies.
We decline to make the mess rather than build the machine that cleans it. Crucially the risk is
**measurable, not assumable**: the steer and the `skill_view` call land in the same turn, so a
steer that never lands is visible in the log (see Verification).

### Why a registered verb and not `/<skill-name>`

The obvious design — route an unknown `/word` to a skill — was proposed, and **rejected on
measurement**:

- `gateway/scanner.py:31` is `_SLASH_CMD_RE = re.compile(r"^\s*/(\w+)")`. **`\w+` stops at the
  first hyphen, and 108 of 180 skill names (60%) contain one.** `/channel-fallback` arrives as
  `target="channel"`. It would ship broken for 60% of its own corpus, and the error would name
  a command the operator never typed. Qualified names (`/builtin:brainstorming`) die the same way.
- "Unknown slash command" is a **detector**, not just an error.
  `tests/journeys/commands/test_reachability_guard.py:7-8` exists because an unregistered
  command "would silently become 'Unknown slash command' in production". A skill fallback turns
  a closed, loud failure into an open one meaning "no such command AND no such skill AND the
  store was reachable AND the name survived `\w+`".
- Registering one command per skill (the reference platform's design) is worse still:
  `test_reachability_guard.py:34` asserts the registry equals `SHIPPED_COMMANDS` **exactly**,
  the Telegram menu rejects >100 commands, and `/help` rung 1 would render 213 entries.

Making the name a **parameter** dissolves all three problems at once: hyphens and
`source:name` survive untouched, the registry stays the single source of truth for what
`/word` means, and unknown commands stay loud.

## Lifecycle

```
/skill use <name> [instruction]
        │
        ├─ scanner.scan → route="command", target="skill"   (a REGISTERED command; no new namespace)
        │
        ├─ _dispatch_turn: CommandRegistry.get("skill") → SkillCommand
        │      └─ build_turn_prompt("use <name> [instruction]")
        │             ├─ trailing `??`  → None ......... DRY RUN: hands back to dispatch so the
        │             │                                   preview renders (see defect 3)
        │             ├─ verb != "use"  → None ......... the other thirteen verbs reply as before
        │             ├─ no name given  → None ......... falls through to the ordinary reply
        │             └─ name given     → [/skill use] tag + "load it with skill_view" + instruction
        │
        └─ text non-empty → msg rewritten, re-scanned, dispatched as an ORDINARY turn
               same pipeline · same routing · same consent · same tools · _prompt_depth+1
```

**Priority order, stated because several conditions can fire on one event:** the dry-run sigil
is checked FIRST (asking to preview must never execute), then the verb, then the presence of a
name. Every negative returns `None`, which hands the turn back to ordinary dispatch — so the
operator always gets the existing, loud reply rather than a silent no-op.

**The name is never resolved here.** `build_turn_prompt` is pure: it does not know whether the
skill exists. `skill_view` decides that inside the turn, and the prompt instructs the model to
say so and offer `skills_list` matches if it does not.

## Invariants

Each maps to a test; where it does not, that is said.

> **I1.** The system prompt is byte-identical before and after a `/skill use`. Law 1 holds *by
> construction* — `assemble` is not on this path at all, and the body never enters the prompt.
> **I2.** A skill body is never `state.input_text`, so it can never be staged as a durable user
> fact. Holds by construction under the steering design.
> — *`test_skill_use.py` pins the prompt's shape; the body's absence from `input_text` is
> structural, since `build_use_prompt` never reads a skill.*
> **I3.** `build_use_prompt` is **pure** — deterministic, no store, no network. The moment it
> needs a database read it has become a second resolver beside `skill_view`.
> — *`test_it_is_pure_and_needs_no_services`.*
> **I4.** The rewritten text never begins with `/` or `@`. The gateway RE-SCANS it, and two
> scanner rules are unanchored: two `@word` tokens route to a parliament, `/panic` anywhere
> trips the panic route. The `[/skill use]` tag guarantees the first character is neither.
> — *`test_it_never_begins_with_a_character_the_scanner_would_re_route`.*
> **I5.** A name reaches `skill_view` byte-for-byte — hyphens and `source:name` intact.
> — *`test_a_hyphenated_name_survives_intact`, `test_a_qualified_name_survives_intact`.*
> **I6.** The other thirteen `/skill` verbs are byte-for-byte unaffected; only `use` returns a
> turn prompt. — *`test_build_turn_prompt_fires_for_use_and_ONLY_for_use`.*
> **I7.** A trailing `??` previews and never executes.
> — *`test_a_dry_run_previews_instead_of_steering`.*
> **I8.** Every verb that dispatches is declared in the meta, so `/help` and `/find` can see it.
> — *`test_every_dispatched_subcommand_is_DECLARED`, derived from the ladder, seen failing on
> the pre-fix state.*

**Withdrawn:** the draft carried "a disabled or archived skill never runs". See defect 2 — that
was my error, not the code's. `enabled=0` removes a skill from the *catalogue*, not from
explicit reach, and enforcing it here would break `/skill enable` itself.

## The three defects the design named — how each was closed

Found by the stability lens during brainstorm. **Two were dissolved by the steering design
rather than mitigated**, which is the strongest argument that the divergence was right.

**1. The skill body filed as a durable USER FACT — HALF dissolved, and I shipped the
wrong half. See the correction at the end of this section.**
`turn_persist` stages `"User: {state.input_text}\n\nAssistant: ..."`, and its machine-lane
guard is a **prefix check** on `("goal-", "incident-")` (`sessions/models.py`) — a Telegram lane
is not one, and a test asserts that. Had the body become `input_text`, `/skill use` on Telegram
would have filed ~3KB of skill prose as something the user said, on every invocation: the
4,480-of-5,212 defect fixed on 2026-08-25, reopened through a door the guard cannot see.
Steering keeps the body a **tool result**, so the 3KB body never becomes `input_text`. That
half held.

> **CORRECTED 2026-08-29, by this item's own validate.** I concluded the flag was unnecessary.
> It was not: the turn PROMPT is still `input_text`, and `turn_persist` stages
> `"User: {input_text}"`. Four live rows read
> `User: [/skill use] The user has invoked the skill "verify-before-claim"...` — the command's
> own directive filed as something Bakir said, embedded, and offered back later as his words.
> `is_machine_lane` cannot see it: that guard is a prefix check on `("goal-", "incident-")`
> and these arrive on `owl:secretary:telegram:dm:...`, exactly as the stability lens warned.
> `PipelineState.input_is_synthetic` **is now built**, set from `_prompt_depth > 0` — a
> structural condition, not a tag match — and `turn_persist` refuses such input as a user fact
> while still keeping the transcript. Both cases live in one predicate,
> `_is_not_a_user_utterance`, because the second was found only because the first could not
> see it.

**2. `enabled` on the resolve path — RESOLVED AS CORRECT, not a defect.**
`SkillIndexStore.get` filters neither `enabled` nor `lifecycle_state`, so `skill_view` returns a
disabled skill and annotates the header with `"  (disabled)"`. My brainstorm called this
"disable is decoration". On reading the code's intent that verdict is **wrong**, and the record
should say so: `enabled=0` removes a skill from the **catalogue** (`list_enabled` enforces both
predicates) — it is not an ACL. A skill the operator names explicitly is a different act from
one the platform offers unprompted, and the same "explicit always wins" rule the memory-routing
decision settled on applies here. `skill_view` already tells the model it is disabled.
**No change made, deliberately.** Filtering inside `store.get` would also have broken
`/skill enable`, which must fetch a disabled skill in order to enable it — the obvious fix was
the wrong one.

**3. `/skill use X ??` would execute rather than preview — CLOSED.**
`??` is intercepted in `CommandRegistry.dispatch`, and the turn-prompt seam runs **before**
dispatch, so a request to preview would have run the skill instead. `build_turn_prompt` now
checks `strip_sigil` first and returns `None`, handing the turn back to dispatch. The existing
helper is **asked, not re-implemented**, so `??` keeps one meaning.

## A fourth defect, found while building

`/skill menu <name>` dispatched at `elif sub == "menu"` and worked, but was **absent from
`_SKILL_META`** — invisible to `/help`, to `/find`, and to the `CommandResolver` corpus. It
slipped because `test_skill_meta.py`'s docstring claims it "asserts the declared metadata
matches the real if/elif dispatch ladder" while `_EXPECTED` is a hand-written set that can only
pin the declaration against itself.

Both were fixed: `menu` is declared, and a new test derives the dispatch verbs from
`inspect.getsource(SkillCommand.handle)` and asserts every one is declared — making the
docstring true and turning two copies of one rule into one source and one reader. The guard was
confirmed to fail on the pre-fix state rather than assumed to.

## Verification

Run after `./start.sh`, with the core's boot time postdating the commit.
**`skills_len` is NOT the evidence** — it is proven inert across 1,572 lines and 403 lanes.

### Result of the first live invocation — 2026-08-29T17:03Z

`/skill use verify-before-claim` on Telegram. **The check that mattered passed.**

| # | check | result |
|---|---|---|
| 1 | the steer fires | **PASS** — `command contributed a TURN PROMPT`, `cmd=skill`, `chars=622` |
| 2 | **the steer LANDS** | **PASS** — `skill_view.execute: entry {'name': 'verify-before-claim'}` → success, `source=builtin`, on the FIRST model call (23,631in/80out) |
| 3 | it runs as an ordinary turn | **PASS** — triage → dispatch → classify → assemble → execute, `owl=secretary`, `intent_class=standard` |
| 4 | the turn completes usefully | **FAIL** — see below |
| 5 | hyphenated + `source:name` forms | **NOT RUN** — one invocation, bare name only. A denominator of one, stated rather than dressed up |

Check 2 is the one the divergence rested on: injection would have made "the model saw the
body" true *by construction*; steering had to earn it, and did, on the first attempt.

### Check 4 failed, and the cause was this design

After `skill_view` the turn kept going: `read_logs` ×2, **fifteen** `shell` calls, input
tokens climbing 23,631 → 24,255 → 37,137 → **~683,000**, the step ceiling reached, and the
reply was *"[stopped: I ran out of steps for this turn before I could finish.]"*

The skill loaded correctly. **The instruction wrapped around it had no stopping condition** —
the no-instruction branch said "apply the skill to what this conversation is already about",
and on a lane whose prior four turns were about logs that is an invitation to investigate
indefinitely. The step ceiling fired and did its job; the operator still got nothing, and a
30-character command should not cost 683k tokens.

**Fixed:** a bare invocation now loads the skill and STOPS — summarise what following it would
involve, ask what to apply it to, call no other tools. A *directed* invocation still executes,
so the verb was not neutered in the course of making it safe. The load line is **conditional**,
because the first bounded draft still opened with "carry out its procedure" and then said "do
NOT begin a multi-step investigation" two lines later — a self-contradiction found only by
RENDERING the prompt rather than reading the code.

### This section was not runnable as first written

Recorded because it is the class of error this programme keeps paying for. The closing query
said *"the TURN PROMPT line and `skill_view.execute` must share a `trace_id`"* — and **that
line carried no trace_id**. It is emitted at the gateway *before* the turn's `TraceContext`
exists, so its top-level `trace_id` is null and the documented join was impossible. The
evidence above is conclusive by name and 9-second adjacency, not by the join written down.
"Run the closing query before you need it" was written in this very document, and not done.

`msg.trace_id` was in scope at the call site and is now in the line's fields, so from the next
invocation the join actually works. PASS = both lines share one trace_id; FAIL = a steer with
no `skill_view` after it, in which case the trade was wrong and the design goes back to
injection behind an async seam.
