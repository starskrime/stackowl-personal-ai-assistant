## Why this exists

The Ask: *"Ours is arguably better. Add the 'explain how to fix it' half?"*

The first clause is true and it is worth stating precisely, because it is the reason this
item is `PARTIAL` rather than `MISSING`. Their `doctor` diagnoses setup issues; ours runs a
live `HealthAggregator` plus a **reachability census** that asks whether a capability can be
*reached*, not merely whether it is registered — a distinction that has already caught real
defects in this programme.

**The second clause was entirely absent.** Measured 2026-09-06: `HealthStatus` carried
`name`, `status`, `message`, `latency_ms` and nothing else, across **72 construction
sites**. There was no field for a remedy, so a contributor that *knew* the fix had nowhere
to put it. Every message is a diagnosis — "database not found: {path}", "runtime not
constructed", "knowledge graph unavailable", "{label} missing: {path}" — and both surfaces
an operator reads rendered exactly that and stopped:

```
stackowl health   ✗  db   down   12ms  database not found: /home/…/stackowl.db
the 2am alert     ✗ db: down — database not found: /home/…/stackowl.db
```

…after which the CLI exits 1. The operator is told, correctly and uselessly, that something
is broken.

## Model

`HealthStatus.remedy: str | None = None` — defaulted, so all 72 existing sites are
byte-for-byte unaffected, the same discipline every added field on `IngressMessage` used.

| Contributor | Failure | Remedy |
|---|---|---|
| `db` | database not found | run `stackowl db migrate`, or check `STACKOWL_HOME` |
| `filesystem` | a required directory missing | create it, or check `STACKOWL_HOME` — every path derives from it |
| `graph` | Kuzu native layer did not load | on ARM usually a missing wheel; `uv sync` and re-run |
| `browser` | runtime not constructed | **expected from the CLI** — the runtime lives in the serve process; use `/browser` |
| `browser` | unavailable: {reason} | it auto-installs at startup; check the reason and the `browser_install` log |
| `prefix_growth`, `unattributed_spend`, `store_cadence` | measurement DEGRADED | **None, deliberately** |
| any contributor | the probe RAISED, and the exception carries an errno or a SQLite phrase | derived by `remedy_for(exc)` — added 2026-09-10, see below |
| any provider | the probe raised `CircuitOpenError` | the breaker is open and retries in ~Ns — **nothing to do**; check the host is reachable only if it never closes |

**`None` is a real answer and the common one**, and that is the design rather than an
omission. Those three report measurements about the platform's own behaviour — "the prompt
prefix is growing" has no command that fixes it. Filling them in would be inventing advice,
and **a field that is always populated is a field readers learn to skim**. The value is
precisely that a remedy appearing means there is something to do. A test asserts they stay
empty, so a later "fill them all in" has to be a decision rather than a reflex.

**The browser row is the one that earns its keep immediately.** `runtime not constructed`
fires on *every* `stackowl health` run from a terminal, because the runtime lives in the
serve process — so the single most-seen degraded line in this platform was one that looked
like a fault and was not.

## Lifecycle

```
contributor.health_check()
    └─ HealthStatus(status, message, remedy?)
            │
            ├─ stackowl health ──▶  ✗  name  status  Nms  message
            │                       →  remedy            (only when set)
            │                       exit 1 if any status != ok
            │
            └─ health sweep (5 min) ──▶ _compose_alert
                                          ✗ name: down — message
                                              → remedy   (only when set)
                                        ──▶ proactive delivery to the operator
```

The `→` clause is appended only when a remedy exists. A dangling arrow on every other line
would train the reader to stop seeing it.

## Invariants

1. **`remedy` defaults to `None`** — adding it changed no existing call site.
2. **A remedy is written only where the contributor knows the fix.** Measurement
   degradations carry none, and that is asserted.
3. **Both surfaces render it.** A remedy the 2am alert drops is a remedy that does not
   exist when it is needed most.
4. **No remedy invents an action.** Every one names a command, a path, or a place to look
   that exists in this tree — `stackowl db migrate` is `cli/app.py:372`; `/browser` is a
   live command; `STACKOWL_HOME` is the documented root of every path.

## Configuration

None. Remedies are properties of a failure, not settings.

## Observability

The remedies are themselves the observability improvement. The JSON form carries the field
for every entry so a machine consumer can branch on it:

```bash
stackowl health --json | jq -r '.[] | select(.remedy) | "\(.name): \(.remedy)"'
```

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| A new contributor ships with no remedy on a PREDICTABLE branch | nothing automatic — deliberate; most should not have one | — | the diagnosis alone, as before |
| A new contributor builds an unhealthy status inside an `except` without asking `remedy_for` | `test_every_arrived_failure_asks_the_one_place_that_decides` | test fails | — |
| A remedy goes stale (a command is renamed) | the same drift any prose has | — | advice that no longer works |
| A remedy is invented for an unactionable state | `TestNoRemedyIsInventedWhereThereIsNoAction` | test fails | — |

The stale-advice risk is real and is the price of prose. It is bounded by invariant 4: each
remedy names something that exists in this tree today, so a rename breaks a grep rather than
only a reader's trust.

## What was still missing — measured 2026-09-10 (DEBT-288)

**This page shipped the field, both renderers and a rule, and the field was never once
populated in production.** MEASURED across the retained logs: **822 sweeps reported
UNHEALTHY subsystems and every one carried `remedies: []`.**

An AST walk over `src/` says why, and the two sets never intersect:

| | count |
|---|---|
| `HealthStatus(...)` construction sites | 72 |
| reporting `down` or `degraded` | 41 |
| of those, inside an `except` — a failure that ARRIVED | **10** |
| of those, carrying a `remedy` | 5 |
| **inside an `except` AND carrying a remedy** | **0** |

Every remedy in the table above sits on a branch the author could PREDICT. Every branch
that turns an arrived failure into a status had none — and that is not carelessness. At an
`except` there is no exception in hand at authoring time, so there is nothing to write.
The only moment the question can be answered is when the exception EXISTS.

**The incident that makes it concrete.** `DbContributor` has two `down` branches. The
file-missing branch is the row in the table above and has never fired on a running
install. The ping-raised branch had no remedy — and it is the one that fired at
2026-09-07T14:32:02Z, the first minute of the four-hour total database failure in which
every write raised `sqlite3.OperationalError: disk I/O error`. The single sweep in the
whole corpus that ever reported `db` down is that one, and its `remedies` is `[]`.

`remedy_for(exc)` in `status.py` is now the one place that decides, and all ten
arrived-failure sites pass their exception to it. **Invariant 4 is not weakened** — it is
enforced there instead of by ten authors' restraint: nothing is returned unless the
exception carries the evidence itself, an `errno` or one of SQLite's fixed operational
phrases. The guard is STRUCTURAL — it requires the CALL, never a non-empty string —
because a per-site judgement about the string is what produced 0 of 10.

**And the "None, deliberately" row above is unchanged in meaning, but was doing two jobs.**
Those three contributors have a second state — *"I could not measure it, because `exc`"* —
which their own comments already separate from a degraded measurement, and which received
the same empty remedy. One contributor, two kinds of failure, one policy. Only the second
changed.

**The loudest case needed no new vocabulary — the exception already carried the answer.**
Of 959 unhealthy subsystem reports, **421 are `provider:NeraAiRaw`**, and every probe
failure behind them raises `CircuitOpenError`, which holds `provider_name` and
`retry_after_seconds` as attributes. That is not an outage anyone should act on: the
breaker is working and retries by itself. The remedy says so, with the window — so the
platform's most repeated alarm reads "known, self-recovering, and here is when" instead of
"something is wrong". A remedy that fired on nothing real would be decoration; this one
lands on the largest real group in the corpus.

The double-timeout branch is the one `down` with no exception behind it, and it now says
so: a non-answer is not an outage. MEASURED on this install — four contributors were
declared `down` at 2026-09-10T01:37Z while a full test suite ran on the same box.

## The verdict that finally has an actuator — 2026-09-10 (DEBT-295)

Everything above is about a diagnosis a PERSON reads. This section is about the one
contributor whose verdict a MACHINE acts on, and it was added because the page's own
subject had a hole in it.

`HealthAggregator.is_live()` — a liveness verdict, distinct from the full sweep — has
existed for months, wired to `WatchdogService`'s `WATCHDOG=1` ping. MEASURED across
every retained log: **1,115 boots, 1,115 `[watchdog] systemd watchdog not configured —
skipping`, zero pings, zero verdicts.** The function was written, wired, tested and
never once called on this install, because `start()` returns before creating its loop
unless systemd exports `WATCHDOG_USEC`. **The mechanism was made conditional on its
transport**, so on every deployment without an external supervisor — which is every
fresh clone, `./start.sh` under nohup included — the platform does not fall back to a
weaker answer. It stops asking the question.

On 2026-09-08 that cost 7h21m: a process alive, serving nothing, `db` ok, `filesystem`
ok, and no turn able to complete. Those two contributors answer *can I reach my
dependencies*. Nothing answered *am I still working*.

`SchedulerProgressContributor` is that question. It reads `MAX(jobs.last_run_at)` —
which the core already writes on every dispatch, success or failure — so it needs no
new writer, no table and no migration, and it arrives with 7.7 days of history to
calibrate against. Over **22,919 consecutive completions**: mean gap 29.1s, and exactly
**two gaps above fifteen minutes — the two recorded outages** (26,527.9s and 15,146.0s).
The third largest is 711.7s. The band between is empty.

Three things about it belong on this page specifically, because they are this page's
subject applied to itself:

* **Its budget is asked, not stated.** `scheduler.longest_legitimate_silence_seconds()`
  is the scheduler declaring its own worst legal silence (defer cap + handler timeout +
  one poll interval); the contributor doubles it. A literal would be a second copy of a
  number `scheduler.py` owns, and raising the handler timeout would then make the guard
  start killing healthy processes rather than make it more patient.
* **Its `down` is the only one in the tree with a process kill behind it**, so its four
  unmeasurable cases — no enabled job, no completion yet, an unparseable timestamp, a
  read that raised — all return `degraded`, never `down`. That is DEBT-288's "I could
  not measure it is not it has regressed", in the one place where getting it wrong
  restarts the platform.
* **Its remedy is the actuator's instruction.** `restart the process; its event loop is
  no longer running work` is not advice for a human here — the gateway acts on the
  verdict directly, then the existing respawn path recovers. This is the first entry in
  this document where the "what to do about it" half is executed rather than displayed.

`WatchdogService` stays. `stackowl install-service` is a live command with a real
installer, so systemd supervision is a shipped deployment mode that has simply never
been used on this box — and it now carries the progress contributor too, through the
same `_build_liveness_aggregator()` recipe. One definition of alive, two actuators.

**The alert half is OPEN, and honestly so.** `_compose_alert` runs only when a subsystem is
actually unhealthy, and the boot after this shipped reported ok=15/15 with 0 ERRORs. Its
rendering is proven by test, not in production. Closing query:

```bash
./scripts/log_since.sh 2026-09-06 'UNHEALTHY subsystems detected.*"remedies": \["'
```

Scoped to the day it shipped: that detection line has existed for months, so an unbounded
count would report success on evidence that predates the remedy entirely.

**The first version of this query could never have closed, and that is worth recording
here rather than only in the debt log.** It grepped for `health sweep found unhealthy` —
the first line of the message `_compose_alert` RETURNS. That string goes to the outbound
alert sink and to `JobResult.output`; **nothing logs it**, and `job_results` holds zero
`health_sweep` rows, so it is not queryable anywhere. Measured 2026-09-06: the sweep
detected unhealthy subsystems **735 times** while that phrase appeared in the logs **zero
times, ever**. So the query was asking reality a question reality could not answer, and it
would have read OPEN forever.

The fix was to move the claim onto a line that IS logged. The detection ERROR now carries a
`remedies` field naming the subsystems whose status had one, which turns "did the alert
carry a fix?" into something the logs can settle.
`tests/audit/test_a_closing_check_looks_for_evidence_that_can_exist.py` now asserts this
property for every log-based closing check in the programme, by walking the AST of every
logging call in `src/` rather than grepping the tree — a string that is merely present in
the source proves nothing about the logs, which is the entire distinction.
