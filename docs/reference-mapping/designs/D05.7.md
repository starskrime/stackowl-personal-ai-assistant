## The premise inverted while I was measuring it

`DEBT-37` — which I filed the day before — assumed long tool chains were thrash
loops. **They are not.**

The headline 46-call chain was `headhunter` running 46 `web_search` calls and
returning a real synthesized list of live Senior/Lead/Staff engineering roles in
Plano, TX. That is **productive fan-out**, not a loop.

| turns with ≥15 tool calls | 365 |
|---|---|
| succeeded | 264 (**72%**) |
| median response | **7,303 chars** |
| had a `failure_class` | 101 |

**A guard keyed on the tool NAME — which is exactly what StackOwl had — would
have flagged working code.** So the item is not "stop long chains". It is *catch
the same call repeated*, which a name-only counter cannot express.

### The quality cliff, stated as correlation

Measured per call-count band, with the baseline that makes it meaningful:

| tool calls | n | median quality | success % | median chars |
|---|---:|---:|---:|---:|
| 0 | 3822 | **0.85** | 99% | 1007 |
| 1–2 | 432 | 0.75 | 99% | 981 |
| 3–4 | 238 | 0.70 | 97% | 995 |
| 5–14 | 476 | 0.40 | 94% | 2261 |
| 15+ | 273 | **0.10** | 96% | 8000 |

Quality collapses monotonically while success stays ~96%: these turns *succeed*
and produce long answers the critic rates near zero.

**This is deliberately NOT what the item guards on.** It is correlation — hard
tasks may need more tools *and* be harder to answer well, and the critic may be
penalising verbosity. Acting on call count would risk halting exactly the work
that needs the calls. Recorded as an open question, not a trigger.

## ONE OF THE THREE DETECTORS COULD NEVER FIRE — found 2026-09-07

The count of detectors is this document's central argument, and it was wrong.
`idempotent_no_progress_warning` — the detector this item exists to add, the one
`TurnProgressTracker` was structurally blind to — **was itself unreachable for its
entire life.**

Both success detectors key on the same signature, and `after_call` returned on the
first that matched. The general one ("same call") was checked before the specific
one ("same call AND same result"), so the no-progress counter was written once, on
the pass where `repeats` was 1, and every later call returned before reaching it.
Pinned at 1 forever, against a threshold of 2. **A subset checked second is
unreachable whenever its threshold is not strictly lower — arithmetic, not
accident.**

The failure path had it right the whole time: `_record_failure` checks
`repeated_exact_failure_warning` (per-signature, specific) before
`same_tool_failure_warning` (per-tool, general). The asymmetry between the two
halves of one method is the evidence.

**MEASURED over ten retained days, 2026-08-28 to 2026-09-07:**

| | firings |
|---|---:|
| `repeated_exact_call_warning` | 155 |
| `same_tool_failure_warning` | 46 |
| `idempotent_no_progress_warning` | **0** |
| `repeated_exact_failure_warning` | **0** |
| **total** | **201** |

142 distinct `args_hash` values, counts 2/3/4 only — no runaway. Top tools:
`browser_extract` 97, `browser_navigate` 38, `web_fetch` 27.

### Why every test was green

Three tests cover this detector and not one of them could see the hole.
`test_idempotent_no_progress_warns_on_a_repeated_RESULT` asserted
`d.code in {"idempotent_no_progress_warning", "repeated_exact_call_warning"}` — a
**disjunction**, satisfied just as well by the detector that answered in its place.
The other two isolate it with `exact_repeat_warn_after=99`, a threshold production
never sets. *A test that passes immediately may be vacuous; test the path production
takes.*

The guard added with the fix is the general form:
`test_every_detector_is_reachable_under_the_SHIPPED_config` uses the shipped
defaults and **no keyword arguments**, censuses the codes the module can emit, and
requires each to be produced by a real sequence. Reverting the ordering kills it and
`test_idempotent_no_progress_warns_on_a_repeated_RESULT`, and nothing else.

## The dedup answer the map asked for

> *"Is our TurnProgressSupervisor the same thing under another name?"*

**No, and it is provable.**

| | ours (`TurnProgressTracker`) | reference |
|---|---|---|
| keyed on | tool **name** | tool **+ args** |
| detectors | 1 (same-tool no-progress) | 3 |
| success handling | `is_trustworthy_success` → `record_progress`, **resetting the streak** | counts repeats on success too |
| action | hard bounce at 3 | warn, halt opt-in |

The gap is not theoretical. `execute.py` resets the streak on a *trustworthy
success*, so **46 successful `web_search` calls never touched the breaker**. Ours
catches failure loops; it is structurally blind to a productive-looking loop that
goes nowhere.

## Ported ALONGSIDE, not instead — and why

The operator's first instinct was to replace ours wholesale. Checking the blast
radius changed the answer: `TurnProgressTracker` is **not only a loop guard**. Its
`turn_made_progress` / `no_progress_tools` outputs feed `pipeline/delivery_gate.py`
— the **trust arc's** honesty check that catches a turn producing nothing but a
refusal. 35 references in `execute.py`, 10 files, 5 test files.

Replacing it would have deleted a shipped feature belonging to a different item.

```
guardrails  →  DECIDES   (3 detectors, warn-only, args-aware)
progress    →  SIGNALS   (turn_made_progress → delivery_gate honesty check)
```

**Only one component makes decisions**, so the "two competing breakers" objection
does not apply.

## Two deliberate divergences

**1. Idempotence from the manifest, not a name list.** Theirs carries
`IDEMPOTENT_TOOL_NAMES` / `MUTATING_TOOL_NAMES` frozensets. We already declare
`action_severity` per tool, and `"read"` *is* the idempotence claim — so a new
read-only tool is covered the day it is written. Hardcoded tool-name lists are
against a standing rule here.

**2. `failed` is required; result text is never sniffed.** Theirs falls back to
`classify_tool_failure`, substring-matching `'"error"'` in the result blob with
hardcoded `terminal`/`memory` cases.

> **I claimed in a brainstorm question that adopting their controller would
> regress failure detection to string-matching. That was wrong, and the operator's
> pushback is what surfaced it.** Their own docstring says the classifier is a
> *"safety-fallback… Production callers always pass an explicit `failed=`"*
> (`run_agent.py:6495` confirms it). So requiring `failed` here is the **faithful**
> port, and it lets StackOwl feed `is_trustworthy_success(success, verified)` —
> preserving B4a, the rule that a claimed-but-unobserved effect must not look like
> progress.

## Warn-only

**There is no hard-stop capability at all. [CORRECTED 2026-09-07 — this said
"`hard_stop_enabled` defaults **False** — operator decision, and the reference
platform's shipped default too".]** `d8b8ba81` (2026-08-30, ESC-68) deleted the
flag, `before_call`, `_halt`, `halt_decision`, `should_halt` and four config
fields: the flag had no setter and `before_call` had no caller, so two of the three
branches were doubly dead. Bakir chose DELETE over enabling them.

That commit updated the code, the config, the tests and the module docstring. **It
did not update this document, which then advertised an operator-tunable flag that
did not exist for eight days** — the fifth surface of a retirement, now named in
`CLAUDE.md`'s checklist and in the loop's own skill. `doc_check.py` reports
deletion-stale documents separately as a result: 11 of the 19.

Repetition is a smell, not proof: the headhunter case shows a high count can be
correct, and a wrong halt truncates real work mid-flight. A genuine loop is
bounded instead by the existing turn iteration cap
(`DEFAULT_TURN_MAX_STEPS = 20`), so **"warn only" is bounded, not unbounded** —
a distinction worth stating, because "never hard-stop" sounds unbounded and isn't.

A warning appends `[loop-guard] …` to the tool result the model sees, so it can
self-correct.

## Invariants

> **I1.** A fan-out with distinct arguments is never flagged. The measured
> 46-query turn must produce zero warnings — pinned by a test built from that case.
>
> **I2.** Arguments are hashed, never stored. A call can carry a token or a file's
> contents, and the signature is logged.
>
> **I3.** Argument ORDER never changes identity. Otherwise `{a,b}` and `{b,a}`
> would look like two calls and a real repeat would go unnoticed.
>
> **I4.** A guardrail never costs a turn its tools. Every call is wrapped; an
> exception is logged and ignored.
>
> **I5.** The controller has no side effects. It returns decisions; `execute.py`
> decides what to do with them.

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| Genuine loop with identical args | exact-repeat detector | Warning appended; model self-corrects | A `[loop-guard]` note in the tool result |
| Model ignores the warning | — | **Accepted** — bounded by the 20-step iteration cap | A turn that used its whole budget |
| Fan-out misread as a loop | `I1` | Cannot happen: distinct args → distinct signatures | Nothing |
| Guardrail raises | `I4` | Logged, ignored, dispatch proceeds | Nothing |
| A tool mis-declares `action_severity="read"` | — | **Not detected.** A mutating tool would be checked for no-progress | A spurious warning |

### Prior art, and where we deliberately diverge

`agent/tool_guardrails.py` — a side-effect-free controller tracking per-turn
observations (repeats, oscillation, no-progress) and returning decisions; the
runtime decides whether a decision becomes guidance, a synthetic result, or a
halt. Config section `tool_loop_guardrails`.

**Adopted:** the architecture, wholesale — the decision/action split, the three
detectors, the signature-based identity, and warnings on by default. **NOT the
warn-then-halt gradation:** it was ported, found unreachable, and deleted whole in
`d8b8ba81`. [CORRECTED 2026-09-07 — this claimed the gradation and the
"warn-on/halt-off default" as adopted, eight days after both were removed.] This is the item in the programme where the reference
design was best and was taken most directly.

**Diverged:** idempotence from the manifest rather than name lists; `failed`
required rather than sniffed. Both are covered above.

**Not adopted:** their config-file section. Ours ships as module constants,
consistent with `D05.2`/`D05.3` — these are not policies an operator would tune
without also reading the code that consumes them.

### How the two Laws hold

**Law 1 — per-conversation prompt caching is sacred.** Untouched: the guardrail
observes dispatches and appends to a tool *result*. No schema, prompt or tools
array moves.

**Law 2 — the core is a narrow waist.** No new model-facing tool. The guidance
rides on an existing result rather than adding a surface.
