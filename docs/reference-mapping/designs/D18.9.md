# A Checksum Written 136 Times And Read Never

**Item.** D18.9 · Migrations — `AHEAD`, track `keep`, wave 9, order 92.
**Ask.** "Keep."
**Answer.** Kept, and verified — which found the half that was missing.

## The claim, checked

The reference platform has no migration framework at all, so `AHEAD` is not in
doubt. Two of the map's specifics are:

* **"90 migrations"** — there are **136**, all applied, highest `0136`,
  `schema_migrations` holding 136 rows. The number was true when written.
* **"idempotent"** — that describes the RUNNER, not the SQL. 68 of the 136 files use
  `ALTER TABLE`, which SQLite cannot re-run; safety comes from `_apply` skipping any
  version already in the ledger. Worth stating precisely, because "idempotent SQL"
  would invite someone to re-run one.

## The defect: a value computed, stored, and never compared

`_apply` has always written `sha256(sql)` into `schema_migrations.checksum`.
**Nothing in `src/` ever read that column back.** An applied migration is skipped by
version, so editing its file changes what a *fresh install* builds while the existing
database keeps the old schema — the same version number describing two shapes.

**It had already happened.** Comparing every stored checksum against its file: **130
matched, 6 drifted** — `0091_turn_metrics`, `0093_session_key_rename`,
`0099_lane_on_work`, `0100_runner_lane_parent`, `0102_session_prompts`,
`0106_messages_role_user_assistant_only`. All six were edited by one commit,
`419493a3 "refactor: no vendor names in shipped code"`, and a diff analysis found
**0 SQL-statement lines changed** in every one. No schema diverged. Nothing would
have distinguished that from a change that did.

**And there is a second database, which is what makes this more than bookkeeping.**
`tests/_schema_template.py` builds schema from the migration FILES while the live
database holds what was APPLIED — structurally different sources that happen to
agree. `stackowl db restore` then replaces the live database from a backup whose
ledger already lists those versions, so the runner skips them forever.

## Why the reader was never wired: it was unwireable

Switching on a byte comparison would have opened with **six false alarms**, every one
a comment edit. A guard that fires on correct code teaches its reader to ignore it —
the same finding D18.7 recorded for the cross-platform checker one item earlier, and
the same reason that checker sat red and unread for months.

So the hash covers what the migration **does**. `_split_sql` — the very function the
runner uses to EXECUTE — gained a `keep_comments=False` mode, and `semantic_checksum`
hashes the statements it returns.

**This is deliberately not a normalisation rule.** A panel lens objected that a
semantic hash "commits us to a normalisation that must stay correct forever". It
would, if it were a regex. It is not: the tokenizer that decides what is a comment is
the same one that decides what gets executed, so there is no second rule to keep
correct — if it is wrong about a `--` inside a string literal, the migration was
already being run wrong. Measured across the 136 files today: zero `/* */` blocks and
zero `--` inside string literals, but the shape exists (`0066_objectives.sql:15` has
`'active', -- comment`), so a strip-to-end-of-line regex was a live hazard.

Measured: **all six drifted files hash identically** before and after that commit,
while the byte hash called all six drift.

## The column belongs to the runner, not to a migration

It was first written as migration `0137`, and **the first behavioural test failed** —
which is the only reason the mistake was caught. `schema_migrations` is the runner's
own bookkeeping, created by `_CREATE_SCHEMA_MIGRATIONS` and never by a migration, so:

* a numbered migration would have to run *before* the column it adds could be read;
* any runner pointed at a different migrations directory — every test fixture that
  builds a schema — would never get the column at all.

`_ensure_sql_checksum_column` now adds it at bootstrap, re-derived from the table's
real shape on every boot. That also answers the sharpest future-proofing objection on
its own terms: a numbered migration can never be un-shipped, and this is deleted by
deleting one function.

## Warn, and the principle is not deference

The panel found the repo's two precedents **disagree**: the backup step fails CLOSED
(*"apply anyway with a warning — is how 'we thought we had a backup' happens"*) while
D18.4 warns and boots. The reconciling rule is better than either precedent:

> **Fail closed when refusing PREVENTS the harm; warn when the harm already
> happened.**

A missing backup is prevented by stopping. A checksum mismatch can only ever concern
an *already-applied* version, and refusing to boot cannot un-diverge a schema — it
adds a second outage to a past event. So it warns, at WARNING, naming the files.

An applied migration whose **file is gone** now warns too. `_pending` computes only
disk-minus-applied; applied-minus-disk was never computed, so a deleted applied
migration was silent. There are zero today — which was luck, not a guard.

## A claim I relayed last invocation, and it was wrong

A measurement lens reported that ~19% of suite time was recoverable because "22 files
outside `tests/db` still construct a real `MigrationRunner`" while a fast template
exists. **Refuted, and verified independently here.** The two populations are
disjoint: 49 sites inside `tests/db` and 35 outside, and `tests/_schema_template.py`'s
own docstring says *"DO NOT USE THIS IN A TEST OF THE MIGRATIONS … Those call sites
are deliberately left alone"* — they assert on what the runner does, and a template
would make them assert on a cached artefact of themselves. Per-site cost also measures
at ~2.5s, not the ~9s the estimate assumed. The recoverable figure is tens of seconds
out of ~1,745, not 19%.

## Verification

```bash
uv run pytest tests/db/test_an_edited_migration_does_not_go_unnoticed.py -q   # 13 passed
uv run pytest tests/db -q                                                     # 115 passed
```

Both RUN on 2026-09-05, not trusted. **Mutation-proven**, each restored from a file
copy and re-run green: removing the verifier call, hashing WITH comments (8 failures —
the false-alarm regression), and sorting the statements. That last one caught a
missing TEST rather than a missing behaviour — the hash was already order-sensitive
and nothing pinned it, though `CREATE` then `ALTER` reversed is not a migration.

**One unreproduced report.** A lens observed `test_migration_0083` failing
in-directory and passing alone. It did not reproduce: `tests/db` ran 115 passed here.
Recorded rather than dismissed — it read the tree while this item was editing it,
which is the condition D18.5's harness exists to flag.
