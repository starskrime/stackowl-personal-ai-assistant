# The Rule Is Right, As Stated It Is Too Blunt, And Prose Does Not Enforce It

**Item.** D18.6 · Change-detector test ban — `MISSING`, wave 9, order 89.
**Ask.** Adopt the anti-pattern: never assert on data expected to change; test invariants.
**Answer.** Adopt it in a narrower form than stated, convert the five real instances,
and enforce it with a guard — because measuring the reference shows what a doc-only
rule achieves.

## As stated, the rule would have deleted 900 good tests

An AST sweep of 1,611 test files found **937** assertions of the shape
`len(X) == <int>`. Nearly all are correct: `assert len(rows) == 1` after inserting one
row is a contract about the operation, not a snapshot of anything.

Narrowing to counts of collections the codebase GROWS left **five**, and the git
history says what they cost:

| instance | what it asserted | history |
|---|---|---|
| `tests/setup/test_provider_catalog.py` ×3 | `len(entries) == 49`, `== 49`, `== 50` | bumped **15 → 17 → 49**; one commit added 32 providers and had to edit this test |
| `tests/tools/test_discovery.py` | `len(names) == 77` on the tool registry | written to prove parity with the hand-written list discovery replaced — valid once |
| `tests/scheduler/test_graph_reconciliation.py` | `len(ids) == 7  # one per TRAIT_NAMES entry` | the comment already stated the relationship the assertion refused to |

All five are converted, and **each replacement is stronger than the count it replaced**:

* The catalog now compares the loaded NAME SET to the directory it loads from. The old
  count caught a YAML that silently failed to load (`_load_dir` catches, logs a warning
  and skips). The set comparison catches that *and* two things a count cannot: a file
  whose declared `name` disagrees with its filename, and two files collapsing onto one
  key.
* Discovery now compares two POPULATIONS — every discovered class registers, and
  nothing else does. Measured: 77 registered, 77 discovered, difference 0. A count
  cannot tell "a class was discovered and never registered" from "a tool was
  deliberately removed"; both just make the number smaller.
* Graph reconciliation asserts `len(TRAIT_NAMES)`, which is what its own comment said.

## The carve-out matters more than the rule

Two count assertions here are deliberate and must survive:

    tests/tenancy/test_the_closed_axis_set_stays_closed_in_both_places.py   == 6
    tests/plugins/test_the_core_tree_does_not_grow_a_vendor_connector.py    == 4

Both guard sets that are **closed by policy**, and both say so in their own failure
message — *"a fifth means the rule was abandoned rather than amended"*. For those,
breaking on growth is the entire function. A ban that cannot tell them from the catalog
would force someone to weaken a multi-tenancy guard to satisfy a lint rule, and the
costs are asymmetric: the catalog error costs a one-line edit, while deleting a
closed-set assertion silently un-guards an authz enumeration and **nothing would ever
say so**.

So the rule enforced here is narrower than "no count assertions":

> A count literal is legitimate when the TEST produced the number, or when the number
> is the subject of a stated closure decision. It is the anti-pattern when it passively
> echoes a fact owned somewhere else.

Mechanically: an equality against a literal > 3, on a collection whose value traces to
a load/discovery/registry call, where the number appears nowhere else in the test.
Applied to the tree it yields **one** flag, a genuine false positive, allowlisted with
its reason.

## Why a guard, when the reference uses prose

Because their tree measures what prose achieves. The rule is stated in their
contributor guide with explicit banned examples. There is **no lint rule, no CI job and
no test** enforcing it — and their own suite violates it verbatim, including a file
that cites the rule by name roughly 150 lines from where it breaks it, plus about
eleven pinned context-length literals. A rule with no enforcer buys docstring citations.

## The panel disagreed, and the disagreement was settled by measurement

One lens judged the item housekeeping — "three instances in one file, one edit of
lifetime cost, and a tripwire that fires once then never again is a guard protecting
nothing". The other measured **five** instances across three files and prototyped the
detector. The first verdict rested on the smaller count, so it was the measurement that
decided it, not a compromise between the two. The tool-registry `== 77` is the case
that settles it: it breaks the next time a tool is added, and this platform mints tools
at runtime.

## What is lost, recorded honestly

A name-set comparison against a directory **cannot see an unintended file appearing** —
a stray or backup `.yaml` becomes a provider and both sides of the comparison agree. The
old count would have flagged that. It would also have flagged all 32 intentional
additions, which is the trade: the count conflates "someone added a file by mistake"
with "someone added a file on purpose" and forces a human to look either way. Only a
count owned by a stated closure decision sees growth *as growth*, which is exactly the
job the two carve-outs above are doing.

## And the same shape bit the record itself, mid-item

This item's completed stages, doc, decisions and changes were first written into
**D04.2's** record — because the edit was anchored on a block of `not_started`
stages, a shape that occurs once per unworked item, instead of on the item's id.
D04.2 was left claiming `document: done` against `designs/D18.6.md`.

**Nothing caught it.** `progress_lint` fired, but only about D18.6 still reading
`not_started`. The falsely completed item passed every check, because a filled-in
record with a doc and decisions is exactly what a finished item looks like. The one
thing that did not match was the document's NAME, and no rule read it.

`misattributed_doc_problems` now does, and the rule is sharper than a filename
match: a design document is named for its item, so an item claiming a doc named for
a DIFFERENT item must be named back by that document. `DOC_STANDARD.md` rule 1 is
"one subsystem, one document", and `designs/D09.3.md` legitimately covers both D09.3
and D10.2 — naming both in its header. It passes. `designs/D18.6.md` mentions D04.2
zero times, so the misattribution fails immediately.

**The guard found a second instance on its first run**, which is how the sharper
form was arrived at: the filename-only version flagged D10.2/D09.3, which is
correct-by-design. Measuring that flag is what produced the rule that tells the two
apart.


## Verification

```bash
uv run pytest tests/test_a_count_assertion_is_not_a_snapshot.py \
              tests/setup/test_provider_catalog.py \
              tests/tools/test_discovery.py \
              tests/scheduler/test_graph_reconciliation.py -q      # 33 passed
uv run python scripts/progress_lint.py                              # sound, 112 items
uv run python -c "
from stackowl.tools.registry import ToolRegistry
from stackowl.tools._infra.discovery import discover_tool_classes
print(len({t.name for t in ToolRegistry.with_defaults().all()}), len(discover_tool_classes()))
"                                                                   # 77 77
```

All RUN on 2026-09-05, not trusted. **Mutation-proven**, each restored from a file copy
and re-run green: reintroducing the catalog count (caught), and a stale allowlist entry
(caught).

**And the detector's own control is not optional.** Its first version returned ZERO
flags on a tree that contained five instances, because it looked for provenance in the
assert instead of in the assignment. Zero is exactly what a working guard looks like
once the tree is clean, so without a positive control there is nothing to distinguish
"clean" from "blind" — and this programme has already shipped a guard that pointed at
nothing. The control is a test in the file.
