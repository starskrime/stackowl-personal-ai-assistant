## Why this exists

The operator asked for "a web dashboard where customer control platform, agents, crons,
see memories", plus "ability to update or install or remove skills, ability to update
agents, crons and etc". Today every one of those is a terminal command or a chat turn,
and there is no surface a browser can open: **zero `.html`, `.css`, `static/` or
`templates/` files exist anywhere under `src/`.**

**And here is the honest version of the gap, because the flattering one is already
wrong in the record.** "This unblocks eight items" counts four re-presentations as new
capability. `tools/scheduling/cronjob.py` already declares eight actions — create,
watch, list, update, pause, resume, remove, run — which is every verb A05.4 asks for;
A05.4's gap line said cron jobs were "invisible unless the operator queries the database
by hand" and that was measurably false, corrected on 2026-09-11. A05.2, A05.3 and A05.8
likewise have working command surfaces.

So the wave-1 payoff is **legibility, not capability**. Two of the eight are jobs a chat
turn genuinely cannot do, and both are navigation over a set too large to narrate: A05.7
(visualise agent interactions) and A05.5 (browse memories — **237** staged facts read aloud
is not a browser). Saying this out loud is the point. Without it, someone later measures
`cronjob list`, finds it works, and asks why it was rebuilt.

## The ladder rung

**Extend existing code** — the highest rung, and it is genuinely available because every
primitive this item needs is already in the tree and running:

| need | already here |
|---|---|
| HTTP server | `aiohttp>=3.11,<4`, a declared dependency, driving `webhooks/receiver.py` |
| fail-closed allowlist | `channels/telegram/helpers.py::is_authorized` — an empty set denies all, including user_id 0 |
| constant-time compare | `hmac.compare_digest` in `mcp/server.py::_sse_auth_ok` and `webhooks/receiver_helpers.validate_hmac_signature` |
| minting and storing a token | `config/secret_writer.py::store_secret` — OS keyring, else a 0600 file, returning a resolver ref |
| showing a token once | `commands/webhook_command.py` — `secrets.token_urlsafe(32)` then "Shared secret (save now, shown once)" in reply text, never in a log |
| owner scoping | `tenancy/owned_repository.py`, `tenancy/principal.py`, 30 owner-governed tables |
| path resolution | `commands/registry.py::CommandRegistry.resolve` walking `metadata.resolve_path` token-by-token, already driving `/browser profile list` |
| supervised lifecycle | `supervisor/supervisor.py::SupervisedTask`, as `WebhookReceiver` uses it |

**So this item does not "build an auth stack", and scoping it that way would produce a
fourth copy of a rule this tree has already paid for four times.** It composes the
primitives above and adds exactly two things that genuinely do not exist: a
peer-credential check (`SO_PEERCRED` appears **nowhere** in `src/`) and anything that
resolves a credential to a **principal** — `tenancy/identity.py::resolve` is a
channel-handle alias map that returns the handle unchanged when unmapped and never
reaches `owner_id`.

## Model

### It is a separate server, and that is a measured decision

The obvious economy is to mount on the webhook receiver's existing `web.Application()`.
**Four couplings say no**, and the first is decisive on its own:

1. **It would ship OFF.** `WebhookSettings.enabled` defaults **`False`**, and the
   orchestrator gates the receiver's entire construction on it. A control plane mounted
   there would exist only for operators who had already opted into webhooks — the
   built-but-not-wired shape this tree names as its commonest defect.
2. **One app, two opposed response policies.** The receiver returns a deliberately
   uniform 401 for both unknown-source and bad-signature so source ids cannot be
   enumerated (F139). An app-level middleware runs over `/webhook/{source}` too, so a
   control-plane rejection would be **indistinguishable from a bad HMAC secret**, and the
   sender would re-provision a secret that was never the problem.
3. **One bind, two security postures.** The receiver's own warning tells the operator to
   "set `webhook.bind_address` to an address the sender can reach". Taking that advice on
   a shared app silently publishes the control plane to the LAN.
4. **One failure account.** `SupervisedTask` parks a task permanently after repeated
   failures, so a control-plane fault would take webhook ingestion down with it, and a
   webhook bind failure would take the control plane down.

They share a **library and an auth module**. Nothing else.

### Authentication is an explicit call, never a middleware

`authenticate(request) -> Principal` is called at the top of every handler, and
`check_origin(headers)` is a plain function callable from both the HTTP path and a future
socket path.

**This is the one thing that is expensive to reverse, and the reason is specific.** A05.6
("what is each agent doing now") will eventually want a live channel, and **HTTP
middleware does not run for WebSocket routes** — so a middleware-based design silently
serves the upgrade unauthenticated, and fixing it later means re-plumbing every handler
written in A05.2 through A05.8. A per-handler call costs one line each and cannot have
that bug. The ticket *store* a live channel needs is deliberately NOT built here: a
Protocol with an in-memory implementation will do, and building the table now would cost
a migration, an `owner_id` column, a sweep and an entry in the 30-table owner-governed set
for a mechanism with no consumer.

### Fail closed means three separate things, and only one of them is the bind

- **No credential configured → the server refuses to start**, loudly. It never boots open.
- **A human obtains that credential by SIGNING IN, not by running a CLI command**
  (DEBT-310, 2026-09-12). `POST /api/v1/login` compares `control_plane.username` /
  `control_plane.password` in constant time and returns the token. It is the ONE
  route that does not go through `_guard` — `_guard` demands the credential login
  exists to hand out — and it keeps the ORIGIN check, which is the whole security
  argument: without it any page on the internet could POST here from a browser
  that can reach loopback and read the token out of the reply. Verified live:
  correct credentials from a foreign origin return 401. The origin rule is SHARED
  (`_origin_ok`) rather than copied, so `test_no_route_handler_performs_ITS_OWN_auth`
  is satisfied rather than exempted.
  `mcp/server.py::_sse_auth_ok` is the counter-example already in this tree: `if not
  expected_token: return True`, documented as backward compatibility, with a loud warning
  at startup. A warning is not a gate. Closing it breaks a working setup and is therefore
  **ESC-171**, the operator's call; this document's own checker is written so that MCP can
  adopt it in one line when he answers.
- **An unidentifiable peer is denied**, not defaulted. No `owner_id: str =
  DEFAULT_PRINCIPAL_ID` on the request path — that default argument appears at five
  owner-scoped construction sites already and is exactly how an unscoped call becomes
  invisible. **MEASURED: 37 sites, not the five the panel named** — it gave examples and I
  was one edit from recording its list as a count.
- **The bind address is NOT part of fail-closed.** Loopback is fail-*absent*, not
  fail-closed, and this tree has the measurement: `webhook.enabled` defaults False AND
  `bind_address` defaults loopback, and that receiver has bound a port **873 times and
  served zero requests**. See ESC-172; the panel split on it from correct premises and
  the disagreement is recorded rather than averaged.

### The request context carries a capability set from day one

Not a boolean `authenticated`. A `frozenset[str]` of severities drawn from the vocabulary
the platform already types — `ToolManifest.action_severity` is
`Literal["read","write","consequential"]` — so "this credential may read but not write" is
expressible on the first day at the cost of nothing. The recorded core finding of this
programme is *"consent gated ACTIONS, nothing gated AUTHORITY"*; a control plane that
authenticates a customer and then lets them do anything is that same defect with a new
front door.

The principal is written as `actor` in the audit chain via the existing
`audit/logger.py::chain_append_via_pool`. If A05.1 writes `"system"` there, every mutation
made by A05.2 through A05.8 is unattributable, and no later fix retroactively attributes
the chain.

### Endpoints register; they do not accumulate in a switch

One `ControlEndpoint` ABC (path segments, method, `action_severity`, required capability)
and an `EndpointRegistry`, in the shape this tree already instantiates three times —
`scheduler/base.py::HandlerRegistry`, `commands/registry.py::CommandRegistry`,
`tools/registry.py::ToolRegistry`. Items A05.2 through A05.8 then each add a
self-registering module instead of editing a growing dispatch.

A write endpoint does not execute work inline. It creates a task row and returns 202,
which is what `WebhookReceiver._parse_and_enqueue` already does. Anything else is the
second engine Bakir's 2026-08-17 rule forbids.

The route must live in the **core** process, where the aggregator and the bus are.

## Lifecycle

Priority order is stated because ordering is behaviour, and ordering is what regresses.
Every condition below fires on the same event — an inbound request — and the first match
wins.

```
boot:
  credential present? ──no──> REFUSE TO START (ERROR).  Never bind, never serve.
        │ yes
        v
  bind ──> reachable from where sources/operators are? ──no──> WARNING, keep serving
        │
        v
  listening, and the probe reports REACHABLE (not merely "bound")

per request, in this order:
  1. Host/Origin mismatch            -> 403, WARNING          (a plain function, so the
                                                               future socket path calls
                                                               the same check)
  2. no / malformed Authorization    -> 401, uniform body
  3. token mismatch (compare_digest) -> 401, uniform body, WARNING naming the remedy
  4. token valid, principal unknown  -> 403  (never fall back to DEFAULT_PRINCIPAL_ID)
  5. endpoint severity not in the principal's granted set -> 403
  6. serve, and record the principal as `actor` in the audit chain
```

Rule 1 precedes authentication deliberately: a browser-driven request from another origin
may carry a perfectly valid cookie-or-header credential, so checking the token first would
authenticate an attack before rejecting it.

## Invariants

> **I1.** The server never binds while no credential is resolvable. Absence is a startup
> failure, never a fallback to open. (The counter-example in this tree is
> `mcp/server.py::_sse_auth_ok` — `if not expected_token: return True`. See ESC-171.)
>
> **I2.** Every handler calls `authenticate()` explicitly. No authentication lives in
> aiohttp middleware, because middleware does not run for a WebSocket upgrade.
>
> **I3.** A request whose credential resolves to no principal is refused. No code path on
> the request side takes `owner_id: str = DEFAULT_PRINCIPAL_ID` as a default argument.
>
> **I4.** The token's plaintext is never written to a log, a YAML file, or an HTTP
> response body. It reaches the operator only through the CLI, once.
>
> **I5.** An unauthenticated response body is byte-identical for "no such route", "bad
> token" and "unknown principal", so none of them can be used to enumerate the others.
> The distinguishing detail goes to the WARNING log.
>
> **I6.** A write endpoint enqueues a task and returns 202. It never performs the work
> inside the request.
>
> **I7.** The control plane's failure can never park the webhook receiver's supervised
> task, nor the reverse.

I1-I5 become assertions directly. I6 is a structural test over the endpoint registry — the
shape `test_no_closing_check_greps_the_logs_unbounded` already uses, where complying with
the form is what makes the rule impossible to forget. I7 is satisfied by construction
(separate `SupervisedTask`) and is asserted by checking the two are registered as distinct
tasks.

## Configuration

`control_plane` in `stackowl.yaml`: `enabled` (default **true** — capabilities ship on,
and an operator switch is an opt-out only), `bind_address` (ESC-172), `port`.
`auth_token` is **not** a config field: it is minted on first boot and stored through
`store_secret("stackowl-control-plane", …)`, so the plaintext never enters a YAML file
the operator might paste into a bug report.

## Observability

The package joins `scripts/logging_visibility.py`'s `BACKGROUND` tuple **in the same
change that creates it**, not afterwards. DEBT-303 is the reason this sentence is here:
`webhooks` was outside that set, so its request path logged at DEBUG — a level this
deployment has written **0 times in 677,108 records** — and a claim in `receiver.py` then
cited one of those invisible lines as evidence. A control plane that declines every
request for a week must not be able to do it silently.

A `control_plane` probe joins `REQUIRED_PROBES` in
`health/reachability/census.py` — currently five names, none of them an HTTP surface.
`WebhookReceiver.health()` reports `bound`, which is listening, not reachable and not
authenticating; that is the same mistake, and 873 boots reported success while serving
nothing.

## Failure modes

| failure | what happens | what notices |
|---|---|---|
| no credential at boot | server refuses to start | startup ERROR; the probe reports the surface absent |
| secret store unwritable | server refuses to start | ERROR — never degrade to no-auth |
| keyring present at boot *N*, absent at *N+1* | a new token is minted and every saved credential 401s | **this is the silent one.** `store_secret` logs every step at DEBUG, so today it would leave no record at all. Promoting it to INFO is part of this item; the value is never logged, only the destination |
| bad token | 401, uniform, with a stable `remedy` in the WARNING log — never in the anonymous response body, which would be enumeration |
| bound where nothing can reach it | serves nobody | WARNING at bind, in the shape `receiver.py::_warn_if_configured_but_unreachable` already uses |

## Divergence from the reference platform

Its dashboard auth is the one subject this programme still cites it on, and two ideas are
taken: **fail closed on an unidentifiable peer**, and **re-check Host/Origin on the socket
because middleware does not run there**. Three things are deliberately not taken. It is
single-user by design, so it has no principal to resolve and no capability set — we keep
both, because this platform is owner-scoped across 30 tables. Its profile-as-home-directory
isolation model is a per-agent concern that belongs to A04, not here. And its ticket store
is a real table; ours is an in-memory Protocol until something consumes it.

## What this deliberately does not do

**Ship an HTML page.** JSON first. The objection is recorded rather than dismissed: the
Improvement lens holds that a route with no page becomes the 874th bind of a port nobody
calls, and it is right that the acceptance criterion for the *item* should be a human
opening something. It is not right that A05.1 must carry it — the write surface must not
precede a proven auth decision, and nobody in this repo has written a line of HTML, which
is a cost this item does not pretend to have priced.

**Build user accounts, roles, SSO, HTTPS termination, CSRF, or rate limiting.** One
operator, one token. `webhooks/rate_limit.py::TokenBucket` already exists and gets wired
when there is traffic to limit, not before.

**Change the MCP transport.** That is ESC-171 and it is his call.
