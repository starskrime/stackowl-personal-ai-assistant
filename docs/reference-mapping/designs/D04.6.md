## Why this exists

The item asked one question: *"Adopt jittered backoff specifically? Ours may be fixed
exponential."* The answer is yes on the facts — exactly one file in all of `src/` imports
`random`, and it is `owls/dna_attribution.py`, so there is no jitter in any retry path.
Measuring *why that mattered* found something the Ask did not name: **the platform's
back-pressure actuator records that it slowed down without slowing down.**

On a classified `RATE_LIMIT`, `resilient_round` calls `limiter.penalize()` and, in the
`else` of that `try`, writes a retry-ledger event named `rate_limit_penalty`. `penalize()`
returned silently when the bucket is uncapped — `if self._capacity is None: return`, placed
*before* its own WARNING. And the bucket is uncapped for **100% of traffic**:
`rate_limit_rpm` is absent from the live `stackowl.yaml`, `from_rpm(None)` returns a
pass-through, and one provider serves all three tiers.

So a 429 would have produced a ledger entry asserting a response that never happened. The
property that distinguishes the two — `is_noop` — already existed on the class with **zero
consumers**.

## Model

Three changes, one principle: **record the effect, never the call.**

| # | Change | File |
|---|---|---|
| 1 | `penalize()` returns whether a penalty was APPLIED; declining is logged at INFO | `providers/rate_limiter.py` |
| 2 | The caller records `rate_limit_penalty` or `rate_limit_unpaced` accordingly | `providers/_resilient_round.py` |
| 3 | `jittered()` — additive-only decorrelation for self-computed delays | `infra/resilience.py` |
| 4 | Applied at the three self-computed sites | `durable/store.py`, `supervisor.py`, `provider_probe.py` |
| 5 | `ResilienceContributor` degrades on the recycle RATE, and is finally constructed | `health/contributors.py`, `scheduler/assembly.py` |

### Which delays may be jittered

| Delay | Owner | Jittered |
|---|---|---|
| `_BACKOFF_SECONDS` ladder | us | **yes** |
| supervisor restart backoff | us | **yes** |
| provider probe (linear `base * attempt`) | us | **yes** |
| `CircuitBreaker._current_half_open_seconds` | **the server**, via `open_for()` | never |
| `retry_actuator` `retry_after + buffer` | **the server** | never |
| Telegram `_flood_until` | **the server** | never |

The breaker's field is the trap: its own docstring says `open_for()` deliberately reuses
`_current_half_open_seconds`, so that one field carries both our adaptive doubling *and* a
provider's `Retry-After`. It is also what the operator is shown (`[open, retry in Ns]`).
Jittering it would make the platform disagree with a contract it was given — the class of
bug that earned a ~10-hour Telegram flood ban on 2026-07-19.

## Invariants

1. **`jittered(d) >= d`, always.** Additive-only. Enforced by a property test over 500 draws
   per magnitude, and fail-closed to `0.0` on a negative, NaN or infinite input.
2. **`jittered(d, fraction=0.0) == d` exactly** — the change is reversible by configuration,
   byte-for-byte.
3. **A `rate_limit_penalty` event implies a penalty was applied.** Its absence is now
   informative: `rate_limit_unpaced` means "told to slow down, unable to".
4. **The resilience alarm clears.** Status is driven by the recycle DELTA between sweeps,
   never the cumulative count, which would latch degraded forever after one bad afternoon.
   **PROVEN LIVE 2026-09-07** — the one thing on this page that stopped being a claim.
   `[health] resilience_contributor: a resource is flapping — recycled repeatedly between
   sweeps` fired once, at 06:35:05Z, carrying `{"flapping": ["db_pool+2"], "threshold": 2}`.
   The `+2` IS the delta and the label IS named, which is what distinguishes this line from
   the cumulative-count version that would have latched: a latching contributor would have
   fired on every sweep after the first, and the retained logs hold exactly one.

**The denominator only became readable on 2026-09-07, and that is the point.** Until
`7704628c` raised the fault classification out of the 4-point DEBUG exit onto its own INFO
record, the cause of every fault was invisible in production — so "zero rate-limit
penalties" and "zero rate-limit events" were the same reading, and neither could be
distinguished from a broken actuator. There are now **43 `[resilient_round] fault
classified` records, every one `cause: transport`, `recovery: retry`**, beside 72
breaker short-circuits and 60 half-open skips that never reach `penalize()` at all.

So the pacing path has had **NO OPPORTUNITY**, stated with a real population rather than
asserted. It is not evidence that pacing works; it is evidence that nothing has yet asked
it to.

## Failure modes

**The rate limiter is still off, and now says so — but nothing has yet made it say
anything.** This item deliberately did not invent an RPM: the right value is the provider's
contract, not ours to guess. Until `providers[].rate_limit_rpm` is set, a 429 is recorded
as `rate_limit_unpaced` and pacing does not happen.

**Re-measured 2026-09-07: `rate_limit_rpm` is still absent from the live `stackowl.yaml`,
and the honest state has never been printed, because no 429 has occurred.** 0 of 43
classified faults were rate-limit; all 43 were `transport`. So the sentence "it is now
visible instead of silent" is a property of the CODE and not yet an observation — the
distinction this document exists to insist on, applied to its own claim. What would close
it is one rate-limit fault, at which point `rate_limit_unpaced` must appear in the same
trace.

**Jitter is preventive here, not corrective — and the record says so.** In the platform's
entire history exactly FOUR task rows ever reached attempt 2. The 7-wide cohorts that
appeared to justify jitter were unreachable-owner rows filed under a non-principal owner,
which the owner-scoped `claimable()` could never claim; they contended for nothing and were
dead-lettered 18 hours later still at attempt 1. The `jobs` "17-wide" cohorts were a
minute-binning artefact — at second granularity the maximum is 6, and their `last_run_at`
spreads over ~90 seconds. Adopted on the operator's explicit call, over this evidence.
