# Untrusted input — fencing what came from outside, and narrowing before reading it

> **Status:** live
> **Map item:** D12.8
> **Source:** `src/stackowl/infra/untrusted.py` (~70 lines), applied in
> `tools/io/web_fetch.py`, `tools/io/pdf.py`, `tools/search/web_search.py`,
> `tools/browser/tools.py`
> **Config:** none — the fence is unconditional; the narrowing is declared per fetch call
> **Last verified:** 2026-09-05, against commit `<pending>`

## Why this exists

The map's gap line said *"a public webhook can currently reach shell."* **That was
falsified on 2026-08-28 and it is the only thing that made this P1.** `WebhookHandlerJob.
execute` is a stub whose step 3 is literally a placeholder — it never enters the pipeline,
so it reaches neither `shell` nor any other tool — and `WebhookSettings.enabled` defaults
to False, so there is no public listener unless an operator turns one on. A gap line
asserting a live path from the internet to `shell` is an emergency; nothing in the tree
supported it.

**So the question became: where does untrusted input actually enter?** Measured
2026-09-03 over 974 tool-using turns: the exposure was never the webhook. It is the
browser, it is live, and it is ordinary work — `web_fetch`+`write_file` 35,
`web_search`+`write_file` 31, `browser_navigate`+`write_file` 27, `web_fetch`+`shell` 24.

And the marker to handle it **already existed, wired to exactly one tool.** `pdf.py` had
fenced its extracted text since it was written, under a PDF-specific name, and nothing
else called it. A scanned PDF was fenced; a fetched web page was not. That is CLAUDE.md
shape #1 — an actuator wired on only some paths — and it stayed invisible precisely
because the one wired path looked like the general rule.

## Model

Two layers, and they do different jobs. Confusing them is the main risk to a reader.

| | **The fence** (this item) | **The narrowing** (ESC-110's answer, on top) |
|---|---|---|
| what it does | marks content as data, not instructions | refuses write-severity tools for the rest of the turn |
| stops | a careless model | a determined page |
| when | as content enters | declared IN the fetch call, before content is readable |
| scope | one string | one turn |

`untrusted.wrap(text, *, source)` fences with `<<<UNTRUSTED_CONTENT>>>` …
`<<<END_UNTRUSTED_CONTENT>>>` and names the origin, because "untrusted" alone tells a
reader nothing actionable while `source=web_fetch:example.com` tells them which page to
go and look at.

## Lifecycle

```
fetch call  ──> agent declares needs_write_after   (before ANY content is in context)
    │                    │
    │                    └─> false ⇒ every write-severity tool refused for this turn
    ▼
content returns ──> untrusted.wrap(...) ──> fenced string enters the model's context
```

**The ordering is the entire security argument.** An agent choosing `needs_write_after=
false` chooses while still uninfluenced; by the time the page is readable the narrowing
has already happened, and nothing the page says can retract it, because a retraction
would have to arrive as a tool call and every write-severity call is refused from that
moment. A test pins that the dispatcher CHECKS before it OBSERVES — otherwise the
narrowing fetch would be refused by the declaration it had just made.

## Invariants

1. **Idempotent.** Tool results are re-wrapped by retries, summarisers and shadow
   replays; already-fenced text is returned unchanged, so the model never sees two
   openings for one body.
2. **Empty content is never fenced** — an empty fence is noise that teaches a reader to
   skim the marker.
3. **Every wrap logs at INFO**, so exposure is countable. Before this item the count was
   unobtainable.
4. **Narrowing is turn-scoped by construction** — the state is a local in the tool loop's
   closure, unreachable by the next turn, so a turn that narrowed itself cannot narrow
   another.

## Observability

`[untrusted] wrapped external content` at INFO, carrying `source` and `chars`.

## Failure modes

**A marker is not a control, and that was deliberate.** Narrowing the toolset after every
fetch would have split real work in two — measured, 66 legitimate turns in seven days.
Which capabilities may survive contact with untrusted input was escalated as ESC-110
rather than defaulted, and answered NARROW ON DEMAND.

**An agent that leaves the default (`true`) is exactly as exposed as before.** That is the
stated price of a self-declaration.

**Two fenced paths are wired but unexercised, and their zero is not a defect.**
`web_fetch` and `pdf` call the fence, and neither has produced a wrap. Measured: the fence
reached them in commit `1767b9ab` on 2026-09-02, and `web_fetch`'s last successful run was
2026-08-31 (522 of its 525 successful exits were on 2026-08-28 alone). A zero over a zero
denominator is not a pass and is not a failure — it is an unexercised path, and it is
recorded here so the next reader does not diagnose it as a hole.

**The webhook lane the map named is still a stub**, so the reference platform's fixed
4-read-only-tool webhook toolset has nothing to constrain here. Building it now would be a
seat for a feature that does not exist. The trigger to revisit is Story 11 — when the
handler dispatches to real business logic, that lane needs the narrowing applied by
default rather than by self-declaration, because there is no agent to declare it.

**CLOSED 2026-09-05.** The closing query returns **213**: `web_search` 178,
`browser_extract` 22, `browser_navigate` 13, first appearing 2026-09-04 (12) and
2026-09-05 (201).

**And the exposure it makes visible is a RATE, not a count.** Of turns that fetch external
content, those also using a powerful tool: **6 of 25 (24%) over 7 days, 110 of 256 (43%)
over 14**. The absolute number fell from the 66 recorded on 2026-09-03 only because
fetching turns collapsed from 256 to 25 — the activity stopped, the exposure did not.
Reporting the count alone would have said "risk receding", which is the same mistake
ESC-114 made when a 24x workload drop was read as a fix.
