# The Storage Half Was Already Complete; The Launcher Was The Instance-Hostile Part

**Item.** D18.3 · Profiles / multi-instance — mapped `MISSING`, wave 9, order 86.
**Ask.** "Do you want multiple isolated StackOwl instances?"
**Answer.** The Ask stands, but on a corrected premise — and three defects were fixed
that are wrong regardless of how it is answered.

## The map's verdict was wrong in both directions

`MISSING` said nothing existed. Measured 2026-09-05, most of it did:

| | measured |
|---|---|
| `StackowlHome` accessors returning a `Path` | **25** |
| contained by `STACKOWL_HOME` | **25** |
| escaping it | **0** |
| import-time frozen paths in `src/` (AST sweep) | **1** |
| test isolation via `STACKOWL_HOME` | **already exists** (`tests/conftest.py`) |

`db_path`, `logs_dir`, `config_file`, `core_socket`, `pid_file`, the kuzu graph, skills,
plugins, secrets — all of it derives from one root that is read **at call time**. The
map's second clause, "no clean test isolation", is simply false: an autouse fixture
already redirects the home, added after test data reached the operator's live `USER.md`.

**But my own first reframing — "it works today, it is only undiscoverable" — was also
wrong, and a panel lens falsified it.** `./start.sh`, which `CLAUDE.md` mandates as *the*
restart path, was the one place the single-accessor discipline did not hold:

    line 34  runtime_dir="$HOME/.stackowl/runtime"          hardcoded
    line 41  nohup … > "$HOME/.stackowl/manual_restart…"    hardcoded
    line 17  pgrep -f "python3? -m stackowl (start|__core__)"   HOME-BLIND

So `STACKOWL_HOME=~/.stackowl-work ./start.sh` would have **killed the running
instance**, deleted its pid and socket, and overwritten its stdout log — while every one
of the 25 accessors correctly resolved into the new home. Isolation complete in `src/`
and absent in the launcher is not isolation.

## Root cause, and what else it reaches

**The single-accessor rule is real and holds across all of `src/`. The launcher is the
one caller that reimplemented the path by hand — and it is a shell script, which is why
nothing caught it: every guard this repo owns reads Python.** That is `CLAUDE.md`'s
"same rule, one case short", with the missing case sitting outside the language the
guards can see.

What else that reaches was measured rather than assumed: `scripts/full_suite.sh:20` also
hardcodes `$HOME/.stackowl/logs`, and it is the only other shell file that names the
home. The fix is the same one applied here — **the shell asks `StackowlHome` instead of
re-deriving the path** — and the new guard reads `start.sh` directly, so the rule now has
an enforcer in the language it was being broken in.

## The three fixes

1. **`start.sh` asks the accessor.** It resolves the home by calling `StackowlHome.home()`
   and **refuses to sweep or delete anything** if that fails, rather than guessing. Its
   orphan sweep — which exists for a real incident, an orphaned `__core__` holding port
   8766 — now decides which home a candidate PID belongs to (via `/proc/<pid>/environ`,
   falling back to `ps eww`) and leaves the others alone, warning loudly when it cannot
   tell. Proven both directions against the live platform: with a custom home the sweep
   returns **empty** while three real StackOwl processes run; with the default home it
   returns **all three**.
2. **The one frozen path is gone.** `_CONFIG_BASE = StackowlHome.plugins_dir()` became
   `default_index_path()`, resolved at call time. Re-measured: `PluginIndex` now follows
   an in-process home switch instead of silently reading the old one.
3. **The capability is documented, and the claim is guarded.** `STACKOWL_HOME` appeared
   nowhere an operator looks — no README exists, `--help` does not mention it, and it was
   classified as legitimate in `test_a_new_env_var_has_to_justify_itself.py` against that
   file's own bar, *"where an operator can discover it"*. It is now in the generated
   config example, and `test_one_home_contains_the_whole_instance.py` asserts the
   containment property that sentence claims, so the documentation cannot become a lie.

## Honest scope — what was NOT claimed

**Multi-instance is not supported, and nothing here says it is.** Five process-level
global names still collide, all measured: the OS keychain service strings
(`"telegram-bot"`, `f"stackowl-provider-{name}"` — profile B's setup overwrites profile
A's credential), the Telegram bot token (the same bot cannot poll twice, and there is no
`Conflict`/409 handler in `channels/telegram/`), the service-unit filename
(`stackowl.service`, `com.stackowl.plist`), and the webhook and MCP ports — **8766 is
bound right now** by the running core. Storage isolation is complete; process isolation
is not. That is ESC-136, and it is the operator's call.

**The freeze had caused no harm.** Every `src/` importer of `plugins.index` is
function-local, so on the production path the constant resolved at first *call*. An AST
sweep found it to be the only one of its kind — not a class of bug. It is recorded here
as what it was: a latent hazard whose trigger was a feature that does not exist yet, and
the single exception to an otherwise call-time-correct codebase.

**A panel contradiction, resolved by measurement rather than averaged.** One lens held
that a `--profile` flag would work because every accessor follows a late-set variable;
another held it would break on the freeze. Both were half right, and the test that
separates them is the finding: every accessor *did* follow the switch, and `PluginIndex`
*was* frozen — so the one exception was precisely the thing that would have made the
proposed feature silently wrong.

**A dependency edge was corrected.** The map claimed profiles are "how Kanban (D07.6)
gets its worker isolation". D07.6's own re-measurement says `tasks` **is** the durable
board, with lease-based claims (`lease_owner`, `lease_expires_at`) — worker isolation
comes from leases, not processes. `blocks: [D07.6]` is dropped, and the correction is
flagged in ESC-136 rather than made silently.

## Verification

```bash
uv run pytest tests/test_the_launcher_honours_the_home_it_is_given.py \
              tests/test_no_path_is_frozen_at_import_time.py \
              tests/test_one_home_contains_the_whole_instance.py -q   # 9 passed
bash -n start.sh && echo "SYNTAX OK"
# the sweep, both directions, against whatever is running now:
sed -n '/^process_home() {/,/^}/p;/^instance_pids() {/,/^}/p' start.sh > /tmp/fns.sh
( home=/tmp/nonexistent-home; . /tmp/fns.sh; echo "custom: [$(instance_pids | tr '\n' ' ')]" )
( home="$(uv run python -c 'from stackowl.paths import StackowlHome; print(StackowlHome.home())')"
  . /tmp/fns.sh; echo "default: [$(instance_pids | tr '\n' ' ')]" )
#   expect: custom EMPTY, default listing the live StackOwl PIDs
```

All RUN on 2026-09-05, not trusted. **Mutation-proven**, each restored from a file copy
and re-run green: a hardcoded `$HOME/.stackowl` in the launcher, a new module-level
`StackowlHome.workspace()`, and an accessor escaping the home each fail their guard.
