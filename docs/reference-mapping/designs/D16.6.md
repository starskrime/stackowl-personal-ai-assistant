# Integrations — Not Rung 6, and a Placeholder in the Morning Brief

**Item.** D16.6 · Integrations — `DIVERGENT`
**Last verified.** 2026-09-04, commit `5c25759c`

## Why this exists

The Ask: *"would Gmail/Calendar be better as a skill + CLI command pair?"* — the map records
the gap as *"ours is rung 6 for something they solve at rung 2"*.

**The premise needs correcting before the question can be answered. It is not rung 6.**

A rung-6 "new core tool" is model-callable. There is **no gmail or calendar tool among the 77
registered — zero**. The entire capability of both adapters is a single method,
`get_morning_brief_section()`, contributing a section to the morning brief through the
`IntegrationAdapter` ABC.

## So the answer is no, and rung 2 is also the wrong shape

Skill + CLI is a *command* shape: the operator types something, or the model reads a recipe.
This capability is neither. It is an adapter implementing an interface the platform already
defines, called by `IntegrationSectionAssembler` when the morning brief is assembled.

**The fitting rung is 4 — a plugin.** `IntegrationRegistry.register()` is documented "open for
extension: plugins can call register() at import time", `IntegrationAdapter` is the ABC, and
`/connect` already tells the operator "install an integration plugin first". The surface for
the right answer exists; only the move is outstanding, and that is ESC-133.

## Defect 1 — a placeholder in the operator's morning brief

`get_morning_brief_section` did this, once `is_connected()` returned True:

```python
items = ["[Gmail brief section — live fetch requires active connection]"]
return BriefSection(key="email", title="Email", items=items[:self._brief_max_items])
```

A section titled **Email**, in the morning brief, whose only content announces that nothing
was fetched. No mail is read anywhere in the method. And `is_connected()` is only
`self._oauth.exists()` — a token *file* being present, not a mailbox being read.

**The same file states the rule it broke**, twenty lines below, for `list_messages`:

> real call when connected + client available, else honest "unavailable" (F024): **NEVER
> fabricate "ok" for an unperformed action.**

Same rule, one method short — with the rule written in the same file. It now returns `None`
and the assembler omits the section, which is the honest answer until a real fetch exists.

**It was unreachable**, so this is a correction rather than a behaviour change: nothing in
`src/` constructs `GmailAdapter`, so the registry the assembler iterates is empty. It becomes
reachable the moment a plugin registers one — exactly the future `/connect` invites.

## Defect 2 — my own guard from the previous item was unsound

D16.4 shipped a tripwire asserting which core modules "register an integration". Its predicate
was: does the file contain the string `IntegrationRegistry` **and** the string `.register(`
anywhere? It reported three — `cli/app.py`, `commands/assembly.py`, `startup/orchestrator.py`
— and **none of them registers an integration**. They register health contributors
(`agg.register(DbContributor(...))`), commands (`registry.register(factory())`) and owls.

Co-occurrence in a file is not a call. That false positive reached the map entry, the D16.4
design document, `progress.yml` and a commit message before this item caught it — and it made
the violation sound *live* when the true state is *unwired*, which is materially different and
changes what ESC-133 should ask.

The predicate is now "does any core module **construct** a vendor adapter" — `GmailAdapter(`
or `GoogleCalendarAdapter(` — one fact with one meaning. Mutation-proven.

**This is the fifth unsound-screen episode in this programme, and the first where the unsound
screen was mine.** The rule it breaks is the one I have been applying to other people's
screens all week: a predicate that cannot distinguish the thing from a mention of the thing is
not a measurement.

## A third thing, found while fixing the first

Removing the placeholder orphaned `self._last_api_call_at = time.time()`, and the ruff gate
caught the now-unused import. Following it: the field is **initialised and written and read
nowhere** — once in `gmail.py`, and three more times in `google_calendar.py`, with no reader
anywhere in `src/` or `tests/`. A write with no reader, shape 1, in both siblings.

Deleted in this change: the field, its initialiser and all four assignments. `time` stays in
`google_calendar.py`, where it measures real latency.

## Invariants

- A brief section is real content or absent — never a placeholder.
- No core module constructs a vendor adapter.
- The guard on the placeholder reads **string literals via AST**, not text: the fix's own
  comment quotes the removed placeholder so a reader knows what went and why, and a substring
  scan cannot tell that comment from live code. It failed on exactly that before being fixed.
