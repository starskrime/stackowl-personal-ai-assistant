## Why this exists

D09.1 was mapped as **"Background review fork" — `MISSING`**: the reference platform forks a
second agent after a turn to ask "should any skill or memory be saved?", and StackOwl runs its
miners as scheduled jobs instead. The gap statement read *"learning is not tied to the moment
the lesson exists"*.

**Re-measured, that verdict does not survive** — and its own 2026-08-22 correction is stale too:

| claim | measured 2026-09-02 |
|---|---|
| `reflect_now` never invoked | **11** invocations since 2026-06-19 |
| the fork inherits the prompt cache | `cached_input_tokens` = 0 on **129,845 of 129,845** records, all-time |
| learning is starved | **6,395** reflections written; `note_applied_lesson` invoked **791** times, most recent today |

So the loop already produces, reads and applies. Building a fork would have been a second
learning engine for no measured gain, against the one-loop rule.

**What the measurement did find** is a different gap, and it is the one this component closes:

```
note_applied_lesson   791 invocations, most recent today
reflect_now            11 invocations since 2026-06-19
synthesize_skills       0, all-time
evolve_now              0, all-time — while holding a GUARANTEED presentation slot
```

**The contrast is the finding, and it is not "the model ignores learning."** A tool that
records something as a *byproduct* of answering is used constantly; tools that ask the model to
stop and do meta-work instead of finishing the user's task are never chosen. That is an
incentive shape, not a discoverability bug — presenting them harder would not change it.

Nobody could see any of that. The platform had no way to answer "which of my capabilities has
never been used?"

## Model

| Concept | Meaning |
|---|---|
| **scope** | Which set is being reported: `"learned"` (the two learned-tool specs) or `"all"` (every registered tool). Two reports in one boot are distinguishable by this field alone. |
| **used** | Every distinct name ever recorded in `task_outcomes.tool_sequence`. Normalized at the store, so a well-formed name for a tool that does not exist can appear — harmless here, because the question only ever asks whether a *registered* name is **absent**. |
| **never_invoked** | Registered names not in `used`. **A question, not a verdict** — see Invariants. |

## Lifecycle

```
boot
 ├─ LearnedToolLoader.load_all(registry, db)
 │    └─ report_never_invoked(learned_names, db, scope="learned")
 └─ after ALL registration completes
      └─ report_never_invoked([t.name for t in registry.all()], db, scope="all")
```

Placed **after** every registration so nothing is missed. Both calls go through one function:
the rule lived inside `learned_tool_loader` first and answered the question for two tools —
the example, not the architecture.

## Invariants

> **I1.** Nothing is removed, disabled or hidden on the strength of this report. It logs.
> **I2.** A used tool is never named as never-invoked.
> **I3.** With no pool, usage is reported UNKNOWN — never a silent zero.
> **I4.** A failed read reports nothing — never a false zero.
> **I5.** Reporting never raises; a usage report may not wedge the boot.
> **I6.** The learned-tool path calls this function rather than carrying its own copy of the query.
> **I7.** The registry-wide report is actually wired — a report nobody calls is decoration.

All seven map to tests in `tests/tools/test_the_platform_can_see_which_capabilities_are_unused.py`.

**I1 is the load-bearing one.** Zero invocations is not proof of uselessness: a tool the
presentation cap dropped was never *offered*. `skills_list` already cost this project that
exact mistake — it showed zero invocations not because the model ignored it but because on
those turns it was not there to call.

## Configuration

None. No thresholds, no toggles, no settings key — the report is unconditional and costs one
query per boot.

## Observability

- `[tools] usage_report: capability usage` — INFO. `_fields`: `scope`, `n_registered`,
  `n_never_invoked`, `never_invoked`.
- `[tools] usage_report: usage UNKNOWN — no pool wired…` — INFO, when usage is unknowable.
- `[tools] usage_report: could not read tool usage…` — WARNING, on a read failure.

```bash
cat ~/.stackowl/logs/stackowl*.jsonl \
  | jq -c 'select(.msg | contains("capability usage"))
           | {ts, scope: .fields.scope, n: .fields.n_never_invoked}'
```

## Failure modes

| Failure | Detected by | Recovery | User sees |
|---|---|---|---|
| No db pool wired | `db is None` | Reports UNKNOWN, returns `[]` | Nothing |
| `task_outcomes` unreadable | exception on `fetch_all` | WARNING, returns `[]` | Nothing |
| Empty registry | `not wanted` | Returns `[]` silently | Nothing |
| Anything else | `except Exception` | Never raises | Nothing |

Every path returns `[]`, and **callers must not read that as "everything is used."** That
distinction is the whole design: an unknown must never read as a clean bill of health.

## Related

- Map items: `D09.2` and `D09.4` are blocked on D09.1 and are unaffected by this outcome —
  the fork they assumed was never built.
- `ESC-46` moved `synthesize_skills` out of the guaranteed presentation set on the same
  reasoning one step earlier.
- **Prior art and where we diverged.** The reference platform's answer to "is the loop
  learning?" is to fork an agent per turn and ask it. We did not adopt that: its own gate is
  1-in-10 turns with memory defaulting to **off**, its cache advantage is nil here
  (0 of 129,845 records), and `reflect_now` already reaches the same handler in-turn. What we
  took instead is the *question* it was asking, answered from data the platform already
  records — and answered about the whole capability surface rather than one turn's worth.
