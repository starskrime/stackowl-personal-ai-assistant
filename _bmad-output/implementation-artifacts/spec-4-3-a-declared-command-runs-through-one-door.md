## Intent

**Problem:** Every tool/command now DECLARES severity and a future command type (story 4.2), but nothing EXECUTES through a single path yet: `CommandRegistry.dispatch` runs `??` preview and `cmd.handle()` with zero authorization; `DurableTask` has no notion of a non-goal "command" unit of work (no `kind`, no `command_id`); and `cronjob.py`'s pause/resume call `JobScheduler.pause`/`.resume` directly, bypassing any door. AD-1/AD-7/AD-26 require one typed submit entry, backed by a COMMAND `DurableTask` kind, executed only by a deterministic core handler registry — not yet the requester-kind/reversibility POLICY (that is 4.4's action-policy gate).

**Approach:** Add `commands/spec/` (CommandSpec table + the one submit entry; imports only `authz/` + `pipeline/durable`, tripwire-enforced). Add a COMMAND `DurableTask` kind (migration 0151) with `command_type`/`command_payload`/`command_id`/`requester_kind`/`nonce`/`utterance_id`, `command_id`-unique for idempotent re-submission, and a `command_receipts` table so a subsystem mutator can make re-execution after a lease reclaim a no-op. Wire `TaskLoop`'s runner to branch on `task.kind`, reserve one claim slot for COMMAND rows, and expose a payload-free gateway→core `TasksEnqueuedFrame` wake. Insert a severity check (via a new `authz.requester.principal_for`, single-owner-grants-everything for now — the real per-requester-kind policy is 4.4) ahead of `CommandRegistry.dispatch`'s preview/handler branch. Migrate `cronjob` pause/resume — and only those two actions — onto `submit_command`, flip their `state_change_census` entries to `migrated`, and add the three AD-1 tripwires (mutator called only from the handler registry, no mutator instantiated in `gateway/`, no dynamic/generic dispatch in the submit entry).

## Boundaries & Constraints

**Always:**
- `commands/spec/` imports only `stackowl.authz`, `stackowl.pipeline.durable`, stdlib and pydantic — enforced by an AST tripwire (AD-7).
- Every `CommandSpec` carries type, typed `payload_model`, severity (from `authz/`), `reversible: bool`, and `undo_command_type: str | None` — non-null iff `reversible` (validator).
- `submit_command` sets `requester_kind` from ingress/trace provenance (`authz.requester.requester_kind_from_trace`), never from the caller-supplied payload dict.
- A COMMAND task's severity check runs before its handler; `CommandRegistry.dispatch`'s `??` preview and `cmd.handle()` both run only after the severity check for a state-changing command.
- The subsystem mutator (`JobScheduler.pause`/`.resume`) writes its `command_id` into `command_receipts` inside its OWN transaction, before applying the mutation, and short-circuits (no-op) if that `command_id` is already present — this is what makes a lease-reclaim re-run safe.
- The mutator alone records the domain event (`job.paused`/`job.resumed`, new — none existed before this story), carrying `CommandContext`; the COMMAND task wrapper records only `command.*` lifecycle events, never the domain event (no double-recording).
- `TaskLoop.claimable()` always includes at least one claimable `kind='command'` row (if any is pending) in its returned batch, even when goal rows would otherwise fill every slot.
- Only `cronjob` pause/resume migrate this story. `create`/`update`/`remove`/`run`/`watch` keep calling `JobScheduler` directly — unmigrated, owned by story 4.7 per the 4.2 census.
- 4-point logging (entry/decision/step/exit) on every new/changed method that does I/O or a non-trivial decision.

**Never:**
- Do not build the action-policy gate (AD-27) — no reversibility/requester-kind-driven consent decision, no read-back, no step-up, no Needs-you item. The severity check this story adds is real but its `principal_for` grants ALL_SEVERITIES to every requester kind for now; that is deliberate and documented, not a bug — 4.4 replaces it.
- Do not build standing authority (4.6), undo execution (4.5 — `undo_command_type` is only DECLARED, never invoked), or voice (`utterance_id`/`nonce` columns exist, unused beyond storage).
- Do not touch `cronjob`'s `create`/`update`/`remove`/`run`/`watch` actions, or any other tool/command from the 4.2 census — every other `pending` ledger entry stays `pending`.
- Do not add a generic `execute_command(command_type: str, **kwargs)` style entry point, `eval`/`exec`, or `getattr`-based dynamic dispatch anywhere in `commands/spec/` — the handler registry is a closed, explicit dict.
- Do not change `ControlPrincipal`, `READ`/`WRITE`/`CONSEQUENTIAL`, or any story-4.1/4.2 test's passing behavior.

**Acceptance Criteria:**
- Given the new `commands/spec/` sub-package, when a command is declared, then its `CommandSpec` has a type, a typed payload model, a severity from `authz/`, a reversibility and an undo command type, `commands/spec/` depends only on `authz/` and `pipeline/durable` (tripwire-enforced), and its module carries a `PLACEMENT:` docstring recording the owner's 2026-09-13 placement vote (AD-1, AD-7, AD-26)
- Given the durable task store, when the platform migrates, then an idempotent migration (0151, `ADD COLUMN`/`CREATE ... IF NOT EXISTS`) adds the 6 COMMAND task fields plus `kind`
- Given any surface or tool, when it submits a command through `submit_command`, then the entry validates the payload, sets requester kind from ingress provenance (never the payload), enqueues a COMMAND task keyed by `command_id`, and a gateway-side enqueue sends the payload-free `TasksEnqueuedFrame`
- Given a COMMAND task, when core executes it, then it runs the severity check via `principal_for`, then the deterministic handler from `CommandHandlerRegistry`, with no model call; the mutator writes its `command_id` receipt in its own transaction so a lease-reclaim re-run is a no-op; `claimable()` reserves a slot for COMMAND rows; `command.*` lifecycle events are recorded by the runner while the mutator alone records the domain event carrying `CommandContext`
- Given `CommandRegistry.dispatch` and the `??` dry-run preview, when a slash command that changes state is dispatched, then authorisation runs through `principal_for` before any handler or preview
- Given the codebase, when the tripwires run, then they fail any call to `JobScheduler.pause`/`.resume` from outside `scheduler/commands.py`'s handlers, any subsystem mutator instantiated under `src/stackowl/gateway/`, and any dynamic/generic dispatch inside `commands/spec/`
- Given job pause and resume from the `cronjob` tool, when driven through `scripts/dev_ingress.py` against the running platform, then each runs as a COMMAND task, is audited (`audit_log` `job_paused`/`job_resumed` with an actor), and appears in the journal (`job.paused`/`job.resumed` + `command.*` rows)

## Design Notes

**Why the severity check is real but toothless today.** `principal_for()` grants `ALL_SEVERITIES` to every `requester_kind` — every dispatch and every COMMAND execution passes. That is correct for this story: epics.md scopes the requester-kind/reversibility POLICY decision to 4.4's action-policy gate, and the owner's own framing of this story is explicitly "not yet the policy decision... just the structural funnel/dispatch point." The refusal branch is proven by unit tests that build a `ControlPrincipal` directly with a restricted `granted` set and assert `.may(severity)` is False and the call site actually stops there — never by a live surface, since nothing live can produce a restricted principal yet.

**Why `requester_kind` derivation is minimal.** The only existing "who is driving this" signal is `TraceContext`'s `principal` ContextVar plus `PRINCIPAL_AUTONOMOUS_SCHEDULER` (a story-3.4 concept, explicitly noted in spec-4-1 as "a separate, already-shipped concept" not to be touched). `requester_kind_from_trace()` reads it: `PRINCIPAL_AUTONOMOUS_SCHEDULER` → `"autonomous"`, anything else → `"owner"` (this platform has exactly one human owner and no live owl/crew/voice actors driving commands yet — `owl`/`voice-unverified` are declared in the `RequesterKind` vocabulary for 4.4+ to start using, never produced by this story).

**Why pause/resume's idempotency doesn't lean on "the UPDATE is naturally idempotent."** `JobScheduler.pause`/`.resume` already happen to be idempotent (`enabled=0` twice is a no-op) — but AD-26's rule ("the mutator writes command_id in its own transaction") is deliberately general infrastructure every future migrated mutator (4.7-4.10) reuses, most of which will NOT be naturally idempotent (e.g. `scheduling.create_job` minting a new row). `command_receipts` + `record_command_execution()` is the one reusable guard; this story's pilot proves the pattern even though its own mutation happens to be idempotent by luck too.

**Why inline (non-tick) execution.** `cronjob.py`'s pause/resume run inside an already-executing LLM turn (the "fast path," not the TaskLoop) and must keep returning an honest synchronous `ToolResult` — `{"pause": True, ...}` cannot become "queued, check back later" without changing tool-call semantics outside this story's scope. `store.create_child_task`/`claim_child_lease` (D1 §7.1) already establish the precedent: create the row, CAS-claim it inline, run it directly, never wait for the tick. `submit_command` follows the exact same shape for a COMMAND row created in-process. The tick-driven path (`claimable()` → `TaskLoop.tick()` → the new `task_loop_runner.py` branch) stays the fallback for anything that could not claim inline (e.g. a future gateway-role submission with no local handler registry) — this is also what the `TasksEnqueuedFrame`/`task_loop.wake()` wiring is for.

**Why `scheduler/commands.py`, not `commands/spec/`, holds the pilot's `CommandSpec`s.** AD-7 restricts what `commands/spec/` may import (only `authz/` + `pipeline/durable`); a subsystem declaring its own commands is not restricted the other way. Every future migrated subsystem (4.7-4.10) gets its own `<subsystem>/commands.py` following this same shape — `commands/spec/` never grows subsystem-specific knowledge.

**Subcommand-level severity in `CommandRegistry.dispatch`.** `dispatch()` operates on the bare top-level command name only; subcommand parsing happens inside `cmd.handle()`. This story checks `COMMAND_CENSUS[name].action_severity` (the top-level entry) at the existing granularity — a command whose bare severity is `read` but which has a `write` subcommand (e.g. `/tier`) is not finer-gated here. Flagged, not fixed: no story before 4.4-4.10 asks for per-subcommand routing-time severity, and the existing `SUBCOMMAND_CENSUS` from 4.2 has no dispatch-time hook to attach to without `commands/base.py`'s `handle()` contract changing — out of this story's scope, logged to `deferred-work.md` if review agrees it's worth a flag rather than silence.
