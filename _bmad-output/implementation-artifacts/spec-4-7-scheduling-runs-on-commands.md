## Intent

**Problem:** Story 4.3 migrated only `cronjob`'s `pause`/`resume` (the pilot). Every other scheduling mutation — `cronjob`'s `create`/`update`/`remove`/`run`, `owl_schedule`'s `pause`/`resume`/`snooze`, and `objective`'s creation — still calls `JobScheduler`/`ObjectiveStore` directly, bypassing the gate, undo and audit trail. The census (`authz/state_change_census.py`) names exactly 8 pending command types owned by this story.

**Approach:** Extend `scheduler/commands.py` with 7 new `CommandSpec`s (create/edit/delete/run-now/snooze/pause-owl/resume-owl) whose handlers call `JobScheduler` methods extended with an optional `context: CommandContext | None` (mirrors 4.3's `pause`/`resume` exactly: `None` preserves today's behavior byte-for-byte). Add a new `objectives/commands.py` for `scheduling.set_objective`, whose handler does ONLY deterministic persistence — the LLM decomposition moves into `objective_tool.execute()`, upstream of `submit_command` (AD-26: no model call in a handler). Generalize `commands/spec/undo.py`'s "resubmit the original payload" to support a captured "restore-to" payload (new `command_receipts.undo_payload` column) for commands whose undo must restore prior state rather than repeat the forward payload (an edit, a snooze), and generalize supersession detection to match on `job_id` rather than full-payload equality for these.

## Boundaries & Constraints

**Always:**
- Every extended `JobScheduler` mutator (`create_job`, `update_job`, `stop_job`, `run_now`, `snooze`) keeps its exact pre-4.7 behavior when called with `context=None` — only a COMMAND-driven caller ever passes one (mirrors 4.3's own contract).
- Each mutator's `context`-given path: idempotency receipt (`record_command_execution`) + the mutation + a new `job.*` journal event commit in ONE transaction (AD-26), exactly mirroring `pause`/`resume`'s existing shape.
- `objectives/commands.py`'s handler does no LLM/model call (AD-26) — decomposition happens in `ObjectiveTool.execute()`, before `submit_command`; the handler receives already-decomposed `SubgoalSpec`s and persists them deterministically.
- `scheduling.pause_owl_job`/`resume_owl_job` are declared distinctly from the already-migrated `scheduling.pause_job`/`resume_job` (the census's own authored, deliberate split — both pairs call the identical `JobScheduler.pause`/`.resume`).
- The AD-1 "one door" mutator tripwire (`test_one_door_tripwires.py`) is extended to cover every newly-migrated method, and `cronjob.py`/`owl_schedule.py` are removed from every allowlist they no longer need.
- 4-point logging on every new/changed method that does I/O or a non-trivial decision.

**Never:**
- Do not touch `authz/action_policy.py::decide()` — its branches are unchanged; a genuinely irreversible scheduling command (delete/run-now/set-objective) needing step-up for EVERY requester kind, including the owner, is the existing gate's honest, unmodified behavior for `reversible=False` — a deliberate consequence documented in Design Notes, not a gap.
- Do not migrate `webhooks/receiver.py`'s direct `create_job` call — out of AC1's named scope (not `cronjob`/`owl_schedule`/`objective_tool`/a slash command); it keeps calling `create_job(context=None)`, allowlisted in the tripwire.
- Do not grandfather standing authority for any of these types (Story 4.8's own scope, per 4.6's Boundaries) and do not resolve a real `authority_grant_id` anywhere here — no live caller here is ever `requester_kind="autonomous"`.
- Do not touch `authz.state_change_census` beyond flipping this story's 8 entries to `migrated`.
- Do not consolidate `objective_tool.py`'s pre-existing `_gate_epic_consent` with the new command-door step-up — both apply to an EPIC creation (documented, accepted redundancy, not this story's scope to fix).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| `cronjob(action="create")` | owner, valid prompt+schedule | Submits `scheduling.create_job`; owner+reversible → `run_at_once`; job row created; undo target captured (`scheduling.delete_job`, the new job_id) | N/A |
| `cronjob(action="update")` | owner, job_id + new schedule | Submits `scheduling.edit_job`; prior `{schedule, goal}` captured as undo payload; new values applied | job not found → structured error |
| `cronjob(action="remove")` | owner, job_id | Submits `scheduling.delete_job` (irreversible) → `needs_step_up` for every requester kind (opens an approval item) | N/A |
| `cronjob(action="remove")` from an owl | owl | Same — approval item opened (AC4) | N/A |
| `cronjob(action="run")` | owner, job_id | Submits `scheduling.run_now_job` (irreversible) → `needs_step_up` | N/A |
| `owl_schedule(action="snooze")` | owner, parseable duration | Submits `scheduling.set_owl_schedule`; prior `next_run_at` captured as undo payload; owner+reversible → instant | N/A |
| `objective(intent=...)`, no repo | owner | Decomposition runs in the tool; submits `scheduling.set_objective` (irreversible) → `needs_step_up` | N/A |
| Undo an edit within 24h | `request_undo(edit's command_id)` | Resubmits `scheduling.edit_job` with the CAPTURED prior payload (not the forward one) — restores old schedule/goal | N/A |
| A later edit supersedes an earlier edit's undo | two `edit_job` commands, same `job_id` | `has_later_completed_command` matches on `job_id` (not full payload) — the earlier one's undo is refused as superseded | `superseded` refusal |
| Re-run `create_job` after a simulated lease reclaim | same `command_id` twice | Second call returns the SAME job (read back via the receipt's captured `job_id`) — no duplicate row | N/A |

## Design Notes

**Declaring `delete_job`/`run_now_job`/`set_objective` irreversible means the OWNER also gets step-up, not just an owl.** `decide()`'s existing branch (`elif not reversible:`) forces `needs_step_up` for every requester kind — there is no owner carve-out for an irreversible action anywhere in the frozen gate (only reversible actions run instantly for the owner). This is Epic 4's own stated invariant ("Step-up is required for: irreversible actions..." — no exemption listed), not a new branch this story adds. The practical UX consequence — deleting a job, running one out-of-band, or creating an objective all now prompt a Telegram/tap approval, where before they were instant — is the honest cost of these three genuinely having no undo, and is accepted rather than special-cased.

**`create_job`'s idempotency check precedes minting a new `job_id`.** Unlike `pause`/`resume`/`edit`/`delete`/`snooze` (which mutate an EXISTING row named by the payload's `job_id`), `create_job` invents a fresh random id on every call — a naive receipt-check-inside-the-transaction would still fabricate a second id before discovering the command already ran. Fixed by capturing `{"job_id": <new id>}` as the receipt's `undo_payload` on the FIRST successful run; a lease-reclaim re-run reads that back and returns the SAME job, never minting a second one. This is also exactly the payload `create_job`'s own undo (`scheduling.delete_job`) needs.

**`objectives/commands.py`'s handler checks for an existing receipt FIRST (a plain read, before git-branch or any persistence), and writes the receipt LAST (combined with the final `objective.set` journal transaction, only after every `ObjectiveStore` write has succeeded).** (Revised by the review pass — see Review Triage Log.) This is what makes "already executed" mean "actually fully done": a retry that finds no receipt starts over cleanly from scratch (git branch included, since nothing committed yet); a retry that finds one means everything already committed, and short-circuits without touching git or the store again. A genuine concurrent race between two callers for the same `command_id` fails loud via the `objectives` table's own `PRIMARY KEY (owner_id, objective_id)` constraint (migration 0066) rather than silently duplicating or lying about success.

**Moving `ObjectiveDecomposer`'s LLM call before `submit_command`** is what AD-26 ("no model call" in a handler) requires. A side effect: an invalid EPIC dependency graph is now refused before any objective row exists at all, instead of today's create-then-mark-`abandoned` — a strict improvement, not a behavior this story set out to change.
