## Intent

**Problem:** `owl_build`/`tool_build` (LLM tools) and `OwlsCommand`/`OwlCommand`'s DNA/objective sub-commands still call `persist_owl`/`registry.replace`/`delete_owl`/`JobScheduler.pause`/skill-store mutators directly, bypassing `submit_command`. `authz/state_change_census.py` names 22 pending "4.9" entries (`owls.build`, `owls.build_tool`, 8 `owl.*`, 12 `skill.*`). `commands/state_census.py`'s own `owl.edit` comment and `deferred-work.md`'s DW-36 explicitly hand this story the open call of whether `/owl edit --tools/--capability_profile` needs a separate authority-widening command type.

**Approach:** `/owl` already funnels create/edit/rename/pause/resume/retire through `OwlBuildTool.execute()` (its own docstring: "the ONE owl surface"), and `owl_build._edit` already re-clamps against `creation_ceiling` (can never widen) — so consolidating `owl.create/edit/rename/retire` onto new `owls.build.*` types (declared once, on `owl_build`'s manifest) resolves DW-36 at the root rather than adding a parallel widen-check. Pause/resume reuse Story 4.7's already-registered `scheduling.pause_owl_job`/`resume_owl_job` (no new type). New `owl_build_commands.py` registers `owls.build.{create,edit,rename,retire,restore,grant}` (`grant` — the ONLY authority-widening action — `severity="consequential"`, forcing unconditional step-up per `decide()`; the tool's existing `_consent_or_refuse`/`_WIDENING_CATEGORY` always-ask gate is untouched, mirroring `send_message`'s own kept double-gate). New `owls_dna_commands.py` migrates the 4 DNA/objective sub-commands (reachable only via `/owl`, since `/owls` is unregistered — `commands/manifest.py:74-77`). New `tool_build_commands.py` migrates `tool_build`'s create/delete. New `skill_commands.py` migrates `skill_manage`/`synthesize_skills`/`/skill`'s 12 shared types, reusing `record_skill_mutation`'s existing snapshot/restore machinery for undo instead of inventing a parallel mechanism.

## Boundaries & Constraints

**Always:**
- Every new/split command type gets a `state_change_census.py` entry (`status="migrated"`); consolidated types (`owl.create/edit/rename/retire` → `owls.build.create/edit/rename/retire`) have their OLD census key deleted (declaration retired in lockstep, per that module's own docstring) and `commands/state_census.py`'s `SUBCOMMAND_CENSUS["owl.create"/"owl.edit"/"owl.rename"/"owl.retire"]` repointed at the consolidated type.
- `owls.build.grant` is `severity="consequential"` — `decide()`'s unconditional first check (`CONSEQUENTIAL → needs_step_up`, `authz/action_policy.py:161`) is what satisfies AC2 ("on the step-up list, never approvable by voice"); no owl ever approves anything in this architecture (approvals are always owner-mediated), so "never approvable by the owl it widens" holds by construction — no new identity plumbing.
- `owls.build.rename`/`.edit` are reversible, undo=self, undo_payload captures the prior field(s) — mirrors `scheduler_mutations.py::update_job`'s self-undo shape exactly. `owls.build.create`'s undo is `owls.build.retire`; `owls.build.retire`'s undo is a new internal-only `owls.build.restore` (undo_payload = the full manifest snapshot via `snapshot_owl`), since retire's own payload (just `{name}`) cannot recreate a manifest.
- `skill.author_edit`/`.author_patch`/`.delete`'s undo reuses the EXISTING `skill.restore_version` type (`record_skill_mutation` already snapshots before/after content) — undo_payload = `{name, source, version: <pre-mutation hash>}` — never a new parallel snapshot mechanism.
- 4-point logging on every new/changed method that does I/O or a non-trivial decision; every handler follows the established read-check-first (`command_receipts`)/write-last shape only where the underlying mutator is non-transactional (file/registry writes) — DB-only mutators (persist_owl, SkillIndexStore rows) use the transactional `record_command_execution`-in-one-transaction shape (`scheduler_mutations.py` precedent) instead.
- AD-1 tripwire (`test_one_door_tripwires.py`) gains groups for `OwlRegistry.replace/.register/.deregister`, `owls_helpers.persist_owl/.delete_owl/.restore_owl`, `ToolRegistry.register/.unregister` (learned tools), `SkillIndexStore.delete/.set_enabled/.set_pinned`; `tools/meta/owl_build.py` is REMOVED from the pre-existing pause/resume group allowlist (`test_one_door_tripwires.py:200`) now that it's migrated.

**Never:**
- Do not migrate `OwlsCommand._edit`/`._remove` — verified DEAD CODE: `/owls` is unregistered (`commands/manifest.py:74-77`, "the class survives, unregistered"), and `/owl` (the only live registration) overrides create/edit/rename/pause/resume/retire/remove to route through `_build`→`owl_build` instead (`owls_command.py:1078-1109`). Noted, not silently skipped.
- Do not touch `authz/action_policy.py::decide()` or `authz/undo.py::decide_undo()` — reused verbatim, unmodified.
- Do not introduce owl-identity tracking on `CommandContext`/`RequesterKind` — AC2's "never approvable by the owl it widens" is already satisfied by severity=consequential + the architecture's owner-only approval routing (no owl approver exists anywhere today); inventing identity plumbing to re-derive the same guarantee is unscoped gold-plating.
- Do not give `owls.build.grant` an undo — its own action set has no "revoke" mutator (`_VALID_ACTIONS` has no such action), and inventing owl-authority revocation is a separate, larger design decision (logged to `deferred-work.md`, mirrors Story 4.8's own deferred standing-authority-listing finding).
- Do not touch `learned_tool_loader.py` — a boot-time re-registration of what `tool_build` already wrote to disk; it has no mutation of its own to migrate (AC1 names it only as part of the same subsystem, not because it changes state itself).
- Do not modify `record_skill_mutation`'s security-scan chokepoint or `skill_validation.py` — reused verbatim inside the new handlers.
- Do not remove or weaken `owl_build`'s/`tool_build`'s existing `_consent_or_refuse` tool-level gate — it stays, exactly as `send_message.py` kept its own tool-level `action_severity="consequential"` gate alongside the new command-level gate post-4.8 (same accepted double-gate shape).

## Design Notes

**Why `/owl create/edit/rename/retire` collapse onto `owls.build.*` instead of keeping the separately-declared `owl.create`/`owl.edit`/`owl.rename`/`owl.retire` types.** `/owl`'s own docstring says it is "the ONE owl surface... every mutation... funnels through the single owl_build engine" — `OwlCommand._build` (`owls_command.py:1078-1109`) calls `OwlBuildTool().execute()` for all of create/edit/rename/pause/resume/retire/remove. Declaring a second, parallel command type per action for the slash-command surface would mint two names for the identical real mutation — exactly what `state_change_census.py`'s own "ONE SHARED NAMESPACE" docstring says never to do (its own worked example: `skill.delete` names the same real action for both `/skill rm` and the `skill_manage` tool). `commands/state_census.py`'s `SUBCOMMAND_CENSUS` entries are repointed at the consolidated type rather than kept as separate declarations.

**Why `owl_build._edit`'s existing clamp resolves DW-36 without a new authority-widening classification.** DW-36 asked whether `owl.edit` needs splitting because `--tools`/`--capability_profile` can widen authority. The ONLY live edit path (`/owl edit` → `owl_build._edit`) already re-clamps every edit against `creation_ceiling` — its own docstring: "an edit can never widen authority past what was approved at mint time." Because this story collapses `/owls edit`'s separate, unclamped legacy mutator (dead code, never reachable) out of scope entirely, the ONLY edit code path left standing is the clamped one — so `owls.build.edit` never needs `consequential` severity; the single, dedicated `owls.build.grant` path remains the only way to widen, exactly as the tool's own UI text already promises ("the only way to widen an owl's authority").
