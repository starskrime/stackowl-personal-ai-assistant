## Intent

**Problem:** `send_message`/`send_file` and the scheduled-delivery seam (`/urgent`, `/brief`, check-in, goal-answer, digest flush) all call `ProactiveDeliverer.deliver()`/`.transport()` (directly, or via `ProactiveJobDeliverer.deliver_for_job()`) without ever going through `submit_command`. The census (`authz/state_change_census.py`) names exactly 4 pending entries this story owns: `messaging.send_message`, `messaging.send_file`, `notifications.broadcast_urgent`, `notifications.deliver_brief`. Nothing that leaves the platform in the owner's name is gated, undoable-by-design (it isn't — sends can't be undone), or grandfathered with standing authority for unattended sends.

**Approach:** New `notifications/commands.py` registers 7 irreversible `CommandSpec`s (the 4 census-named ones, plus `notifications.deliver_check_in`/`deliver_goal_result`/`deliver_digest` — new types for scheduled job-handler surfaces the census never tracked, since it only covers tool/slash-command declarations, not job handlers) whose handlers call `ProactiveDeliverer.deliver()`/`.transport()` or `ProactiveJobDeliverer.deliver_for_job()`, each extended with an optional `context: CommandContext | None = None` (mirrors 4.7: `None` preserves today's behavior byte-for-byte). Widen `standing_authority.grant()`'s `provenance` to include `"seeded"` (4.6 explicitly deferred this pending real evidence). Wire `submit_command` to resolve a job-scoped `authority_grant_id` via `standing_authority.find_active` before creating the task row (carried on the existing but unused `tasks.authority_grant_id` column), and have `execute_command_task` read it instead of hardcoding `None` — the first live caller of Story 4.6's dormant carve-out. Grandfather existing enabled jobs' standing authority via an idempotent startup routine; grant `provenance="seeded"` authority from the job seeder for morning_brief/check_in/notification_digest (all three are platform-seeded, `scheduler/assembly.py`).

## Boundaries & Constraints

**Always:**
- Every extended mutator (`ProactiveDeliverer.deliver`/`.transport`, `ProactiveJobDeliverer.deliver_for_job`) keeps its exact pre-4.8 behavior when called with `context=None`.
- Each command handler's context-given path: read-check-first (a plain receipt read, no side effect) — a found receipt means already-sent, skip re-sending — then the real send/transport, then `record_command_execution` LAST, only once a terminal outcome is known (mirrors 4.7's own post-review `objectives/commands.py` fix: never mark "already executed" before the irreversible network effect is known).
- `submit_command` gains an optional `authority_scope: tuple[Literal["job"], str] | None = None`; ONLY the 4 job-triggered types (`deliver_brief`, `deliver_check_in`, `deliver_goal_result`, `deliver_digest`) pass `("job", job.job_id)` — the 3 owl/owner-attended types (`send_message`, `send_file`, `broadcast_urgent`) never do (no job scope, and `decide()`'s grant carve-out only ever applies to `requester_kind="autonomous"`).
- `/brief` and the scheduled morning-brief job share one migrated call site (`MorningBriefHandler._deliver()` — both already route through `execute()`), so one command type covers both triggers.
- The AD-1 "one door" tripwire gains groups for the 3 delivery mutators; newly migrated callers are removed from their allowlists.
- 4-point logging on every new/changed method that does I/O or a non-trivial decision.

**Never:**
- Do not migrate `website_watch.py`/`threshold_watch.py`/`perch.py`/`capability_gap_escalation.py`/`telegram_canary.py`/`scheduler.py`'s own generic `deliver_for_job` call/`objectives/driver.py`'s call — out of AC1's named scope (not `send_message`/`send_file`/`/urgent`/`/brief`/check-in/goal/digest); they keep calling `deliver_for_job(context=None)`, allowlisted in the tripwire (mirrors 4.7's `webhooks/receiver.py` carve-out).
- Do not touch `authz/action_policy.py::decide()` — its branches, including the `authority_grant_id`+`autonomous` carve-out, are reused verbatim from 4.6, unmodified.
- Do not touch `authz.state_change_census` beyond flipping this story's 4 pending entries to `migrated`; the 3 new command types this story introduces are never added there — the census's own aperture is tool/slash-command declarations (4.2's scope), never job handlers.
- Do not invent a new journal event type — `delivery.attempted`/`provider.rerouted` (Story 2.9, written unconditionally inside `ProactiveDeliverer._record_delivery`) already record every send; this story's only new journal writes are `authority.granted` (Story 4.6's grant API, reused verbatim for grandfather/seed).
- Do not resolve `authority_grant_id` inside `execute_command_task` — it stays I/O-free (AD-7/4.6 Boundaries); resolution happens in `submit_command` before the task row is created, carried on `tasks.authority_grant_id` (already exists, migration 0153) the same way `gate_verdict` already is.
- Do not grandfather `telegram_canary` — a synthetic probe, not named in AC1's scope.

## Design Notes

**Why 3 new command types have no census entry.** `authz/state_change_census.py`'s own docstring scopes it to "a live surface (a tool or a slash command)" — its forward-direction tripwire checks `ToolManifest.command_types`/`CommandDeclaration.command_types`, neither of which any scheduler job handler ever populates (job handlers aren't tools or slash commands, so they were never in Story 4.2's declaration sweep). The census dict is authored, not derived (its own docstring: "NOT computed from the live tool/command trees"), so an entry's absence here means "never within 4.2's aperture," not "out of 4.8's scope" — `deliver_check_in`/`deliver_goal_result`/`deliver_digest` are new command types this story is free to introduce without touching the census, and its own closure tripwire (`test_state_change_census_has_no_stale_entries.py`) only checks the reverse direction (no orphaned entries), never that every `CommandSpec` has one.

**Why the receipt is written LAST, after the real send.** A message send is an external, non-transactional side effect (unlike 4.7's pure DB mutations) — there is no way to commit "receipt + send" atomically. Checking for an existing receipt FIRST (a cheap read, no side effect) before ever sending, and writing the receipt only once a terminal `DeliveryStatus` is known, means a crash mid-send either leaves no receipt (a safe retry re-sends) or a receipt only after the real outcome — this is the exact "read-check-first, write-last" shape 4.7's review pass converged `objectives/commands.py` onto for its own non-transactional git-branch step.
