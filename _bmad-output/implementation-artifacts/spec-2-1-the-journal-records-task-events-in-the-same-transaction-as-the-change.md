## Intent

**Problem:** The platform has no single, trustworthy record of what it actually did — durable task lifecycle transitions (enqueue/claim/finish/dead-letter) commit with no journal row, so nothing later can prove what happened without disagreeing.

**Approach:** Add `src/stackowl/journal/` — a versioned event-type registry, a `journal.record(conn, event)` API that inserts one append-only row in the caller's own SQLite transaction (transactional outbox), a leak guard that redacts secret-shaped strings before storage, and a journal health contributor. Wire the four durable-task lifecycle transitions to record through it in the same transaction as their state change.

## Boundaries & Constraints

**Always:** `journal.record` runs inside the caller's already-open `DbPool.transaction()` connection — never opens its own. `event_id` is UUIDv7 text from one helper in `journal/`. Every registered event type has exactly one typed `attrs` model (subclass of a frozen, `extra="forbid"` base — mirrors `ipc/frames.py`'s `_Frame`), one emitting process, one record kind, one attention class, declared once in the registry; `actor_kind`/`target_kind` come only from the closed list (`owner`, `device`, `voice_worker`, `autonomous`). `record()` raises loudly on an unregistered type or an `attrs` instance that fails its model's own validation — never silently drops or coerces. Every string value in `attrs` is scanned by the leak guard (reusing `infra/observability.py`'s redaction) before the row is built; a redaction is recorded on the event. A `record()` failure is logged with 4-point logging, degrades a registered `JournalHealthContributor` with a remedy, and always re-raises. `journal/` imports nothing from any subsystem.

**Never:** No attention-policy computation (ambient/needs_you classification) — Story 2.2. No narrator, no record readers, no gateway push, no retention/pruning — later stories. No free-text fields in any `attrs` model (ids, enums, bounded labels, counts only). Do not touch or extend `events/bus.py` (the in-process `EventBus` is a separate concern). Do not modify `sprint-status.yaml`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Committed change | `DurableTaskStore.claim()` wins the row (rowcount=1) inside `transaction()`, then `journal.record(conn, task.claimed)` | Both the task UPDATE and the journal row are visible after commit | n/a |
| Rolled-back change | Same, but the transaction block raises after `journal.record` | Neither the task UPDATE nor the journal row exists afterward | Exception propagates; test asserts zero journal rows |
| Unregistered type | `journal.record(conn, event)` with a `type` never registered | No row inserted | Raises loudly (`ValueError`/`KeyError`-class), logged, never swallowed |
| Invalid attrs | `attrs` instance doesn't match its type's registered model (wrong subclass, or fails its own field validation) | No row inserted | Raises loudly before any SQL executes |
| Secret-shaped string in attrs | An `attrs` field value matches a bearer-token/API-key/AWS-key shape | Row stores the redacted value; `attrs` JSON also carries a redaction marker | No error — redact and record, don't fail the write |
| `record()` raises mid-call (e.g. DB error) | Any exception inside `record()` | Error logged (4-point, `exc_info`), `JournalHealthContributor` reports `degraded` with a remedy string | Re-raised to the caller — never swallowed |
| Task dead-lettered via a dependent's cascade (`_deps_satisfied`) | A dependency task itself dead-letters, cascading | A `task.dead_lettered` row is recorded for the cascading task too | Same atomicity/redaction rules as the direct path |

**Acceptance Criteria:**
- Given no journal table exists, when the platform migrates, then `journal_events` exists with the envelope columns and the cursor as `INTEGER PRIMARY KEY AUTOINCREMENT`, and `src/stackowl/journal/__init__.py` carries a `PLACEMENT:` paragraph.
- Given the event registry, when an event type is declared, then it has exactly one `attrs` model, one emitting process, a record kind and an attention class, actor/target kinds from the closed list, and `record()` refuses an unregistered type or invalid `attrs` loudly.
- Given a subsystem changing state on its connection, when it calls `journal.record(conn, event)`, then the event is inserted in that same transaction (a forced rollback leaves no event; a commit always leaves one), and `event_id` is UUIDv7 text from `journal/ids.py`.
- Given any string value in an event, when it is recorded, then the leak guard redacts secret-shaped matches and marks that it redacted; canary secrets driven through the real task emitters never land in the journal.
- Given the durable task store, when a task is enqueued, claimed, finished, or dead-lettered (including the dependency-cascade path), then the matching event is recorded at the action site with the task as target, a closed-set `outcome`, and a `record_ref` to the task row.
- Given the journal recorder, when a record call fails, then the error is logged with 4-point logging, `JournalHealthContributor` reports `degraded` with a remedy, and the failure is never swallowed.

## Design Notes

`enqueue()` performs two writes today (`create()` then an `UPDATE`) with no shared transaction; wrap both plus `journal.record` in one `self._db.transaction()` block rather than adding a third write. `mark_delivered`/`mark_completed_unaddressed` both map to `task.finished` with `outcome="ok"` — the delivered-vs-unaddressed distinction lives in `TaskFinishedAttrs.completion_mode`, not in `outcome`, since the conventions' `outcome` enum has no such value. `CommandContext` (AD-3's actor/device/requester-kind carrier) doesn't exist yet — it's Epic 4 — so these six internal engine transitions use `actor_kind="autonomous"` with a stable actor id, which the closed list already anticipates for exactly this case; a later epic can thread a richer `CommandContext` through without changing the journal schema.
