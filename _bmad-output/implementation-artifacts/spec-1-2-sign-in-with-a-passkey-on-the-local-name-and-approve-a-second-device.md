## Intent

**Problem:** The kit (Story 1.1) proves HTTPS/mDNS trust on the install name, but nothing yet proves passkey enrolment, device-bound signed bearer tokens, and second-device approval by matching code actually work — AD-16, AD-17, AD-37, FR66-69 are unverified.

**Approach:** Extend the same throwaway kit with a setup-code ceremony (terminal, plus a *separate test* Telegram bot), py_webauthn passkey registration/authentication at the install-name origin, a non-extractable WebCrypto device key with signed bearer-token requests, and a name+matching-code second-device approval flow (signed tap or test-bot Telegram button). Done when the kit's automated Chromium check (a CDP virtual authenticator) proves setup-code refusal, passkey create/get, token-replay refusal and matching-code approval; real-device runs and live Telegram remain Story 1.6's job.

## Boundaries & Constraints

**Always:** setup code minted only at kit start (never by a network request), accepted only from home-network sources (reuse `is_source_allowed`); py_webauthn RP ID = install name, exact expected origin, `user_verification=Required`, backup-eligible/backup-state flags recorded; device key is a non-extractable WebCrypto ECDSA P-256 key, token stored in IndexedDB after `navigator.storage.persist()`; every authenticated request carries the bearer token plus a signature over method/path/timestamp/server-nonce/body-hash, a replay without the key refused with a uniform 401; only one device-approval request pending at a time; the kit's own test Telegram bot reads its token from the kit's own config/env (never the platform's), and refuses to start with a remedy if that token equals the platform's resolved `telegram_channel.bot_token` (read from `~/.stackowl/stackowl.yaml`, resolving `file:`/`env:`/`keychain:` references the same way the platform does, without importing the platform package).

**Never:** call the real Telegram Bot API from tests (stub/fake HTTP only — Telegram allows one poller per bot, and a real call could knock the live platform bot offline); import or touch `src/stackowl/authz/` or any platform identity code (it doesn't exist yet — Epic 5's job); change how Story 1.1's CA/cert/mDNS work behaves; require a real phone or a live Telegram bot for this story's own automated-check completion bar (that's Story 1.6's); commit `spikes/bridge/results/*`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| First start, no passkey | `kit.py start` | Setup code printed to terminal; also sent via the test bot when exactly one allowed test user is configured, terminal-only when none or several | n/a |
| Setup code used off-network | registration attempted from a disallowed source | 403 via the existing subnet guard | Logged remedy |
| Bot token collision | kit's test bot token equals the platform's resolved `telegram_channel.bot_token` | Kit refuses to start | Printed remedy, non-zero exit |
| Passkey registration | valid unconsumed setup code + `navigator.credentials.create()` | py_webauthn verifies; device key + bearer token issued | Invalid attestation/challenge rejected |
| Replayed token | copied bearer token, no valid signature | Uniform 401 | Logged, no state change |
| Second device request | new device posts a name | Same name + short matching code shown on both devices | A second concurrent request is refused while one is pending |
| Approval | signed tap on first device, or Telegram inline button | Second device enrolled, its own token issued | Mismatched/expired code rejected |

**Acceptance Criteria:**
- Given a first start with no enrolled passkey, when the kit issues a setup code, then it prints to the terminal, is also sent to the single allowed test Telegram user only when exactly one is configured (terminal-only for none or several), and is accepted only from the home network with no network route able to mint one.
- Given the kit's test Telegram bot, when it starts with a token equal to the platform's configured `telegram_channel.bot_token`, then it refuses to start and prints a remedy instead of polling.
- Given a valid setup code, when the owner creates a passkey, then py_webauthn verifies it with RP ID = install name, the exact expected origin, `user_verification=Required`, and the backup-eligible/backup-state flags are recorded.
- Given successful sign-in, when the browser creates its device key, then it is a non-extractable WebCrypto ECDSA P-256 key, the token is stored in IndexedDB after `navigator.storage.persist()`, every request carries the token plus a method/path/timestamp/nonce/body-hash signature, and a copied token replayed without the key is refused with a uniform 401.
- Given a signed-in first device and a new second device, when the second device requests access, then both devices show the same device name and matching code, a signed tap or a Telegram approval enrols the second device, and only one device request can be pending at a time.
- Given the Chromium virtual authenticator, when the automated check runs, then it proves setup-code refusal, passkey create/get, copied-token refusal, and matching-code approval.
