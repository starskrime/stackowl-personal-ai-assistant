## Intent

**Problem:** Story 3.1 shipped only a MINIMAL internal resolver (`journal/needs_you.py`'s `open_item`/`_resolve_open_item`) used exclusively by `record()`'s own registry-driven open/close wiring. There is still no public API an owner-facing surface (Telegram, the Bridge strip, voice, a notification deep link) can call to actually answer an item — so two surfaces answering the same item at once could each believe they won, and a stale or expired item could be answered again.

**Approach:** Add the public `needs_you.resolve()` in `journal/needs_you.py`: one atomic conditional `UPDATE ... WHERE id = ? AND resolved_cursor IS NULL` (the same one-statement race-safety shape `open_item`/`_resolve_open_item` already use) that either wins and records `needs_you.resolved` in the same transaction, or loses and returns the already-winning outcome (resolved, expired, or a version/digest refusal). Add one seeded, idempotent scheduled job that expires stale items, and make `open_items()` opportunistically sweep expired items too. No real caller wires this in yet (3.3/3.4/3.6 do) — same "ships correct, zero real callers" shape Story 3.1 used for `resolves` and `NeedsYouKind.DEVICE`.

## Boundaries & Constraints

**Always:**
- The winning determination is ALWAYS one atomic conditional `UPDATE ... WHERE id = ? AND resolved_cursor IS NULL AND version = ?` — never an application-level check-then-write. A prior `SELECT` may inform an early, cheap refusal (e.g. a digest mismatch), but the actual state change is decided only by the conditional `UPDATE`'s own affected-row count.
- A real resolution (`resolve()` winning, or the expiry path winning) writes `needs_you.resolved` (already registered by Story 3.1) via `journal.record()`, in the SAME transaction as the `needs_you` row's `UPDATE`, using `record()`'s existing `outcome` field (`Outcome.OK` for a real answer, `Outcome.EXPIRED` for an expiry) to distinguish the two — no new event type, no schema change to `NeedsYouResolvedAttrs`.
- No new column on `needs_you` (AD-28's column list is closed). "Digest" is a value COMPUTED on demand from the row's existing `kind`/`record_ref`/`version` (`compute_item_digest`, sha256-hex-16 like `journal/digest.py`'s own registry digest) — never stored.
- `answer` is redacted via `redact_secret_shapes()` before it is written to the `needs_you` row — it bypasses `record()`'s own `attrs` scanning entirely (AD-4: "never free text or a rendered message string" for `attrs`; `answer` deliberately lives only on the row, per AD-28's "the answer on this row is authoritative"), so this module must scan it itself.
- Exactly one expiry-sweep scheduled job exists, seeded idempotently via `_seed_minutes_schedule` (the same idempotent-by-`handler_name` mechanism `journal_prune`/`objective_driver`/etc. already use) — never a second seed call, never an unconditional insert.
- Every new/changed function gets 4-point (ENTRY/DECISION/STEP/EXIT) structured logging, matching `needs_you.py`'s existing style.
- `resolve()` never raises for a legitimate protocol outcome (already-resolved, expired, refused) — those are `NeedsYouResolution.outcome` values, not exceptions. It raises only `NeedsYouItemNotFoundError` for an `item_id` that does not exist at all (a caller bug).

**Never:**
- Do not add IPC/frame-sending inside `resolve()` itself — no `ConsentResponseFrame`-equivalent exists yet for `needs_you` (that is Story 3.5's `reply_target` work). `resolve()` returns the winning `NeedsYouResolution` (including `waiter_kind`/`waiter_id`); delivering it by frame is the future caller's job.
- Do not enqueue an answer as a task of any kind — confirmed no "COMMAND task" concept exists anywhere in this codebase yet (grepped: none). `resolve()`/the expiry sweep import nothing from `pipeline/durable/`'s task-enqueue path; prove this structurally with a test.
- Do not wire any real caller (Telegram, consent tools, `SocketConsentPrompter`) to call `resolve()` — confirmed zero production call sites set `waiter_kind`/`waiter_id` today; that is Story 3.3+.
- Do not change `record()`'s public signature or return type to expose the numeric `journal_events.cursor` — look it up via `SELECT cursor FROM journal_events WHERE event_id = ?` (indexed, `UNIQUE`) on the same `conn` instead.
- Do not bound `answer`'s length — AD-28 names no such limit, and the column is unbounded `TEXT`; inventing one is unrequested scope.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Clean win | Open item, matching `expected_version`, not expired | Row `UPDATE`s, `needs_you.resolved` recorded (`Outcome.OK`), `NeedsYouResolution(outcome="resolved", answer=...)` returned | No error expected |
| Two concurrent answers | Two `resolve()` calls for the same open item, both matching version, via real `asyncio.gather` | Exactly one call's `UPDATE` affects 1 row; the other affects 0, re-reads, and returns the FIRST call's winning `answer`/`outcome="resolved"` unchanged | No error expected |
| Already resolved | Item already has `resolved_cursor` set, `answer` non-null | `resolve()` writes nothing; returns `outcome="resolved"` with the existing `answer` | No error expected |
| Already expired | Item already has `resolved_cursor` set, `answer` NULL (expiry's own signature) | `resolve()` writes nothing; returns `outcome="expired"` | No error expected |
| Version mismatch | Open item, `expected_version` != current `version` | No write; `outcome="refused"`, `NeedsYouResolution.version` carries the CURRENT version | No error expected |
| Digest mismatch | Open item, `expected_digest` != `compute_item_digest(kind, record_ref, version)` | No write; `outcome="refused"` | No error expected |
| Answer arrives after `expires_at` | Open item, `expires_at` in the past, not yet resolved | Resolver resolves it as `outcome="expired"` through the SAME conditional-`UPDATE` path (ignores the submitted answer/version/digest entirely) | No error expected |
| Expiry sweep tick | One or more open items with `expires_at` in the past | Each resolves as `expired`, one `needs_you.resolved` (`Outcome.EXPIRED`) per item, in its own transaction; job never raises | Never raises out of `execute()` — logs and returns a failed `JobResult`, mirroring `journal_prune`'s own contract |
| `open_items()` called with stale items present | Unresolved rows whose `expires_at` has passed | Sweep runs first (best-effort — failure is logged, never propagated), THEN the open-set `SELECT` excludes the now-expired rows | Sweep failure never breaks the read |
| Unknown `item_id` | `resolve()` called with an id no row has | Raises `NeedsYouItemNotFoundError` | Loud, typed — a caller bug, not a protocol outcome |

**Acceptance Criteria:**
- Given an open item, when `needs_you.resolve` is called, then it runs `UPDATE … WHERE id = ? AND resolved_cursor IS NULL` in the same transaction as the `needs_you.resolved` event, and the `answer` on the row is the authoritative value returned.
- Given two answers to the same item arriving concurrently (real `asyncio.gather`), when both call the resolver, then exactly one wins and the other receives the winning outcome unchanged.
- Given a resolved or expired item, when another answer arrives, then the resolver returns the winning outcome and changes nothing.
- Given an answer carrying an item version or digest different from the current item, when it reaches the resolver, then it is refused and the item is re-shown with its current version.
- Given an item whose `expires_at` has passed, when the seeded expiry sweep runs, or any surface reads or answers the item, then the item resolves as `expired` through the same resolver, and exactly one expiry sweep job exists, seeded idempotently, so no expired item stays open in the strip.
- Given a winning resolution, when it commits, then the returned `NeedsYouResolution` is the only thing that could be delivered to the item's waiter, and no test or production code path enqueues an answer as any kind of task.

## Design Notes

**Why `resolved_cursor` needs a two-step write (claim, then fix up), not `_resolve_open_item`'s single-`UPDATE` shape.** `_resolve_open_item` (Story 3.1) gets its `resolved_cursor` value for free — recorder.py already knows the OUTER triggering event's own `journal_cursor` before it ever calls into `needs_you`. The public `resolve()` has no such outer event: the act of answering IS the event, and `journal.record()`'s public API returns only `event_id` (a string), not the numeric `cursor`. So `resolve()`: (1) wins the race with one conditional `UPDATE ... SET resolved_cursor = 0 [claim sentinel — 0 is never a real `AUTOINCREMENT` cursor], answer = ?, resolved_by = ? WHERE id = ? AND resolved_cursor IS NULL AND version = ? RETURNING *`; (2) only the winner calls `journal.record()` for `needs_you.resolved`, looks up its real cursor via `SELECT cursor FROM journal_events WHERE event_id = ?`, and fixes up `resolved_cursor` to the real value with one more `UPDATE ... WHERE id = ?` (unconditional — safe, since only the winner reaches it, already inside the same still-open transaction, invisible to any other reader until commit).

**Why `answer IS NULL` is what disambiguates "expired" from "resolved with a real answer."** Both outcomes set `resolved_cursor`; neither AD-28 nor this story adds a status column. Expiry never sets `answer` (nothing was ever submitted); a real resolution always does (even an empty-string answer is still non-NULL). This lets `resolve()`'s and `_expire_item()`'s "already resolved — return the winning outcome" branch tell the two apart from one `SELECT`, with no new column.

**Digest is computed, never stored.** AD-28's rule text ("a resolution carries the item version and command digest that were shown") describes the Telegram approval flow's OWN vocabulary (NFR49/AD-27, Story 3.6), but AD-28's own closed column list has no `digest` column. `compute_item_digest(kind, record_ref_json, version)` derives a digest deterministically from data the row already stores — a version bump automatically changes the digest too — so a future caller (Telegram's opaque button token) can embed a digest without this story inventing a new persisted field.
