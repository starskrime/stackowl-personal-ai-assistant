## Intent

**Problem:** Outbound message deliveries, delivery-channel fallback (reroute) decisions, and gateway-side channel ingress leave no durable journal record — `journal/enums.py::RecordKind` has no `DELIVERY`/`PROVIDER`/`CHANNEL` member, even though AD-2's own comment names "deliveries, providers, ... channels" as part of the eventual full set.

**Approach:** Register `delivery.attempted`, `provider.rerouted` (both emitted from `notifications.deliverer`, core-side) and `channel.message_received` (emitted from `startup.orchestrator`'s gateway-role receive loops, using the GATEWAY's own local `DbPool` — AD-9) at the real chokepoints these three concerns already funnel through: `ProactiveDeliverer.deliver`/`transport` (every proactive job, scheduled digest, turn-answer stream-miss fallback, and health canary already calls one of these two), `ProactiveDeliverer._maybe_reroute` (the one `RecoveryActuator`-driven fallback-channel cascade), and the 5 near-identical per-channel receive loops inside `StartupOrchestrator._phase_gateway` (`_message_loop`/`_telegram_loop`/`_slack_loop`/`_discord_loop`/`_whatsapp_loop`) — each already calls `msg = await adapter.receive()` and shares one `db_pool` local in lexical scope. Two new small modules (`journal/delivery_events.py`, `journal/channel_events.py`) each open their OWN `DbPool.transaction()` (mirrors `journal/turn_events.py`'s Story 2.7 shape: none of these five call sites has an existing state mutation to piggyback a journal write onto) and insert a `delivery_records`/`channel_ingress_records` row + call `journal.record()` in the same commit.

## Boundaries & Constraints

**Always:** `delivery.attempted` fires from BOTH `deliver()` exit paths (the router-decided early return for `batched`/`suppressed`, and the post-`_maybe_reroute` final return) and from `transport()` (the digest-flush path) — three call sites, one shared private helper on `ProactiveDeliverer`. `delivery_status` (the full closed `DeliveryStatus` Literal, COPIED not imported into `journal/delivery_events.py` — `journal/` imports nothing from `notifications`, same rule `turn_events.py::_ActionSeverity` already documents) lives in `attrs`; the envelope `outcome` collapses it: `delivered`→`OK`, `failed`→`FAILED`, `batched`→`PENDING`, `suppressed`→`PARKED` (documented mapping, Design Notes). `delivery.attempted.channel` is always the ORIGINALLY-addressed channel (never reassigned after a reroute) — the fallback channel a reroute actually used is `provider.rerouted.to_channel` instead; a reader correlates the two via `notification_id`/`job_id`. `provider.rerouted` fires ONLY when `_maybe_reroute`'s `RecoveryActuator.recover(...)` returns `outcome.recovered=True` (a genuine channel switch happened — "state change", not a failed reroute attempt) — `outcome=Outcome.OK` always. `channel.message_received` fires once per `IngressMessage` actually produced by `adapter.receive()` (never for a `receive()` that raised — that path already retries without producing a message) — `outcome=Outcome.OK` always, `actor_kind=ActorKind.OWNER` (the owner sent it), using `msg.channel`/`msg.session_key`/`msg.trace_id`. None of the three new helpers participate in `journal/turn_budget.py`'s per-`trace_id` write budget (AD-38's mechanism is scoped to the turn's own high-volume model/tool/delegation actions per Story 2.7; delivery/channel volume is bounded by real message traffic, one row per real event — see Design Notes). Every raw `INSERT INTO delivery_records`/`channel_ingress_records` value passes through `redact_secret_shapes` first, same as `turn_action_records` (2.7's own review-round fix, applied here from the start). Both new helpers NEVER let a journal failure propagate into the real delivery/ingress action: `try/except Exception`, log ERROR with `exc_info`, degrade journal health via the existing `journal.health.note_failure`, return — mirrors `turn_events.py::_record_turn_event`'s B5 contract exactly, including building `attrs` INSIDE the guarded region. `ProactiveDeliverer` gains an optional `db_pool: DbPool | None = None` constructor param (mirrors `outbox`/`conversation_store`'s existing optional-duck-typed shape) wired from `notifications/assembly.py` (`db` is already in scope at the one construction site). `RecordKind.DELIVERY`, `RecordKind.PROVIDER`, `RecordKind.CHANNEL` are new additive members (AD-2's own comment already names all three).

**Never:** Do not record a `delivery.attempted` for a `_transport`/`_transport_file` retry-fallback sub-call `_maybe_reroute` makes internally — that sub-attempt IS what `provider.rerouted` (on success) or nothing (on a still-failed reroute, since no state changed) already covers; recording it again from inside `_transport` itself would double-count against the one `deliver()`-level `delivery.attempted` row. Do not touch `NotificationRouter._apply_decision`/`router_helpers.write_log_row` or `DeliveryLedger.claim_dispatch`/`mark` — both are pre-existing owning stores for the router's OWN `notification_log`/`delivery_attempts` tables (already `_hot`-declared) and wrapping them in `db.transaction()` for the first time is a larger, riskier touch than this story's narrow "add missing journal coverage" scope; not required by any AC. Do not instrument all 5 gateway receive loops as one shared code edit that changes their control flow — each gets the identical one-line helper call inserted right after `msg = await adapter.receive()` succeeds, nothing else in any loop changes. Do not build a `journal/retention.py` prune rule or coverage/upcaster tripwire (2.10/2.11 own those). Do not carry `notification.message`, tool/adapter exception text, or a Telegram/Slack/etc. display name into any `attrs` field — metadata only (AD-4). Do not restart the live production core/gateway process.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| `deliver()` transports and succeeds | router returns `delivered`, transport succeeds | `delivery.attempted` recorded, `outcome=ok`, `attrs.delivery_status="delivered"` | n/a |
| `deliver()` transport fails, no reroute configured | transport fails, `fallback_channel` empty | `delivery.attempted` recorded, `outcome=failed` | n/a |
| `deliver()` transport fails, reroute recovers | `_maybe_reroute` returns `delivered` | ONE `delivery.attempted` (`outcome=ok`, `channel`=original) AND ONE `provider.rerouted` (`outcome=ok`, `from_channel`/`to_channel`) | n/a |
| Router decides `batched`/`suppressed` (no transport) | early return before `_transport` | `delivery.attempted` recorded, `outcome=pending`/`parked` respectively | n/a |
| Digest flush calls `transport()` directly | `_transport(channel, message, chat_id=None)` | `delivery.attempted` recorded (`category=None`, `job_id=None`), `outcome` from result | n/a |
| Reroute attempted but still fails | `outcome.recovered=False` | No `provider.rerouted` row; the outer `delivery.attempted` still records `outcome=failed` | n/a |
| Gateway receives a real inbound message | any of the 5 loops' `adapter.receive()` returns | `channel.message_received` recorded via the GATEWAY's own `db_pool`, `outcome=ok` | n/a |
| `adapter.receive()` raises | loop's own `except Exception` retry branch | No `channel.message_received` recorded | n/a |
| No `db_pool` wired (e.g. a test construction) | `ProactiveDeliverer(db_pool=None)` | Silent no-op, same as `turn_events.py`'s `db_pool is None` skip | n/a |
| Canary secret string in `notification.message`/`category` | driven through a real helper call | Canary never appears in `delivery_records`/`channel_ingress_records`/`journal_events.attrs` (NFR33) | n/a |
| The recording transaction itself fails | `journal.record()` raises inside the helper's `db_pool.transaction()` | Caught, logged ERROR, journal health degrades; the real delivery/ingress outcome is UNAFFECTED | n/a |

## Tasks & Acceptance

**Execution:** `journal/enums.py` (3 new RecordKind members) → migration `0148` → `health/store_cadence.py` → `journal/delivery_events.py` → `journal/channel_events.py` → `journal/__init__.py` → `notifications/deliverer.py` (db_pool field + `_record_delivery` + 3 call sites + `_maybe_reroute`) → `notifications/assembly.py` (wiring) → `startup/orchestrator.py` (5 call sites) → all tests.

**Acceptance Criteria:**
- Given a delivery attempt (`deliver()` or `transport()`), when it resolves, then `delivery.attempted` is recorded with a closed `delivery_status`/outcome code, in its own atomic transaction with its `delivery_records` row.
- Given a failed transport recovers via the fallback-channel reroute, when the reroute succeeds, then `provider.rerouted` is recorded with `from_channel`/`to_channel` and `outcome=ok`; a reroute that does NOT recover records nothing extra.
- Given channel ingress in the gateway process (any of the 5 receive loops), when a message arrives, then `channel.message_received` is recorded through the gateway's own `db_pool` into the shared `journal_events` table (AD-9 fan-out merges it by cursor with core-emitted events without further code changes — the merge itself is 2.5's existing mechanism).
- Given canary secret strings driven through each of the three real recording helpers, when the row is inserted, then no canary appears unredacted in `delivery_records`/`channel_ingress_records`/`journal_events.attrs` (NFR33).
- Given the tripwires run, when they check the registry, then `delivery.attempted`, `provider.rerouted`, and `channel.message_received` each resolve to an `attrs` model, a `record_kind`, an `attention_class`, and a narration.
