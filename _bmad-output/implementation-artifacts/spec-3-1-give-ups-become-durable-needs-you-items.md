## Intent

**Problem:** Three give-up events (`heal.exhausted`, `task.dead_lettered`, `job.parked`) are already classified `needs_you`/`high` by the attention policy, but classification alone opens no durable, queryable record — it is lost the moment the journal row scrolls past. Two more give-ups have no journal presence at all: a cost-tracker budget warning is a fire-once in-memory `EventBus` notification, and a repeated gateway↔core Hello mismatch is a single critical log line the gateway emits right before it permanently stops watching core. None of this survives a restart or can be queried later.

**Approach:** Add one `needs_you` table owned by `journal/`, and generic wiring inside `journal.record()` itself: any event whose registered `attention_class` is `NEEDS_YOU` opens (or, via a partial unique index, no-ops on) a durable item in the same transaction and records `needs_you.opened`; any event whose registered `resolves` names an already-open item's opening type closes it through one minimal internal resolver and records `needs_you.resolved`. Wire `needs_you_kind=incident` onto the three existing types, add two new `NEEDS_YOU` event types at their real give-up call sites (a cost-tracker budget warning → `alert`; a gateway-side repeated-Hello-mismatch stand-down → `incident`), and register a retention hold so the prune job never deletes an event an unresolved item still references.

## Boundaries & Constraints

**Always:**
- `attention_class`/`intensity`/`needs_you_kind` are computed only by the registry at registration time, never by an emitter (AD-5) — same invariant `recorder.py` already enforces for the first two.
- Every item open/close happens in the SAME transaction as the journal event that triggers it (AD-24) — no second, out-of-band write.
- The partial unique index on `dedupe_key` (over unresolved rows) is the ONLY thing enforcing "one open item per target" — no application-level check-then-insert race; prove this with a real concurrent-writer test (mirror `tests/scheduler/test_poller_cas_claim.py`'s `asyncio.gather` idiom against a real migrated DB).
- Every new/changed function gets 4-point (ENTRY/DECISION/STEP/EXIT) structured logging, matching `recorder.py`'s existing style.
- New `attrs` models are metadata-only (AD-4): ids, numbers, closed enums, bounded (≤64 char) labels — never free text or a rendered message string.
- `needs_you.opened`/`needs_you.resolved` are themselves `AMBIENT` (opening/closing a needs-you item must never itself open one — no recursion).
- `journal.record()` gains one new keyword-only parameter: `bypass_write_gate: bool = False`. When `True`, skip the `writes_paused()` refusal (`recorder.py`'s existing "Spec 2.3" check) for that one call only — every other check (registry lookup, attrs validation, attention/intensity computation, leak-guard redaction) still runs unchanged. Documented, in the parameter's own docstring, as narrowly scoped: only for a write the GATEWAY makes about its OWN local give-up decision, never for anything whose correctness depends on core's schema/registry matching the gateway's. The write-gate (`write_gate.py`'s own docstring) exists because "the gateway cannot prove its schema/registry match the core actually writing journal rows right now" — that rationale does not apply to `link.hello_mismatch_standdown`: it is a gateway-self-originated event, built from the gateway's own already-loaded registry, describing the gateway's own decision, with no core involvement in producing it. Used by exactly one call site: `_supervise_core`'s stand-down write. Do NOT call `write_gate.resume_writes()` anywhere in this flow — that would reopen the write-gate for every OTHER concurrent writer in the gateway process for the duration of the `await db_pool.transaction()` call, reintroducing the exact schema-safety hole Spec 2.3 built the gate to close. The scoped parameter is the only sanctioned mechanism.

**Never:**
- Do not build the full public `needs_you.resolve` API (version/digest refusal, concurrency-proof owner-answer path, waiter delivery, expiry sweep) — that is Story 3.2's own AC list in full. This story's resolver is a minimal internal primitive (`journal/needs_you.py`) used only by `record()`'s registry-declared `resolves` wiring; Story 3.2 extends/promotes it.
- Do not invent a real "job resumed"/"task requeued" emitter to exercise `resolves` — no such call site exists today (`job.parked`/`task.dead_lettered` are terminal; `scheduler.resume()` is a different, paused-job lifecycle that writes the legacy `audit_log`, not the journal). Prove the mechanism with registry-level test-only types, mirroring `RetentionHoldRegistry`'s own "ships correct, zero real callers" precedent (Story 2.11).
- Do not touch `journal_prune.py`, `BatchAuditor`/`audit_log` (DW-25), or `scheduler.resume()`'s existing legacy audit-log write.
- Do not register a `RecordReaderRegistry` reader for the new `RecordKind.NEEDS_YOU` — no AC needs one yet.
- Do not remove or change `CostTracker`'s existing in-memory `_warned_dates`/`_exceeded_dates` dedup or the `BUDGET_EXCEEDED_EVENT`/`EventDeliveryBridge` path — additive only, alongside it.
- Do not open an item for `heal.attempted`, `heal.healed`, `job.started/finished/failed`, or any other `AMBIENT` type.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| First give-up for a target | `heal.exhausted` recorded for subsystem X, no open incident for X | `needs_you` row opens (`kind=incident`, `intensity=high`); `needs_you.opened` recorded; same transaction | No error expected |
| Duplicate give-up while open | Second `heal.exhausted` for the same X while its incident is still open | No new row (partial unique index no-op); no second `needs_you.opened` | No error expected |
| Never-classify event | `heal.attempted` / `heal.healed` recorded | No `needs_you` row opens | No error expected |
| Budget crosses 80% | `CostTracker._check_budget` sees `ratio >= 0.8` for a date for the first time | `alert` item opens for that date | No error expected |
| Repeated Hello mismatch | `gateway_link.consecutive_hello_mismatches` reaches `_MAX_CONSECUTIVE_HELLO_MISMATCHES` inside `_supervise_core` | `incident` item opens before the gateway stands down respawns | No error expected |
| Resolving type declared | Test-only opening type X (`needs_you_kind=incident`) and resolving type Y (`resolves=("X",)`) both registered; X recorded, then Y recorded for the same target | X's item closes through the internal resolver; `needs_you.resolved` recorded, `resolved_by="system:Y"` | No error expected |
| Forced rollback | Caller's transaction rolls back after `record()` raises mid-insert | Neither the `journal_events` row nor any `needs_you` row commits | Exception propagates; caller's `transaction()` rolls back (existing behavior, unchanged) |
| Prune vs. open item | `journal_prune` runs while an incident's opening event is still unresolved | That event's `cursor` is excluded from the delete batch | No error expected |
| Open-set query | Multiple unresolved items at mixed intensities | Returned ordered by `intensity` (`high` before `normal`) then `opened_cursor` ascending | No error expected |

**Acceptance Criteria:**
- Given no `needs_you` table exists, when the platform migrates, then an idempotent migration creates it (owned by `journal/`) with `id`, `kind`, `intensity`, `record_ref`, `dedupe_key`, `waiter_kind`, `waiter_id`, `expires_at`, `version`, `opened_cursor`, `resolved_cursor`, `answer`, `resolved_by`, and a partial unique index on `dedupe_key` over unresolved rows keeps one open item per target.
- Given an event the attention policy classifies `needs_you`, when it is recorded, then an item opens in the same transaction with its intensity set only by the registry, a `needs_you.opened` event is recorded, and a second `needs_you` event for the same kind and target while the item stays open opens no duplicate.
- Given `heal.exhausted`, `task.dead_lettered`, or `job.parked`, when recorded, then an `incident` item opens at `high`, while `heal.attempted` and `heal.healed` never open an item.
- Given the cost tracker's budget warning, or the repeated Hello mismatch from Story 2.3, when it happens, then an `alert` item, or an `incident` item, opens respectively.
- Given the registry declares `resolves` for an opening type, when a resolving event is recorded, then the recorder closes the matching open item through the internal resolver and records `needs_you.resolved`.
- Given unresolved items, when the open set is requested, then `journal/` returns every unresolved item ordered by intensity then `opened_cursor`, and the Story 2.11 prune job never deletes an event referenced by an unresolved item because each open item is registered as a retention hold.

## Design Notes

**Why the open/close mechanism lives inside `record()` itself, not at each call site.** AC2 and AC5 both describe "when it is recorded" as the trigger, and AD-3 says the registry declares resolving types "for the recorder" to act on -- both already name `record()` as the actor. Doing this per-call-site (like Story 2.6's own transaction-wrapping did for the journal row itself) would mean five, then N, independent re-implementations of "compute a dedupe key and try an insert" -- exactly the "two copies of one rule" this codebase's own docstrings repeatedly reject. One generic hook, driven entirely by registry metadata, means a later story adding its sixth `NEEDS_YOU` type needs zero new plumbing -- only a registration.

**Why `resolves` ships with zero real callers.** The investigation for this story found no existing "give-up, then un-given-up" event pair anywhere in the codebase: `job.parked` deletes the job row (terminal), `task.dead_lettered` has no requeue emitter, and `scheduler.resume()` -- the only "undo a give-up" verb that exists -- operates on a *different*, paused-job lifecycle and writes the legacy `audit_log`, not the journal. Inventing a fake resolution path to exercise this AC would be scope creep past what any acceptance criterion asks for. `RetentionHoldRegistry` (Story 2.11) already established the precedent this codebase uses for exactly this situation: ship the mechanism provably correct, prove it with registry-level tests, and let the first real story that needs it (a future epic) be the one that registers a real `resolves` pair.

**Why the gateway can write `link.hello_mismatch_standdown` directly.** The gateway and core are two processes, but they share one SQLite file -- `_phase_gateway` documents this explicitly at orchestrator.py:1918-1922 ("Both processes share the same SQLite DB file, so DbPool-backed storage ... is what actually lets both processes observe the same ... state") and already constructs its own `db_pool` at orchestrator.py:1090. Threading that existing pool into `_supervise_core` is strictly additive -- no new IPC frame, no relay through a core that has, by definition, already exited by the time the stand-down decision fires.

**`budget.warning`/`link.hello_mismatch_standdown` both use `table=None`.** Neither event describes a single owning row -- a budget warning is a signal over an aggregate (the day's total), and the stand-down is a signal over a counter with no row of its own. `EventTypeSpec.table`'s own docstring names this exact case ("`None` for a type whose `record_ref` carries no sqlite table at all") -- previously only exercised by `memory.written`'s `md`-backed case, extended here to a second, distinct reason (no owning row, not a different storage backend).

**Unresolved items accumulate as retention holds until Story 3.2 ships -- accepted, bounded, interim.** `budget.warning` opens at most one `alert` per calendar date (its `dedupe_key` is date-scoped); the three incident-opening give-ups dedupe per target. Nothing in this story or in the codebase today closes any of them -- Story 3.2 is the first to ship an expiry sweep and a real `resolves` pair. Between this story landing and 3.2 landing, every opened item's triggering `journal_events` row is held from `journal_prune` (via the `"needs_you"` retention-hold source) and the `needs_you` row itself is never deleted (rows in that table are never pruned at all, by design -- only the `journal_events` cursors they reference are held). This is the same "ships correct, its consequence is temporarily inert" shape `RetentionHoldRegistry` itself took for the whole of Story 2.11 (zero real hold sources registered until THIS story). The accumulation rate is small and bounded (at most ~1 new `alert` row per day, plus whatever incidents/hello-mismatches genuinely occur) and self-resolving once Story 3.2 ships next in this epic's own sequence -- not a reason to build a bespoke early resolver here, which Boundaries already forbids.
