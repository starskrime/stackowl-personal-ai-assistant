## Intent

**Problem:** Stories 1.1-1.3 proved TLS/mDNS trust, passkey sign-in/device approval, and push/mic, but nothing yet proves the Bridge's live stream carrier -- AD-9, AD-11, AD-12, AD-14's WebTransport-cert clause, AD-31, AD-38, NFR11, NFR13, NFR14, NFR46 are unverified: whether an aioquic WebTransport listener actually interops with a real browser and falls back cleanly to SSE, whether cursor-resume survives a real gap with no loss or duplicates, whether leader-tab hand-off and slow-client backpressure hold.

**Approach:** Extend the kit with an aioquic WebTransport listener sharing the existing HTTPS port's number over UDP (AD-13), short-lived self-signed hashed certs, a `fetch`-streamed SSE+POST fallback built on the existing `signedFetch`, a small synthetic-but-realistic cursor-numbered event fixture (no real recorded-event journal exists yet to pull from) replayed at recorded rates including a burst, client-side Web Locks+BroadcastChannel leader election, and a bounded per-client queue with resync-on-overflow. Proven by an automated Chromium check measuring connect/resume-replay time and kit server memory as P50/P95, writing `results/B2-carrier-desktop-chrome-automated.json`. Real-device interop (Safari, cellular, Jetson memory) remains Story 1.6's job.

## Boundaries & Constraints

**Always:** aioquic WebTransport listener binds the identical port number as the aiohttp TCP site, UDP only, no `Alt-Svc` advertised (AD-13); WebTransport certs are self-signed ECDSA P-256, valid at most 14 days, current+next SHA-256 hash served only from an authenticated (signed-request) HTTPS route, rotated with overlap (AD-14); 0-RTT refused, CONNECT `Origin` checked before auth, a session whose signed auth message is late by 5s or exceeds 4KB is closed, QUIC address validation/connection caps/request-size caps applied (AD-38, NFR25); SSE fallback is `fetch`-streamed GET plus HTTPS POST on the same origin, carrying the same `Authorization`/timestamp/nonce/signature header set `signedFetch` already builds, never `EventSource`, no credential ever in a URL (NFR14); both carriers deliver one envelope family from one cursor-numbered event source, heartbeats carry `head_cursor` at an announced interval, a stream with no heartbeat within one timeout reads as stale (NFR11); resume-from-cursor after backgrounding/app-switch/network-drop replays the gap with no loss or duplicates on both carriers, proven by comparing sent vs. received cursors (NFR13); tabs share one stream via Web Locks leader election plus `BroadcastChannel`, hand-off on leader close, no cursor gap (AD-31); a bounded outbound queue per client sends `resync` and drops that client's queue on overflow, the replayer/fan-out never blocks (NFR46, AD-38); `aioquic` is declared only in `kit.py`'s PEP 723 block, mirroring the `pywebpush` precedent, never touching root `pyproject.toml`/`uv.lock`.

**Never:** exercise real multi-device/network interop (Safari/iOS, cellular, a real WebTransport peer beyond localhost under test) -- Story 1.6's job; touch Stories 1.1/1.2/1.3 behavior (CA/mDNS/cert, passkey/token/device-approval, push/mic) beyond additive route/module additions; import or touch `src/stackowl/authz/` or any real journal/event module (platform code, read-only reference; none exists yet to pull from regardless); add CSP/Permissions-Policy middleware (Story 1.5's scope) unless the check actually fails without it; commit `spikes/bridge/results/*`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| WebTransport available | browser supports WebTransport, UDP open | connects over WebTransport after its signed auth message validates | n/a |
| WebTransport unavailable | no WebTransport support, UDP blocked, or handshake still fails after one hash refresh | falls back automatically to `fetch`-streamed SSE + HTTPS POST, same origin, same signed headers | n/a |
| Late/oversized auth message | signed WebTransport auth message arrives >5s late or >4KB | session closed before any stream data sent | closed, no leak |
| Stream killed mid-flow | active stream connection dies | client marks stream stale within one heartbeat timeout | n/a |
| Resume after gap | reconnect after backgrounding/app-switch/network-drop, with last cursor | gap replayed exactly, no loss/dupes, verified on both carriers | n/a |
| Leader tab closes | two open tabs, leader tab closes | surviving tab takes over via Web Locks + BroadcastChannel, no cursor gap | n/a |
| Client queue overflow | a deliberately throttled client's outbound queue overflows | client receives `resync`, resumes from its cursor; replayer never blocks | n/a |

## Design Notes

No real recorded-platform-event journal exists yet (AD-2/AD-9's journal is still spine-only, not built code -- confirmed by search across `src/stackowl/`). "A recorded sequence of real platform events, sanitised to metadata" is therefore built as a small synthetic-but-realistic fixture (numbered cursor, mixed event kinds, a deliberate burst) rather than pulled from a live source -- the shape and rate profile are what's under test, not provenance.

Forcing the WebTransport-unavailable branch deterministically in an automated Chromium check needs a client-side test seam (e.g. `window.BridgeStream` accepting a forced-fallback mode) rather than relying on actually blocking UDP in CI, mirroring the existing `window.Bridge*` test-seam precedent from Stories 1.2/1.3.

Real-device WebTransport interop (Safari 26.4+/iOS 27, cellular drop, Jetson-class memory budgets) remains out of scope for "done" here, mirroring Stories 1.1-1.3's identical scoping: the epic's "How this epic runs" section makes the automated Chromium check this story's completion bar, with every real-device run owed by Story 1.6 (parked `awaiting-operator` there). Nothing in this story requires an action only a human can perform outside the repo, so it dispatches through the normal ready-for-dev pipeline, not `awaiting-operator`.
