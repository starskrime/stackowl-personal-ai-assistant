## Intent

**Problem:** `ProgressEventFrame` (core -> gateway) exists on the wire but nothing ever constructs one (confirmed: the only non-test construction site anywhere in the tree is `tests/ipc/test_codec.py`) — so split-mode TUI progress is permanently dark. Meanwhile the journal (Story 2.1/2.2) now durably records events with a monotonic `cursor`, but nothing reads it: no fan-out, no reader, no push.

**Approach:** Delete `ProgressEventFrame` and its dead gateway receiver. Add `journal/fanout.py` (a pure, DB-injected `read_since`/`notify_committed`/`wait_for_commit` primitive the journal package owns). On the core side, a background loop wakes on `notify_committed()`, reads its own new rows via `DbPool.fetch_all` (no held-open transaction — AD-38) and pushes each as a new `JournalEventFrame` on the existing link, in cursor order, only ever containing already-committed rows (AD-24 is satisfied for free: a rolled-back event never reaches `journal_events`, so a reader can never see one). On the gateway side, `GatewayLink._route`'s new `JournalEventFrame` branch narrates (`journal.narrate`) and re-emits the EXISTING `pipeline_step_changed` EventBus event (zero TUI/`PipelineStrip` changes) — deduped against an in-memory `last_delivered_cursor` watermark. A `HelloFrame` (re)connect (survives a core `os.execv`) triggers a catch-up `fetch_all` from that same watermark before resuming live delivery, so a hole (rollback/prune) or a restart never loses or duplicates a row.

## Boundaries & Constraints

**Always:** A row is pushed only after its transaction commits (fan-out reads `journal_events`, which by construction never contains an uncommitted or rolled-back row — no new pre-commit hook is added anywhere). `journal.record()`, `DbPool.transaction()` and every existing journal-emitting call site's SQL stay untouched except the one added `journal_fanout.notify_committed()` line immediately after each of `pipeline/durable/store.py`'s six `async with self._db.transaction()` blocks that call `journal_record`. Every fan-out read (core's push-loop, gateway's catch-up) is a bounded `DbPool.fetch_all("... WHERE cursor > ? ORDER BY cursor LIMIT ?", ...)` — never a `transaction()`, never held open across more than one query (AD-38). The gateway's `last_delivered_cursor` watermark is the ONLY de-dup authority: a frame or catch-up row whose `cursor <= last_delivered_cursor` is silently dropped; one whose `cursor >` it is delivered and advances the watermark — this uniformly absorbs both a live push racing a reconnect catch-up AND a genuine wire duplicate. `PROTOCOL_VERSION` bumps 3->4 (frame shape change, Spec 2.3/2.4 precedent). Gateway reconstructs the typed `attrs` model (`get_registry().get(frame.event_type).attrs_model.model_validate(frame.attrs)`) before calling `journal.narrate()` — safe only because the Story 2.3 Hello registry-digest check already guarantees gateway and core share one identical registry; state this reasoning in a code comment. Both loops' cursor watermark initializes to `SELECT MAX(cursor)` at boot (own process start) — neither process ever floods a fresh connection with full history.

**Never:** Do not touch `pipeline/progress/emitter.py`'s existing `pipeline_step_changed`/`bus.emit` mono-mode path, `PipelineStrip`, `tui/coordinator.py`, or `coordinator_messages.py` — the gateway re-emits the identical `{step_name, step_index, total_steps}` shape onto the SAME event name, so the existing rendering pipeline needs no change. Do not build the AD-29 full-snapshot/resync mechanism (browser-class multi-client backfill) — out of scope, later epic; this story's cursor-watermark resume covers only "don't lose/dup across a CORE restart" (AC3's literal scope), not a fresh gateway-process boot re-fetching all history, nor a remote client's historical backfill. Do not build a schema-version upcaster framework — every registered type today is `schema_version=1`, so there is nothing to upcast; log this scope boundary to `deferred-work.md` (same rigor as Story 2.4's DW-14/DW-15). Do not add a new health contributor for fan-out lag/backlog — a lost live push self-heals on the next commit's push or the next reconnect's catch-up read (no data loss), and budget/health degradation is Story 2.11/2.12's scope. Do not poll: both loops are woken only by `notify_committed()` (own-process signal) or a `HelloFrame` (reconnect) — never a timer.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Event committed | A `journal.record()`-backed transaction commits | Core's push loop wakes, reads the new row(s) via `fetch_all`, sends one `JournalEventFrame` per row in cursor order | n/a |
| Transaction rolled back | The `async with transaction()` block raises after `journal_record` | No row exists in `journal_events`; the push loop's next read never sees it; nothing is pushed | n/a (proven by construction, not a new check) |
| Gateway receives a `JournalEventFrame` | `frame.cursor > last_delivered_cursor` | Narrated, `pipeline_step_changed` emitted on the gateway EventBus, watermark advances to `frame.cursor` | n/a |
| Duplicate/stale frame or catch-up row | `cursor <= last_delivered_cursor` | Silently dropped, watermark unchanged | n/a |
| Cursor hole (row rolled back/pruned) | `fetch_all(... WHERE cursor > ? ...)` simply omits the missing cursor | Delivery continues from the next present cursor; never blocks | n/a |
| Core `os.execv` restart / lost link | `HelloFrame` (re)arrives | Gateway runs one catch-up `fetch_all` from its own `last_delivered_cursor` BEFORE resuming live frame delivery; every row committed during the gap is delivered exactly once | n/a |
| `ProgressEventFrame` referenced anywhere | Codebase-wide | Deleted from `ipc/frames.py`'s union, `gateway_link.py`'s receiver, `ipc/__init__.py` exports, `test_codec.py`'s fixture | Any remaining reference is a compile/import error, not a silent no-op |

## Tasks & Acceptance

**Execution:** `journal/fanout.py` first (nothing else compiles without it) -> `journal/__init__.py` exports -> `ipc/frames.py`/`ipc/__init__.py` (frame swap, protocol bump) -> `pipeline/durable/store.py` (notify wiring) -> `gateway_link.py` (receiver + catch-up) -> `orchestrator.py` (push loop + wiring) -> `deferred-work.md` -> all tests together (the frame swap breaks `test_codec.py` immediately).

**Acceptance Criteria:**
- Given core records an event, when its transaction commits, then core pushes it to the gateway as a `JournalEventFrame` on the existing link, and never before commit (proven by construction: a rolled-back event is never read).
- Given the gateway receives pushes and (later stories) records its own action sites, when fan-out delivers, then it merges by cursor, drops duplicates via the `last_delivered_cursor` watermark, and never blocks on a hole.
- Given a core `os.execv` restart or a lost link, when the link returns (`HelloFrame`), then the gateway catches up from its last delivered cursor before resuming live delivery, with no loss or duplication across a real restart.
- Given `ProgressEventFrame`, when this story lands, then it is deleted everywhere (frame, union, receiver, exports, test fixture), `PROTOCOL_VERSION` bumps, and split-mode TUI progress renders via the unchanged `pipeline_step_changed`/`PipelineStrip` path, sourced from journal events, with the journal never polled (only `notify_committed()`/`HelloFrame`-driven).

## Design Notes

**Why the frame carries the full row instead of just a cursor watermark:** AC1's literal text is "core pushes THE EVENT... as a typed journal frame" — a watermark-only ping wouldn't satisfy that reading, and carrying the row avoids a second DB round-trip on the gateway's hot/live path (only the catch-up path re-reads).

**Why the gateway can safely rebuild the typed `attrs` model from a wire dict:** `journal.narrate()` requires `isinstance(event.attrs, spec.attrs_model)`. This is safe here specifically because Story 2.3's Hello exchange already refuses the link unless gateway and core report the identical registry digest — so `get_registry().get(frame.event_type)` on the gateway is guaranteed to be the SAME spec core used to build the row.

**Why no new HelloFrame field is needed for AC3:** the gateway (not core) owns the resume decision, and it already tracks its own `last_delivered_cursor` in memory across a core-only restart (the gateway process itself never restarts in that scenario) — it just re-reads from that point. A gateway-process-own restart re-initializes the watermark to current `MAX(cursor)` (skip-history default), which is a deliberate, disclosed boundary (see Never), not an oversight.

**Why `pipeline_step_changed` reuse, not a new TUI event:** today's only registered journal event types are `task.*` (Story 2.1); nothing "step-granular" is journaled yet (Story 2.7 adds tool/model-call events later). Reusing the existing event name/shape means zero TUI code changes now AND zero further TUI changes when 2.6-2.9 add more event types — they flow through the identical pipe automatically.
