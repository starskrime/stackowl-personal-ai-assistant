## Intent

**Problem:** `IpcServer` accepts any local connection on the gateway<->core socket and `_accept_core` trusts every accepted connection as core, calling `gateway_link.set_connection()` unconditionally — so a child of core's own shell (or any same-user process) can connect and displace the real link (measured incident, review-security.md M6), reading owner ingress and injecting forged consent/journal traffic. The socket directory also carries default permissions, not owner-only.

**Approach:** AD-33/NFR32/M6, layered on Spec 2.3's Hello exchange: (1) `IpcServer.start()` makes the socket's parent directory owner-only (0700). (2) `_accept_core` checks the connecting peer's OS-verified PID (`SO_PEERCRED`, Linux — this repo's only verified/production platform) against the exact core PID this gateway spawned, *before* any Hello is sent — a mismatch or unverifiable peer is refused and logged as a `SecurityError`, never reaching `set_connection`. (3) A per-boot random secret is minted once per gateway process and passed to every core spawn (initial + every crash-respawn) via env; `os.execv` inherits it unchanged, satisfying the restart AC with no special-casing. Core includes it in its `HelloFrame`; the gateway verifies it in `GatewayLink._route` before trusting the link, alongside the existing compatibility check.

## Boundaries & Constraints

**Always:** Peer-PID check runs before anything Hello-related is sent to an accepted connection — an impostor gets zero protocol information. A failed peer-PID or link-secret check raises a `SecurityError` subclass (CRITICAL log + audit + notify are automatic via the existing `SecurityError.__init__` side effects) and the connection is closed without ever calling `set_connection`/`run` for a peer-PID failure, or by propagating out of `GatewayLink.run()`'s per-frame loop (a `LinkAuthenticationError` is NOT swallowed by its existing `except Exception` resilience wrapper) for a link-secret failure. The link secret is never logged in full: name every field/log key holding it so it ends in `secret` (the existing `SensitiveFieldFilter`/`is_credential_name` already redacts any `*secret` key everywhere in structured `_fields` — reuse it, do not build a second redaction mechanism). The secret is generated once per gateway boot (`secrets.token_urlsafe`) and passed identically to every `spawn_core` call (initial spawn and every `_supervise_core` respawn) so `os.execv` (which inherits env unchanged) and a crash-respawn both present the same value. `HelloFrame.link_secret: str | None = None` (optional — only core's outgoing Hello carries a real value); `PROTOCOL_VERSION` bumps 2->3 (matches Spec 2.3's own precedent for any `HelloFrame` shape change); `extra="forbid"` stays.

**Never:** Do not build Windows named-pipe IPC transport — it does not exist at all today (`asyncio.start_unix_server`/`open_unix_connection` are POSIX-only; the gateway<->core split cannot run on Windows regardless of this story), so NFR32's Windows ACL clause is out of scope; log this to `deferred-work.md` with the same evidentiary rigor as Spec 2.3's DW-11. Do not build verified macOS peer-credential support (no macOS host to validate the raw `LOCAL_PEERCRED`/`LOCAL_PEEREPID` socket-option numbers against) — `peer_pid()` returns `None` on any platform lacking `socket.SO_PEERCRED`, and the caller fails CLOSED (refuses), so this is a disclosed scope boundary, not a silent gap; log it too. Do not conflate a link-secret failure with `link_health.note_mismatch()`/`consecutive_hello_mismatches` — that counter drives `_supervise_core`'s stand-down-respawning decision for genuine version skew, and counting an impersonation attempt there would let an attacker force the gateway to stop respawning the real core (a self-inflicted DoS). Do not touch `channels/dev_ingress.py`/`DevIngressListener` — separate, already allow-listed, out of scope; it incidentally gets the same 0700 parent directory since it shares `runtime/`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Real core connects | Peer PID == the PID `spawn_core` returned | Hello sent, link established as today | n/a |
| Impostor connects | Peer PID != supervised PID (e.g. a shell child) | Connection refused before any Hello is sent; `set_connection` never called | `LinkAuthenticationError` (SecurityError) — CRITICAL log + audit, no secret in either |
| Peer credentials unverifiable | `SO_PEERCRED` absent (non-Linux) or `getsockopt` raises | Treated as unverified -> refused (fail-closed) | WARNING naming the platform, then refused as above |
| Core presents wrong/missing `link_secret` | PID matched, `HelloFrame.link_secret` wrong or `None` | Link refused; write-gate stays paused; `consecutive_hello_mismatches` NOT incremented | `LinkAuthenticationError` raised from `_route`, propagates out of `run()`, connection closed |
| Core presents correct `link_secret` + compatible Hello | Everything matches | Link established, writes resume, buffered turns flush — unchanged from Spec 2.3 | n/a |
| `os.execv` core restart | Same PID, same inherited env secret | New connection's peer-PID check passes (same PID); Hello's secret matches; link accepted with no special-casing | n/a |
| Socket directory created | Platform start (Linux/macOS) | `runtime/` (parent of `core.sock`) is `0700` | A chmod failure logs ERROR but does not abort boot |

- Given the platform starts on Linux or macOS, when the IPC socket directory is created, then it is `0700` (Windows named-pipe ACL is out of scope — no such transport exists; logged to `deferred-work.md`).
- Given a connection on the IPC socket, when Hello arrives, then the gateway has already checked peer credentials against the core process it supervises (refusing before Hello if they don't match) and verifies the per-boot link secret in Hello; a peer failing either check is refused with a logged remedy (via `SecurityError`'s automatic CRITICAL log + audit), and the secret never appears in any log line.
- Given a core `os.execv` restart, when the new core connects, then it presents the secret for this boot (inherited via env, unchanged) and the link is accepted with no special-case handling.
