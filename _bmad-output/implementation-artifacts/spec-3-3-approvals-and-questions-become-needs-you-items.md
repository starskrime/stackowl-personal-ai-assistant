## Intent

**Problem:** `needs_you.resolve()` (AD-28, Story 3.2) has zero real callers. Today a consent request (`tools/consent.py::ConsentPolicy.request`) and a clarifying question (`interaction/clarify_gateway.py::ClarifyGateway.ask`/`wait_for_answer`) each park on their own in-memory `asyncio.Future`/`asyncio.Event`, entirely invisible to `needs_you` — lost on a core restart, with no durable record of "the owner still needs to answer this."

**Approach:** Open a durable `approval`/`question` item (with `waiter_kind="turn"`) the moment `ConsentPolicy.request()` / blocking `ClarifyGateway.ask()` starts waiting, and settle it through `needs_you.resolve()` the moment the in-memory wait returns an answer — using `resolve()`'s own returned outcome, never the raw local answer, as what the turn actually acts on. At boot, resolve every still-open `waiter_kind="turn"` item as `expired` before the gateway accepts turns (the in-memory waiter that opened it is provably gone).

## Boundaries & Constraints

**Always:**
- Open the item and bind its waiter in the SAME transaction as the triggering journal event (AD-24), before the human is ever asked.
- Every item this story opens carries `waiter_kind="turn"` — no durable waiter exists until Epic 4.
- Settle exclusively through `needs_you.resolve()`; use ITS returned `NeedsYouResolution` (never the prompter's/gateway's raw local answer) as the value the turn acts on — this is what makes "the first answer wins" true even against a concurrent boot-sweep/expiry.
- Approval expiry = existing `HUMAN_DECISION_TIMEOUT_SECONDS` (1200s, `tools/consent.py:351`); question (blocking clarify) expiry = existing `CLARIFY_TTL_SECONDS` (1800s, `interaction/clarify_gateway.py:86`) — reuse, never invent a new number.
- A missing/`None` `db_pool` is a no-op (consent/clarify behave exactly as before) — mirrors `consent_events.record_consent_decision`'s existing convention, so every unwired test/caller stays byte-identical.

**Never:**
- Never open an item for: an F-71 pre-resolved/auto-answered clarify (nothing is ever shown to a human), or a turn-yield (`blocking=False`) clarify (no in-flight turn waiter exists to bind).
- Never touch Story 3.4 (fail-closed/`ChannelRegistry` routing), 3.5 (`reply_target` frame), or 3.6 (Telegram buttons/digest UI) — separate stories, out of scope here.
- Never widen `journal.record()`'s public return type or `needs_you.open_item()`'s parameters to thread waiter info through. Bind the waiter with a dedicated, separately-called `needs_you` function inside the same open transaction instead — mirrors `_resolve_open_item`'s own single-purpose-statement shape.
- Never touch the 5 channel-specific `ConsentPrompter` implementations (Telegram/Slack/Discord/WhatsApp/TTY) — they all funnel through the ONE `ConsentPolicy.request()` await; that single choke point is where `resolve()` is called, so AC3's "all five" is satisfied with zero per-channel changes.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Approval answered in time | Owner responds before `HUMAN_DECISION_TIMEOUT_SECONDS` | `needs_you.resolve()` settles the item; `ConsentPolicy.request()` acts on the resolution's answer, not the raw prompter return | No error expected |
| Blocking clarify answered | Owner replies before `CLARIFY_TTL_SECONDS` | `wait_for_answer()` resolves via `needs_you.resolve()` and returns its answer | No error expected |
| Core restarts, item still open | An `approval`/`question` item has `waiter_kind="turn"`, `resolved_cursor IS NULL` | Boot resolves it `expired` through the resolver before the gateway accepts turns | Never left open with nothing waiting |
| Non-blocking clarify (turn-yield) | `ask(blocking=False)` | No needs_you item opens | N/A — explicit non-goal |
| F-71 auto-resolved clarify | `ask()` resolves via `_resolve_default` before delivery | No needs_you item opens | N/A — nothing was ever shown to a human |
| `db_pool` unwired | Test/caller builds `ConsentPolicy`/`ClarifyGateway` with no `db_pool` | Behavior unchanged from today, no needs_you write attempted | Never raises |

## Spec Change Log

### 2026-09-18 — bad_spec amendment (review pass 1)
- Trigger: two grouped, verified findings from this pass's review — Group A (medium: neither `ConsentPolicy.request()` nor `ClarifyGateway.wait_for_answer()` settles a bound needs_you item on a non-boot abandonment exit — timeout, cancel, or a raising prompter) and Group C (high: `target_id`/`dedupe_key` scoped to bare `session_key` lets two distinct, concurrent decisions collide onto the SAME item, so a losing caller can silently adopt an unrelated caller's answer via `resolve()`'s "already settled" branch).
- Amended: `## Code Map` and `## Design Notes` below, to require (1) a public, small `needs_you` primitive for settling an abandoned/non-answered item (not just the happy-path `resolve()`), called from every non-happy-path exit of both call sites, sharing logic via one helper rather than duplicated per-call-site code; and (2) a `target_id` that uniquely identifies the SPECIFIC decision being made (the clarify's own `clarify_id` for questions; a freshly-minted per-request id for approvals), not the bare `session_key` — replacing this spec's original "one open item per session" scoping.
- Known-bad state avoided: an unresolved question/approval item silently outliving the process it was opened for with no proof it was ever meant to stay open (Group A); and a losing caller's tool-approval/deny decision being silently overwritten by an unrelated concurrent caller's answer because both collapsed onto the same dedupe target (Group C) — the latter is a real cross-request contamination bug, not cosmetic.
- KEEP (verified working, must survive re-derivation byte-for-byte in spirit): `bind_waiter()`'s single-conditional-UPDATE shape and its "second statement in the same transaction" rationale; `expire_stranded_turn_waiters()`'s unconditional, `waiter_kind='turn'`-scoped, one-item-per-own-transaction, never-raise shape, and its boot wiring immediately after `set_needs_you_db_pool(db_pool)` (already proven by a passing AST guard test — keep both the wiring and the guard); the `consent.requested`/`clarify.raised` event registrations, their `table=None` rationale, and their `record_consent_requested`/`record_clarify_raised` helper shape (only the `target_id` VALUE they're called with changes, not their signatures); the "act on `resolve()`'s own returned outcome, never the raw local answer" rule for the happy path (already correctly implemented and tested on both call sites, including the consent-side differing-answer race test) — this rule now ALSO applies to the new abandonment-settlement path; the reuse of `HUMAN_DECISION_TIMEOUT_SECONDS`/`CLARIFY_TTL_SECONDS` for expiry; the `db_pool`-unwired no-op behavior and its tests on both call sites; the boot-sweep AST guard test's structure; all passing registration/unit tests in `test_needs_you.py`, `test_consent_events.py`, `test_interaction_events.py` that are unaffected by the target-id change (dedupe-per-target tests will need re-deriving against the new target scheme, per the amendment above).

## Design Notes

**Why one choke point per surface, not five.** `ConsentPolicy.request()`'s single `await self.prompter.prompt(req)` and `ClarifyGateway.wait_for_answer()`'s single resolved-branch are each the ONE place every channel's answer already funnels through before the turn acts on it. Resolving there — and using `resolve()`'s own returned outcome instead of the locally-obtained answer — makes "prompters only render an item and hand its answer to the resolver, they never decide" true with zero changes to the 5 channel-specific prompter classes.

**Why `bind_waiter()` is a second statement, not a wider `open_item()`.** `open_item()`'s single-INSERT shape exists so "did this call open the item" is answered from one `RETURNING id`, never a read-then-write. Binding the waiter happens a moment later in the SAME transaction, on a row this transaction's own `open_item()` call just inserted (nothing else can see it yet) — a second conditional UPDATE adds no race, and keeps `journal.record()`'s public signature — used by dozens of unrelated call sites — untouched.

**`waiter_id` example values.** Nothing reads `waiter_id` for delivery yet (no cross-process "deliver by frame" exists until a later epic) — it exists for the boot sweep's own bookkeeping/logging. A fresh id per open request (e.g. the clarify's own `clarify_id`, or a freshly minted id for consent) is sufficient; exact minting is an implementation detail, not a contract.

**`resolved_by` convention.** Follow the existing `"system:{type}"` (auto) / a bounded, ≤64-char label shape already enforced by `NeedsYouResolvedAttrs`; an owner-driven resolution should identify the answering channel, e.g. `f"owner:{channel}"` — exact string is an implementation detail.

**Why `target_id` is a fresh per-request/`clarify_id`, not `session_key` (review pass 1 amendment).** The item's `dedupe_key` is `f"{kind}:{target_kind}:{target_id}"`, and the partial unique index enforces ONE open item per `dedupe_key`. Scoping `target_id` to bare `session_key` conflates "one open DECISION per session" with "one open ITEM per session" — but a session can legitimately have more than one decision in flight (two different tools requested close together; two session-less callers that both collapse onto `session_key=""`), and when it does, the SECOND request's `bind_waiter()` call silently steals the FIRST's still-open item (it matches on the same `dedupe_key`), so both requests' `needs_you_item_id` end up pointing at the SAME row. Whichever `resolve()` call reaches that row SECOND then receives the FIRST caller's answer back as "already settled" — and `ConsentPolicy`'s post-prompt code adopts that returned answer unconditionally, so one caller's approve/deny can silently become another, unrelated caller's approve/deny. Scoping `target_id` to something that already uniquely identifies THIS specific decision (the `clarify_id` `ask()` already mints; a fresh id minted at the top of `ConsentPolicy.request()`) closes this: two concurrent decisions never share a `dedupe_key`, so they never share an item. `ClarifyGateway`'s own pre-existing session-level "cap one pending" replace logic is UNCHANGED and remains the real enforcement of "one live question per session" — needs_you's own dedupe is now a narrower, correct guarantee ("one open item for this exact decision"), not a session-wide guarantee it was never actually safe to make.

**Why abandonment (not just the happy path) must settle the item (review pass 1 amendment).** `resolve()`'s "act on its own returned outcome" rule was written for the happy path (a real answer arrives) and the boot path (AC4, `expire_stranded_turn_waiters`) — but a bound item can also stop being waited-on WITHOUT either: `wait_for_answer()`'s TimeoutError/cancelled/abandoned-wake branches, and `ConsentPolicy.request()`'s prompter-raised branch. None of those are "the human answered" or "core restarted" — they are "this specific wait gave up while the process kept running." Left alone, the item stays open until its OWN `expires_at` plus the pre-existing 1-minute periodic sweep (`needs_you_expiry_sweep.py`, unaffected by this story) — bounded, but real, and it will matter the moment a later epic renders open items to a UI (a stale, already-abandoned question/approval would still show as pending). Every such exit that follows a successful open+bind must settle the item itself (through the shared settle primitive, not a duplicated inline block), the same way the boot sweep settles a stranded item — just triggered by local abandonment instead of by a fresh process having no memory of it.
